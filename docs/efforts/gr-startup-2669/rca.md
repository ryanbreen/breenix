# Issue 2669: early GR startup refusal

## Evidence and limits

`table.txt` is generated by `python3 extract.py` from the eight named Vigil serial captures. The script checks the classification and last IRQ register value and exits nonzero if either differs. The four refusal captures end with `0x40120=1`; the four clean captures end with `0x40120=0`. Refusals report graphics durations of 7,524,842–7,531,139 us; clean captures report 12,012,208–12,027,945 us. These are whole graphics-probe durations, not the poll duration. Refusals show `IRQ_RESTORED`, then `GR_REFUSAL`, then the `after` IRQ; clean captures show `channel-drained`, image bulk, IRQ restoration, stage, and `after` IRQ. The full ordered GR line names and selected values are in the table.

The last IRQ is **after teardown**, not a snapshot at the timeout. `gk208/mod.rs:426-437` captures `before`, calls `gr::probe`, prints the refusal, then captures `after`. On the probe error path `gr/mod.rs:585-598` calls `hardware.finish()` and cleanup before propagating the error. `gr/mod.rs:787-804` quiesces the graphics channel and resets the controller; `gr/channel.rs:1279-1316` disables/preempts both channels, empties the runlist and unbinds them. Consequently neither `0x40120=1` nor the zeroed channel-0 registers in the after snapshot establish the PBDMA's state or progress at the timeout. The observation is a correlation, not a live scheduling trace.

## Code mechanism

The native startup path opens a second channel, activates the pair and executes the first channel (`gr/mod.rs:351-358`); the diagnostic probe also opens the second before activate and execute (`gr/mod.rs:515-521`). `gr/channel.rs:480-497,823-835` makes channels 0 and 1 and submits both to one runlist, although the second is reserved for terminal output and remains empty during normal production rendering (`gr/mod.rs:354-355`). The first withheld-release control in `gr/channel.rs:1217-1225` submits sequence 1 with a 10,000 us observation budget; its command still carries SET_REFERENCE (`gr/channel.rs:255-277`). Publication writes the descriptor and GP_PUT (`gr/channel.rs:908-956`). Before the negative observation, the code waits up to `BOUND_US=2,000,000` us for consumed and emits the exact refusal on timeout (`gr/channel.rs:238,891-899`).

`Monitor::snapshot` (`gr/channel.rs:2209-2240`) defines current using `0x40120`; it reads live `0x40014` if current and the channel's saved USERD GP_GET at `+0x88` otherwise. Yet its final consumed predicate also requires `current`, the matching progress/reference and a matching bound instance. Thus a descheduled channel cannot satisfy the predicate even if its saved GP_GET shows it consumed sequence 1. The adjacent reference register `0x40028` is PBDMA state too; merely dropping `current` without establishing channel-specific reference evidence could mistake another channel's state for this channel's progress.

The contrast is specific: CE's `ce.rs:358-375` selects live GP_GET or saved USERD and permits descheduled completion in the shared-channel case while retaining other health and receipt checks; its nonshared case still requires current. The emergency path `emergency.rs:359-379` checks health separately and chooses live or saved GP_GET in `consumed`. These paths demonstrate the existing saved-GP_GET design; they do not establish that GP_GET alone satisfies GR's reference and ordering contract.

## Inference and next experiment

A plausible mechanism is that both channels become schedulable, channel 0 consumes its withheld-control stream, and channel 1 becomes current before the monitor observes the required simultaneous state. If channel 0 stays descheduled for the two-second poll, the unconditional `current` gate prevents recognition of its saved progress. The last IRQ's `0x40120=1` is consistent with a difference in final state, but because it follows teardown it cannot establish that schedule, that saved GP_GET reached 1, or whether the stream really executed. A genuine submission or engine failure remains possible. The code specifies the predicate's behavior, not the cause of these individual timeouts.

The next unit should model the actual monitor and scheduling order deterministically: force channel 0's valid stream and channel-specific completion evidence, save its GP_GET, switch to channel 1 before polling, and compare with an actually unconsumed stream and wrong-channel reference. The old predicate must fail the former; any fix must pass it without accepting the latter or changing the two-second bound. Determine from permitted hardware documentation how reference evidence survives a switch before choosing a source fix. A boot, if needed to distinguish hypotheses, requires an explicit code-derived prediction and failure-only observation before teardown; this unit performs no boot.

The register and runlist interpretation above follows the existing code's citations to the MIT rnndb `fifo/gf100_pfifo.xml` and the MIT FIFO `gk104.c:430-456` (`gr/mod.rs:188`, `gr/channel.rs:830-831`); no firmware image or proprietary source is used as evidence.
