# D2: Breenix's C toolchain

Design, 2026-10-20, from main at 718994f6. This document specifies future work; it reports no native-build or hardware acceptance results. The `toolchain` effort in `docs/efforts/path.json` carries out section 8, and its suite manifest is `docs/suites/toolchain.json`. The program this belongs to is [the server plan](../metal/server-plan.md).

**Operator decisions and rulings** (2026-10-20, ET; the server plan records the full list):

- **D2:** we write our own C compiler, assembler, ELF linker and make, clean-room from the C, ELF and x86-64 ABI specifications. No ported compiler. Cross-building on the Mac and pushing the result covers the gap until ours builds on the box.
- **S2:** toolchain code is architecture-independent where possible; iteration runs on the host harness and ARM64 QEMU, and the R240 carries the acceptance proofs.
- **S5:** Rust on the box is deferred until our C toolchain rebuilds itself.
- **D6:** the effort covers each target. x86-64 on the R240 leads, and the catch-up brings ARM64 QEMU, Parallels and VMware to the same bar; for this effort the catch-up is section 9's ARM64 port.

## 1. Decision, implementation language and boundaries

D2 and the rulings in [the server plan](../metal/server-plan.md#operator-decisions-and-rulings) govern this design, superseding the compiler-port recommendations of the two design passes summarized there. The `toolchain` effort follows `server`, `users` and `filesystem` in `docs/efforts/path.json` (S2, D6). Development need not wait for filesystem migration (D1); native builds can initially use ext2. D3 controls hardware scheduling, D4 controls access, S5 defers native Rust, and S6 assigns watchdog work to the server effort. S4's partition-retention rule remains a filesystem dependency, not toolchain work. S3's uptime measurement is not a toolchain gate.

**Write the compiler, assembler, linker and make in C11**, with an intentionally conservative C subset for their bootstrap sources. Rust would improve implementation safety and fit Breenix's kernel, but a Rust-written C compiler cannot rebuild itself with a C compiler. Requiring rustc first would invert S5. C enables the requested fixed point without a second implementation. Use checked allocation/size arithmetic, translation-unit arenas, explicit ownership, bounds-checked binary readers and host sanitizers to mitigate the cost.

Proposed commands: `bcc` (installed as `cc`), `bas` (`as`), `bld` (`ld`), `bmake` (`make`); add small `ar`/`ranlib` and `nm` utilities sharing object readers. Keep components independently executable and testable. `bcc` orchestrates preprocessing, compilation, assembly and linking; `-E`, `-S`, `-c`, `-o`, `-I`, `-D`, `-U`, `-L`, `-l` expose those boundaries. Unknown options fail explicitly.

The same C sources build into Mac-native tools with the host compiler, and Breenix ELF tools against our libc. The Mac hosting layer uses Mac process/file services; it does not execute Breenix syscalls. Generated Breenix programs use only Breenix headers, startup and libc. Mac ARM64 can host an x86 cross-compiler; it cannot directly execute the resulting ELF.

Clean-room inputs are published specifications and Breenix's own interfaces. Read/copy/adapt no Linux, BSD, Mesa, QEMU, GRUB, foreign filesystem, libc or compiler implementation source, including compiler test suites. Existing compilers are executable black-box bootstrap/oracle tools, not source references. BusyBox is the existing application workload, not implementation guidance.

Pin editions and hashes of [C11 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf), ISO C17 and its defect corrections, the [System V AMD64 psABI](https://gitlab.com/x86-psABIs/x86-64-ABI/-/jobs/artifacts/master/raw/x86-64-ABI/abi.pdf?job=build), [ELF gABI](https://gabi.xinuos.com/), [Intel SDM](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html) and [AMD APM](https://docs.amd.com/v/u/en-US/40332_4.09_APM_PUB). Maintain a clause-to-feature ledger; unresolved specification gaps become explicit work, not guessed compatibility.

## 2. Cover the gap, then bootstrap

**Deliver first.** Retain the Mac SDK's clang/lld cross-build route using our headers and the x86 C-ABI `libc.a`. Add binary-safe exec stdin to `bsshd` before SFTP: separate stdin/stdout/stderr pipes, channel EOF, exit status, window updates, partial writes and concurrent pumping under backpressure. Run commands through POSIX `/bin/sh -c`; today's whitespace splitting cannot implement shell redirection. Do not put binary transfers through a PTY. A later SFTP subsystem can use the same authenticated channel and file-publication machinery.

Delivery inherits S1: close compiled-in credentials, password access, root sessions and telnet before persistent exposure; keys-only LAN port 22, pinned host identity, operator UID/GID/groups/home (the users effort's `wrb` account, S7). The transport grants no extra privilege. Upload into an exclusive temporary file in the operator's workspace; verify length and SHA-256, set mode, fsync, rename and sync the containing directory before reporting publication. Interrupted, oversized or failed writes must leave the previous destination intact. This is application deployment, not the privileged kernel upgrade path. Test failure/status propagation and flow-control deadlocks as well as successful uploads.

Install a versioned development bundle: tools, Breenix headers, C-ABI archive, script, source and manifest. System installation is a separate administrative action; daily builds stay under `/home`. Keep Rust and libc archive production on the Mac throughout this effort.

Bootstrap names are precise:

1. **Stage 0:** pinned existing Mac compiler/linker cross-build our C tool sources into Breenix executables.
2. **Stage 1:** those executables run on Breenix and rebuild the sources using our compiler, assembler, linker and make, producing stage 2.
3. **Stage 2:** rebuild the identical sources again, producing stage 3. Compare stage 2 and stage 3 bytes for each tool.

Early compiler work is a declared subset, sufficient first for hello and then its own conservative sources. Self-hosting does not establish C11 conformance. Expand C11 coverage before adding C17 corrections and workload extensions.

## 3. Compiler architecture

**Preprocessor.** Implement C translation phases: source decoding, trigraphs and line splicing, comments, preprocessing tokens, includes and conditional expressions, object/function/variadic macros, argument prescan, recursion suppression, stringification and token pasting, predefined macros, `_Pragma`, `#line` and adjacent strings. Preserve spelling and expansion locations plus include stacks. Own the compiler-support headers (`stddef.h`, `stdint.h`, `stdarg.h`, `float.h`, `limits.h`, `stdatomic.h` and relevant builtins); today's wrapper obtains several from Clang's resource directory. Do not ship those as our implementation or permit host include paths to leak into target builds.

**Parser and semantics.** Recursive descent for declarations/statements and precedence parsing for expressions; explicit scope, tag, label and typedef-name namespaces. Build a typed AST, handling declarators, prototypes, old-style definitions required by C11, qualifiers, storage/linkage, integer promotions/conversions, constant expressions, aggregate layout/bitfields, designated initializers, compound literals, flexible arrays, `_Generic`, `_Static_assert`, alignment and `_Thread_local`. Diagnose incompatible declarations, invalid lvalues, wrong arguments and control-flow constraints before lowering. Emit `file:line:column`, source range and macro-origin notes; recover at declaration/statement boundaries without cascading indefinitely.

C11 completion includes scalar atomics/memory ordering, non-lock-free aggregate atomics through our own runtime helpers, floating conversions/environment interactions and the implemented conditional-feature profile. Initially advertise `__STDC_NO_VLA__` and `__STDC_NO_COMPLEX__` truthfully; remove a macro only after implementing and testing that feature. BusyBox may require VLAs later. Compiler coverage and a conforming hosted C library are separate claims. C17 is a later defect-correction milestone, not an initial flag that silently means C11.

**IR.** Lower to typed, basic-block, three-address operations: integer/FP arithmetic, comparisons, loads/stores, address calculations, branches, calls, returns and explicit memory copies. Keep signedness, alignment, volatile and atomic operations, source locations and call signatures. Parameterize target widths/layout; do not substitute the compiler host's `sizeof(long)` or floating evaluation for target semantics. Fold required constant expressions with target-width arithmetic and independently implemented literal rounding. ABI lowering follows semantic IR, rather than infecting the parser with registers.

**x86 code generation.** Start `-O0` with stack slots, frame pointers, scratch-register selection and explicit spills; use RIP-relative addresses and a small static code model, checking displacement limits. Handle signed/unsigned division, shifts, narrow-value extension, indirect calls, switch dispatch, short-circuit evaluation, setjmp's returns-twice semantics and volatile ordering. Emit stable assembly consumed by `bas`; avoid a separate machine-code emitter initially. Disable the red zone as today's C wrapper does. Preserve callee-saved registers and call-site stack alignment. Runtime helpers must come from our audited libc or newly authored support library, without implicit host libgcc/compiler-rt linkage. Later add constant propagation, unreachable-block removal, local common-expression elimination and linear-scan allocation. No speculative FP reassociation, vectorizer, LTO or aggressive alias analysis initially.

**ABI.** Use LP64: 8-bit bytes, 32-bit int, 64-bit long/pointers. Implement the psABI classifier for scalar and aggregate arguments/returns: recursive eightbyte classification, mixed INTEGER/SSE pieces, register exhaustion rollback, memory arguments and hidden structure-return pointers. Integer arguments use RDI/RSI/RDX/RCX/R8/R9; float/double use XMM0–7. Results use RAX/RDX and/or XMM0/1 as classified. Align RSP to 16 bytes before ordinary calls; preserve FP control state. Test packed/unaligned aggregates and bitfields across separately compiled callers/callees. These are C's SSE rules, not the kernel/Rust soft-float target. See the psABI's [calling convention](https://www.ucw.cz/~hubicka/papers/abi/node10.html).

Varargs use the register-save area, `gp_offset`, `fp_offset`, overflow-area pointer and `%al` vector-register-count upper bound; apply default promotions and mixed aggregate rules. Implement `va_start`, `va_arg`, `va_copy` and `va_end` through our support header/builtins. x86 `long double` is x87 extended precision in 16-byte storage: support memory arguments and x87 returns/arithmetic, not an alias to double. These conventions come from the psABI's [varargs description](https://www.ucw.cz/~hubicka/papers/abi/node13.html).

**TLS is part of first useful linking.** Our `errno.h` expands `errno` to `*__errno_location()`. In `pthread.rs`, that function reaches a descriptor through `%fs:8`; `%fs:0` contains the thread pointer. Startup initializes this before `main`. Thus errno needs working runtime TLS, but not a compiler-generated TLS relocation of its own. Separately implement C `_Thread_local` using local-exec addressing: `SHF_TLS`, `STT_TLS`, `.tdata/.tbss`, `PT_TLS` and negative variant-II TP offsets. Respect template alignment and zero-fill in newly created threads. Test initialized/uninitialized TLS and independent errno values in two threads, then fork/exec.

## 4. Assembler and objects

Choose a documented Intel-style emitted dialect matching Breenix's existing inline assembly: registers, explicit memory widths, base/index/scale/displacement, RIP-relative expressions, segment overrides and symbolic addends. A directive layer supplies sections/flags, symbol binding/type/size, alignment, strings/data, zero-fill and TLS relocation modifiers. Support local labels and forward references; initially use long branches, then deterministic relaxation. Encoding tables come from ISA manuals, including REX, ModRM/SIB, immediate-width and high-byte-register restrictions.

Cover compiler integer instructions, scalar SSE/SSE2 and x87; libc's startup, syscall, setjmp, atomics, fences and memory/string operations. For the kernel's existing `.asm` files, add the actual NASM-shaped surface: `section/global/extern`, `%define`, `%macro`, alignment, data directives and `bits 16/32/64`. AP startup needs mode transitions, far transfers and descriptor/control registers; interrupt/syscall assembly needs GS addressing, `swapgs`, interrupt returns and privileged instructions. Keep this separately measured from userland readiness. Do not claim NASM compatibility or a native Rust kernel build.

Emit ELF64 little-endian `ET_REL`/`EM_X86_64`: section/string/symbol tables, local-before-global ordering, `SHT_NOBITS` and explicit-addend `SHT_RELA`. Preserve section-symbol references, visibility, weak symbols, sizes and alignments. Keep object readers/writers shared with the linker, but use independent fixtures to avoid agreeing on the same malformed encoding. Reject unsupported directives/instructions with locations.

## 5. Static linker and the existing libc contract

Read ordinary ELF objects and Unix `ar` archives, including long member names and symbol indexes. Support strong/weak/common/undefined resolution, left-to-right archive processing with member extraction to a symbol fixed point, explicit repeated archive groups, whole-archive selection, COMDAT selection, section groups and optional section garbage collection rooted at entry/retained sections. Preserve mergeable sections without deduplicating initially. Implement relocatable `-r` links preserving symbols/addends for BusyBox. Report duplicate definitions, unresolved symbols, bad bounds and relocation overflow with object/member/section/offset. Emit deterministic archive indexes; `nm` supplies the suite/build tools' symbol queries.

The baseline is [the current driver](../../scripts/breenix-cc) and [userspace script](../../userspace/programs/linker.ld): `_start` comes from `libc.a`; base `0x40000000`, 4 KiB section alignment, separate RX/R/RW loads, headers mapped by the first load, `PT_TLS`, and non-executable `PT_GNU_STACK`. Parse the script constructs actually used: `ENTRY`, `PHDRS`, `SECTIONS`, location counter, arithmetic, `SIZEOF_HEADERS`, `ALIGN`, wildcard input selectors, flags and segment assignment. Extend for kernel scripts with assignments, `KEEP`, `COMMON`, output format/architecture and `/DISCARD/`; script syntax is an explicitly documented compatibility surface, not part of ELF itself.

Keep `.tbss`'s TLS zero-fill from consuming file bytes or incorrectly advancing ordinary data layout. Preserve TLS offsets, segment alignment and `p_filesz/p_memsz`; match aux-vector/program-header discovery used by our startup. No interpreter, dynamic loader, shared libraries or runtime unresolved relocations. Allocated orphan sections receive an explicit placement policy or a diagnostic, not accidental layout.

**Observed LLVM inputs:** `llvm-readelf -r` on one x86 C-ABI `libc.a` (`libs/libbreenix-libc/target/x86_64-breenix-c/release/libc.a`, built from a recent branch, SHA-256 `a3c7c87a58ca0706fab0d600ebbe83fe8785e52f5fff59e7fe4ad99598206b0c`) found exactly these four relocation types: `R_X86_64_64` (972), `PC32` (9,370), `PLT32` (6,279), `GOTPCREL` (139). This is an inspected artifact, not a claim that it reproduces main at `718994f6`. M1 must inventory the exact delivery archive, its members, flags and hashes.

Implement `64=S+A`, `PC32=S+A-P`, statically resolved `PLT32` calls, and genuine GOT slots containing resolved symbol addresses for `GOTPCREL`; a static executable can still need a GOT. Add `32/32S` with unsigned/signed extension overflow checks, `R_X86_64_PC64`, `R_X86_64_NONE`, and `GOTPCRELX/REX_GOTPCRELX` handled without optional relaxation. Support `TPOFF32/TPOFF64` for local-exec TLS: symbol template offset minus aligned template memory size, plus addend. Later initial-exec `GOTTPOFF` uses resolved GOT offsets. Do not claim TLSGD, TLSLD, TLSDESC, IFUNC or dynamic relocation support. LLVM version changes can add relocation types: fail by name and implement the published semantics; do not rebuild libc with weaker flags to evade the requirement. Retain the libc symbol/provenance audit.

## 6. Make and workload compatibility

Target [POSIX.1-2024 make](https://pubs.opengroup.org/onlinepubs/9799919799.2024edition/utilities/make.html). Begin with a clearly labeled serial subset; completion requires target/prerequisite graphs, cycle diagnostics, timestamps, suffix inference, archive members, includes/remaking includes, macro expansion/precedence and substitutions, automatic variables, recipe prefixes, recursive `MAKEFLAGS`, specified options/exit statuses and special targets. Issue 8 includes `::=`/`:::=`, `.WAIT`, `.NOTPARALLEL` and bounded `-j` with a shared recursive token pool; budget them rather than calling a simple dependency runner POSIX make. Use `/bin/sh`, preserve recipe-line shell boundaries and report child failures/signals. Test incremental/no-op builds, changed headers, equal timestamps, missing files and interrupted recipes.

BusyBox's build is a separate compatibility milestone. Today's [build wrapper](../../scripts/build-libc-busybox.sh) uses GNU make/Kbuild, `HOSTCC`, generated sources, relocatable links and archive/symbol tools. POSIX make plus ISO C alone is insufficient. Add only documented, workload-required GNU C extensions (attributes, builtins, `typeof`, statement expressions, extended asm) and make extensions (pattern rules, conditionals, functions, `call`/`eval`, variable flavors and includes), from published manuals, without implementation source. The [GNU make manual](https://www.gnu.org/software/make/manual/make.html) specifies the latter. Native `HOSTCC=cc` builds generators for Breenix too. Extract/patch/configure locally, with pinned inputs; importing prebuilt generators or objects does not count as building BusyBox on the box.

## 7. Oracle and acceptance order

Write our own C torture-style cases from standard clauses: preprocessing corners, declarators, promotions, aliasing within defined behavior, initializers, bitfields, alignment, calls, varargs, FP edge cases, atomics and TLS. Include compile-fail constraint cases with useful locations. No imported compiler tests. Avoid undefined behavior; represent unspecified outcomes as permitted sets. Compare exit status, stdout/stderr and file contents, not addresses or timing. Floating cases use specified tolerances/rounding rules.

For each case, Mac clang cross-builds a reference ELF against the identical Breenix sysroot; our Mac-hosted compiler builds a candidate. Execute both on the same Breenix target and compare with independently stated expectations. Native guest compilation adds a third path. Cross-call mixed objects in both directions to expose ABI errors. Mix our/LLVM assembler and linker outputs as black-box differential checks; foreign implementation source stays unread. Clang agreement alone is not correctness.

Compile unchanged `userspace/libc-suite` C sources, including `abi_check.c` and `harness.c`, and preserve the manifest's case identities, assertions and thresholds. Its existing recipe requests C17, `-O2` and rounding-aware behavior; native acceptance follows the C17/optimization milestone, not an unnoticed flag downgrade. Document our small `-O2` pipeline honestly. Missing functionality remains a named failure, not a substitute successful stub.

Fixed point: identical sources, headers, libc archive, flags, paths, locale, epoch and ordering for stages 2/3; deterministic temporary names, symbol order, archive metadata and padding. Compare complete shipped bytes, not stripped binaries. Control date/time macros and debug paths before generation. Compare every tool, rerun behavior cases on the resulting tools, and retain hashes. Equality demonstrates bootstrap stability, not absence of shared bugs or malicious bootstrap influence.

“We can build things” has five successive meanings: **hello compiled/run over SSH → multi-file Makefile project → tools rebuild themselves with stage-2/3 equality → libc suite compiled on-box → BusyBox built on-box**, with the existing required applet list and per-applet compile/link/usage results plus the utilities suite. Native C does not imply rebuilding the Rust-written libc or kernel.

## 8. The toolchain effort's milestones

Estimates are engineering weeks for one experienced implementer, including focused tests/review, excluding waits for server prerequisites. Each milestone's measure in `docs/efforts/path.json` is the suite categories in its second column; the `toolchain` suite has no cases yet, and each category's cases arrive with the lane that implements it. Keep each milestone's manifest measurable; intermediate subsets do not complete later coverage. M9's `libc-suite` category compiles the libc suite's unchanged C sources on the box and compares their results case by case with the `libc` suite; M10's `busybox` category carries the per-applet compile, link and usage results the `libc` suite's `busybox` category defines, plus the `utilities` suite on the natively built applets.

Total planning range: **75–124 engineering weeks**, roughly 18–30 months of uninterrupted single-person work; allow 25–40% integration contingency. Budget approximately 50–90 kLOC of implementation/support tools plus substantial independent tests. These are estimates, not measured output. A small hello compiler is much earlier than production C11/BusyBox coverage.

Use the host harness and ARM64 QEMU for portable front-end/object/make iteration (S2); an ARM-hosted compiler may emit x86 objects without executing them. x86 execution acceptance is leased R240 metal evidence, not x86 QEMU. Long bootstrap/build cases need explicit per-case resource/time limits added to the suite contract; retain existing limits for existing cases. Register summaries only after child completion, verified outputs and the normal suite verdict/DONE contract. Record elapsed time, peak memory and temporary disk use; start serial builds and tune concurrency from measurements. Retain commit, sysroot/tool hashes, commands, case results, serial and SSH transcript per milestone. Run affected checks once per code state. Persistent acceptance uses the operator account and D3's preemption/return protocol; scheduling belongs to subsequent implementation work.

## 9. ARM64 later: the catch-up

Under D6 this port is the effort's catch-up: ARM64 QEMU, Parallels and VMware measure the `toolchain` categories once Breenix's tools emit and run ARM64 code there. Until then those targets show the categories as not run.

x86 code generation means a target-specific instruction selector, register allocator constraints, ABI classifier, assembler encoder and relocation backend, not an x86-specific C frontend. Share preprocessing, AST/types, semantic IR, diagnostics, archive handling, linker layout machinery and make. Hosting on ARM64 is already useful cross-compilation; emitting ARM64 is additional work.

An ARM64 port needs published AAPCS64/ELF specifications: x0–x7/v0–v7, homogeneous FP aggregates, different varargs, SP alignment, branch ranges/veneers, ADRP/ADD and paired relocations, instruction encoding and variant-I TLS via TPIDR_EL0. Target literal/layout code must handle Breenix ARM64's binary128 `long double`, unlike x86's x87 format. Reuse tests with target expectations, then repeat native rebuild/fixed-point and libc/BusyBox proofs on ARM64. Reserve approximately **16–26 additional engineering weeks** after stable IR/ABI boundaries; do not present it as renaming registers.
