# R240 physical-root suite evidence

Review correction: installation reuse described below is historical behavior of
`5f0792a0`, superseded by `a9786929`. Main-path boots now reinstall a fresh root
with the requested target, including on a kernel-only change. This prevents
prior fixed-path outputs from satisfying a later raw writeback check and restores
fresh fixtures for other suites. The current delivery carries a `BREENIX-BOOT 1`
payload for disk-root modes; the obsolete console-intent format and its reader
have been removed. Firmware install verification
updates disk ownership before kernel mount.

Current hardware acceptance is recorded in the consolidated validation comment on
[PR #1992](https://github.com/ryanbreen/breenix/pull/1992). It distinguishes fresh-root
isolation, install ownership before mount, and the final physical-disk suite runs.
The historical measurements below do not validate the repaired delivery policy.

The earlier review launches `20261018T221031Z-metal` and
`20261018T221148Z-metal` ended at exit 75 before build delivery or power-on because
startup reconciliation could not confirm power-off (#1994).

Scoped host checks cover reinstall/credentials, pre-mount ownership, current
payload delivery, console handling, driver behavior, root staging and public-source
privacy. The current-format change removes the obsolete console reader and its
translation shim. No older-kernel compatibility is provided. Hardware validation
uses the R240 lease and its normal power-off cleanup.

The operator's 2026-10-18 disk-root decision replaces RAM-disk roots for main-path
default, suite and console boots. The driver stages and installs a fresh root
before kernel entry; per-boot target intent selects the mode. Recovery install and xHCI fault boots
retain their RAM-disk paths.

## Historical measurements at `5f0792a0`

The following three suite boots used kernel and tools commit `5f0792a0`.
Each record reports `disk: root`, `bootShape: disk-root`, a complete capture,
three of three disk-root stages, exit 0 and confirmed power Off.

| Suite | Boot record | Cases passed | Raw writeback checks |
|---|---|---:|---:|
| files-io | `20261018T213224Z-metal` | 219/219 | 5/5 |
| signals | `20261018T213238Z-metal` | 125/125 | Not declared by its manifest |
| directories | `20261018T213245Z-metal` | 117/117 | Not declared by its manifest |

The files-io boot installed the changed userspace image. Signals and directories
both retained `installedBy: 20261018T213224Z-metal`; their payloads omitted the
root image. This measures installation reuse across the suite switch.

Cold readback record `20261018T214647Z-metal` inherited the files-io lease after
confirmed power-off. Its firmware read and uploaded 268435456 bytes before loading
a kernel or mounting a filesystem. The host verified the root record, length and
upload digest, confirmed power Off, and ran the retained manifest scorer with
that raw image. Both the suite and readback records ended at exit 0. The verdict:

```text
PASS: SUITE files-io DONE passed=219 failed=0 skipped=0 total=219; raw disk checks passed=5
```

The raw image SHA-256 is
`d9cb8b89f673c762fa5b9b4fc4003bf98384e990e1c84b057000d7a3fee2f298`.
Raw captures, root images and site configuration remain in private evidence.

Earlier attempts remain failures: `20261018T205529Z-metal` stopped before power-on
when piped SOL buffered its banner; the wrapper now disables buffering.
`20261018T205743Z-metal` and `20261018T212440Z-metal` failed firmware HTTP address
mapping. The uploader now selects the boot interface and its boot-path address.
An intervening disk-root boot invalidated the first guest-only files-io result,
so that disk was not accepted as raw evidence. The automatic lease handoff removes
that interval between suite and readback.

The persistent root also exposed consumed dense truncate fixtures in
`20261018T211126Z-metal` (217/219). The two cases now recreate their inputs before
their existing allocation/free-count assertions. The five manifest disk checks
and their expected bytes were retained.

SOL is captured through a blocking pipe before terminal processing, with producer
stdio buffering disabled. A local capture exercise checked binary bursts and
reconnect appends. The signals manifest accepted 125/125 cases without a damaged
record. That passing boot and capture hardening do not establish the precise
cause of the historical 11-byte kernel/BMC/SOL loss in #1973.

Scoped host checks covered target selection, disk installation/reuse, lease
handoff, console capture and the existing driver cases. The production builds
added no warnings. Validation used the R240 lease; no x86 QEMU boot was run.

Tools were deployed from the tested branch through `scripts/metal/metal-deploy`.
After landing, deployment uses main through the same repository path; the final
validation comment records the deployed commit. Suites are not rerun solely for
a merge or push.
