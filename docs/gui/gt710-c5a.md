# C5a: offline DDR3 memx review

C5b subsequently captured the missing words and resolved both offline scripts;
see [the C5b capture report](gt710-c5b.md). The C5a record below describes its
original incomplete snapshot and the separate initialization prerequisite.

C5a is blocked on missing capture inputs for an **exact executable card
script**. The offline decoder, generator, ordered conditional trace and host
checks are available. No boot, deployment, branch-tools lock, PMU command,
GPU write, PR or merge belongs to this step. K1 and G1 govern the work;
the C5a brief's offline-only override applies.

The complete ordered trace is [gt710-c5a-memx.txt](gt710-c5a-memx.txt).
Source-level writes carry register, mask, data, full result expression,
source line and emission condition. The [JSON report](gt710-c5a-memx.json)
contains the full decoded selected-group tables, both phase configurations,
operations, CPU writes, unresolved inputs and resulting register expressions.
It deliberately has `exact=false` and `words=null` for the captured card.
These are offline review artifacts; no hardware execution was performed.

## Reproduction and scope

```
python3 tests/gt710_memx_test.py
python3 scripts/metal/gt710_memx.py tests/fixtures/gt710_c5a_card.json \
  --output docs/gui/gt710-c5a-memx.txt --json docs/gui/gt710-c5a-memx.json
```

`--registers SNAPSHOT.json` replaces the input snapshot with explicitly supplied
register/value pairs. The tool has no hardware transport or execution API.
Its supported calculation slice is v11 RAMMAP/RAMCFG, v20 timings, v40 PLL
limits, v41 GPIO and DDR3 mode 1, which cover this board's 405000 to 900000 kHz
transition. Other layouts require implementation, not conversion to zeroes.
The generator's mode-2 limitation is an offline implementation boundary;
it is not a new hardware admission predicate. No kernel path is changed.

For a complete *synthetic* snapshot, it resolves `ramfuc_mask` no-op
suppression, forced MR0 writes and `memx.c` batching. Each phase has its own
wire words and EXEC boundary; the aggregate words concatenate those streams
for inspection and do not replace the two EXEC calls. This is a static
host register model. Real autonomous register changes during a first EXEC
must be read at the second calculation, as nouveau does; synthetic values
are not evidence that this card will retain them.

C1's private ROM is 262144 bytes with SHA-256
`560026acd8fe588e0fde898f0b542bb9aac914f4da4b45ed7017bd90de5a8294`,
from inventory boot `20261031T143655Z-metal`. C2's 97-word POST inventory
snapshot is from `20261031T165022Z-metal`, serial line 520. The fixture
contains selected table bytes, selected table-pointer data and the captured
clock register words. It contains neither the complete ROM nor VBIOS
instruction streams. Table values describe the board configuration; they
are not substituted for missing live timing or mode-register reads.

|---|---:|---:|---:|---:|---|---|---|---|

| target 900000 | 1 | 1 | 32 | 1 | `0x1aab` | `0x00012001` | `0x1aab0000` | `0x1aab` |

At 405 MHz, P=2 gives an 810 MHz VCO; rejecting the output because it is
below the VCO minimum would add a refusal nouveau does not make. At 900 MHz,
P=1 and the reference PLL supplies memory directly. Rounded fractional
coefficients imply about 900001.1 kHz in the mathematical model, not a
hardware readback. The second PLL is not programmed for this transition.
The captured `0x132000=0x18010000` has enable clear;
`0x132020=0x20030001`, `0x132024=0x00021d01`,
`0x132030=0x10000003`, `0x1373f4=0x11` describe the inherited reference path.
`0x132034` was not captured.

## Two scripts, including host-side writes

`gk104_ram_calc:1112-1154` copies the lower-frequency configuration and
substitutes the target's `ramcfg_11_02_04`, `ramcfg_11_02_03` and
`timing_20_30_07`. Here the first two stay 0 and the last changes **5 to 6**.
The intermediate differs from the former configuration, so nouveau first
calculates/executes an intermediate **405000 kHz** script, then calculates/
executes **900000 kHz**. DDR3 does not otherwise consume `timing_20_30_07`;
that does not authorize deleting the intermediate phase.

Each script follows this source-defined order; the linked text contains
79 of 79 intermediate and 82 of 82 target source operations, including conditionally elided writes:

1. Set `0x10f808` bit 30, ENTER host/FB pause, display control `0x62c000=0x0f0f0000`.
2. Disable automatic refresh, precharge/refresh, toggle PFB control,
   delay 1000 ns, write `0x10f090=0x60` then `0xc000007e`.
3. Program the literal `0x10f824` configuration masks, isolate the clock,
   set `0x1373ec` from RAMCFG and put `0x1373f4` in the reference-change state.
4. If coefficients or fractional low word differ, disable PLLs as the
   source says, write reference coefficients and fractional words,
   enable the reference PLL and WAIT at `0x137390`, mask/value `0x00020000`,
   **64000 ns**. No additional persistent lock predicate is added.
5. Select reference mode 1, apply the target's `0x132040` bit 16 / 20000 ns
   delay where its table requests it, write `0x10f65c`, `0x10f6b8/6bc`,
   restore PFB flags and write the eleven timing words and packed fields.
6. Restore refresh, enable/reset DLL, write MR2/MR1/MR0, issue the second
   forced DLL reset and source delays; toggle `0x10f830` bit 24 in mode 1.
7. Toggle PFB control around `0x10f318=1`, delay, LEAVE, restore display
   control `0x62c000=0x0f0f0f00` and the configured `0x10f200` bit 11.

The MR calculations preserve unspecified inherited bits. For this board:

- 405 MHz: MR0 = `(oldMR0 & ~0xf74) | 0x630`, MR1 = `oldMR1 & ~1`,
  MR2 = `(oldMR2 & ~0x38) | 0x08`.
- 900 MHz: MR0 = `(oldMR0 & ~0xf74) | 0xe14`, MR1 = `oldMR1 & ~1`,
  MR2 = `(oldMR2 & ~0x38) | 0x20`.

These are calculated values, prior to the forced reset operations, which
set then clear MR0 bit 8. Nouveau preserves the inherited MR1 ODT bits
`0x244`; its v20 path does not obtain a replacement ODT from this ROM.

`gk104_ram_prog:1231-1248` surrounds each EXEC with seven CPU masked
writes from `gk104_ram_prog_0`: a 1 MHz table selection before EXEC and the
phase's frequency afterwards. The generator computes the diff indicators

The values are OR data, not complete register values. `core/device.h:121-126`
writes even with a zero mask, whereas `ramfuc.h:118-127` suppresses an
unchanged memx write unless forced. Both preserve `(old & ~mask) | data`;
masking `data` itself would break several source operations.

PMU encoding follows `pmu/memx.c:19-42,110-140`: header
`(payload_word_count << 16) | opcode`; WR32 is opcode 3 with address/value
pairs, WAIT is 4 with address/mask/value/timeout, DELAY is 5 with nanoseconds,
ENTER/LEAVE are 1/2 without payload. A cache reaching 64 words flushes before
append, and WAIT/DELAY flush individually. The card's exact no-op decisions
and full values are unresolved, so the card report emits no packed words.

## Scanout, blocking and observable failure

The DDR3 script calls ENTER/LEAVE, not WAIT_VBLANK. With a display subdevice,
it writes `0x62c000=0x0f0f0000` after ENTER and `0x0f0f0f00` after LEAVE.
These are the literal upstream display controls, not evidence that vblank
was observed or a frame remained intact.

For GK208, firmware `memx.fuc:83-156` clears bits `0xaa2`, then bit 0 at
`0x001620`, clears bit 0 at `0x0026f0`, asserts FB_PAUSE through PMU OUTPUT_SET
(offset `0x7e0`, bit 2) and waits for OUTPUT (offset `0x7c0`) bit 2. LEAVE
clears that request through OUTPUT_CLR (offset `0x7e4`), waits for OUTPUT
bit 2 to clear, then re-enables the `0x0026f0` and `0x001620` bits in source
order. Those firmware operations are effects of ENTER/LEAVE, not extra
host-generated WR32 commands. The pause acknowledgement loops have no
local timeout. `memx_exec` replies with elapsed pause time and PMU input,
not a memory-integrity verdict.

Changing refresh, DLL and timings while memory fetch is paused can disrupt
scanout. The source specifies neither a time bound nor vblank synchronization for a visible
frame here. C5 before display takeover still encounters an inherited display
if it is active; the existing sink does not become safe merely because the
Breenix console has not taken ownership. C6 must assess active-display effects
separately. No console or GPU suite was run for this offline step.

Possible later observations include: no EXEC reply / stuck FB_PAUSE; the
reference PLL staying at 405 MHz or failing its source wait; a reply after
the wait timed out; unchanged memory clock; readback corruption, PFB faults,
failed GR/CE completion, frozen or underflowing display, or a blank signal.
A PMU reply does not measure frame loss or clock stability. K1 requires subsequent register-derived frequency,
workload response, reversal and repeatability; the independent GPC counter
can also expose a disturbed core domain. No new refusal predicate or
success threshold is added in this offline code.

conditional reference programming, CPU writes and no-op suppression:

```
10f290 10f294 10f298 10f29c 10f2a0 10f2a4 10f2a8 10f2ac 10f2cc 10f2e8
10f300 10f304 10f320
10f400 10f410 10f420 10f430 10f440 10f444 10f468
10f808 10f824 10f82c 10f830 132034 132040 1373ec
```

The capture address list in `kernel/src/gpu/gk208/c2/observe.rs:77-101`
contains none of those 32 words. The table fixture intentionally leaves them
absent. [Issue #2617](https://github.com/ryanbreen/breenix/issues/2617) tracks this gap.
The coordinator needs to authorize or supply a read-only snapshot,
including live timings and MR0/1/2, then review the resolved script and the
initialization precondition. A later transition must recalculate the target
phase from its live post-intermediate state as nouveau does. No read-only
boot was improvised under C5a's offline-only instruction.
