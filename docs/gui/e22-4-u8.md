# E22 22.4-u8: forced capture races

Check commit `d511d914` replaces the five pending capture-race bodies in
`uitest_suite/frames.rs` and adds the host fired-witness check. Check commit
`d88147ab` adds the controlled-app and typed-refusal checks. The implementation
follows both commits. The cumulative selection and case meanings are unchanged.

Each overlap arms the existing CAPTURE_STALL (18) for the window, starts a
reader through libuitest capture, waits for its fired counter to rise, requests
the app action, then releases with RELEASE_STALL (11). The judge requires the
release counter to rise too. An action taking one second from arming fails:
the kernel self-releases its stall after one second. These checks prevent an
expired stall from qualifying a complete but unforced capture.

- Drawing: commit N+1 while A is paused; A must return N's full pattern, root
  and returned commit identity.
- Two readers: A is paused, the app's commit command is sent, and B captures
  before the command reply is consumed. A returns N; B must return one of the
  two produced generations whole, with its own returned id and matching tree.
- Resize: resize to 160x100 and commit while A is paused. A must retain the old
  320x200 extent, pixels, root and id. Any capture error, including ENOENT, fails.
- Destroy: destroy while A is paused, require the whole old commit, then make
  another libuitest capture and require typed ENOENT. Three warmup rounds and
  twenty measured rounds use one persistent reader and the same app workers;
  MemFree must meet the existing BreenGL destroy case's 64 KiB bound.
- Threads: producer 0, producer 1, then producer 0 commit alternately. Captures
  pin each of those three commits across the other thread's next commit. The
  expected producer ids must differ, and ordinals must advance by one.

The explicit `uitest-app_test --capture-control` mode has two persistent
producer threads and a private session socket. The workers serialize drawing
through one BreenGL Window, paint u6's RGB marker through GPU batches in the 200 rows (100 after resize), write its root, and verify the returned ordinal. Create, commit, resize,
destroy and quit commands return the producing identity and extent. Other app
modes keep their existing path. Captures use separate one-shot arena files;
readers open their mappings inside the reader thread and remove each file after
its capture. `capture::window_result` preserves a typed device error while
`capture::window` keeps its String-returning API and partial-slot behavior.

The cases use Session::connect without starting a compositor. Section 3.1
permits commits without one, and window CAPTURE reads the pinned window buffer. This keeps unrelated
composition pins and allocations out of the destroy measurement. The round
count and memory bound follow windows_capture_across_destroy. B may return N or
N+1, as the plan requires each reader's whole commit rather than one scheduling
order. No third-party implementation was copied or adapted.

Code reading found no section 3.1 contract violation: window/ops.rs capture
snapshots extent/id while taking pixel and tree pins; its resize replaces the
buffer pool while the captured target's Arc remains held; window/present.rs Pin
and window/mem.rs retain the copied memory through destruction. No kernel or
driver source or control was changed.
