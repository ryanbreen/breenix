# C3-0: offline voltage map before voltage control

K1/G1 and the coordinator's C3-0 brief govern this step. This is an offline
host decoder change: no boot, deployment, branch-tools lock, kernel change,
voltage write or clock write. The calculations below describe the ROM model,
not measured stability at a new frequency. C2's counter scale is not changed.

The authenticated C1 baseline capture is `20261031T150451Z-metal`; the earlier
C1 inventory `20261031T143655Z-metal` contains the same 256 KiB ROM SHA-256:
`560026acd8fe588e0fde898f0b542bb9aac914f4da4b45ed7017bd90de5a8294`.
Raw ROMs, GPIO capture bodies, serial and generated JSON stay in private run
artifacts. Temperature inputs 31 and 32 C come from C3b's retained
`20261031T182115Z-metal` records; they are explicit model inputs, not a C1
sensor reading. C1 had `needs-setup`. The speedo fuse was not captured.

Reproduce using the retained C1 directory, which holds `run.json`,
`serial.txt` and `gt710-pixels.rle`:

```
python3 scripts/metal/gt710_clock.py --capture PRIVATE_C1 --temperature-c 32 --output PRIVATE_REPORT
python3 scripts/metal/gt710_clock.py --rom PRIVATE_ROM --temperature-c 32
```

Without `--temperature-c`, linked temperature terms remain bounded by their
ROM clamps. `--speedo` accepts a captured fuse value if a later step supplies
one; the decoder leaves unavailable inputs unresolved. It exposes the vmap path, missing inputs, request
range, upward-rounded VID range, per-pin sense and logical level, cstep
membership and inherited memory clock.

`log1=1`, so physical high means logical 1. The C1 words were: [G]

VID bits 4..0 are **01001**, VID **9**, table value **912500 uV**. This is
GPIO sense interpreted through the ROM regulator table, not an analog voltage
measurement. No VID PWM function is selected; the captured PWM words do not
select the voltage on this board. A missing pin read or a `0xbadf` PRI error
now leaves the state unmeasured; an absent DCB function is masked as in
nouveau's GPIO initialization. [G]

## Performance levels, cstep base and boost

The perf v40 table at `0x6df0` supplies these two active levels. The numbers
in the raw GPC column are the clock-tree/programming units; nouveau displays
that domain divided by 2000 as MHz, hence the core column. Memory is the
perf table frequency, not an effective DDR marketing rate. [P, C]

| Pstate | Raw GPC kHz | Core MHz | Memory kHz | Vmap ID / link | Request at 31 C | Request at 32 C | Rounded VID / mV |
|---:|---:|---:|---:|---|---:|---:|---|
| 7 | 810000 | 405 | 405000 | 9 -> 10 | 890841 uV | 889941 uV | 8 / 900 |
| 15 | 1307000 | 653.5 | 900000 | 7 -> 8 | 890841 uV | 889941 uV | 8 / 900 |

Vmap v20 is at `0x76d3`. IDs 7 and 9 clamp their mode-0 polynomial to
856250 uV exactly. Links 8 and 10 are mode 1 with coefficients
`[1048576, 0, -59, 0, 0, 0]`, clamped to 0..62500 uV. At temperature T,
the added term is `62500 + ((-59*T*15625) >> 10)`, clamped first, then
added to 856250. At 31/32 C the offsets are 34591/33691 uV. Speedo cannot
change these fixed base results. At unknown temperature their aggregate
range is 856250..918750 uV (VIDs 5..10 after rounding); using that wide range
alone does not decide whether 912.5 mV suffices. [M]

The cstep v10 table's pstate-7 entry selects maximum index 0; pstate 15
selects 42. Nouveau constructs indices 0 through the selected index, inheriting
the pstate memory clock and adjusting the core domains with boost constraints.
Index 0 is the **810000 kHz raw cstep base**, voltage ID 11 -> 10, with the
same 890841/889941 uV request and 900 mV rounded setting as above. Index 19
is the explicit **1307000 kHz** cstep, ID 31 -> 56 -> 4 -> 3. It has a
speedo-dependent requirement distinct from the perf-base ID 7. [C, M]

Boost v11 at `0x6f1e` has no voltage ID and no independent memory target:

| Active boost record | Raw base clamp kHz | Domain 2 (ROP) | Domain 4 (hubk06) | Domain 1 (hubk07) | Memory inherited from perf |
|---|---|---|---|---|---|
| Pstate 7 | 270000..810000 | 810000 fixed, 100% | 810000 fixed, 100% | 810000 fixed, 100% | 405000 kHz |
| Pstate 15 | 1307000..1908000 | 1307000..1908000, 100% | 1080000 fixed, 100% | 1307000..1908000, 100% | 900000 kHz |

Neither active boost record has a domain-0 override: GPC uses the global
clamp. Each has seven zero-percent, zero-range domain-16 padding subentries.
Two remaining boost base records are zero-filled, with ten such padding
subentries each; two remaining cstep membership records are zero-filled
pstate-0/index-0 entries with no active perf level. Cstep slots 43..59 have
frequency 0 and voltage ID 0; they are unused, not 1187.5 mV operating points.
The host report retains the raw table records and identifies unused indices.

For an explicit formula for each row, mode-0 IDs 13..54 have the signed
coefficients retained in the JSON and evaluate
`arg0/10 + arg1*S/10 + arg2*S*S/100000` with each division truncating
toward zero, then clamp to that ID's min/max. Add the already-clamped linked
term: IDs 13..22 link 55; 23..47 link 56; 48..54 link 57. Those links point
through zero-valued 4 -> 3. At 32 C links 55/56/57 contribute
18646/27578/18136 uV respectively; at 31 C they contribute
19119/28219/18533 uV. These temperature terms do not depend on speedo, while
the initial polynomial does. The private report includes both 31 and 32 C
matrices and the original coefficients. [M]

At today's 912.5 mV and 31–32 C:

- The perf-base raw GPC **1307000 kHz** requires table setting **900 mV**.
  The 810000 kHz cstep base requires that same setting.
- The explicit 1307000 cstep (index 19) needs **900..1000 mV** including
  the base floor at 32 C; its actual point cannot be resolved without speedo.
- The highest GPC established by the ROM voltage bounds alone is
  **1307000 kHz raw** (653.5 MHz displayed core), using the base or the
  lower-index cstates clamped to it. This describes the voltage model; hardware stability at that clock is
  unmeasured.
- The upper candidate not excluded by the clamps is index 27,
  **1516000 kHz raw** (758 MHz core); it could need **912.5..1062.5 mV**.
  Index 28 already needs at least **925 mV**. The actual maximum in the
  1307000..1516000 range is unresolved without speedo. This is not permission
  to program 1516000 at 912.5 mV.

`highest_at_current_uv` labels its lower endpoint `guaranteed_gpc_khz`
and its upper endpoint `possible_gpc_khz` with `exact=false`. These mean
voltage-model bounds over missing inputs, not measured achievement; a particular physical speedo may not attain the
upper endpoint. With no
temperature input the lower endpoint is unmeasured and the coarse upper
endpoint is 1647000 kHz; that coarser result must not replace the 31–32 C
analysis. Nouveau's vmap limit IDs 1, 0 and 2 are above 912.5 mV, so they
cannot further restrict this current-voltage comparison. [M]

The missing input is the chip's speedo. MIT `volt/gk104.c:72-87` reads fuse
offset `0x3a8` around writes to GPU `0x122634`. C1 recorded the thermal fuse,
clock registers and VID/PWM inventory, not this speedo read. The offline
decoder has no MMIO access interface. The coordinator must choose any later
capture or operating point; no exact maximum is fabricated from POST VID.
Follow-up: [#2614](https://github.com/ryanbreen/breenix/issues/2614).
The independent absolute counter-scale question remains
[#2612](https://github.com/ryanbreen/breenix/issues/2612).

## Why the cycle counter reads one sixteenth of raw GPC

The C2d boot `20261031T173430Z-metal` reported these exact serial lines:

```text
GT710_CLOCK_MEASURED {"phase":"post","domain":"gpc","status":"ok","khz":50625,"method":"gpc0-pre-counter-ptimer","cycles":1013898,"interval_ns":20027536,"ptimer_ns":20027536,"bracket_ns":19040,"counter_restored":true}
GT710_CLOCK_MEASURED {"phase":"low","domain":"gpc","status":"ok","khz":33750,"method":"gpc0-pre-counter-ptimer","cycles":675094,"interval_ns":20002640,"ptimer_ns":20002640,"bracket_ns":21216,"counter_restored":true}
GT710_CLOCK_MEASURED {"phase":"restored","domain":"gpc","status":"ok","khz":50625,"method":"gpc0-pre-counter-ptimer","cycles":1012701,"interval_ns":20003712,"ptimer_ns":20003712,"bracket_ns":20352,"counter_restored":true}
```

These are serial lines 893, 940 and 980. The reported rounded rates are
810000/16, 540000/16 and 810000/16. The sampler uses the nvatiming GPC0
pre-counter method: `CTRL=0x40002`, `PRE_OP=0xffff` (the four-input truth
table is always true), differences of the live accumulator `0x1800a8`, and
PTIMER elapsed nanoseconds. It counts asserted PRE samples in the local
GPC performance-counter domain; with constant-true PRE this is that counter
domain's tick rate. It does not count issued instructions, completed
fragments, SM occupancy, or a selected shader event. PRE_SRC is immaterial
to a constant-true truth table. [T]

**The checked sources do not document a divisor of 16.** rnndb names this
accumulator `CTR_PRE_NEXT`, assigns `0x180000` to GPC domains, names mode 2
QUAD and counter mode 0 SIMPLE, and leaves CTRL bits 18..20 `UNK18`.
`0x40002` sets that unknown field to 1; it is not documented there as a
prescaler. PERIODIC_PERIOD bits 21..23 are 0 (disabled), not 16K or /16.
Nvatiming prints the resulting count after one second directly as Hz with
no factor correction. Nouveau GF100 PM uses the same `0x40002` setup and
reads event/PRE counters separately from its cycle normalization counter
at +0x70; it supplies no /16 interpretation. rnndb's clock-tree divider
fields likewise do not establish the counter tap's relationship to raw GPC.
[T]

The precise physical tap/divider producing the observed scale is therefore
unresolved. A divided PM-domain clock is consistent with the observation;
it is an inference, not a documented hardware divisor. Retain the measured
rate and its ratio without multiplying it into an absolute GPC measurement.

Separately, MIT nouveau `clk/gk104.c:494` defines GPC's display divisor as
**2000**, whereas its reader returns raw kHz. Thus raw **810000 kHz** is
reported as **405 MHz**, and raw **540000 kHz** as **270 MHz**. [C]
The observed counter is **1/8 of that displayed-core rate**: 50.625 versus
405 MHz, 33.75 versus 270 MHz. The factor of two in raw-versus-real/reporting
units explains only two of the observed factor of sixteen; it does not
explain the remaining factor of eight. K1's accepted relative down/up
response remains the coordinator's ruling; no absolute-scale fix or new
hardware claim is made in C3-0.

## Validation

Check-only commit `c6e762b6` precedes the decoder extension. Its three new
checks failed on missing `current_vid`, `cstep_levels` and
`voltage_requirement` before implementation. The implementation passed these
three checks, the two existing C1 offline ROM/voltage checks, and C1's bulk
capture authentication check (6 checks). They cover active-low polarity,
missing/PRI-error reads, signed division, temperature links, unresolved
speedo, upward rounding, cyclic links, boost clamping, inherited memory and
perf-base voltage floors. The retained real capture was decoded at unknown,
31 and 32 C without adding a ROM fixture to the repository.

The x86 release command `CARGO_BUILD_JOBS=4 taskpolicy -b cargo build
--release --features gt710_clock_probe --bin qemu-uefi` finished in 1m 58s
with no warnings/errors. It ran once; subsequent changes are Python and
prose, so the kernel tree is the same. No boot was performed in this step.

Claim-lint invocations and results are recorded in the private C3-0 run
notes, including changed-hunk and commit-message checks.
