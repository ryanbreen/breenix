# Breenix OS Project Roadmap

This is the master project roadmap for Breenix OS: current development status,
completed phases, in-progress work, and planned work. Update after each PR
merge and when starting new work.

Detailed, per-issue tracking lives in GitHub Issues (`gh issue list` /
`gh issue create` in `ryanbreen/breenix`), not here — this file stays a
short pointer to what's current. Live turn-by-turn ARM64/Parallels work
log: `docs/planning/ralph-roadmap.html`.

## Current Development Status

Focus is ARM64/Parallels: teardown/process-lifecycle correctness, SMP
scheduling, and the userland/POSIX compliance stack (dashboard:
https://v0-breenix-dashboard.vercel.app/).

- ✅ **PR-C: typed net-lock guard replaces no-op x86 IRQ primitives, closes the same-CPU net-table deadlock class** (Aug 2026, part of the #545 4-PR sequence) — `net::irq_save()`/`irq_restore()` were real DAIF masking on aarch64 but compile-time no-ops on x86_64, so nine spin-locked net statics (TCP_CONNECTIONS, TCP_LISTENERS, SEQ_COUNTER, ARP_CACHE, ARP_PENDING_QUEUE, NET_CONFIG) had zero exclusion on x86: a thread holding one could be interrupted into the inline-dispatched NetRx softirq, which reacquires the same lock on the same CPU and spins forever. Replaced both free functions with a typed, `!Send`, `#[must_use]`, Drop-released `NetLockGuard`: on x86 a real bottom-half disable (Linux `spin_lock_bh` equivalent, via the existing per-CPU softirq count so `irq_exit()`'s dispatch predicate goes false while held; `cli` was rejected because masking IF=0 across the TCP state machine would blow the interrupt-path timing budget), on aarch64 unchanged DAIF read/mask/restore. Also closed two unguarded raw `.lock()` call sites (`ipc/poll.rs`, `syscall/socket.rs`) structurally, by making `TCP_CONNECTIONS`/`TCP_LISTENERS` module-private behind `pub(crate)` accessors, so a future unguarded external lock is a compile error, not a review miss.

All three now use the established discipline (guard bound first so it releases last, explicit early `drop()` of the inner mutex guard, no logging or cross-lock calls held under it). The round-1 coverage ratchet had certified completeness against a hand-authored 6-static list written by the same PR it gated — exactly how those three statics stayed invisible to it — so it was replaced with a static enumerated straight from source (every `static NAME: <type>` under `kernel/src/net` whose type names `Mutex`/`RwLock`, atomics excluded on purpose), each required to be either guarded-by-construction or on a documented thread-context-only allowlist (empty today), with a discovery-floor canary so a blind enumerator (path-scope or parser regression) can't silently stop protecting anything; the same discovered set now also feeds the hardirq-surface ratchet.

- ✅ **x86 context-switch routing/rollback fixes found day-after #557's ring-transition work — closes #545's D3 prerequisite** ([PR #558](https://github.com/ryanbreen/breenix/pull/558), Aug 2026)
  - Two independent defects, x86-only (`kernel/src/interrupts.rs` is `#![cfg(target_arch = "x86_64")]`). Defect 1: the saved-frame routing predicate carried a conjunct (`process.main_thread.has_started`) that was always `false` for every process created via `create_user_process` — a user thread preempted in kernel mode was misrouted to the userspace restore path and killed with `terminate(-11)`; fixed by making the routing predicate token-identical to the ring-3 enforcement predicate. Defect 2: six early returns in `check_need_resched_and_switch`/`switch_to_thread` returned after `scheduler::schedule()` had already committed the dispatch (ready-queue push, `cpu_state.current_thread`, per-CPU pointer, TSS.RSP0) without rolling any of it back, leaving the recorded current naming a thread that wasn't running; all six now call `abort_dispatch_and_resume` + `set_need_resched`, the same undo `abort_dispatch_and_resume` already did for first-userspace-entry.
  - **OQ1 mechanism**: pinned against a preserved gate run's serial log — idle's kernel frame got saved into thread 20's saved context because defect 2 fired one tick earlier (a save-lock failure left the recorded current naming thread 20 while idle was still executing), then defect 1's misrouting turned the correctly-saved-but-misattributed frame into a fatal refusal. Defect 1 alone would not have fixed that run (it would have silently resumed thread 20 on idle's stack); defect 2 is what prevents the bad save. They ship together on purpose.
  - **Round 2** (post-review) closed two further blockers found in the initial rollback shape: B1 — `abort_dispatch_and_resume` was forcing `Blocked` resume threads to `Running`, silently dropping any wake that landed on them (both waker paths only match `Blocked*`/`Ready`, never `Running`); fixed to read the resume thread's state once and only force-`Running` + dequeue when it was already `Ready`/`Running`, leaving `Blocked*`/`Terminated` untouched. B2 — the `SignalDeliveryResult::Terminated` arm rolled back only scheduler bookkeeping while the saved frame, `TSS.RSP0` and `CR3` still named the just-terminated thread's process; fixed to complete a switch to idle (`setup_idle_return` → `switch_to_idle` → `switch_to_kernel_page_table`) instead, mirroring the existing `RestoreError::KernelFrame` refusal precedent, so no skew remains.
  - **Fault-injection proof (B3)**: a fire-once shim forced the `:308` save-path `try_manager()` fallback to fail; serial shows the injected `Failed to acquire lock to save kernel context for thread 18`, the very next attempt saves *thread 18's own* kernel frame (RIP/RSP match exactly on later restore, no cross-thread skew), and the boot reaches `USERSPACE TEST COMPLETE`/`TEST RUNNER: All tests passed` with 0 panics. Injection patch fully reverted (empty diff) and one clean boot confirmed post-revert. The other five rollback sites (`:271`, `:278`, `:562`, `:899`, `:1064`) rest on the structural ratchets plus a caller-by-caller state-axis audit rather than a second live fault injection.

- ✅ **AArch64 IRQ-resume page-table corruption fixed** ([PR #531](https://github.com/ryanbreen/breenix/pull/531), Aug 2026, closes [#528](https://github.com/ryanbreen/breenix/issues/528))
  - Root cause: compiler-generated NEON `memset` (used for page-table zeroing) ran on hardware-FP kernel codegen. The aarch64 IRQ entry/exit path does not preserve FP/SIMD registers, so an IRQ landing mid-`memset` resumed with a clobbered `q0`, spraying live machine values over the rest of the table — the contiguous 32-byte-boundary tails with 16-byte repeats captured by the Gate-0 discriminator.
  - Fix: split-target architecture. Kernel builds general-regs-only/soft-float (Rust and C, via `-mgeneral-regs-only`), eliminating live kernel `q`/`v` state across IRQ/syscall boundaries by construction (0 FP/SIMD-register operand lines across the entire linked kernel ELF, down from 4,807 at `main`). Userspace is unchanged — hard-float, 142/142 ELFs byte-identical to `main` (SHA-256).
  - Note: userspace FP/SIMD state is *not* preserved across task switches — that EL0↔EL0 exposure is separate and pre-existing, tracked at [#529](https://github.com/ryanbreen/breenix/issues/529). This fix only removes kernel-side FP clobbering.
