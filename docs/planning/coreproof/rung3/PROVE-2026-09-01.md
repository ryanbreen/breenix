### M(new) — `coreproof_mut_outgoing_fallback_requeue` (#607): the default leg is vacuous by construction; `strand_inject_live_outgoing` re-finds it

**FIX ROUND correction (B1, B2).** The paragraph originally here claimed
`--require-cov` could not be used against this mutation because "there is no
`coreproof_mut_` `proof_cover!` counter registered for it in `coverage.rs`."
That sentence was false at these bytes when it was written: this branch's
own `kernel/src/proof/coverage.rs` registers `MutSite::OutgoingFallbackRequeue`
(short name `outgoing_fallback_requeue`), and `driver_h::note_outgoing_
fallback_coverage` populates it from `INLINE_SCHED_NULL_FALLBACK` deltas.
Gating the original leg on it exposes what the reported "0/3 violations, an
honest instrumented miss" actually was:

`docker/qemu/run-coreproof-gate.sh --component H --features
coreproof_mut_outgoing_fallback_requeue --require-cov
coreproof_mut_outgoing_fallback_requeue --seeds 3 --profile max`:
**3/3 boots vacuous.** Every closing record reports
`cov=...,outgoing_fallback_requeue=0`, and the gate's own vacuity guard
prints `mutation window is vacuous — cov=outgoing_fallback_requeue=0` on
every boot; `ARM64 CORE-PROOF GATE: FAILED` (correctly — a vacuous trial is
not a pass). (`evidence/fix2-b1-require-cov-vacuous.txt`)

**The miss is structural, not a density shortfall (B2).** On this workload,
`inline_schedule_trampoline` only calls `strand_oracle::inject_if_armed`
when `idle_id == old_id` (`context_switch.rs`'s `injected_leg` computation,
the `not(feature = "strand_inject_live_outgoing")` arm). The mutated block
itself is `if old_id != idle_id && (should_requeue_old ||
old_ready_after_save) { sched.requeue_thread_after_save(old_id); }` —
gated on `old_id != idle_id`. Since the only injected null-fallback in this
workload always has `old_id == idle_id`, the mutated block is a **provable
no-op on every injected entry**, and organic (non-injected) null-fallback
entries are 0 across this whole record's 216 gate boots (leg 2's 50, leg
3's 6, leg 4's 160): `grep -rl 'CPU_IDENTITY_SPLIT'` over all of them
returns 0 files, so `COREPROOF_INLINE_HANDOFF_SELF_RETRACTED` was never set
by real production traffic in this window (§6 below, added by this fix
round, fixed a separate identity bug in that same tag — the zero count
itself was already correct either way, since it counts organic sets, not
retractions). No amount of additional seeds or wall-clock time reaches the
mutated block on this workload; #734 as originally filed named the wrong
mechanism (stimulus density) — corrected below.

**The re-trial, using the lever the review named.** `strand_inject_live_
outgoing` (`kernel/Cargo.toml`, `= ["boot_tests"]`) already exists in-tree
for exactly this: it widens `inline_schedule_trampoline`'s one-shot
injection to also fire when the outgoing thread is a dedicated, no-wakeup
driver thread (a `ret_zero_pc_oracle`-owned victim, `outgoing_tid=10` in
every serial below), forcing `old_id != idle_id` on the injected leg — see
`docs/planning/teardown-unification/607-576-serials/README.md`'s "Leg S"
for this feature's own pre-existing, independently-verified behavior.
Combined with the mutation, across 16 boots over three runs:

* `--features coreproof_mut_outgoing_fallback_requeue,strand_inject_live_outgoing
  --require-cov coreproof_mut_outgoing_fallback_requeue --seeds 3`: 2/3

  (`evidence/fix2-b2-live-outgoing-require-cov.txt`).

fired_cpu=2:fired_iter=919`. This is a genuine re-find of #607 using the

Reported honestly as ~31% per boot across these 16 boots, not as a

**Disclosed, not swept under the 5/16: `--require-cov` does not compose
with this leg.** Every boot in the widened-injection combination reports
`cov=outgoing_fallback_requeue=0` **regardless of whether the mutation was
caught** — confirmed on boots that DID catch it
(`evidence/fix2-b2-live-outgoing-require-cov.txt`). Mechanism:
`strand_inject_live_outgoing`'s one-shot injection fires once, early in
boot (its own report line settles 3 s after `every_compiled_test_fired()`,
but the underlying injection lands at or before `[BOOT_TESTS:PASS]` —
before `driver_h::run()`'s `open_window()` baseline capture).
`note_outgoing_fallback_coverage`'s coverage counter is a delta *since that
baseline*, so it structurally cannot observe a one-shot event that already
happened before the window opened. `OUTGOING_HANDOFF_STRANDED` still
catches it because `strand_oracle::stranded_count()` is a **state** read
(baseline-vs-cadence), not a window-delta of the underlying event, and the
strand persists until something resolves it — which the mutation, by
design, prevents. `--require-cov coreproof_mut_outgoing_fallback_requeue`
is therefore the wrong anti-vacuity tool for this specific leg; the leg's
own anti-vacuity evidence is the predicate firing with real peer
attribution instead, exactly as reported above.

#734 is corrected (see the GitHub issue) to name the structural
reachability gap and this lever, rather than "stimulus density."

## 6. FIX ROUND (2026-09-01) — M1: the §1.4 attribution latch used two identities (#735)

The closure review (`docs/planning/coreproof/rung3/review.md`) found that
`schedule_from_kernel`'s self-retraction tag site
(`context_switch.rs`, inside the `pivot_cpu.index() != cpu_id` retraction
arm) stored `COREPROOF_INLINE_HANDOFF_SELF_RETRACTED[cpu_id]` — the
**carried** identity — while `inline_schedule_trampoline`'s classification
site reads its own fresh `CpuId::current()`, i.e.
`COREPROOF_INLINE_HANDOFF_SELF_RETRACTED[pivot_cpu.index()]` — the identity
the trampoline this exact retraction produces actually runs under, since
`aarch64_inline_schedule_switch` is a same-physical-core stack pivot and
branch (never a cross-CPU handoff) and interrupts stay masked from the
retraction through trampoline entry. Two wrong-way consequences: (a) the
retraction's own designed self-recovery reads an untagged fresh slot and is
misclassified `ALREADY_CONSUMED_UNEXPLAINED` instead of `ATTRIBUTED` — a
false positive on the rung's headline predicate; (b) the `true` left on the
carried slot has no lifetime bound, so a later, unrelated null read on that
same CPU — potentially a genuine future `#605`-class specimen — silently
absorbs it as `ATTRIBUTED` instead of correctly `UNEXPLAINED`, a false-green
path. `impl-notes.md` and the original `#735` filing argued this was
"self-consistent, not a bug"; that argument is wrong — it reasons about a
different, later, unrelated trampoline invocation on the carried CPU's own
future scheduling activity, not the invocation this retraction itself
produces.

**Fix.** Two changes, `kernel/src/arch_impl/aarch64/context_switch.rs`:

1. The tag site now indexes by `pivot_cpu.index()` (the fresh identity),
   not `cpu_id` (the carried one) — store and read now agree on the
   identity the resulting trampoline invocation actually runs under.
2. A new `coreproof_reset_self_retracted_tags()` function (same
   `#[cfg(feature = "coreproof")]` gating, observation-only, no
   perturbation — same category as `strand_oracle::inject_if_armed`) resets
   every CPU's tag to `false`. Called from `driver_h::run()` immediately
   after `coverage::open_window()` (`kernel/src/proof/driver_h.rs`),
   bounding the latch's lifetime to one measured window: a `true` left by
   activity before the window opens can never be consumed as `ATTRIBUTED`
   for a later, unrelated null read inside it.

**Residual scope, disclosed (fix2 review, N1/N2).** Two narrow gaps remain
