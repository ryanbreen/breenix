### M4 — `coreproof_mut_pending_next` (#589): CAUGHT, well inside the 5-minute bar

`docker/qemu/run-coreproof-gate.sh --component H --features
coreproof_mut_pending_next --require-cov coreproof_mut_pending_next --seeds
3 --profile max`. Build 6.00s (warm incremental against leg 2's own cache),
total wall clock `2026-09-01T02:04:45Z`→`02:05:30Z` (**45s**, build
included — comfortably inside the design's ≤5-minute bar).

**3/3 boots caught the mutation**, `pred=PENDING_NEXT_UNRESOLVED` on every
boot, non-vacuous `cov=pending_next` coverage (2, 3, 3 per boot). Example
record: `[COREPROOF:VIOLATION:v1:comp=H:seed=0x00000000077e4620:iter=11616:
site=IncomingHandoffCommit:...:pred=PENDING_NEXT_UNRESOLVED:
detail=9223372036854775808:fired_cpu=18446744073709551615:
fired_iter=18446744073709551615]` — the `u64::MAX` sentinel `fired_cpu`/
`fired_iter` pair (m2's own fold-in) correctly marks this as H's
self-armed, synchronous half of the contract (§1.3), not a peer-armed
catch.

**Bonus corroboration, disclosed rather than silently dropped:** all 3
boots *also* independently caught `pred=OUTGOING_HANDOFF_STRANDED` (with a
real, non-sentinel `fired_cpu`/`fired_iter` pair — the peer-armed half).
This is a genuine, expected side effect of M4's own mutation shape, not a
second bug: `resolve_pending_next_locked`'s real-resolution arm compiled
out means the incoming thread never actually gets dispatched, so after
`STRAND_DWELL_MS` (2,000 ms) `strand_oracle` correctly also sees it as a
Ready thread that never ran — i.e. "stranded" by its own, independent
definition. Reported here as a live example of the design's own
"corroborating signal, not a second predicate" principle (§1.3), observed
under a real mutation rather than only asserted from source reading.
(`evidence/leg3-mutation-m4-pending-next-caught.txt`)

### M(new) — `coreproof_mut_outgoing_fallback_requeue` (#607): honest instrumented miss, independently re-confirmed

`docker/qemu/run-coreproof-gate.sh --component H --features
coreproof_mut_outgoing_fallback_requeue --seeds 3 --profile max` (no
`--require-cov`: this mutation's predicate reads `strand_oracle`'s own
`stranded_count()`/`ready_shape=` directly, per spec §4.2 — there is no

**0/3 violations** — `iters` 91,311 / 115,287 / 60,640, `ARM64 CORE-PROOF
GATE: PASSED`. This independently reproduces the implement slot's own
disclosed miss (issue **#734**) to the exact iteration counts reported
there (39,388/44,920/51,701 in the implement slot's own run — a different
seed draw, same 0/3 result).

**Instrumented, not argued from silence.** Every `[SCHED_STRAND_ORACLE:...]`
sample across all 3 boots (7–201 samples/boot, up to 1,317 threads checked

moved once in any boot. This is the "cov numbers" a `--require-cov` flag

the same marker the fix's own commit message cites (spec §4.2). The miss is
therefore a genuine stimulus-density gap (H's unchanged workload does not
reliably land a live, non-idle outgoing thread specifically at the moment

predicate, the mutation's gating, or the driver's scoring — matching #734's
own disclosed scope exactly.
