### JACKPOT — `coreproof-blank-seams.py` could not parse this branch's own seams (harness bug, fixed)

**What broke.** The first `--bytes` run failed with real `rustc` errors —
not a byte mismatch, a build that would not even compile once blanked:

```
error: expected statement after outer attribute
    --> kernel/src/task/scheduler.rs:2823:9
error: expected statement after outer attribute
    --> kernel/src/task/scheduler.rs:4409:9
error[E0658]: attributes on expressions are experimental
    --> kernel/src/task/scheduler.rs:2915:17
```

The `coreproof_production_clean` host test's own anti-vacuity leg
(`the_scan_reddens_on_a_build_that_carries_the_harness`) failed for a
different, related reason: building `--features boot_tests,coreproof` (no
`coreproof_component_c`) also failed on this branch's tree — not from
blanking, but because a build was attempted before the environment gaps in
§0 were closed. Re-run after §0, it passed cleanly.

**Root cause.** Rung 2 added `#[cfg(...)]` guards directly above several
seam invocations in `kernel/src/task/scheduler.rs`: Component A's nine
pre-existing `proof_point!` calls each needed a `not(coreproof_component_c)`
guard (a Component C build compiles a *different* `SiteId` enum with no
matching variant), and M7's new `proof_cover!(MaskedLockBare)` and the new
`ScheduleEntry` seam are each gated on their own feature — eleven guarded
call sites in total. `scripts/coreproof-blank-seams.py` (unchanged from the
pilot) blanks only the macro-invocation text, preserving line/column count.
That is correct for a *bare* seam call, but for a *guarded* one it leaves the
`#[cfg(...)]` attribute in the source with nothing valid left to attach to:

* where the blanked call was the last statement in its block, the attribute
  has no target at all — a hard parse error (`scheduler.rs:2823`,
  `:4409` — the `#[cfg(feature = "coreproof_mut_masked_lock_bare")]` arm,
  which is a hard parse failure regardless of that feature's truth value,
  because the parser needs *some* statement to skip past and finds only
  whitespace before `}`);
* otherwise the attribute silently reattaches to whatever real statement
  happens to follow, which — when the guard's condition is true in a plain
  production build, as `not(coreproof_component_c)` is — the compiler must
  fully parse as a genuine attributed node, and a `#[cfg(...)]` directly on
  a bare, non-macro expression statement (an assignment, a call) hits
  `E0658` (`stmt_expr_attributes`) on this toolchain (`scheduler.rs:2915`,
  where the attribute reattached to `outcome = UnblockOutcome::Transitioned;`).

This is a harness bug, not a production defect: it only manifests when the
LEG 3 blanking pass runs, never in an ordinary build. It is squarely the
"harness bug, fix and note" branch of this task's own instructions, and
fixing it is required for Leg 1 (byte-identity) to be provable at all on
this branch.

**Fix.** `scripts/coreproof-blank-seams.py` now blanks a coreproof-specific
`#[cfg(...)]` guard *together with* the seam call it immediately precedes —
same rule as the macro text: same length, same line, nothing shifts, and
only guards that themselves mention `coreproof` are touched (an unrelated
attribute that happened to sit next to a seam for some other reason would be
left alone). A bare seam call with no guard is handled exactly as before.
Verified via a dry run against a scratch copy of `kernel/` before spending a
full two-build cycle on it: all three former failure sites blank to valid,
brace-terminated whitespace. Re-run end to end: LEG 3 passes, byte-identical,
20 seams blanked (same count as before the fix — the fix changes *what* gets
blanked around a guarded call, not how many calls there are).

The fix lives at `scripts/coreproof-blank-seams.py` in this same branch —
committed alongside this record, not deferred to a separate PR, per the
project's "any failure you find is your problem, fix forward" policy: this
is exactly the harness this rung's own Leg 1 depends on.
