# Breenix SSH transfer throughput

## Predictions before live measurements

Source baseline is `62d56c37`. The deployed kernel is `51de870b`. The paths below match across those revisions. The reported upload transferred 20,000,000 random bytes in 59 s (0.339 MB/s). The same client and payload reached another LAN host in about 1 s.

| Suspect | Source and predicted effect |
|---|---|
| SSH receive credit and packet size | `libs/libbreenix/src/ssh/channel.rs:14–18, 109–117` advertises a 1 MiB receive window and a 32 KiB maximum channel packet. `transport.rs:290–309` debits each received data message. A 1 MiB window alone would require a roughly three-second credit round trip to explain the observed rate. A credit bottleneck should show the sender exhausting the window and waiting for adjustments. A 32 KiB maximum adds fixed per-packet work. The 256 KiB transport length cap in `packet.rs:17, 236–246` is a separate limit. |
| SSH window adjustments | `userspace/programs/src/bsshd.rs:701–715` and `libs/libbreenix/src/ssh/transport.rs:246–249` return credit on every successful pipe write, including partial writes. `channel.rs:238–252` sends a standalone encrypted control packet each time. `packet.rs:127–136` sends its body and integrity bytes in separate writes outside queued mode. Expect excess reverse packets and cipher calls on uploads. If this is significant, client channel debugging should show frequent small adjustments while credit remains plentiful. |
| Piped relay and packet assembly | `userspace/programs/src/bsshd.rs:666–735` polls for each relay round, receives at most one SSH packet per round, and sends command output in at most 4 KiB chunks using blocking socket writes. The receive path toggles nonblocking mode for each packet (`libs/libbreenix/src/ssh/packet.rs:159–169`) and repeatedly zero-fills missing bytes after short socket reads (`:212–235`). Expect extra syscalls, more small packets on downloads, and extra memory traffic on fragmented uploads. The poll wait watches both pipes and sockets (`kernel/src/syscall/multiplex.rs:62–98, 134–155`), so the 100 ms timeout is a fallback. A 100 ms recurring gap needs wire evidence before it can be attributed to polling. |
| Cipher and integrity work | `libs/libbreenix/src/ssh/kex.rs:31–32, 389–424` negotiates AES-256-GCM or AES-128-CTR with HMAC-SHA-256. `cipher.rs:29–72` allocates and copies per packet in either mode. Both encrypt a counter for each 16 bytes in software (`crypto/aes.rs:229–246, 280–294, 321–335, 377–387`). GCM adds a 128-iteration multiply with bytewise shifts/XORs for each 16 bytes of AAD and ciphertext (`crypto/gcm.rs:31–63, 82–120, 186–209, 248–280`). CTR instead hashes the packet in 64-byte SHA-256 blocks with 64 rounds each, with fixed HMAC setup and finalization per packet (`crypto/hmac.rs:38–109`, `crypto/sha256.rs:62–115, 156–183`). Predict substantially higher GCM cost per byte in both directions if crypto dominates. Holding payload and command constant while changing only the negotiated cipher should expose it. |
| SFTP read and write sizes | `userspace/programs/src/bsshd_sftp/codec.rs:4–6, 76–104` caps a request body at 256 KiB. `bsshd_sftp.rs:93–106, 286–303` allows a read of 262,135 bytes and writes the full supplied data after framing overhead (25 plus the handle length bytes for WRITE). `:36–57` serves pipelined requests serially and flushes each reply. At a 32 KiB client request size these caps are above the client's demand. Expect a measurable difference between SFTP and SSH exec with an identical cipher if filesystem I/O, request processing, or the additional SFTP copies dominate. The 64 KiB kernel pipe also copies bytewise (`kernel/src/ipc/pipe.rs:57, 133–156, 183–203`). |
| TCP receive window and scaling | `kernel/src/net/tcp.rs:200–204, 598–616, 1080–1112` uses a 65,535-byte receive window and only negotiates MSS. Both directions use 16-bit peer window values and about 64 KiB of default buffering (`:836–839, 1029–1035, 1251–1265`). A fully open 65,535-byte window needs a roughly 193 ms RTT to limit throughput to 0.339 MB/s. On a short LAN path, suspect a persistently small or closed advertised window, or frequent loss, if TCP alone is slow. A nearly full receive buffer during SSH alone can also be a consequence of slow consumption. |
| TCP ACK and recovery policy | `kernel/src/net/tcp.rs:2327–2375` immediately ACKs every data segment and FIN, accepts only contiguous payload, and `:2872–2882` can send an extra ACK after the reader frees one MSS or half the buffer. Predict a high ACK count and additional RX/TX work. A dropped segment can cause a train of discarded later segments and duplicate ACKs. `:1420–1454, 1461–1502` times retransmission with a 200 ms minimum (`:218–223`) and does not carry out fast retransmit in the duplicate-ACK branch. If loss limits throughput, expect repeated sequence ranges and long trace gaps. |
| TCP MSS | `kernel/src/net/tcp.rs:188–198, 770–790, 1251–1266` uses 1,460 bytes at Ethernet MTU and falls back to 536 only if the peer omits MSS. SSH control packets and message tails will be smaller. Predict data near MSS during sustained TCP bursts. A capture can distinguish a wrong SYN MSS from fragmented writes or a temporarily restricted peer window. |
| BCM5720 RX ring and interrupt | `kernel/src/drivers/bcm5720/mod.rs:69–81, 514–531, 741–747` posts 63 buffers of 1,536 bytes and uses a 128-slot completion ring. A line-rate burst can consume 63 full frames in under 0.8 ms without refill. The interrupt writes the mailbox, counts the MSI, and raises NetRx (`:116–127`). Coalescing uses 72 hardware ticks or five frames (`:600–608`). The drain copies and reposts one buffer per completion, with a full fence and two index writes (`:815–881`). It clears the status bit, re-arms after observing an empty ring and checks for a concurrent update. A refill or servicing bottleneck should show bursts followed by drops or no ACK progress on both raw TCP and SSH uploads. The 63 usable entries can hold a single full 65,535-byte TCP window of full-size segments. The downstream ACKs themselves use a TX descriptor with immediate coalescing (`:767–799`). |

## Live measurements

Use the same bounded random payload for fresh connections, separately for upload and download. For SSH exec, use a byte-counting sink and read back the upload fixture as a source. Compare the default negotiated cipher with AES-128-CTR/HMAC-SHA-256, keeping the command and payload fixed. Compare SFTP with SSH exec to expose storage and protocol cost. Use an existing safe plain-TCP tool if installed. The stock BusyBox applet list lacks netcat, and the in-tree TCP cases are test fixtures. Capture packet headers at the client to check effective MSS, offered window, ACK cadence, and retransmission when practical. Wait for the toolchain delivery marker before any live access.

Protocol references: [SSH channel flow control](https://www.rfc-editor.org/rfc/rfc4254.html#section-5.2), [SFTP v3](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02), [TCP](https://www.rfc-editor.org/rfc/rfc9293.html), [TCP window scale](https://www.rfc-editor.org/rfc/rfc7323.html#section-2), [GCM](https://csrc.nist.gov/pubs/sp/800/38/d/final).
