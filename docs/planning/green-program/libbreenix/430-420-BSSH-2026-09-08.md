## Protocol and implementation

[RFC 4254 section 5.3](https://www.rfc-editor.org/rfc/rfc4254#section-5.3)
defines EOF as a directional end of data and requires CLOSE acknowledgement
unless CLOSE was already sent. A channel is closed after sending and receiving CLOSE.
[RFC 4254 section 6.10](https://www.rfc-editor.org/rfc/rfc4254#section-6.10)
defines the exit-status channel request, with want-reply false and a uint32 status.

The local process completion sequence is:
CHANNEL_REQUEST(recipient=remote_id, request=exit-status, want_reply=false,
status=child exit code), CHANNEL_EOF(remote_id), CHANNEL_CLOSE(remote_id),
then receive the peer's CLOSE. For peer-initiated CLOSE, reply once; a received
CLOSE after our own CLOSE does not trigger a redundant packet.

[RFC 4252 section 7](https://www.rfc-editor.org/rfc/rfc4252#section-7)
defines the signed publickey request.
[RFC 8332 sections 2 and 3](https://www.rfc-editor.org/rfc/rfc8332#section-3)
retain ssh-rsa as the public-key blob type while using rsa-sha2-256 as the
authentication/signature algorithm.

The authentication signature input is this byte encoding (string lengths are SSH uint32
lengths, not textual separators):

string(session identifier) || byte(50) || string(username) ||
string(ssh-connection) || string(publickey) || boolean(TRUE) ||
string(rsa-sha2-256) || string(public key blob).

The request carries those fields without the session identifier, followed by
string(signature blob). The signature blob is string(rsa-sha2-256) ||
string(RSASSA-PKCS1-v1_5/SHA-256 signature over the input above).
The client first sends the optional unsigned query and checks PK_OK's algorithm
and key against its request.

## Review round V-1 — 2026-09-08

Finding V-1: CLOSE completion did not validate its recipient. The server now
requires a complete uint32 recipient, an exact five-byte CLOSE payload, an
active channel, and recipient equality with that channel's local_id before
setting closed or sending an acknowledgement. A bad recipient returns
ChannelNotFound; a malformed payload returns Protocol. These errors cannot
satisfy finish's closed-state completion condition.

The regression in tests/bssh_auth_close_structure.rs compiles the production
server CLOSE match arm, uint32 decoder, and CLOSE sender against a packet sink.
It checks four truncated payloads, two wrong recipients (including remote_id),
trailing data, and no active channel. It checks the seven invalid payloads both
before and after our CLOSE was sent, asserts unchanged state and no reply, then
checks valid and repeated CLOSE handling and the acknowledgement's remote ID.
This is a host behavioral test of extracted production code; it does not execute
finish's poll loop or encrypted packet I/O.

[Baseline regression](serials/430-420/v1/v1-red.txt) fails because the original
handler accepts a one-byte CLOSE as Disconnected. The initial harness draft
