Round 1 of review fixes (ruling R176). Date 2026-09-05.

byte. The serials and this document land after it, so each of the 5 gate
results below is from that tree.

## 1. The defect and its producer

`kernel/src/time/timer.rs` programs the x86 PIT at `PIT_HZ = 200`
(`timer.rs:13`), so one `TICKS` increment is 5 ms. Before this round,
`get_monotonic_time()` (`timer.rs:114-119` on `9b3dd4af`) returned that tick
counter unmodified, under a doc that read "Milliseconds since the kernel was
initialized (PIT-based, 1ms resolution)" and a body comment that read "At
1000 Hz, ticks == milliseconds". Neither statement is true of an x86 build.
On aarch64 the only writer of `TICKS` is CPU 0's arm of
`arch_impl::aarch64::timer_interrupt::timer_interrupt_handler`, programmed at
`TARGET_TIMER_HZ` = 1000 Hz, so a tick is 1 ms and the identity held there.

The producer is that one function. It is not in a Tier-1 file: the Tier-1 timer
entry is `kernel/src/interrupts/timer.rs`, a different file. 0 Tier-1 files are
touched by this branch.

The repair scales at the producer:

```rust
pub fn get_monotonic_time() -> u64 {
    get_ticks().saturating_mul(MS_PER_TICK)
}
```

`MS_PER_TICK` is `1000 / PIT_HZ` on x86_64 and 1 elsewhere, with a
`const _: () = assert!(1_000 % PIT_HZ as u64 == 0, ...)` so a `PIT_HZ` that
does not divide 1000 refuses to build rather than truncating the factor.

Fixing at the producer rather than at the callers was the choice the issue
poses. Correcting callers individually would have left `sys_get_time()`
(`kernel/src/syscall/handlers.rs:1853`) returning ticks under a millisecond
name.

### 2.6 `test_timer_delay`'s x86 band

Review B3. The x86 arm waits on `get_monotonic_time()` and scores against
`MIN_MS = 5`, `MAX_MS = 20`. Since #767 that clock returns milliseconds in
whole 5 ms steps, so `elapsed` can take 4 values inside that band, the loop
exits at the first reading at or past 10, the re-read lands on 10 or 15, and 1
further tick is a `delay too long on x86_64` FAIL. Per R176 the tolerance is
re-expressed at the granularity of the clock: `MAX_MS + 2 * MS_PER_TICK`, the
nominal 20 ms plus the 2 ticks the reading itself can contribute. 30 ms on x86.

This is a widening, and it is the one criterion this round loosens. It is
confined to the x86 arm; the aarch64 arm keeps the 5..=20 band it was measured
with, and `tests/teardown_structure.rs`'s ratchet still pins
`const MAX_MS: u64 = TARGET_MS * 2;` and the ARM64 starvation-attribution
predicates. Per 2.5 the x86 arm ran 0 times in this round, so the change is
argued from that arithmetic, not from a boot.

## 3. The oracle

`kernel/src/time_test.rs` gained `sample_timer_scale()` /
`report_timer_scale()`. A sample reads the tick counter either side of one
`get_monotonic_time()` read and scores `ms` against
`[ticks_before * MS_PER_TICK, ticks_after * MS_PER_TICK]`. It reports an
invariant (the ratio between two clocks read microseconds apart), not a
wall-clock number. `ticks_nonzero` is the anti-vacuity term: a tick counter
still at 0 satisfies any scale factor, so such a sample is a non-verdict
rather than a pass. The marker:

```
[TIMER_SCALE_ORACLE:x86:ms_per_tick=5:ticks_before=N:ms=M:ticks_after=K:ticks_nonzero=1:in_range=1:PASS]
```

What it discriminates, stated plainly: it is a producer/constant-consistency
check. Both sides read `MS_PER_TICK`, so a PIT programmed at some rate other
than `PIT_HZ`, or a wrong `PIT_HZ`, passes it unchanged. It reddens on 2 mutations: the
producer mutation — which is what made `bebfa6d2` red on main — and a deleted
call site. Scoring `ms` against `get_monotonic_time_ns()` over a short window
would score the stronger claim against an independent clock; that is not what this round shipped, and the
weaker scope is stated here rather than implied (review m4).

Two call sites, because the two gated x86 profiles reach the check from
different places:

* the shipped profile through `test_timer_resolution()` in
  `kernel_main_continue` (`main.rs:2157` at head), which also keeps its
  pre-existing panic on a scale mismatch;
* the `boot_tests` profile through `run_x86_timer_scale_gate()`, dispatched
  first in the x86 `boot_tests` gate list at `main.rs:674` (head), after the
  `interrupts::enable()` at `main.rs:615` that has the tick counter advancing.

The second call site exists because of a measurement, not a guess: at
`bebfa6d2` a 900 s `boot_tests,testing,external_test_bins` boot emitted 0
`PRECONDITION` lines and 0 `TIMER_SCALE_ORACLE` lines while completing its
userspace suite through `[TOMBSTONE_QUIESCE:...]` and the http_test end-of-run
markers. `kernel_main_continue` is preempted before `main.rs:2151`
(`9b3dd4af` numbering) once the test userspace starts, so that profile did not
reach the shipped call site in the boot measured.
`report_timer_scale()` emits at most once per boot, which is what lets both
gates pin the emission count at 1.

`run-x86-boot-tests.sh`'s header for the marker named `test_timer_resolution()`
as the emitting site for the profile that script runs, which is the site this
same measurement says it does not reach (review m2). The header now names
`run_x86_timer_scale_gate()` and says which profile each site serves.
