# #767 — `get_monotonic_time()` returned PIT ticks where its callers read milliseconds

Branch `fix/767-timekeeping-x86`, off `origin/main` at `9b3dd4af`.
Head `2c8481e3`. Date 2026-09-05.

## 1. The defect and its producer

`kernel/src/time/timer.rs` programs the x86 PIT at `PIT_HZ = 200`
(`timer.rs:13`), so one `TICKS` increment is 5 ms. Before this round,
`get_monotonic_time()` (`timer.rs:114-119` on `9b3dd4af`) returned that tick
counter unmodified, under a doc that read "Milliseconds since the kernel was
initialized (PIT-based, 1ms resolution)" and a body comment that read "At
1000 Hz, ticks == milliseconds". Neither statement is true of an x86 build.
On aarch64 the only writer of `TICKS` is CPU 0's arm of
`arch_impl::aarch64::timer_interrupt::timer_interrupt_handler`, programmed at
`TARGET_TIMER_HZ` = 1000 Hz, so a tick is 1 ms and the identity held there.

The producer is that one function. It is not in a Tier-1 file: the Tier-1 timer
entry is `kernel/src/interrupts/timer.rs`, a different file. No Tier-1 file is
touched by this branch.

The repair scales at the producer:

```rust
pub fn get_monotonic_time() -> u64 {
    get_ticks().saturating_mul(MS_PER_TICK)
}
```

`MS_PER_TICK` is `1000 / PIT_HZ` on x86_64 and 1 elsewhere, with a
`const _: () = assert!(1_000 % PIT_HZ as u64 == 0, ...)` so a `PIT_HZ` that
does not divide 1000 refuses to build rather than truncating the factor.

Fixing at the producer rather than at the callers was the choice the issue
poses. Correcting callers individually would have left `sys_get_time()`
(`kernel/src/syscall/handlers.rs:1853`, and the legacy `GET_TIME` arm at
`arch_impl/aarch64/exception.rs:1919`) returning ticks under a millisecond name
across the syscall ABI.

## 3. The oracle

`kernel/src/time_test.rs` gained `sample_timer_scale()` /
`report_timer_scale()`. A sample reads the tick counter either side of one
`get_monotonic_time()` read and scores `ms` against
`[ticks_before * MS_PER_TICK, ticks_after * MS_PER_TICK]`. It reports an
invariant (the ratio between two clocks read microseconds apart), not a
wall-clock number. `ticks_nonzero` is the anti-vacuity term: a tick counter
still at 0 satisfies any scale factor, so such a sample is a non-verdict
rather than a pass. The marker:

```
[TIMER_SCALE_ORACLE:x86:ms_per_tick=5:ticks_before=N:ms=M:ticks_after=K:ticks_nonzero=1:in_range=1:PASS]
```

Two call sites, because the two gated x86 profiles reach the check from
different places:

* the shipped profile through `test_timer_resolution()` in
  `kernel_main_continue` (`main.rs:2151`), which also keeps its pre-existing
  panic on a scale mismatch;
* the `boot_tests` profile through `run_x86_timer_scale_gate()`, dispatched
  first in the x86 `boot_tests` gate list at `main.rs:667`, after the
  `interrupts::enable()` at `main.rs:615` that has the tick counter advancing.

The second call site exists because of a measurement, not a guess: at
`bebfa6d2` a 900 s `boot_tests,testing,external_test_bins` boot emitted 0
`PRECONDITION` lines and 0 `TIMER_SCALE_ORACLE` lines while completing its
userspace suite through `[TOMBSTONE_QUIESCE:...]` and the http_test end-of-run
markers. `kernel_main_continue` is preempted before `main.rs:2151` once the test
userspace starts, so that profile did not reach the shipped call site in the
boot measured.
`report_timer_scale()` emits at most once per boot, which is what lets both
gates pin the emission count at 1.

## 5. The networking gate: 5 of 6 stages, on this branch and on main alike

The census names the ARP pending TTL as the blast-radius item that needs a
networking run. The in-tree gate for it is `docker/qemu/run-dns-test.sh`, which
runs its QEMU inside a Docker container. The beast Incus container has no
`docker` binary (`which docker` exits 1), so the same QEMU command line and the
same six stage checks were run natively (driver `/root/p767-step5.sh`). That
substitution is the one deviation from the script as written.

Branch (`2c8481e3`), image
`sha256 ...` per `/root/p767-step5.log`; stage count 5 of 6:

```
DNS Test: Starting
DNS_TEST: google_resolve SKIP (network unavailable)
DNS_TEST: example_resolve OK      (resolved ip=104.20.23.154)
DNS_TEST: nxdomain OK (error=ServerError(3))
DNS_TEST: empty_hostname OK
DNS_TEST: long_hostname OK
DNS_TEST: txid_varies OK
DNS Test: All tests passed!
```

The missing stage is the script's `DNS_TEST: google_resolve OK` line.
`userspace/programs/src/dns_test.rs:58-66` takes its own SKIP arm when
`is_network_error()` holds, and the script's stage list requires the OK line, so
a SKIP scores 5 of 6 however the rest of the run went.

Baseline at `origin/main` `9b3dd4af`, same driver shape
(`/root/p767-step6a.sh`), image
`sha256 e174221a483bb374b85eceea2228c4eb7e3c998896ed5ef4093ead57a413ab7f`:

```

DNS_TEST: google_resolve SKIP
DNS Test: All tests passed!   (count 1)
```

Same count, same single SKIP, same successful `example.com` resolution and
NXDOMAIN handling. The shortfall is a property of this container's outbound DNS
for that one hostname, measured the same day on both trees, and is not a
regression from this branch. It is disclosed rather than repaired here: the fix
would be to relax the script's stage list to accept the program's SKIP arm, and
loosening a gate's criterion to make a run pass is not something this round
should do on its own judgement.

The ARP path is exercised and green elsewhere in this round: both x86
boot-tests gate runs resolved `example.com` through SLIRP and completed an HTTP
fetch over TCP, which requires ARP resolution of the gateway with the corrected
`ARP_PENDING_TTL_MS` window in force.

## 6. Reds, and what is not claimed

Reds classified: one, the DNS gate's `google_resolve` stage, attributed above by
an `origin/main` baseline run of the same gate on the same host on the same day.
Unattributed reds: 0.

Not claimed:

* No before/after latency, throughput or timing-quality claim. The oracle scores
  a ratio between two clocks; this round does not measure whether the PIT keeps
  good time.
* No claim that any gate red was caused by #767 before this round. The issue
  itself records that it was derived from the code and its constants, not from
  an observed failure, and this round did not find one either.
* No claim about profiles not run here: `interactive`, `disable_x86_prod_init`,
  and the x86 staged registry (`x86_staged_registry`, off by default) were not
  booted. `test_timer_delay`'s new millisecond reading is therefore argued from
  the code and from the two boot-tests runs that dispatch the loopback gates,
  not from a boot that ran that specific registry entry.
* No claim that the `boot_tests` profile reaches `test_timer_resolution()`. The
  measurement in section 3 says it does not, which is why the second call site
  exists.
* The shortened registry/teardown deadlines are argued from 3 of 3 green x86
  boots (2 boot-tests + 1 production), not from a soak. A wait that is now one
  fifth as long could still be marginal under a load these runs did not produce.
* The image hashes in section 4 are of a rebuild at the same commit, not of the
  exact images the gate scripts built during their own runs.
