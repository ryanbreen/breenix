# #796 — `fcntl(F_SETFD)` returned `EAGAIN` from process-manager lock contention

Branch: `fix/796-fcntl-eagain-census`. Base: `origin/main` at `814bc652`.

Observed signature (production-profile aarch64 gate, 1 boot in 10 on main
`bdb5be90`, recorded in #796):

```
[TTY_ORACLE:FAIL:cloexec_exec:fcntl_setfd_failed:EAGAIN]
```

`tty_oracle`'s `cloexec_exec` arm calls `fcntl(slave, F_SETFD, FD_CLOEXEC)` as its
first step. `FileDescriptorTable::set_fd_flags` (`kernel/src/ipc/fd.rs`) has no
`EAGAIN` return path — its only error is `EBADF`. The `EAGAIN` was produced
*before* the `F_SETFD` dispatch arm was reached, by `sys_fcntl`'s process-lookup
preamble turning a failed `try_manager()` try-lock into `SyscallResult::Err(11)`.

### (c) How the R22-era lock discipline classifies the PROCESS_MANAGER lock

Sources read: `kernel/src/process/mod.rs` (`manager()`, `try_manager()`,
`with_process_manager()` and their doc comments), the `#745` PM-window
re-derivation comment at `kernel/src/syscall/handlers.rs:1876-1918`,
`kernel/src/arch_impl/aarch64/context_switch.rs:6955-6971`,
`kernel/src/arch_impl/aarch64/exception.rs:2330-2336`,
`kernel/src/interrupts/context_switch.rs:339-357`, and the
`SCHED_AFTER_PM_VIOLATIONS` lock-order marker at
`kernel/src/task/scheduler.rs:4877` / `:4975`.

1. **Two acquisition modes, deliberately distinguished.**
   `manager()` blocks; on aarch64 it masks `DAIF` *before* taking the mutex and
   releases the mutex *before* restoring `DAIF` (`process/mod.rs:62-72`,
   `:106-127`, `:208-227`). `try_manager()` does not block and does not touch the
   interrupt state: its body is 6 lines (`process/mod.rs:315-321`) and contains 0
   `daif`/`cli`/`sti` operations and 1 `try_lock()`.
   claim-lint:ok: `process/mod.rs:315-321`, quoted in full in the repair section.

2. **Lock order is PM before SCHEDULER, and the two must not nest.**
   `set_next_ttbr0_for_thread` uses `try_manager()` explicitly "to prevent an
   AB-BA deadlock between PROCESS_MANAGER and SCHEDULER locks"
   (`aarch64/context_switch.rs:6962-6964`), and a commit that runs while this CPU
   still owns PM is a *gate-failing* violation counted by
   `SCHED_AFTER_PM_VIOLATIONS` and printed as
   `[EXEC_LOCK_ORDER:VIOLATION:PM_HELD]`.

3. **Is the PM lock taken from IRQ / exception context?** Full grep of the
   interrupt and exception files, which are, named individually because a brace
   list in an earlier draft named a file this tree does not have
   (`kernel/src/arch_impl/aarch64/irq.rs`; the directory's files are `boot`,
   `constants`, `context`, `context_switch`, `cpu`, `cpuinfo`, `elf`,
   `exception_frame`, `exception`, `gic`, `mmu`, `paging`, `percpu_custody`,
   `percpu`, `privilege`, `smp`, `syscall_entry`, `timer_interrupt`, `timer`,
   `trace`, `ttbr0`): `kernel/src/interrupts.rs`,
   `kernel/src/interrupts/context_switch.rs`,
   `kernel/src/arch_impl/aarch64/exception.rs`,
   `kernel/src/arch_impl/aarch64/context_switch.rs`,
   `kernel/src/arch_impl/aarch64/timer_interrupt.rs`,
   `kernel/src/arch_impl/aarch64/timer.rs` and
   `kernel/src/arch_impl/aarch64/gic.rs`.

   | site | context | mode |
   |---|---|---|
   | `interrupts.rs:726` | x86 page-fault CoW (synchronous exception) | `try_manager()` — non-blocking, falls back to the direct-CR3 path |
   | `interrupts.rs:965` | x86 demand-paged user-stack growth, inside `handle_stack_growth` (declared at `:947`), an arm of the page-fault handler — **not** signal delivery, which is `syscall/handler.rs:596` in table (b) | `try_manager()` — non-blocking, `return false` |
   | `interrupts/context_switch.rs:347`, `:792`, `:920`, `:1397`, `:1742` | x86 timer-IRQ dispatch + signal check (**asynchronous IRQ**) | `try_manager()` — non-blocking; on failure it *refuses the dispatch* and re-arms `need_resched` |
   | `aarch64/context_switch.rs:6965`, `:7216` | aarch64 timer-IRQ dispatch (**asynchronous IRQ**) | `try_manager()` — non-blocking, `TtbrResult::PmLockBusy` |
   | `interrupts.rs:1421`, `:1713` | x86 page-fault / GPF **`if from_userspace` kill arms** (synchronous exception from ring 3) | `with_process_manager()` — **blocking** |
   | `aarch64/exception.rs:447` | aarch64 EL0 fault victim resolution (synchronous exception from EL0) | `with_process_manager()` — **blocking** |

   The aarch64 timer and interrupt-controller files (`timer_interrupt.rs`,
   `timer.rs`, `gic.rs`) contain no PM access at all — 0 hits for
   `try_manager`, `with_process_manager` or `process::manager` in the three.

   **Classification.** The grep finds 13 PM accesses in the interrupt and
   exception files and the table lists 13 of 13: 9 of 13 non-blocking
   `try_manager()`, 4 of 13 blocking. The 7 asynchronous-IRQ accesses (5 in x86
   `interrupts/context_switch.rs`, 2 in aarch64 `context_switch.rs`) are all in
   the non-blocking group, and 0 of the 4 blocking accesses sits in asynchronous
   IRQ context: those 4 are **synchronous traps from userspace** — the same
   context class as a syscall. The aarch64 CoW handler states the safety argument
   verbatim at `exception.rs:2331-2335`:
   claim-lint:ok: 13 of 13 sites are printed in the table directly above.

   > "This is safe because CoW faults from EL0 guarantee the current CPU doesn't
   > hold PROCESS_MANAGER — we were in userspace when the fault occurred. Using
   > try_manager() (non-blocking) would fail under SMP contention when another CPU
   > holds the lock during fork/exec, killing the faulting process."
   >
   > claim-lint:ok: verbatim quote of the comment at
   > `kernel/src/arch_impl/aarch64/exception.rs:2331-2335`; the word "guarantee"
   > is that comment's, reproduced rather than asserted afresh here.

   That is exactly the shape of #796, one trap type over.

   Therefore the STOP condition for this task — *the PM lock is taken **blocking**
   from asynchronous IRQ context, i.e. the #789/#791 class* — is **not** met, and
   repair option (a) is available. The 7 non-blocking IRQ-context accesses are
   disclosed here rather than elided: they exist, they are the reason
   `try_manager()` exists, and 7 of 7 have a degrade path (refuse the dispatch
   and re-arm `need_resched`, or skip the signal check) instead of waiting, so 0
   of the 7 can deadlock against a thread that holds the lock blocking.
   claim-lint:ok: the 7 sites and their degrade arms are rows 3 and 4 of the table
   above; the refusal comment is quoted in point 4 below.

3b. **The grep above does not reach the softirq bottom halves, and one of those
   does block on PM.** This is a correction, recorded at the finding's own words:
   an earlier draft of this document and of the `sys_fcntl` comment generalised
   the table above into "no asynchronous interrupt handler on either architecture
   blocks on this lock". That sentence is false, and the files above cannot
   establish it because the bottom halves live outside them.
   `kernel/src/net/udp.rs:146` `deliver_to_socket` takes the **blocking**
   `crate::process::with_process_manager(...)` — `PROCESS_MANAGER.lock()` inside
   `without_interrupts` (`process/mod.rs:296-311`) — and it is reached from
   `net/mod.rs:1170` `ipv4::handle_ipv4` <- `net/mod.rs:1153` `process_packet` <-

   `task::softirqd::do_softirq()` dispatches at IRQ exit on both architectures

   registered on both (`net/mod.rs:786`, `:810`).

   What actually makes the repair safe is narrower than the false sentence, and
   is stated as a property of *this CPU* rather than of the whole tree:

   * **aarch64.** `manager()` executes `msr daifset, #0xf` **before**
     `PROCESS_MANAGER.lock()` and restores DAIF only in `Drop`
     (`process/mod.rs:209-222`, `:106-127`). No IRQ, hence no softirq, is taken
     on this CPU across either the wait or the hold.
   * **x86_64.** `manager()` masks no interrupt state, but `rust_syscall_handler` brackets
     the whole syscall in `preempt_disable`/`preempt_enable`
     (`syscall/handler.rs:192`, `:543`) and `per_cpu::irq_exit()` runs
     `do_softirq()` only when `preempt_count() == 0` (`per_cpu.rs:716-724`). No
     softirq can run on top of an x86 syscall frame at all.
   * **A peer CPU's softirq** that blocks on PM simply waits this window out.
     The dependency is one-directional and cannot close a cycle: 0 of the 2
     operations inside the `sys_fcntl` window (the process lookup and the
     `fd_table` mutation) waits on the network stack.
     claim-lint:ok: the window's 2 operations are
     `find_process_by_thread_mut` at `handlers.rs:3949` and the `match cmd` arms
     at `:3959-4005`.

   **Residual, filed rather than claimed away (#812).** The DAIF argument covers
   `manager()` holders and no others. `try_manager()` (`process/mod.rs:315-321`)
   touches no interrupt state, aarch64 syscalls run with IRQs unmasked
   (`syscall_entry.S:201` `msr daifclr, #0x3` before the handler call), and
   aarch64's `in_interrupt()` is `HARDIRQ|NMI|SOFTIRQ` bits only
   (`arch_impl/aarch64/percpu.rs:464-467`) — it does not consider a plain
   preempt-disable, which is all `rust_syscall_handler_aarch64` raises
   (`syscall_entry.rs:83`). So an aarch64 `try_manager()` holder inside a
   preempt-disabled syscall (`signal.rs:2219`, `:2263`, `:1867`, `:1910`,
   `arch_impl/aarch64/syscall_entry.rs:218`) sits in a window where the NetRx
   softirq can run on that same CPU and block on the lock it already owns.
   claim-lint:ok: #812 carries the 6-step chain and its citations.
   That is pre-existing on `origin/main`, is not created or widened by this branch —
   the branch removes two of those `try_manager()` sites and the `sys_fcntl` one,
   replacing them with the DAIF-masked acquisition — and is filed as #812 with
   the full chain. No reproduction is attached to it.

4. **A PM holder is not preempted away, so a hold is bounded — but the two
   architectures get there by different mechanisms, and they are not the same
   refusal.** This too is a correction: an earlier draft said "2 of 2 dispatch
   entry paths refuse identically" and named the aarch64 `TtbrResult::PmLockBusy`
   arm as the twin of the x86 refusal. They are structurally different, and only
   the x86 one leaves the lock-holding context running.

   * **x86.** `kernel/src/interrupts/context_switch.rs:347` takes `try_manager()`
     **before** the scheduling decision — `scheduler::schedule()` is at `:360` —
     and on failure `return`s, so the interrupted, possibly PM-holding thread
     keeps running. That is exactly what the comment at `:339-346` says:
     *"Refusing here leaves the lock-holding context — the only one that can
     release it — running."* That comment's "both entry paths" are the **two x86
     dispatch entry paths** (kernel-entry and userspace-entry), not an
     x86/aarch64 pair.
   * **aarch64.** `set_next_ttbr0_for_thread`
     (`arch_impl/aarch64/context_switch.rs:6964-6971`) is called from *inside*
     `dispatch_thread_locked`, **after** a thread has been selected, and its
     `TtbrResult::PmLockBusy` remedy (`:4862-4885` kernel arm, `:5102-5119` user
     arm) is `setup_idle_return_locked(...)` + `requeue_thread_after_save(...)` +
     `set_need_resched_inner()`: redirect **this** CPU to idle and requeue the
     **incoming** thread. It leaves no lock-holding context running, because the
     PM holder it collided with is on some other CPU.
   * **What bounds the aarch64 hold instead** is that `manager()` masks DAIF for
     the guard's lifetime (`process/mod.rs:209-222`), so a holder acquired that
     way cannot be preempted at all. That argument covers `manager()` holders
     only: `try_manager()` (`process/mod.rs:315-321`) touches no interrupt state,
     so an aarch64 holder acquired through it is outside this bound — see point
     3b's residual and #812.

   claim-lint:ok: the two remedies are the code at
   `interrupts/context_switch.rs:339-360` and
   `arch_impl/aarch64/context_switch.rs:4862-4885` / `:5102-5119`, read at these
   bytes; the x86 quotation is verbatim from `:344-346`.

5. **Corollary, recorded because it decides the oracle's shape.** On a
   uniprocessor boot two *threads* cannot contend for PM at all: the holder
   cannot be preempted (point 4), so the second thread does not run. Real
   thread-vs-thread PM contention — and therefore #796 itself — needs a
   dispatching peer CPU. The two x86 gates this round runs
   (`docker/qemu/run-x86-boot-tests.sh:130`,
   `docker/qemu/run-x86-prod-profile-boot-test.sh`) boot `-smp 1`; the aarch64
   strict and production gates boot `-smp 4`.
   claim-lint:ok: the `-smp` values are the QEMU argv lines in those 2 of 2
   scripts, quoted in the oracle section below.

## STEP 2 — repair, per site

Rows 1-3 of census table (a) take the blocking `crate::process::manager()`.
Rows 4-6 are untouched.

### Row 1 — `sys_fcntl` (`kernel/src/syscall/handlers.rs`)

`try_manager()` + `Err(11)` becomes `crate::process::manager()`. The argument,
re-derived at these bytes and recorded in the comment that now sits at the
acquisition:

1. **The caller is preemptible thread context, entered from userspace.**
   `sys_fcntl` is reachable only through the syscall dispatcher, i.e. on a trap
   taken at EL0/ring 3. `aarch64/exception.rs:2331` takes the blocking
   `manager()` from the same context class for a CoW abort and states the same
   justification: a CPU that was running userspace when it trapped does not
   already own PROCESS_MANAGER, so this acquisition cannot self-deadlock.
2. **No bottom half can run on THIS CPU across the wait or the hold** (census
   (c) point 3b). Note what this does *not* say: an asynchronous bottom half
   **can** block on this lock — `net/udp.rs`'s `deliver_to_socket`, on the NetRx
   softirq, does. What holds is per-CPU: aarch64's `manager()` masks DAIF before
   taking the mutex, and x86 runs the syscall preempt-disabled while
   `per_cpu::irq_exit()` dispatches softirqs only at `preempt_count() == 0`. A
   peer CPU's softirq waiting on PM waits this window out, and 0 of the 2
   operations in the window wait on it.
   claim-lint:ok: the 2 operations are named in census (c) point 3b.
3. **The wait is bounded by the holder's window** (census (c) point 4), by DAIF
   masking on aarch64 and by the x86 dispatch refusal on x86 — two different
   mechanisms, not one shared refusal.
4. **This is already the discipline in this file.** `sys_dup` and `sys_dup2`,
   the two functions directly above `sys_fcntl`, mutate the same
   `process.fd_table` from the same context under a blocking
   `crate::process::manager()`. `sys_fcntl` was the outlier, not the precedent.
5. **No lock-order exposure.** The window takes no scheduler lock and publishes
   no thread, so `SCHED_AFTER_PM_VIOLATIONS` / `[EXEC_LOCK_ORDER:VIOLATION:PM_HELD]`
   cannot fire from it. (An earlier draft also said the window "does no I/O".
   That was wrong and is withdrawn: see the cost paragraph below.)
6. **What the repair costs, named rather than left implicit.** The change is not
   free, and 0 of the 3 costs below were disclosed before this round:
   claim-lint:ok: R157 finding F4; the 3 costs are the 3 bullets that follow.
   * On aarch64 both sites move from an interrupts-enabled `try_manager()` to a
     **fully DAIF-masked window covering the wait *and* the critical section**,
     because `manager()` masks before the mutex and unmasks in `Drop`
     (`process/mod.rs:209-222`, `:106-127`). Inside that masked window
     `sys_fcntl` runs a `log::debug!` per dispatch arm
     (`handlers.rs:3926/3933/3940/3947/3954/3961`) and
     `sys_sigsuspend_with_frame_aarch64` runs `log::info!` at `signal.rs:2184`
     and `:2194`. Those reach COM2: `kernel/src/logger.rs:977-978` enables every
     level below `Trace` and `kernel/Cargo.toml` sets no `release_max_level_*`
     feature.
   * The wait's bound is the **longest PM hold in the tree**, not a short one:
     `ProcessManager::exec_process_with_argv` (`process/manager.rs:3872`) runs
     `load_elf_into_page_table` at `:3976` with PM held, inside
     `arch_without_interrupts` (caller at `handlers.rs:2572-2593`).
   * This is not novel. The cited precedent, `sys_dup`/`sys_dup2` at
     `handlers.rs:3774`/`:3821`, already pays exactly the same cost on the same
     lock from the same context. What is new is that the cost is now written
     down instead of being implied by a "bounded" adjective.

Option (b) — bounded retry with a yield — was not used here, because the
conditions for (a) are met and (b) would leave the wrong errno reachable at the
end of the bound. There is no correct errno to return: POSIX has no "the kernel
was busy" answer for `F_SETFD`.

### Rows 2 and 3 — `sys_sigsuspend`, both architecture bodies (`kernel/src/syscall/signal.rs`)

Same change, same argument. Two details specific to these sites:

* The guard scope does not change. Both bodies already confined the PM window to
  a `{ }` block that closes before
  `with_scheduler(block_current_for_signal_with_context(...))`, so the repair
  does not create a PM-held scheduler acquisition.
* The same cost applies, and is disclosed at each site's comment: on aarch64 the
  window is DAIF-masked across the wait and the block, including the `log::info!`
  calls at `signal.rs:2184` and `:2194`; on x86 the window is preempt-disabled
  but IRQ-enabled, and its `log::info!` calls sit inside it too. Both waits are
  bounded by exec's ELF load in the worst case.
* The inner "process manager not initialized" and "process not found" arms keep
  returning `ESRCH`. Those are about the manager being absent or the caller
  having no process row, not about lock contention, and they are out of this
  issue's scope.

### Rows 4-6 — `graphics.rs`, deliberately unchanged

`sys_fbinfo`, `sys_fbdraw` and `sys_fbmmap` are Breenix-private syscalls with no
POSIX name, so there is no errno list for `ErrorCode::Busy` to violate. Each
already spins (4096 or 65536 iterations) before giving up, and the comment at
`graphics.rs:2355` records why the fallback exists: a blocking acquisition there
can deadlock against the render thread. Changing them would be a regression.

## STEP 3 — the oracle

`fcntl_pm_contention_oracle`, a `boot_tests`-profile in-kernel oracle
(`kernel/src/test_framework/registry.rs`), registered in `SYSCALL_TESTS` at
`TestStage::ProcessContext`.

**What it does.** A kthread pinned to a live peer CPU takes PROCESS_MANAGER and
holds it for an 8000 us window measured on `CNTVCT_EL0`, with interrupts masked
for the length of the hold. The driving test thread waits for the window to
open, reads the lock's state independently, then issues 64
`fcntl(fd, F_SETFD, FD_CLOEXEC)` calls through the production `sys_fcntl` and
counts how many return `EAGAIN`.

**Marker.**

```
[FCNTL_PM_CONTENTION_ORACLE:aarch64:attempts=N:armed=1:holder_cpu=C:pm_busy_probe=1:calls=64:eagain=0:first_errno=9:first_wait_us=W:hold_done=1:joined=1:PASS]
```

**Anti-vacuity.** Two fields keep a green verdict out of reach without real
contention:

* `pm_busy_probe` is an independent try-lock read taken immediately before the
  measured call, so "contended" is a reading rather than an assumption about the
  peer's timing;
* `first_wait_us` is the measured duration of the first call, floored at 1000 us
  of the 8000 us window, so a call that sailed through an uncontended lock scores
  FAIL.

**Where that floor is enforced, after R157/F3.** In the first round it was
enforced in exactly one place — the in-kernel conjunct
`first_wait_us >= FCNTL_PM_MIN_WAIT_US` in the oracle's own `passed` predicate
(`registry.rs:4419`, constant at `:4184`) — while the gate pattern pinned
`first_wait_us=[0-9]+`, which accepts `first_wait_us=0`. Deleting that one
conjunct therefore left the gate and 30 of the 30 structure suites then in the
tree green on an oracle that no longer measured a wait; 0 of those 30 mentioned

* **#796 is not shown unable to recur through some other path.** What the
