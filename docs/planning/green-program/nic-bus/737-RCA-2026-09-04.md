## Q2 — The producing defect, in causal order

<!-- claim-lint:ok: 1 of 1 rep-prefixed string op on the path (grep -cE 'rep

The static RCA named one open premise and could not close it: *"that a `rep
movs`/`rep stos` actually executed between the timer gate and `Location::file`
on this path"*. **This slot closed it.** The instruction exists, it is reached on
every `log::trace!` from the ISR, and its destination range covers the poisoned
slot exactly.

<!-- claim-lint:ok: 763325 of 763325 lines from one objdump run in this slot;

All addresses below are ELF-relative, from the pinned `40e744a5…` binary
(`objdump -d -C` over it produces 763325 lines, re-run here and matching the
static RCA's count).


**1. The timer IDT entry point does not clear DF.**
`kernel/src/interrupts/timer_entry.asm` — 372 source lines, `grep -c cld` → `0`.
In the emitted image, the whole timer entry region `0x36f491`–`0x36f60e`
(171 instructions, 8 labels) contains 0 `cld` and 0 `std`. It is the only
IDT-reachable entry point in the image without one:

```
$ grep -cE '^ +[0-9a-f]+:\tfc +\tcld' <full objdump>   -> 15
   0x2a62a4 debug_handler        0x2a6ed5 double_fault_handler
   0x2a8661 keyboard_handler     0x2a89f1 serial_handler
   0x2a8b61 irq10_handler        0x2a8c81 irq11_handler
   0x2a8e84 divide_by_zero       0x2a9004 invalid_opcode
   0x2aa674 page_fault_handler   0x2ae244 generic_handler
   0x2ae605 stack_segment_fault  0x2af214 general_protection_fault
   0x36ed51 memmove (its own restore)
   0x36f307 syscall_entry        0x36f63d breakpoint_entry
```

12 of those are the `extern "x86-interrupt"` handlers
(`grep -rc 'extern "x86-interrupt"' kernel/src/interrupts.rs` → `12`), which get
a `cld` from LLVM's `x86_intrcc` prologue. That LLVM emits it unprompted is the
cleanest available confirmation that **the hardware does not clear DF on
interrupt entry** — the interrupt gate clears IF, not DF. The other two are the
hand-written entries that carry an explicit one
(`kernel/src/syscall/entry.asm:50`, `kernel/src/interrupts/breakpoint_entry.asm:60`).
`timer_entry.asm` is the third hand-written entry and the only one that omits it
— and it is the highest-frequency gate in the system at 1000 Hz.

**2. A ring-3 thread can legitimately hold DF=1.**
Userspace contexts are created with `rflags = 0x202` (DF clear), so DF does not
arrive from initialisation. It arrives from `memmove`'s backward arm. In the
faulting process's own binary:

```
$ grep -cE '^ +[0-9a-f]+:\tfd +\tstd' <http_test>  -> 1   (at 0x4001e387)
$ grep -cE '^ +[0-9a-f]+:\tfc +\tcld' <http_test>  -> 1
```

One `std…cld` window, a few instructions wide.

**3. The timer preempted thread 21 inside that window.**
The specimen's fatal frame carries `RFLAGS: 0x10482` = `RF | DF | SF | 0x2`:
DF **set**, IF **clear**. The kernel contains exactly 1 instruction that sets DF
(`0x36ed30`, inside `memmove`), and the faulting RIP is not in `memmove`; IF=0
rules out a nested interrupt setting it inside this frame. The `<S>` marker
(`kernel/src/interrupts/context_switch.rs:446`, emitted only when
`from_userspace`) is the last thing on the serial before the fault block, with
no following `[SW]`. So the frame is the timer ISR entered from ring 3, and DF
came across the gate with it.

A census of the whole boot supports this rather than assuming it — of the 4
page faults that printed a diagnostic block, **the one with DF set is the fatal
one**:

```
$ grep -o 'DIAG:PAGEFAULT\] RFLAGS: 0x[0-9a-f]*' serial_user.log.txt | sort | uniq -c
      2 ... 0x10202     (ring 3, DF clear — ordinary demand paging)
      1 ... 0x10246     (ring 3, DF clear — ordinary demand paging)
      1 ... 0x10482     (ring 0, DF SET  — the panic)
```

**4. The ISR reaches a `log::trace!` on its success path.**
`context_switch.rs:446` `<S>` → `save_current_thread_context_with_guard`
(`0x32e7c0`) → `save_userspace_context` (`0x27fae0`) →
`log::trace!`. There are **2** silent-by-construction `log::trace!` sites on this
path, not the 1 the static RCA identified — it censused only macros lexically
inside `context_switch.rs` and missed the callee's own:

- `kernel/src/task/process_context.rs:267` — inside `save_userspace_context`,
  reached **first**; present at `8b02ea29` as well as at HEAD.
- `kernel/src/interrupts/context_switch.rs:642` (HEAD) / `:456` (`8b02ea29`).

**7. With DF=1 that copy runs downward, straight across the spill slot.**
`rep movsq` decrements `rdi` per iteration when DF is set. With
`rdi = rsp+0x90` and 16 iterations it writes:

```
0x90, 0x88, 0x80, 0x78, 0x70, 0x68, 0x60, 0x58, 0x50, 0x48, 0x40, 0x38, 0x30, 0x28, 0x20, 0x18
                                                          ^^^^
                                            the &Location spill, 11th write
```

Range covered: `[rsp+0x18, rsp+0x90]`. The poisoned slot `[rsp+0x40]` sits
inside it, at iteration index 10. The source runs downward from
`RecordBuilder::new`'s own `rsp+0x10`, i.e. it reads *below* its own stack
pointer — stale bytes from already-returned frames. The value that landed in the
slot in this specimen was `8`, which is unremarkable stale-stack content and
needs no "`&(*null).field_at_offset_8`" story.

That is an internal-consistency check the specimen passes: the fault lands
exactly where the chain predicts and nowhere earlier.

### Statement of the defect

<!-- claim-lint:ok: "every rep-prefixed string operation runs backwards" is the
     definition of DF=1 on x86-64, not a survey claim; the survey figures beside
     it are 226 of 226 rep movs/stos sites in this image (223 + 3, grep -c here)
     and 0 of 171 timer-entry instructions carrying a cld. -->
> `kernel/src/interrupts/timer_entry.asm` has no `cld`. An x86-64 interrupt gate
> preserves DF, so a userspace thread preempted inside its own `memmove`
> backward arm (`std … cld`) enters the timer ISR with DF=1. Every `rep`-prefixed
> string operation the ISR then executes runs backwards. On the from-userspace
> preempt path the ISR reaches `log::trace!`, whose `log_impl` calls
> `RecordBuilder::new`; that function returns its 128-byte struct with a
> `rep movsq` into an out-pointer `0x50` bytes above `log_impl`'s spill of the
> `&'static Location`. Backwards, that copy overwrites the spill with stale
> below-stack bytes; `log_impl` reloads it into `%rdi` and `Location::file`
> dereferences it, faulting at whatever value landed there — `0x8` in the
> archived specimen.

The blast radius is not limited to this call site. With DF set, the image has
223 `rep movs` and 3 `rep stos` sites reachable in kernel context. The
`Location::file` fault is the loud one; it is not necessarily the only outcome.

### The exact next experiment

The chain above is deterministic given DF=1, which turns #737 from a lottery
into a one-boot test. A userspace program that executes `std` and then spins
CPU-bound for a few timer ticks (no `fork`, no syscall needed) should fault at
`Location::file` on the first from-userspace preemption that lands in its
window. Expected before a fix: red within a handful of ticks, at this exact RIP.
Expected after: clean completion, plus a check that the program's own DF is
still set when it resumes — which also pins the property that `cld` in the
handler does not corrupt userspace DF (IRETQ restores RFLAGS from the frame, and
`save_userspace_context` / `restore_userspace_context` round-trip
`interrupt_frame.cpu_flags` through `thread.context.rflags`).

If that oracle does **not** go red on current bytes, M1 is falsified as the
producer of this specimen and M2 returns.

## Q3 — What a fix touches, and what it must not

### It touches a Tier-1 file, and therefore needs approval first

| file | tier | why it is in scope |
|---|---|---|
| `kernel/src/interrupts/timer_entry.asm` | **Tier 1 — "Absolutely Forbidden (ask before ANY change)"** | the defect; needs one `cld` |

Per `CLAUDE.md`, Tier-1 files require explicit user approval before **any**
change. **This fix cannot be written without asking first.** That is the single
most important thing about it, and it is why this record stops at the diagnosis.

The change itself is exactly the shape Tier 1 permits once approved: one
instruction, one byte, no locks, no allocation, no formatting, no logging, and
no measurable time cost on a path budgeted at <1000 cycles. It brings the file
in line with its own two siblings (`syscall/entry.asm:50`,
`breakpoint_entry.asm:60`) and with the 12 LLVM-generated handler prologues.
Placement: before any `rep`-capable code and before the call into Rust; it needs
no undo, because IRETQ restores RFLAGS from the interrupt frame.

### It must not touch

### It must not be "fixed" by deleting the log calls

Removing the two `log::trace!` sites (`process_context.rs:267`,
`context_switch.rs:642`) would make this specimen stop reproducing while leaving
DF=1 leaking into the ISR, where 226 other `rep movs`/`rep stos` sites remain.
That is a false fix: it deletes the symptom's messenger and keeps the defect.
Removing them on **cost** grounds is a legitimate separate item — each builds a
full `Record`, including `Location::file`, inside masked-IRQ context only to
discard it, the same class of waste #775 addressed and a site PR #787 did not
touch — but it must not be booked as closing #737.

Touching `context_switch.rs` / `process_context.rs` for that separate item is
Tier-2 (high scrutiny), which the operator's 2026-08-12 ruling permits when the
approach needs it.

## Q4 — What the default x86 gate does not cover here, and the smallest honest re-wiring

### The gaps

1. **The gate has no statistical power against this defect at all.**
   `docker/qemu/run-x86-gate.sh` runs a small number of boots; detecting a
   1-in-300 event with 95% confidence needs ~897. A gate run is not a sample.
2. **A #737 red arrives unattributed.** The panic exits QEMU, the
   `USERSPACE TEST COMPLETE` marker is absent, and `scripts/x86-gate-verdict.sh`
   fails with `marker '...' not found`. It fails safe — and under R52 an
   unattributed failure is itself gate-failing — but it carries no signature, so
   a #737 red is indistinguishable from any other early death.

3. **Nothing anywhere asserts DF=0 on kernel entry.** There is no runtime check

4. **The gate never deliberately enters the kernel with DF set.** The

5. **`poll_tcp_oracle` is not in the x86 roster, and its tracking issue is

### The smallest honest re-wiring

Two pieces. Neither claims to close #737; together they make the defect
impossible to reintroduce silently and make the fault deterministic.

<!-- claim-lint:ok: the census this ratchet would anchor on is the 15-site cld
     list and the 3 hand-written asm entries in kernel/src (find -name '*.asm'
     returns 3, of which 2 carry a cld) plus the 12 extern "x86-interrupt"
     handlers (grep -rc in kernel/src/interrupts.rs -> 12) -- all counted here.
     The two named mutations are the anti-vacuity legs; neither has been run,
     because this slot wrote no test. -->
**(a) A build-time entry-point ratchet — 0 boots, no flakiness.**
A structure test in the spirit of the existing `tests/*_structure.rs` ratchets:
over the emitted kernel image, enumerate every IDT-reachable entry point and
assert each one clears DF before reaching any `rep`-prefixed string operation or
any call into Rust. Census-anchored, per the program's standing lesson: derive
the entry-point set from the IDT installation sites in
`kernel/src/interrupts.rs`, never from a literal name list, so a new gate added
later is covered by construction rather than forgotten. Anti-vacuity: deleting
the `cld` from `timer_entry.asm` must redden it, and deleting it from
`syscall/entry.asm` must redden it independently.


This is the piece that carries the weight. It is deterministic, costs no boot
time, and would have caught the defect at any point in its life.

**(b) A fork-free DF oracle on the x86 roster — one boot, two-sided.**
The `df_preempt_oracle` from §Q2: `std`, spin CPU-bound across several timer
ticks, `cld`, verify its own DF round-tripped, exit 0. Red on current bytes,
green after the fix, and it pins the RFLAGS-preservation property the fix must
not break.

Its blast radius on the gate is genuinely zero, which is what makes it the
*smallest* honest addition rather than a repeat of the #697 saga: the census pin
is derived at `docker/qemu/run-x86-boot-tests.sh:227` by counting `fork()` call
sites per roster program, and the script's own comment (line 183) records that
"one that never forks contributes 0 and changes nothing here" — with 13 of 15
current roster programs already fork-free. A fork-free oracle shifts
`PRODUCTION_REAPED_ROWS` by 0. It does move `EXPECTED_EXITS` by 1, which is a
declared constant in the gate script and is meant to move when the roster does.

Not proposed: re-wiring `poll_tcp_oracle`. It is unrelated to this path, and it
is the thing that was fork-heavy and census-shifting. It should be reopened on
its own merits (#697 closed on partial scope), not folded in here.

## Findings that do not fit, or that correct earlier work

1. **The battery ran `8b02ea29`, not `b257e69e`** (§Q1). Its "third independent
   zero-catch run" framing does not hold, and the post-#787 rate is unmeasured.
2. **The two passes collided in `/root/breenix-737`** because both briefs named
   that path. The static RCA's build is what the battery booted. The lesson is a
   harness one: parallel slots on a shared host need distinct clone directories,
   and a boot battery should record the hash of the image it boots, not the
   commit it believes it checked out.
3. **The battery's breakpoint target was correct but late.** `rust_begin_unwind`
   is genuinely reached (`interrupts.rs:1498` panics), so a catch would have
   fired. But it stops *after* the page-fault handler has run on the IST stack —
   `info registers` there describes the panic path, not the faulting frame. The
   harness's dump block does not walk back to the saved interrupt frame, so even
   a catch would not have delivered the DF reading or the ring-3 RIP that the
   static RCA's discriminators call for. A conditional breakpoint on
   `Location::file` with `$rdi < 0x10000`, as the static RCA proposed, remains
   the better trigger.
4. **The static RCA's silent-caller census was 1 short.** It counted log macros
   lexically inside `context_switch.rs` and missed
   `process_context.rs:267`, inside the callee `save_userspace_context`, which is
   reached first. Two silent `log::trace!` sites are on the path, not one.
5. **The "40 lines earlier `UNHANDLED INTERRUPT`" lead is dead**, and this slot
   re-measured it: `grep -n` puts `UNHANDLED INTERRUPT` at line 494 and
   `Accessed Address` at 2507 of a 2531-line log — 2013 lines apart, in a
   different boot phase. The static RCA had already corrected this; recording it
   again because three earlier sources repeated the wrong figure.
<!-- claim-lint:ok: 4 of 4 [DIAG:PAGEFAULT] RFLAGS values in
     serials/702-rca/anomaly_exited_114/serial_user.log.txt, counted here
     (2x 0x10202, 1x 0x10246, 1x 0x10482); n=4 is a small sample and is
     offered as a correlation within one boot, not as a rate. -->
6. **The specimen's `[DIAG:PAGEFAULT]` blocks are richer than any earlier
   write-up used**, and the RFLAGS census across all 4 of them (§Q2 step 3) is
   the observation that makes DF more than a curiosity: 3 benign faults with DF
   clear, 1 fatal fault with DF set.

7. **`SS: 0x0` in the fatal block is not an anomaly** — the page-fault gate uses
   an IST and a long-mode stack switch loads a null SS. It should stop being
   carried as a lead.
8. **Two accounts of the specimen's provenance conflict.** Issue #737's body says
   it was boot 114 of 150 in the #702 catch loop at `8b02ea29` (rate 1/150); the
   battery report says it came from the 26-boot triage sweep instead. The
   directory name `anomaly_exited_114` favours the issue body. Left unresolved
   here; it changes the denominator anyone quotes for the historical rate.
<!-- claim-lint:ok: 2 of 2 source facts read here (logger.rs:1104
     set_max_level(Trace); logger.rs:980-990, the Trace early-return, which
     touches 3 fields before returning), corroborated by 0 [TRACE] and 1252
     [DEBUG] lines in the specimen. -->
9. **`log::trace!` is not free in this kernel.** `set_max_level(Trace)` plus a
   sink that drops TRACE inside `Log::log` means every `trace!` builds a full
   `Record` — `Location::file` included — inside masked-IRQ context and throws it
   away. `logger.rs:984` even calls `record.target()`, `record.args()` and
   `format_args!` on the record it is about to discard.

10. **Not chased:** `net/mod.rs`'s `LOOPBACK_QUEUE` is a
    `Mutex<Vec<LoopbackPacket>>`, and `Vec` drain/remove reaches `memmove`'s
    backward arm — a kernel-origin `std` window. It cannot be *this* specimen
    (the `<S>` marker requires `from_userspace`), but with no `cld` on the timer
    gate it is a second way for a DF=1 ISR frame to exist, on a different
    thread's stack.
