B1-B3 proof, live leg: gdb_chat.py's resync_symbols() correcting a REAL
mismatch on a real boot, on beast (breenix-x86 container), at a6679e7c.

The environment (this beast container, this host/QEMU/OVMF combination) has
been observed to pick 0x10000000000 on every boot sampled by the fix round's
own live-two-boot-test evidence -- the mismatch case never occurs naturally
here. Forced it: temporarily set GDBChat.KERNEL_BASE_X86 (the class-level
initial guess) to 0x8000000000 -- the OTHER value #739's own README cites as
historically observed elsewhere -- so the guess is deliberately wrong for
whatever this real boot actually picks, then drove a real GDB session
end-to-end through the documented interface (no gdb_session.sh fifo -- driven
directly via GDBChat, matching gdb_chat.py's own documented direct-invocation
usage, to sidestep unrelated shared-host session flakiness).

Full script: instantiate GDBChat(arch="x86_64"), start(), wrap _send_raw to
log every raw GDB command issued, run `continue` in a background thread,
poll real serial output for the bootloader's own `virtual_address_offset:`
line, SIGINT the real gdb_pid, call resync_symbols() for real (no stubbing),
and assert on the ACTUAL commands sent.
