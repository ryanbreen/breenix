# #702 RCA hunt — result: zero-specimen run (rate observation, not padded)

## Bottom line

150 boots of the exact profile #702 was measured on (beast `breenix-x86`,
`main`@`8b02ea29`, KVM, `-cpu host`, `testing,external_test_bins`,
`BREENIX_NET_MODE=none`), each with QEMU's gdbserver live (`-s`, no `-S`),
watching for the #702 signature (serial output stalls with the last kernel
line being exactly `E1000 network device found` and none of the later boot
markers ever appearing) produced **zero matches of that signature**. No GDB
attach was ever triggered — there was nothing to attach to.

This is reported as a rate observation, not a negative proof the bug doesn't
exist. Combined with the issue's own filing data (`main`@`782ab96f`: 0/26 in
the original triage-sweep battery), the honest running total on `main` across
both samples is **0/176** for this exact signature. At the issue's own
branch-measured rate (1/26), the probability of seeing zero hits in 150
independent trials is ~0.3%; at the more conservative end of the issue's
stated range (1/52) it's ~5.6%. Neither rules the bug out, but both make "the
same ~1-in-26-to-52 rate reproduces readily on plain `main`" look less likely
than "the one observed hit was rarer on `main`, or sensitive to something this
run's environment/timing didn't reproduce (host load, the specific
triage-sweep battery's concurrency, or something specific to the branch under
test in that sweep)."

## What was run

- Budget: up to 150 boots or ~5 hours, whichever first. **150 boots hit
  first**, at 8304s (~2h18m) elapsed — well under the 5-hour cap.
- Harness: `/root/p702-rca/` on beast (fresh clone of the repo at
  `/root/p702-rca/repo`, `main`@`8b02ea29`, never the shared `/root/breenix`
  gate checkout). `docker/qemu/run-x86-gate.sh`'s full-mode QEMU invocation
  was reproduced boot-for-boot: `BREENIX_QEMU_ACCEL=kvm`,
  `BREENIX_QEMU_CPU=host`, the same `qemu-uefi` release binary
  (`cargo build --release --features testing,external_test_bins --bin
  qemu-uefi`), the same repacked `test_binaries.img`/`ext2.img`, and
  `BREENIX_NET_MODE=none`. The only addition was `-s` appended via
  `qemu-uefi`'s own "forward extra CLI args" path (no `-S`, so the guest runs
  free — GDB only halts it on attach, not at boot).
- Detection: polled `serial_kernel.log` size every 1s. A boot was declared
  "stalled" after 12s with no growth (empirically safe: a clean full-profile
  boot's own worst observed quiet gap was 3s, boot-to-completion ~57s at
  idle). On a stall, the last non-blank kernel line was compared verbatim
  against `[ INFO] kernel::drivers::pci: E1000 network device found`; only an
  exact match would have counted as a #702 specimen and triggered the GDB
  attach step. A 100s per-boot cap and the `USERSPACE TEST COMPLETE` marker
  handled the clean-boot and other-anomaly cases.
- Attach mechanics were built and validated (not exercised for real, since no
  match occurred): `target remote localhost:1234`, symbols loaded via
  `add-symbol-file` at the kernel's PIE runtime address, `info registers`,
  `backtrace`, disassembly around `$pc`, a stack dump, and a 12x `stepi` trace
  with `info symbol $pc` at each step, repeated across three attach/detach
  rounds to see whether a caught specimen was spinning, wedged, or
  livelocking. See "Harness correctness notes" below for a real discovery
  made while validating this against healthy boots.

## Results by boot

- 150/150 boots completed the run-x86-gate.sh QEMU invocation.
- 133 clean (reached `USERSPACE TEST COMPLETE`).
- 15 failed immediately at startup with `Failed to get "write" lock` on
  `breenix-uefi.img` — **this was the harness's own fault, not kernel
  behavior**: an earlier smoke-test boot (started manually while validating
  the GDB attach mechanics) was killed by PID (`kill -9 $wrapper_pid`) without
  also killing its `qemu-system-x86_64` child, which stayed alive holding the
  disk-image write lock until I found and killed it directly. Those 15 boots
  were removed from `specimens/` before this report (they were never real
  kernel data) and the main loop recovered cleanly on boot 16 once the
  orphan was killed. Disclosed here rather than silently subtracted from the
  budget.
- 1 stalled but **not** the #702 signature (boot 47, preserved as
  `anomaly_offsig_047/`): stopped mid-`sys_execv` while
  `ProcessPageTable::new()` was copying the 256 upper-half kernel PML4
  entries for the new address space. This is a different code path
  entirely (process/exec page-table setup, not PCI enumeration) and is not
  claimed as related to #702 — noted only because the harness caught it and
  the instructions call for preserving everything.
- 1 crashed and exited on its own (boot 114, preserved as
  `anomaly_exited_114/`): `KERNEL PANIC: panicked at kernel/src/interrupts.rs:1493:9:
  Kernel page fault at 0x8 (error: PageFaultErrorCode(0x0))`. Also unrelated
  to #702 (a near-null-pointer kernel page fault, not a silent PCI-enumeration
  hang) — caught by the "wrapper process exited before completion marker"
  branch of the harness, preserved for completeness.
- 0 matches of the exact #702 signature.

## Mechanism

**Not named.** No specimen of the #702 signature was caught, so there is no
RIP, backtrace, or register state to report for the actual bug. What this run
does rule out, at the stated confidence level: it is not a mechanism that
fires anywhere near as reliably as 1-in-26 on a plain `main` boot of this
exact profile under KVM on this beast host in this harness's environment. It
remains fully consistent with the bug being real but rarer, or with something
about the original triage-sweep battery (concurrent boots, different host
load, the specific branch/interleaving under test that run) making it more
likely to surface there than in a dedicated, sequential 150-boot loop.

## Harness correctness notes (worth keeping for the next attempt)

- **The documented GDB symbol-offset constant is wrong/incomplete.**
  `breenix-gdb-chat/scripts/gdb_chat.py` (and CLAUDE.md's example) use a fixed
  `KERNEL_BASE_X86 = 0x10000000000` (1 TiB) for the PIE kernel's runtime
  `add-symbol-file` offset. Empirically, across two otherwise-identical smoke
  boots of the same binary, the bootloader printed **two different**
  `virtual_address_offset` values (`0x8000000000` and `0x10000000000`) on
  `serial_user.log`. Using the stale fixed constant produces a GDB session
  where `info registers`/disassembly/`stepi` all still work (they just read
  live memory) but `info symbol $pc` and `backtrace` silently fail
  (`No symbol matches $pc`, `?? ()` frames) with no error loud enough to catch
  by casual use — a debugging session could easily "work" while producing
  meaningless symbol names. This harness fixed it by reading each boot's own
  `virtual_address_offset:` line from its `serial_user.log` and computing the
  `add-symbol-file` offsets fresh per boot; that offset-corrected pipeline was
  validated live against a healthy boot (`x86_64::instructions::interrupts::enable_and_hlt`
  / `kernel::interrupts::context_switch::idle_loop` resolved correctly). This
  is worth fixing in `breenix-gdb-chat/scripts/gdb_chat.py` itself so future
  GDB sessions on x86 don't silently mis-symbolicate.
- Empirical timing for this profile: healthy boot ~57s wall-clock at idle
  host load, worst observed serial-quiet gap during a healthy boot was 3s.
  These numbers back the harness's 12s-stall / 100s-per-boot-cap thresholds
  and may be useful for tuning any future gate/harness timeouts.
- `pkill -f <pattern>` invoked via `ssh ... 'bash -lc "...pkill -f
  qemu-system-x86_64..."'` can self-match: when the pattern is embedded
  literally in the `bash -lc` argv string being pattern-matched, `pgrep`/`pkill
  -f` can match the invoking shell itself. Hit this twice while building the
  harness (an inline `pkill` briefly killed its own containing ssh session).
  The final harness avoids this by using real script files (`loop.sh`,
  `attach.sh`) on disk rather than inline `bash -lc "..."` strings that
  contain the search pattern.

## Recommendation for the next attempt

Given the zero-specimen result at n=150 sequential boots, the next practical
step (not attempted here, out of this task's scope) would be to try
reproducing under conditions closer to the original triage-sweep battery —
e.g. running boots concurrently (contending for host CPU/IO the way a
52-boot battery likely did) rather than strictly sequentially, since PCI
enumeration's `in`/`out` port I/O timing under KVM could plausibly be
sensitive to host scheduling contention in a way a quiet, sequential loop on
an otherwise-idle beast host does not reproduce.
