## 1. What was missing

`verify.md` (this arc's design pass) found that both arches already emit
rich, count-bearing device-enumeration summaries to serial on every boot —
`pci::enumerate()`'s `"PCI: Enumeration complete. Found N devices (B VirtIO
block, W network)"` on x86/Parallels/VMware, and `init_virtio_mmio()`'s
per-device + summary lines on aarch64 QEMU MMIO — but **no gate anywhere
asserted anything about them**. A boot that silently died right after device
detection (#702's own shape: a hang right after "E1000 network device
found") or that quietly degraded to zero devices read identically to a
healthy boot to every existing marker-grep gate. §3 of `verify.md` has the
full sweep; the summary table there shows "Device-count assertion: none" on
every profile.

`verify.md` also swept live issues fresh against this layer's exact file
boundary and found one in-scope, blocking issue: **#702**, an x86 boot that
hangs silently inside PCI enumeration right after E1000 detection (~1/26-52
rate, unattributed, GDB-attach RCA still needed). This arc does not close
#702 — that is explicitly out of scope (read-only design pass, then this
implement pass, neither authorized to chase a rare GDB-attach RCA) — but the
census leg makes that failure region *legible*: its absence is now itself a
named, attributed signal instead of an undifferentiated "USERSPACE TEST
COMPLETE was absent".

## 2. What was built

Census-anchored device-enumeration assertions, self-counted against each
script's own device flags (never a second hand-maintained literal — the
#549/#551/[[gate-target-fidelity-528]] lesson), added to the four gates
`verify.md §4a` named:

- `docker/qemu/run-x86-gate.sh` — the beast merge gate (both `kthread` and
  `full` modes). Self-counts VirtIO-block devices from
  `src/bin/qemu-uefi.rs` (the flags are compiled into that binary, not
  declared in the shell script itself).
- `docker/qemu/run-x86-boot-tests.sh` — the production frame-custody gate.
  Self-counts from its own `-device virtio-blk-pci` lines.
- `docker/qemu/run-aarch64-full-test.sh` — self-counts the five
  `-device virtio-*-device` flags in its own QEMU invocation, asserts the
  MMIO total matches and that both `network` and `block` appear in the
  per-device breakdown (not just folded into an opaque total).
- `docker/qemu/run-aarch64-service-sequence-gate.sh` — same assertion,
  landed inside `classify_serial()`'s existing anti-vacuity idiom (an
  `UNATTRIBUTED` verdict with a named reason, matching the shape of its two
  neighboring oracle-absence checks) rather than inventing a new top-level
  bucket and touching the bucket-tally/`print_census` machinery elsewhere in
  that file.

Also built: `docker/qemu/run-vmware-gate.sh`, a new script implementing
`verify.md §4b`'s design — a fixed-wait / read-evidence / `vmrun stop ...
hard` cycle modeled on the Parallels truncate/boot/read/stop cycle
CLAUDE.md already documents, closing the "unproven by any recorded boot"
gap for the VMware e1000 NIC fallback. Unlike the four QEMU gates above,
this is a one-time operator-run capture, not a merge gate — see §5.

**Correction (fix round, 2026-08-31, review finding B6):** the sentence
above originally described the start half of that cycle as `vmrun start
... nogui`, matching `verify.md §4b`'s ratified design exactly. As shipped
by the implement/confirm rounds, it did not: `run-vmware-gate.sh`
backgrounded `run.sh --vmware`, and `run.sh`'s own VMware branch called
`"$VMRUN" start "$VMX_FILE" gui` unconditionally (falling back to `nogui`
only if that call *errored*, which `vmrun start ... gui` typically does
not — it opens a real window and returns 0), so every capture this arc ran
opened a window on the operator's desktop. This fix round implements the
ratified design for real: `run.sh` now reads a `BREENIX_VMWARE_NOGUI` env
var and, when set, calls `vmrun start ... nogui` directly, skipping the
gui-first attempt entirely; `run-vmware-gate.sh` sets that var before
invoking `run.sh --vmware`. The rest of the cycle (fixed wait, read
evidence, `vmrun stop ... hard`) is unchanged from what shipped, and F10's
cleanup hardening (below) was added in the same round.

**Zero kernel bytes added.** Every leg rides serial lines the drivers
already emit; nothing in `kernel/src/**` changed on this branch.

## 3. Two bugs this arc found in itself, by actually running the gates

Both were caught by executing the gates against real boots, not by re-
reading the code — exactly the failure mode the arc-4 lesson ("fix, don't
argue") warns about skipping.

### 3a. x86: the `network==0` assumption was wrong

`verify.md`'s design reasoned that `run-x86-gate.sh` (which sets
`BREENIX_NET_MODE=none`) and `run-x86-boot-tests.sh` (whose raw QEMU
invocation has no `-netdev`/`-device e1000` at all) would find zero network
devices, and drafted `network==0` as the honest expectation for both. A
first self-check boot immediately falsified that:

```
PCI: Enumeration complete. Found 9 devices (3 VirtIO block, 1 network)
E1000 network device found
```

QEMU (confirmed against the beast host's version, 8.2.2) auto-attaches its
own default NIC whenever no `-net`/`-netdev`/`-nic` option is given at all —
`BREENIX_NET_MODE=none` only skips the *explicit* args in `qemu-uefi.rs`, it
never passes QEMU `-nic none`, so QEMU's implicit default (an e1000 at
`00:02.0`, confirmed by PCI ID `[8086:100e]`) fills the gap. Both scripts'
assertions were corrected to the honest floor (`network >= 1`), which
happens to restore `verify.md`'s original design intent, just for the
opposite reason than assumed. See `serials/x86-run-x86-gate-kthread-pass-
20260831.txt` for the full census excerpt on the corrected code.

### 3b. aarch64: the self-count regex matched its own error messages

The self-count pattern `-device virtio-[a-z]*-device`, run unanchored
against `run-aarch64-full-test.sh`'s own source, matched not only the five
real `-device` flags in the QEMU invocation but also the literal device-flag
names quoted inside two of this leg's own `FAIL_REASON` strings ("...though
`-device virtio-net-device` is attached"). Self-count came back 7 instead of
5, making the assertion permanently false on every boot, healthy or not —
the textbook vacuity failure this leg exists to prevent, just relocated into
the leg's own source rather than the kernel's. Caught by manually running
the extraction logic against a real boot's serial and getting a `5 != 7`
mismatch on a *known-good* boot. Fixed by anchoring the pattern to
`^[[:space:]]*-device ...` so it only matches actual command-line flags;
reconfirmed count is 5 in both `run-aarch64-full-test.sh` and
`run-aarch64-service-sequence-gate.sh`.

## 5. VMware e1000-fallback capture — result

`docker/qemu/run-vmware-gate.sh`, run three times end-to-end on this Mac
(first run caught the production-profile log-level gap below and was fixed;
the second and third both passed cleanly, confirming the fix and the
hardened cleanup):

```
VMware e1000-fallback gate: PASS
  virtio-net PCI attempted and failed, e1000 fallback initialized
  [drivers] Found 60 PCI devices
```

Full serial in `serials/vmware-e1000-fallback-boot-20260831.txt`. The
relevant lines:

```
[drivers] VirtIO network (PCI) init failed: No VirtIO network PCI device found
[e1000] Found device 10d3 at 02:00.0
...
[drivers] Intel e1000 network driver initialized
[net] Using Intel e1000 driver (VMware)
```

This closes `verify.md §4b`'s "unproven by any recorded boot" gap for real:
the e1000 fallback (unchanged since `e144f93a`, 2026-03-10) is now measured,
not just read as source. `run.sh`'s VMX generation confirms the mechanism —
`ethernet0.virtualDev = "e1000e"`, unconditional, so `virtio::net_pci::init()`
deterministically fails to find a virtio-net device and the e1000 branch is
the only path that can ever succeed on this platform, exactly as the
production boot demonstrates.

**One production-profile gap this run found and fixed in the gate, not the
kernel:** `run.sh --vmware` builds the plain production profile (no
`--features`), and `pci.rs`'s `"PCI: Enumeration complete..."` census line
is a `log::info!` call — filtered out of a production boot's serial by the
default log level, unlike every QEMU gate in this arc, which all build with
a `testing`/`boot_tests` feature that raises it. The first VMware run
correctly reddened on this ("device-enumeration census line absent"). The
unconditional `serial_println!` sibling line, `"[drivers] Found N PCI
devices"` (`kernel/src/drivers/mod.rs`), *is* present on a production boot,
so `run-vmware-gate.sh` was corrected to check that line instead. This is
the same "measure the shipping profile" lesson the TTY arc (arc 4) already
learned: a leg that only checks a `log::info!` line is a leg that silently
stops proving anything the moment the profile that ships doesn't include it.

**Operational note, not evidence, but disclosed honestly:** `run.sh
--vmware`'s own background `vmware.log` monitor is a pipeline
(`tail -f "$VM_LOG" | while ...`) inside a backgrounded subshell; killing
the subshell does not touch the already-forked `tail -f` half of that
pipeline, which survives as an orphan. Observed directly across the first
two runs (leaked `tail -f .../vmware.log` processes, reparented to PID 1,
harmless but leaked). `run-vmware-gate.sh`'s cleanup now also reaps any
`tail -f .../vmware.log` process by path on every exit path; the third run
confirmed a fully clean `vmrun list` (0 VMs) and `ps aux` (no stray
processes) afterward. No VM was left running at the end of any run,
including the one that hit the log-level bug above — `cleanup_vm()` runs on
every `EXIT`, pass or fail.

**Hardened further in this fix round (review finding F10):** the stop call
right before disarming the EXIT trap discarded `vmrun stop`'s exit status
(`|| true`) and then unconditionally blanked `VMX_FILE`, so a stop that
silently failed would leave the trap's own cleanup as a no-op — exactly the
"leave no VM running" rule this repo's memory is emphatic about. The script
now confirms with `vmrun list` before blanking `VMX_FILE`; if the VM is
still listed, the variable stays set and the EXIT trap's `cleanup_vm`
retries the stop instead of silently doing nothing.

## 7. In-layer / adjacent defects found, fixed or filed

- **Filed #719**, not fixed: a fresh x86 checkout (a new git worktree or
  clone) fails to build `qemu-uefi` at all. `Cargo.toml`'s
  `bootloader`/`bootloader-x86_64-common` git dependencies float on
  `branch = "main"` with no `rev`, and `Cargo.lock` is gitignored, so a
  fresh resolution lands on whatever commit is at the tip of upstream's
  `main` at that moment — currently one that requires a newer nightly's
  `Step` trait shape than the pinned `nightly-2025-06-24` provides. This
  affected this arc's own x86 self-check (worked around locally with an
  uncommitted, borrowed `Cargo.lock` from a long-lived checkout that never
  re-resolved) and will affect any future fresh x86 checkout the same way.
  Not fixed here: the right fix (pin a `rev`, and/or stop gitignoring
  `Cargo.lock`) is a build-system-wide decision with tradeoffs (floating on
  upstream fixes vs. reproducibility) outside a bus/NIC evidence arc's
  remit, and is not a defect in this layer's own files.
- **Fixed in this arc, not filed separately** (small, caught during
  self-check, corrected before landing): the two self-inflicted census-leg
  bugs in §3 above (x86 `network==0` assumption, aarch64 unanchored
  self-count regex) and the VMware gate's production-profile log-level gap
  and orphaned-`tail` cleanup leak in §5.
