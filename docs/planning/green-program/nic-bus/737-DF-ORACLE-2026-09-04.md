## 0. What is claimed, in one line

**REPRODUCED.** On current `main` bytes plus this branch's test-only additions,
a fork-free userspace program that holds DF=1 across a scheduling quantum kills
the boot on the first from-userspace preemption, at
`core::panic::location::Location::file`'s first instruction, with the direction
flag set in the fatal frame — 3 boots out of 3, byte-identical fault records.

## 1. The two artifacts

### 1.1 `df_preempt_oracle` — a fork-free x86_64 roster program

`userspace/programs/src/df_preempt_oracle.rs`. It prints a start marker,
executes `std`, spins CPU-bound inside a single inline-asm block with no call
out of it, samples RFLAGS with `pushfq` immediately before its `cld`, samples
again after, and prints

```text
[DF_PREEMPT] window <n> begin iterations=<k>
[DF_PREEMPT] window <n> end elapsed_ms=<m> rflags_before_cld=0x<..> rflags_after_cld=0x<..>
[DF_PREEMPT] ticks_spanned=<n> df_after_cld=<0|1> df_roundtrip=<ok|bad>
```

before exiting 0. The clock is read outside the DF=1 window, because a syscall
would leave it. There is no call out of the window between `std` and `cld`, so
the program does not run its own `memmove` backwards over its own stack.

### 1.2 `tests/entry_point_df_structure.rs` — the entry-point `cld` ratchet

Host-side, source-level, census-anchored, no boot. It derives the hand-written
entry points by shape rather than by a name list:

1. each `*.asm` under `kernel/src/interrupts/` and `kernel/src/syscall/`, kept
   if `kernel/build.rs` assembles it or a `global_asm!`/`include_str!`/
   `include!` pulls it in;
2. each `global <symbol>` directive in those files;
3. policed unless the Rust tree declares the symbol as a *parameter-taking*
   callable — those are entered by an ordinary `call` from compiled Rust, where
   the SysV ABI already has DF clear at entry.

and asserts that each policed entry executes `cld` before its first `call` into
Rust and before any string instruction. The `extern "x86-interrupt" fn`
handlers are **exempt and censused**: LLVM's `x86_intrcc` prologue emits the
`cld` itself, so the property is a fact about the compiler, not about this
tree's text. The test prints that exempt count on each run (14 handlers across
3 files, measured below) so the exemption stays countable.

The test was **expected red** on the bytes this slot measured (`385cdf85`) and
was left red at that commit. It turns green only together with the
operator-approved `cld` — which landed in `e1622d7f`, so at the branch head this
test is green: 4 passed / 0 failed as the fix round measured it
(`serials/737-df-fix-2026-09-04/ratchet/`), and 5 passed / 0 failed after R157
added a scope assertion (`serials/737-r157-2026-09-04/ratchet-head.txt`).

```text

<S>[DIAG:PAGEFAULT] ==============================
[DIAG:PAGEFAULT] Fault addr: 0x0
[DIAG:PAGEFAULT] Error code: 0x0
[DIAG:PAGEFAULT] RIP: 0x10000359d80
[DIAG:PAGEFAULT] CS: 0x8
[DIAG:PAGEFAULT] RFLAGS: 0x486
[DIAG:PAGEFAULT] RSP: 0xffffc90000e9c0b8
```

and the kernel's own decode of that frame names the flag outright:

```text
    cpu_flags: RFlags(
        DIRECTION_FLAG | SIGN_FLAG | PARITY_FLAG | 0x2,
    ),
```

Five things line up, each of them the RCA's prediction:

1. **The `<S>` marker immediately precedes the fault block.** `<S>` is emitted
   in `kernel/src/interrupts/context_switch.rs` only when the timer entered
   from userspace, i.e. this is the from-userspace save path, entered while the
   oracle's DF=1 window was open.
2. **DF is set in the fatal frame** — `0x486` = DF | SF | PF | 0x2, with IF
   clear, so no nested interrupt set it inside this frame.
3. **CS = 0x8**, ring 0: the fault is in the kernel, not in the oracle.
4. **The RIP is `Location::file`'s first instruction.** The bootloader printed
   `virtual_address_offset: 0x10000000000`, so `0x10000359d80` is ELF-relative
   `0x359d80`, and in the kernel ELF booted:

   ```
   $ nm -C --defined-only -n <kernel ELF>   -> nearest preceding symbol at 0x359d80 is
                                              core::panic::location::Location::file, offset 0x0
   $ objdump -d -C --start-address=0x359d80 <kernel ELF>
   0000000000359d80 <core::panic::location::Location::file>:
     359d80:  48 8b 07     mov    (%rdi),%rax
     359d83:  48 8b 57 08  mov    0x8(%rdi),%rdx
     359d87:  48 ff ca     dec    %rdx
     359d8a:  c3           ret
   ```

5. **Its only caller reloads the spill slot the RCA named.** There is exactly 1
   `call ... <core::panic::location::Location::file>` in the whole image, and
   the instruction feeding it is `mov 0x40(%rsp),%rdi` — the same `[rsp+0x40]`
   spill of the `&'static Location` that `RecordBuilder::new`'s backwards
   `rep movsq` overwrites.

### 3.1 The first oracle build did not reproduce, and why that is not a falsification

The first version of this program used one window and stopped as soon as it had
spanned 10 ms. It completed cleanly:

```text
[DF_PREEMPT] window 1: iterations=10000000 elapsed_ms=32 rflags_before_cld=0x646 rflags_after_cld=0x246
[DF_PREEMPT] ticks_spanned=32 df_after_cld=0 df_roundtrip=ok
```

`0x646` carries DF, so the flag *did* survive that window — but the boot carried
**0 `<S>` markers between the program's own start line and its result line**, so
that window took timer ticks without ever taking the from-userspace **save**
path, which is the step the mechanism needs.

The reason is in `kernel/src/interrupts/timer.rs`: `need_resched` is raised only
when the thread's quantum expires (`TIME_QUANTUM` = 10 ticks), and it is the
reschedule, not the tick, that reaches `save_userspace_context` and its
`log::trace!`. A 32 ms window is shorter than one quantum on this profile.

So that run is **not** evidence against M1. It is a design gap in the oracle,
and it is why the shipped version escalates until a window measurably spans
`MIN_WINDOW_MS` = 200 ms and brackets each window with begin/end markers, so a
reader can count the kernel's own save markers landing inside a window. It is
recorded here rather than dropped, because "the oracle completed" would have
been a false negative if it had been reported without the `<S>` census.

## 6. What is NOT claimed

* **No fix landed *in this slot*.** At `385cdf85`,
  `kernel/src/interrupts/timer_entry.asm` is Tier-1 and untouched by this
  branch, and the ratchet is red on purpose; it lands green only with the
  operator-approved `cld`. That approval came (R156) and the instruction landed
  in `e1622d7f`, one commit later — so at the branch head a fix HAS landed and
  the ratchet IS green. `737-FIX-2026-09-04.md` is the record of it.
* **The two `log::trace!` sites are a separate item.** Deleting
  `kernel/src/task/process_context.rs:267` and
  `kernel/src/interrupts/context_switch.rs:642` would stop this specimen
  reproducing while leaving DF=1 leaking into the ISR. They are worth removing
  on cost grounds — each builds a full `Record` inside masked-IRQ context only
  to discard it — but that is not a #737 fix and must not be booked as one.
* **No rate is claimed.** These three boots say the defect is deterministic
  *given* a from-userspace reschedule inside a DF=1 window. They do not measure
  how often production workloads land in that window, and this slot ran no
  battery.
* **The ratchet is a lexical check, not a control-flow analysis.** Its own doc
  comment states the limit: a `cld` on a branch the entry can skip would satisfy
  it. 3 of 3 policed entries in the tree today are straight-line-then-merge
  shapes where the two coincide.
* **The gate-host `/tmp` collision was worked around, not fixed.**
  `docker/qemu/run-x86-boot-tests.sh` and `docker/qemu/run-boot-parallel.sh`
  still hardcode shared `/tmp` paths, so two clones on one host can still score
  each other's boots. This branch changes neither script's output paths.

## 7. The fix, as text — not applied in this slot; landed in `e1622d7f`

One instruction, one byte, in a Tier-1 file. When this section was written it
needed explicit operator approval before anyone wrote it. R156 granted it and
the next slot applied it in `e1622d7f` — the same instruction at the same
placement (immediately after the entry `cli`, before the first register push),
with the accompanying comment reworded; the landed diff is quoted verbatim in
`737-FIX-2026-09-04.md` section 1. Placement is before any `rep`-capable code
and before the call into Rust; it needs no undo, because IRETQ restores RFLAGS
from the interrupt frame, which is the property `df_roundtrip=ok` pins.
