## 2. Block rate: 23/120 (19.2%) — not back to `#764`'s ~60%, and not this
## experiment's own bracket

| battery | reader code | block rate |
|---|---|---|
| `#764` baseline (`serials/764-rca/battery.tsv`, 76 boots) | no bracket at all | 46/76 = 60.5% |
| `#772` round 1 (`serials/772-exp/`, 60 boots) | in-band bracket around the data read | 2/60 = 3.3% |
| `#772` round 2 (this battery, 120 boots) | out-of-band bracket (whole process) | **23/120 = 19.2%** |

Round 1 diagnosed its 3.3% as an observer effect: three syscalls
(`open`/`read`/`close` of `/proc/trace/counters`) sitting between `accept()`
returning and the blocking `read()` starting, inserting a p50 1290 ms gap
(true median 1286.5 ms — `772-EXPERIMENT-2026-09-03.md:98`).
This round's rework moved both counter reads out of that span entirely — one
before `accept()` is even called, one after the EOF-wait verdict is decided —
and that removal is independently confirmed in this battery's own serials,
not just claimed: `pre - acc` (the accept-return-to-pre-read gap, exactly
where round 1's bracket sat) is **0 in 107/120 boots (89.2%)**, nonzero in
only 13/120, min 0 / p50 0 / max 1603 ms
(`772r2-results-final.jsonl`, field `reader_stamps.pre - reader_stamps.acc`).
The bracket is genuinely gone from *that* span — but round 2's bracket does
not occupy that span. It occupies a different one, process-start to
`accept()`, which `pre - acc` is blind to by construction. That span is
exactly where the cause lives, below.

The rate did rise from round 1's 3.3% (removing round 1's bracket helped,
as predicted) but it did **not** return to `#764`'s 60.5% — it stopped at
roughly a third of the way there. `w0_to_pre == 0` (reader already sitting
in the blocking read before the peer's write — `#764`'s own proxy for
"about to block") is true in **25/120 (20.8%)** of this battery's boots,
against `#764`'s reported **55/76 (72.4%)**, next to a 19.2% block rate —
already pointing at the same span `pre - acc` cannot see. `data_latency_ms`
across all 120: min 64, p50 177, max 7153 ms.

**The cause is round 2's own `START` bracket.** Whether the data read
blocks at all is decided by a race between the reader reaching
`accept()`/`read()` and the peer's `write()`; round 1's report already
stated the causal law (`772-EXPERIMENT-2026-09-03.md:104-106`): "entering
the blocking read before the peer's write is precisely the precondition for
blocking at all." Measuring `acc - w0` (the reader's `accept()`-return
stamp minus the peer's pre-write stamp) directly across both rounds'
committed serials shows the shift:

| battery | reader work before `accept()` | `acc - w0` p25 / p50 / p75 | boots with `acc <= w0` |
|---|---|---|---|
| round 1 (`serials/772-exp/`, 60 boots) | none | -63 / **-53** / -1 ms | 49/60 (81.7%) |
| round 2 (`serials/772-exp-r2/`, 120 boots) | procfs read + `println!` | +79 / **+129.5** / +159 ms | 29/120 (24.2%) |

A ~183 ms median shift, in exactly the direction and at exactly the
location round 2's `START` bracket was inserted. Conditioned within round
2's own 120 boots, blocking tracks `acc <= w0` almost exactly:

```
acc <= w0 (reader wins the race): n=29,  blocked 23  -> 79.3%
acc >  w0 (peer wrote first):     n=91,  blocked  0  ->  0.0%
```

<!-- claim-lint:ok: acc>w0 -> blocked 0/91 (0.0%) in this battery, the
     empirical confirmation of the construction claim -- table above,
     re-derived from serials/772-exp-r2/boot_*/{serial_user,serial_kernel}.txt
     by this correction round. -->
Blocking is impossible by construction once the peer's write lands before
`accept()` returns — `tcp_recv` succeeds on the first try and the wait loop
is never entered. Round 2's `START` bracket moved 76% of boots into that
bucket; that is the whole of the 60.5% → 19.2% gap.

Cost is not just the three syscalls (`open`/`read`/`close`) round 1 already
named: `/proc/trace/counters` generation calls `emit_root_custody_summary()`
and `emit_tombstone_census()` (`kernel/src/fs/procfs/trace.rs:206-210`),
each a blocking `serial_println!` — visible in
`boot_001/serial_user.txt:676-677`, immediately before the `START` marker
at `:724` — plus a heap `String` render of ~90 counters, plus the
userspace `println!` of the marker itself.

**Coordinator ruling R105 (round 3 review), the lesson this round leaves

## 6. A parser bug found and fixed mid-analysis (disclosed, not hidden)

`census_r2.py`'s turn-count anchor picks the most recent
`unblock(<tid>): Added to per_cpu_queues` line before an episode's own
`woken` line, to start counting restores from the genuine external wake
signal rather than from ordinary pre-wake scheduling noise (this is round
1's own technique, reused here). The bug: that anchor was not reset when a
**new** episode's own `entering blocking path` line was seen, so a stray
`unblock(<tid>)` line left over from the **accept()** call's own resolution
— which uses the identical `unblock(<tid>): Added to per_cpu_queues` line,
since it is a generic per-thread wake primitive, not recv-specific — could
leak into the very next recv episode's turn count if that episode had no
`unblock()` line of its own to anchor on instead.

Caught directly, not by inspection: `boot_040`'s live run reported
`eof_turns=4`; a manual raw-log check of thread 28's own lines showed the
EOF episode itself (`entering blocking path` at 2645, `woken` at 2818) has
exactly **one** `Restored kernel context` line (2816) between them — the
other three restores the script counted (2355, 2452, 2542) belong to the
*accept* episode earlier in the same boot (`unblock(28)` at line 2227, which
predates the EOF episode's own start at 2645 by 400+ lines), anchored via
the exact bug described above.

**Fix**: reset the unblock anchor to `None` whenever a new `entering
blocking path` line is seen (an unblock signal cannot precede the block
episode it resolves, so any unblock seen before this point cannot belong to
what's about to start). Re-ran the corrected script over all 120 boots:
**8 boots' `eof_turns` changed**, all downward, all from this exact
accept-episode-leak mechanism (`boot_010` 2→1, `boot_034` 2→1, `boot_040`
4→1, `boot_053` 2→1, `boot_058` 2→1, `boot_064` 2→1, `boot_065` 2→1,
`boot_114` 2→1) — `eofMultiTurnBoots` corrected from a live 17 down to **9**.
**Zero `data_turns` changed** — both DATA specimens (`boot_011`, `boot_088`)
were independently verified against raw logs before and after the fix and
are unaffected (their episodes each had their own genuine `unblock()` line,
or, for `boot_088`, no earlier accept episode with an unblock line to leak
from). A second independent boot (`boot_019`) was manually re-verified
against raw serial after the fix and matches exactly (data turns=1 via its
own `unblock(28)` at line 2096, eof turns=3 via three restores at
2422/2503/2554 with no unblock line of its own — the fixed anchor correctly
falls back to the episode's own block-enter line). `772r2-results.jsonl`
keeps the live, pre-fix numbers for the record; `772r2-results-final.jsonl`
is authoritative and is what every count in this report cites.
