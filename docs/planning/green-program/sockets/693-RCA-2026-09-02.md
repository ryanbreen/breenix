# #693 RCA — `late_lost_wake` is a late publication, not a lost one

Branch `fix/693-poll-wake-loss`, head `85596f62`, off `main` @ `3d601400`.
Host: beast `breenix-x86` (Incus VM), profile `testing,external_test_bins`,
`BREENIX_NET_MODE=none`, `-smp 1`, KVM `-cpu host` (the environment #693 was
filed from) and TCG `-cpu qemu64` (the default x86 gate's accelerator, which the
issue's second comment measures at 26/30 FAIL).

## 1. The question #693 left open, and the answer

#693 states its undecided fork verbatim:

> **Not** established: whether the peer's `send()` was actually issued and its
> readiness lost, or whether the peer's own `recv` of the token never completed
> so it never wrote at all.
> <!-- claim-lint:ok: verbatim quote of #693's own text; settled by 368/368 in §4 and 13/13 in §5 -->

The first, with one correction to its wording. **The peer's `send()` is issued,
and it is issued after the poll's timeout has already expired.** Readiness is
never published inside the poll's window, so there is nothing for the kernel to
lose; and the peer does complete its token receive, so the second branch is
wrong too. On 13 of 13 reproductions the parent's post-timeout read of the
socket precedes the peer's 23-byte write in the kernel's own syscall log. The
`late_lost_wake` name is a mis-attribution.

## 2. Instrumentation added (userspace only)

`userspace/programs/src/poll_tcp_oracle.rs`, commits `6ec3f492`, `ba15015e`,
`85596f62`:

* `peer_exit()` and the rewritten `late_peer()`: the stage-3 peer emits
  `[POLL_TCP_ORACLE:PEER:branch=…]` and exits with a code naming the branch —
  `sent` (0, with the byte count and both stamps), `token_recv_failed` (11),
  `token_clock_failed` (12), `write_clock_failed` (13), `send_failed` (14). The
  previous code was `let _ = socket::send(server, &msg);` then
  `process::exit(0)`, so each of the 5 branches reached the same exit status,
  which therefore carried no branch information.
* `late_lost_wake_probe()`, emitted before the reap: `probe_ms`, a `timeout=0`
  re-poll of the same fd, and a non-blocking read of it — the socket's receive
  queue and readiness flags, read at the instant the blocking poll gave up.
* The `late_lost_wake` detail now carries `entry`, `returned`, the peer's reaped
  status and its exit code; `late_woken_by_clock` carries `entry`, `returned`
  and the peer's `write_ms`.

The oracle has no x86 launch site — it was un-wired at the #568 landing and is
wired only on aarch64 — so it cannot be observed on x86 until one is added.
Every battery in §3 therefore ran with the launch site added back as an

`serials/693-fix/x86-launch-site.patch` with its apply/revert pair. That patch

## 4. Evidence — the peer writes on 368 of 368 trials

Across the four arms, 368 of 368 stage-3 trials that emitted a branch line
emitted `branch=sent` with `n=23 want=23`:

```
peer branch census: {'sent': 368}
```

368 of 368 as run. Re-derivable from the 3 committed driver outputs: 324 of
324, same result, no `token_recv_failed`, no `send_failed` and no clock failure
in either count. #693's second candidate — the peer never wrote at all — is
refuted on 368 of the 368 trials.

What varies is *when* it writes. The peer sleeps to an absolute instant on the
kernel's own monotonic clock and reports both stamps, so its overrun is
measured, not inferred. Over the same 368 trials, `write_ms - token_ms -
delay_ms`:

```
as run, 368 trials:      min = 47 ms   p50 = 420 ms   p90 = 2592 ms   max = 10318 ms
re-derivable, 324:       min = 84 ms   p50 = 426.5 ms p90 = 2592 ms   max = 10318 ms
trials with overrun > 5000 ms: 11 in both counts
```

The second row is the one this repository can check: it is the same statistic
over the 3 committed driver outputs, and the recipe that prints it is in #766.
p90, max and the 11-trial count are identical in the two counts; the min and
the median differ because the 44 unpreserved trials are missing from the
second. An 80 ms sleep routinely takes hundreds of milliseconds to seconds,
and 11 trials overran by more than the poll's entire 5000 ms budget.

## 5. Evidence — the write lands after the poll gives up

Two independent readings, both mechanical.

**(a) Kernel-side syscall ordering, 13 of 13 specimens.** The probe's
non-blocking read appears in the kernel log as `sys_fcntl F_SETFL: fd=N
flags=0x800` followed within four lines by
`sys_read: TCP no data, O_NONBLOCK set - returning EAGAIN`; the peer's payload
send appears as `sys_write: Wrote 23 bytes to TCP connection` (23 is
`LATE_MSG_LEN = 7 + 8 + 8`). Line numbers below are 1-based, the numbers `grep
-n` and `sed -n 'Np'` print, and they name the LAST occurrence of each pattern
in the file, which is the trial the verdict was made on (a boot that climbs the
delay ladder writes 23 bytes more than once). On 13 of the 13 preserved
specimens the probe's read comes first:

| specimen | probe EAGAIN read | peer 23-byte write |
|---|---|---|
| kvm2/boot19 | 3063 | 3074 |
| tcg/boot3 | 3511 | 3814 |
| tcg/boot5 | 3617 | 3825 |
| tcg/boot11 | 2737 | 2751 |
| tcg/boot17 | 3968 | 3998 |

13 of 13. The probe read the socket after the poll returned and found it empty,
and the peer's write reached the kernel afterwards.

**(b) Clock arithmetic, the three specimens built with the stamps.** Both sides
stamp the same kernel monotonic clock, so no ordering of console prints is
involved:

| specimen | entry | returned | peer token_ms | peer write_ms | write − returned | peer sleep for delay |
|---|---|---|---|---|---|---|
| tcg3/boot11 | 18888 | 24138 | 19208 | 29686 | **+5548 ms** | 10478 ms for 160 ms |
| tcg3/boot24 | 29704 | 37186 | 29677 | 38757 | **+1571 ms** | 9080 ms for 1280 ms |
| tcg3/boot25 | 18968 | 24219 | 18939 | 27892 | **+3673 ms** | 8953 ms for 160 ms |

In the 3 stamped specimens the peer's publication instant is 1.5–5.5 s later
than the poll's return instant, and `probe_ms` is at or within 2 ms of
`returned`: 24138 vs 24138 on tcg3/boot11, 37188 vs 37186 on tcg3/boot24, and
24219 vs 24219 on tcg3/boot25. So each probe's `rescan_ready=0 …
nbread_err=EAGAIN` is a reading of the socket taken within 2 ms of the poll's
return and 1.5–5.5 s before the peer's write.

Print order on the shared console is *not* a reliable third reading and is
recorded here only to say so: on `kvm2/boot19` the peer's marker prints before
the parent's probe marker even though the kernel log shows the probe's read
first, because the parent can be preempted between its probe's syscalls and its
own print. That inversion is why the stamps were added.

**Positive control.** The complementary case appears in the same batteries as
`late_woken_by_clock`, which is only reachable when the poll returned `POLLIN`.
`tcg3/boot18`: `entry=21311 returned=27106 write_ms=26697` — the peer published
409 ms *before* the return, and the poll did report `POLLIN`, late against its
own 5000 ms deadline but not lost. In 0 of the 16 preserved failures is
readiness published and then not observed.

## 6. Mechanism

`late_peer` waits for the parent's readiness token, stamps `token_ms`, and calls
`sleep_until(token_ms + delay_ms)`, which is `libbreenix::time::sleep_ms` →
`sys_nanosleep` (`kernel/src/syscall/time.rs:166`). `sys_nanosleep` puts the
thread in `BlockedOnTimer` with an absolute deadline and takes it off the
per-CPU ready queue (`Scheduler::block_current_for_timer`,
`kernel/src/task/scheduler.rs:3354`); the deadline is honoured by
`wake_expired_timers` (`kernel/src/task/scheduler.rs:3618`), which pops the heap
entry, publishes `Ready`, and pushes the thread back on the queue
(`kernel/src/task/scheduler.rs:3731`). Publishing `Ready` is not dispatching:
x86 runs one queue (`MAX_CPUS = 1`, `kernel/src/task/scheduler.rs:1012`) as a
round robin with a fixed 50 ms slice (`TIME_QUANTUM: u32 = 10` ticks,
`kernel/src/interrupts/timer.rs:33`, at `PIT_HZ = 200`,
`kernel/src/time/timer.rs:14`), and a couple of dozen threads are alive by the
time stage 3 runs. That count is re-derivable from a committed serial rather
than from the unpreserved first battery: in
`serials/693-rca/x86-693rca-tcg3-boot24-late_lost_wake-kernel-20260902.txt`
the peer's 23-byte write is at line 2776, and the 2775 lines before it hold 31
`Added thread` lines against 11 `exited with code` lines. So a full round is of
order a second and the woken peer waits behind it — the measured overrun
distribution in §4. The parent
meanwhile sits in `sys_poll` (`kernel/src/syscall/handlers.rs:3937`), whose loop
breaks on `now >= deadline_ns` after 5000 ms; when the peer's overrun exceeds
that budget the poll returns 0 with empty `revents`, which is the correct answer
for an unwritten socket. `poll_fd`'s `TcpConnection` arm
(`kernel/src/ipc/poll.rs:186`) reads `conn.rx_buffer.is_empty()` live through
`with_tcp_connections` (`kernel/src/net/tcp.rs:591`), a blocking lock and not a
`try_lock`, so an empty scan is a reading rather than a skipped one.
`stage_late` then reports `late_lost_wake` from `ready != 1 || revents & POLLIN
== 0` alone (`userspace/programs/src/poll_tcp_oracle.rs:441`), a predicate whose
inputs exclude the peer's publication instant — and on those bytes had no way to
obtain it, because the peer's stamps travel inside the payload whose absence is
what this arm handles. The same verdict is therefore emitted
for "the kernel dropped a publication" and for "the peer had not published yet",
and 13 of the 13 reproductions are the second.

## 7. Defect locations

1. `userspace/programs/src/poll_tcp_oracle.rs:441` — the `late_lost_wake`
   predicate. It names a kernel wake-loss from evidence that does not
   distinguish one. This is what #693 is blocked on and what made both the 1/24
   KVM number and the 26/30 TCG number untriageable.
2. `kernel/src/syscall/time.rs:166` (`sys_nanosleep`) with
   `kernel/src/interrupts/timer.rs:33` (`TIME_QUANTUM`) and
   `kernel/src/task/scheduler.rs:3731` (the timer wake's tail enqueue,
   `push_back`; the guard immediately above it is `:3720`, round-2 review F9):
   the deadline is honoured to within a tick, but dispatch after it is bounded only
   by a full 50 ms-per-thread round robin, which over this profile's 24-thread
   population is of order a second, measured at p90 = 2592 ms and max =
   10318 ms. This is the quantity that makes the peer late, and the same
   quantity behind #694's `late_window_missed` (26 of 119 boots here).

## 8. What this does not establish

* It does not rule out a genuine lost wake as a separate, rarer shape. It
  establishes that the 13 reproductions and the specimen #693 records are not
  one, and that the verdict naming them cannot tell the two apart. A real lost
  wake would show as `rescan_ready=1` or a positive `nbread_n` in the
  `[POLL_TCP_ORACLE:LOSTWAKE_PROBE:…]` line; 13 of the 13 preserved specimens
  read `rescan_ready=0 … nbread_err=EAGAIN` instead.
* It does not touch #737. This investigation did not reach the teardown page
  fault, and no shared mechanism was looked for beyond noting that the two
  signatures do not overlap.
* The 50 ms quantum and the thread population in §6 are measured for this
  profile on this host. This work does not separate how much of a dispatch gap is
  quantum exhaustion from how much is threads blocking early.
* GDB was not attached. The state that decides the question is the socket's
  receive queue and readiness at the instant the poll gives up, and the probe
  reads exactly that from inside the failing process at exactly that instant,
  cross-checked against the kernel's own syscall log on 13 of 13 specimens
  (§5a); a breakpoint cannot be aimed at a 1-in-64 event on KVM, and the state
  it would read is the state the probe already reports.

## 10. Recommended repair (not applied here)

**Superseded.** This section's third outcome -- readiness present at the
timeout stays `late_lost_wake` and a FAIL -- is exactly what the round-2
review (finding B2, ruling R93) and 693-FIX-2026-09-02.md §2.6 reversed: that
outcome is what a correct kernel produces under ordinary dispatch latency
(§5's own positive control below), so it is demoted to a report
(`LostSuspected`) rather than kept as a FAIL. A reader implementing this
section as written would rebuild the false-positive channel the round removed;
read §2.6 instead for the outcome that shipped.

`stage_late`'s timeout arm should decide against the peer's measured publication
instant, the way its `entry > token_ms` precondition already decides against the
peer's token stamp. With the peer's stamps on the console and the probe reading
the socket at the moment of the timeout, three outcomes separate cleanly:
readiness present at the timeout, or published before the return with the poll
still reporting an empty `revents`, is `late_lost_wake` and stays a FAIL; the
peer not having published leaves the wake question undecided, which is the
`late_window_missed` category, and it should report the peer's measured overrun
so the latency in §6 is visible instead of mislabelled. The scheduling latency itself is
separate work and carries its own issue: **#766**, filed 2026-09-02 with the
324-trial overrun distribution below and the four file:line citations in §7
item 2.

## 11. By-catch — `get_monotonic_time()` returns ticks, not milliseconds, on x86

Filed as **#767** on 2026-09-02, with this section's citations re-run against
`main` @ 509802e5 and three consequences this section did not name:
`sys_get_time()` at `kernel/src/syscall/handlers.rs:1830` hands the tick value
to userspace as "milliseconds since boot";
`kernel/src/test_framework/registry.rs:1265` carries a comment asserting the
x86 PIT runs at 1000 Hz, which `PIT_HZ = 200` contradicts; and 17 of the 39
`get_monotonic_time()` call sites in `kernel/src` are in that one registry file.

`kernel/src/time/timer.rs:86-94` documents `get_monotonic_time()` as
"Milliseconds since the kernel was initialized (PIT-based, 1ms resolution)" with
the body comment "At 1000 Hz, ticks == milliseconds", and returns `get_ticks()`
unscaled. On x86 `PIT_HZ = 200` (`kernel/src/time/timer.rs:14`), so a tick is
5 ms and the value is one fifth of the milliseconds it claims; the module header
and the `TICKS` doc comment carry the same 1000 Hz statement. The x86 callers
that read it as milliseconds are `kernel/src/net/mod.rs:486` and
`kernel/src/net/mod.rs:510`, where `ARP_PENDING_TTL_MS = 5_000` is applied to a
tick value and so expires after 25 s rather than 5 s, and
`kernel/src/rtc_test.rs:63`, where a `2000`-unit spin runs for 10 s. The PIT
fallback inside `get_monotonic_time_ns` (`kernel/src/time/timer.rs:109`)
inherits the same factor, so an x86 boot whose TSC calibration failed would run
its whole monotonic clock 5× slow. That did not happen in this battery: 16 of the 16 preserved
failing boots log a `TSC calibration complete` line (the calibrated values
range from 2400 to 2420 MHz across them), so the millisecond figures in this
document are TSC-derived and unaffected.
`kernel/src/syscall/handlers.rs:4048` carries a matching stale comment ("1ms —
one timer tick at 1000Hz") beside `poll_interval_ns`. On aarch64 the tick is
1 ms and these statements hold; the defect is x86-only.
