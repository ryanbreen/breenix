## Method: reading the counters out-of-band (R105)

`kernel/src/tracing/output.rs`'s GDB-callable dump family
(`trace_dump_counters()` and siblings) is absent from this build's linked
binary — confirmed by `nm` on the built kernel ELF (10,685 symbols, not a
stripped binary — other `dump_*` functions like `dump_thread_placement` and
`dump_iret_frame_to_serial` are present), which lists
`DISPATCH_NO_PROGRESS`/`DISPATCH_NO_PROGRESS_REFUSED`/`DISPATCH_KERNEL_RESTORE_TOTAL`
as live data symbols but has 0 hits for `trace_dump` or `dump_counters`
anywhere in that symbol table. 0 call sites for the dump family were found in
this repo's x86 boot path (`grep -rn trace_dump kernel/src/main.rs` -> 0
hits) — unlike `main_aarch64.rs:2021`, which calls `trace_dump_counters()`
directly — so with no `-C link-dead-code`, it does not survive to the link.
This is a
pre-existing gap in the documented GDB workflow, not something this fix
touches — not filed as an issue by this slot (out of this round's scope);
noted here so the next slot that reaches for `call trace_dump_counters()` on
x86 knows why it will not resolve.

The counters are still readable, out-of-band, without it: `TraceCounter` is
`#[repr(C)]` (`name: &str`, `description: &str`, then `per_cpu: [CpuCounterSlot;
MAX_CPUS]` at `#[repr(C, align(64))]`), so `per_cpu[0].value` sits at a fixed
+64-byte offset from the symbol's own address (`kernel/src/tracing/counter.rs`'s
struct layout, unconditional on build config). Each boot: free run under a
gdbstub (`qemu-uefi ... -s`, no `-S` — the guest halts only once GDB
attaches, confirmed 30/30 x86 boots this round by each boot's own
`gdb_output.txt` showing a live register dump rather than a connection
error, e.g. `serials/772-fix-a/red_1/gdb_output.txt`), poll the serial log
for the same two markers `x86-gate-verdict.sh`
requires (`USERSPACE TEST COMPLETE`, `TEST_TALLY:`) — i.e. attach only after
the recv episode this boot measures has already resolved and been logged —
then attach GDB, which halts the guest, read
`*(u64*)(sym_addr + KERNEL_BASE + 64)` for each of the three counters (x86
needs `+ KERNEL_BASE`, parsed from that boot's own `virtual_address_offset:`
serial line, since the bootloader's PIE placement is not fixed —
`scripts/test_tracing_via_gdb.sh`'s method), then kill the guest. All 30 x86
boots in this round ran `-smp 1`, so cpu0 is the only slot that can be
non-zero. PASS/FAIL is scored from the serial content already captured by
the time GDB attaches — `x86-gate-verdict.sh` (which runs
`x86-strand-census.sh` first) against the same two serial files the standing
gate produces — so the verdict is not an artifact of the GDB attach; the
attach happens strictly after everything the verdict script reads has
already been written.
