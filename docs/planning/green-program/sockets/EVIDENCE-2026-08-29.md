## 2. The instrument

`userspace/programs/src/poll_tcp_oracle.rs` runs on every aarch64 boot, from
`init`. It was also wired into `RING3_SMOKE` on x86 while the round-3 evidence
was taken, and **that x86 wiring was removed at landing** — see §10 for the
measurement that forced it and for what the removal costs. It exists
because nothing else in any profile blocks in `poll()` on an
`FdKind::TcpConnection`: `libbreenix`'s receive deadline was rewritten to avoid
that path (citing #568 by number) and `poll_test` only polls a *listener* with
`timeout=0`. Three stages:

| stage | what it drives | what it must show |
|---|---|---|
| `idle` | block on a connected fd with nothing to read, 120 ms timeout | returns 0 having consumed the whole timeout |
| `armed` | data already pending at the call | POLLIN from the entry scan |
| `late` | a forked peer publishes readiness *while the poller is parked* | POLLIN, delivered by the write and not by the clock |

Verdict marker `[POLL_TCP_ORACLE:PASS|FAIL:...]`, emitted twice because console
output interleaves at byte granularity.

## 3. Stage 3's bound, and the two ways it was wrong

Stage 3 is the only stage a stale snapshot cannot pass by luck, so its
anti-vacuity bound is the whole instrument. It took three revisions.

**Revision 1 (round 1) — measured the wrong two clocks.** It started the
parent's stopwatch at the parent's `poll()` entry and compared the elapsed time
against `LATE_WRITE_DELAY_MS`, which is the *child's* sleep. The child forks
first, so its 80 ms starts before the parent reaches `poll()`; the parent's
elapsed is `80 - (fork-return-to-poll latency)` and can only approach the bound
from below. The bound sat on top of its own distribution. In round 1's own
50-boot aarch64 gate the mode of `late_ms` was exactly 80 and four boots landed
under it (66, 71, 78, 79) — about 8% of healthy boots reddened by construction,
with the same string appearing on unmutated x86 boots.

**Revision 2 — right idea, wrong contents.** A shared absolute `write_deadline`
computed before the fork, with the child sleeping *until* it. Correct in
principle and unusable in practice: process creation was inside the window the
parent had to beat, and on beast's KVM x86 boot with 24 live userspace processes
the parent could not reach `poll()` inside 80, 160, 240 or 320 ms. Every trial
reported `late_parent_never_parked ... last_slack_ms=0`
(`serials/x86-forkwindow-precondition-miss-*-20260829.txt`).

**Revision 3 (shipped) — the peer measures, and proves it waited.** The parent
forks, hands the child a one-byte readiness token over the *reverse* direction
of the same connection (so it cannot make the polled fd readable), and only then
stamps `entry` and polls. Process creation is spent before either clock starts.
The child stamps the moment it receives the token, waits to `token_ms +
delay_ms` on its own clock, stamps again, and ships both stamps as the payload.
The parent proves:

```
entry    <= token_ms                  the parent had already committed to this
                                      poll before the peer's clock started
write_ms >= token_ms + delay_ms       the peer really waited
return   >= write_ms                  the poll did not return before the write
```

Together those put the whole of the peer's delay strictly inside the poll, so
the reported `park_ms = write_ms - entry` is at least `delay_ms`. `entry >
token_ms` is a **precondition, not a verdict**: the payload has already been
consumed, so the trial is retried with the delay doubled (80, 160, 320, 640,
1280 ms, all far inside the 5 s poll timeout) and only an exhausted budget
fails. That is the fix for revision 1's defect — parent-side scheduling latency
is not a kernel fault and must not be reported as one.

Two smaller repairs rode along:

* `IDLE_MIN_ELAPSED_MS` was a hand-picked 80 against a 120 ms timeout. It is now
  derived from the timeout itself (a poll that returns 0 consumed its whole
  timeout), with one millisecond of give for the truncation of the two stamps.
  Strictly stronger than what it replaced.
* `monotonic_ms()` folded a clock error onto `0`, a legal reading — a kernel
  fault could arrive disguised as a test-timing artifact. It now fails with
  `clock_error` naming the site that asked.

### The mutations

Each applied singly to otherwise-clean branch bytes, built, and run through a
real gate.

A is defect 1's proof: the kept fix is load-bearing, and the oracle is the
caller that reaches it. C and D are the instrument's own proof: stage 3 detects
a lost wake, and refuses a trial in which readiness preceded the poll.

Mutation D is why revision 3 has a third bound. Against the two-bound version it
**PASSED**, reporting `park_ms=0`: `entry <= write_ms` and `returned >=
write_ms` were both satisfied because the two stamps landed in the same
truncated millisecond. A bound a degenerate run satisfies is not a bound, and
only mutating the oracle found it.

Mutation D also found a defect in the build harness. `userspace/programs/build.sh`
pipes both cargo invocations into `while read line`, so the pipeline's status is
the loop's — always 0 — and the script printed "build successful" while leaving
the PREVIOUS ELFs installed. An uncompilable mutation silently reused the last
good binary and "passed". Both pipelines now run under `set -o pipefail` and
abort with the failing stage named; proven by appending `fn broken( {` to a
source file, which now exits 1 with `ERROR: userspace build FAILED` where it
previously exited 0.

## 5. Defect 2: the scheduler reorder, reverted in round 2 and reinstated in round 3

### What round 2 got wrong

Round 2 reverted the reorder because the mutation offered as proof did not
separate: the kernel *without* the reorder passed the oracle 2/2 on beast's KVM
host, and the red the mutation was credited with (`late_vacuous`) is the same
string an unmutated branch-head boot produced there. That reasoning was sound.
The mistake was what round 2 concluded from the A/B battery it then ran.

The battery counted **emitted verdicts and gate results**. It did not count
threads that were *silenced*. Applying the strand measurement — a thread whose
last `Saved kernel context for blocked thread N` is followed by no
`Restored kernel context for thread N`, and which never exited — to round 2's
own preserved serials gives:

| round-2 battery, re-read | arm A — reorder OUT (shipped) | arm B — reorder IN | arm M — pristine main |
|---|---|---|---|
| `poll_tcp_oracle` saved blocked and never restored | **4/8** | **0/8** | n/a (no oracle) |
| oracle verdict emitted at all | 4/8 | **8/8**, all PASS | n/a |
| `clonevm_exec_test` stranded | 2/8 | 0/8 | 3/8 |

So round 2's "zero oracle failures in sixteen beast x86 boots" counted four
silent non-verdicts on the shipping arm as clean passes. That is the same error
this branch blocked on in the opposite direction one round earlier: there, FAILs
outside the census; here, hangs outside the census. The gate could not see it
because every check it had reads markers, and a stranded thread emits none.
`scripts/x86-strand-census.sh` now exists for exactly that reason and is wired
into `scripts/x86-gate-verdict.sh` ahead of the completion check.

### Round 3: proved at scale, at the merge-candidate bytes

Interleaved A/B on beast `breenix-x86` (KVM, `-cpu host`,
`testing,external_test_bins`, `BREENIX_NET_MODE=none`) at kernel commit
`efe08b17`. Both kernels were built once from that commit and their UEFI images
kept, so the arms differ **only** by `kernel/src/task/scheduler.rs`; boots
alternate CAND, OUT, CAND, OUT so host order effects cannot favour either arm —
round 2's arms ran as sequential blocks, which review's N6 correctly flagged as
unmodelled. Both builds reported 0 warnings. Per-boot outcomes for all 40 boots
are in `AB-2026-08-29-round3.md`.

| | CAND — reorder IN (the merge candidate) | OUT — same tree, reorder reverted |
|---|---|---|
| boots | 24 | 16 |
| `poll_tcp_oracle` saved blocked and never restored | **0/24** | **12/16** |
| any thread stranded at all | **0/24** | 13/16 |
| oracle verdict emitted | **24/24** | 4/16 |
| `TEST_TALLY` emitted | 24/24 | 3/16 |
| kernel panic or fault record | **0/24** | **0/16** |

One-sided Fisher on 0/24 against 12/16 is **3.3e-7**. It is not a bare p-value:
the mechanism is the one this branch wrote down and filed as **#691**. On x86
there is no `requeue_thread_after_save()` caller and no `DEFERRED_REQUEUE`, so
when `wake_expired_timers()` runs *after* the outgoing-thread disposition it
takes the `is_current_on_any_cpu` arm — publishing `Ready`, consuming the
thread's only timer-heap entry, and deliberately not enqueueing, on the
documented assumption that the running thread will notice after its halt or that
`DEFERRED_REQUEUE` will catch it. Neither holds for a thread being switched out
in that very call, and neither exists on x86 at all. The thread is left `Ready`,
in no queue, with no heap entry. Waking first removes the read-before-write
inversion and the existing enqueue in the disposition block takes ownership.
The wake path's SMP guard is untouched, byte for byte.

### Panic hunt

Round 1 was suspected of a near-null page fault. Across all 24 merge-candidate
boots and all 16 reverted-arm boots — 40 in total, on the arm's own preserved
serials — there is **not one** panic, page fault, double fault, general
protection fault, `FATAL_REGS` record, `Accessed Address` line or allocator
`Freed node aliases existing hole` line. The reorder does not fault. Every red
in this battery is a stall, an oracle verdict, or a tally failure.

### The reinstated hunk

Byte-identical to round 1's shape (`07ba27c0`), and the rest of
`scheduler.rs` is byte-identical to `main`: the diff against `main` is two
hunks in `Scheduler::schedule()` — one adding the call before the disposition
block, one removing it from after.

## 9. Honest statement about #568

**Not closed.** Three shapes have been separated inside one issue, and two of
them are fixed:

* **defect 1 — the hard wedge.** Both `sys_poll` blocking waits hand-inlined the
  halt and the x86 half was a bare `hlt` with `IF=0`. Fixed; re-derived
  independently by review; mutation A reproduces the original wedge at branch
  HEAD with the recorded last kernel line.
* **defect 2 — the strand.** The polling thread was published `Ready`, taken off
  the timer heap, enqueued nowhere, and never scheduled again. Fixed by the
  `Scheduler::schedule()` reorder; **0/24 against 12/16**, p = 3.3e-7, with the
  mechanism (#691) named and the wake path's SMP guard untouched.
* **the residual lost wake.** `poll()` still returns `ready=0 revents=0x0000`
  after its full timeout in about 1 boot in 24 on the beast KVM battery, with the
  peer having run and exited cleanly. Filed as **#693**. #568 stays open until
  that is understood. **That 1-in-24 is the bespoke battery's rate, not the
  shipping gate's**: on `run-x86-boot-tests.sh` under TCG the same bytes produced
  `FAIL:late_lost_wake` on 20 of 30 boots, and neither number is discriminated
  against TCG starvation because the verdict does not carry the peer's exit
  status or stamps. See §10.

What round 2 said here — "defect 2's existence is unproven, and no issue is
filed on it" — was wrong, and it was wrong against evidence round 2 itself
preserved. The correction is recorded rather than quietly overwritten because
the failure mode it illustrates is the durable lesson: **a check that reads
markers cannot see a thread that has been silenced, and counting a silent
non-verdict as a pass converts a hang into a green boot.** That is now a gate
check (`scripts/x86-strand-census.sh`), not a habit.


## 10. Landing: the oracle is un-wired on x86 (#697)

This section is the correction §9 needs. §9's "about 1 boot in 24" is the rate
on the bespoke beast KVM battery. It is **not** the rate on the gate that
actually ships, and until now the in-repo record carried only the optimistic
number.

### The default x86 gate, measured

`docker/qemu/run-x86-boot-tests.sh` is byte-identical to main on this branch. It
was run 30 times at the merge-candidate bytes on beast `breenix-x86` under TCG.
The per-boot table, with the census derivation recomputed boot by boot, is
preserved in-repo at
`serials/x86-default-gate-soak-census-20260829.md`. The numbers are:

| what | number |
|---|---|
| gate result | **FAIL 30/30** |
| oracle verdict `FAIL:late_lost_wake` | **20/30** |
| oracle verdict `FAIL:late_window_missed` | 6/30 (this is #694) |
| oracle verdict `PASS` | 4/30 |
| `loopback_wake_test` red (#692) | 0/30 |

The 30/30 gate failure is fully explained and is the oracle's, not the kernel's:

```
CENSUS_REMOVED = 6 + attempts        (run-x86-boot-tests.sh:472 requires removed == 6)
```

exact on 30 of 30 boots (`removed` histogram 7->4, 8->16, 9->1, 10->2, 11->7),
because `stage_late` `fork()`s a peer **inside** its
retry ladder, so every attempt adds one production row reaped through the live
`complete_wait` path -- the quantity `PRODUCTION_REAPED_ROWS=4` pins. The
minimum the oracle can emit is `removed=7`, so there was no configuration in
which it passed. That is the whole of #696, which is closed as explained.

The 26/30 oracle FAILs are, as they stand, **undiscriminated**: the
`late_lost_wake` arm `waitpid()`s the peer and reports without reading the
peer's exit status or its `token_ms`/`write_ms` stamps, so it cannot separate
"the kernel lost the wake" from "the peer never got scheduled to write" under
TCG. Neither the 20/30 nor §9's 1/24 can be read as a count of kernel defects
until that changes.

### What landed

`poll_tcp_oracle` is **removed from x86** at landing: the `RING3_SMOKE` roster
entry in `kernel/src/main.rs` and the `[POLL_TCP_ORACLE:` marker assertion in
`docker/qemu/run-boot-parallel.sh` are both gone, each replaced by a comment
citing **#697**. With the oracle gone the census pins return to main's shape:
`run-x86-boot-tests.sh` emits `removed=6` and passes 3/3 at the landing bytes.

Nothing else was weakened to achieve that. No tolerance was widened, no
assertion was relaxed, and `scripts/x86-gate-allowlist.txt` is still empty.
`scripts/x86-strand-census.sh` and its wiring into `scripts/x86-gate-verdict.sh`
stay: the census is what makes a silenced thread visible to the x86 gate at all,
and it is what the §5 evidence is computed from.

**The aarch64 wiring is untouched, byte for byte.** The `init.rs` launch is
still `#[cfg(target_arch = "aarch64")]`, all eight aarch64 gates still pin the
marker's presence and its FAIL arm, and the service-sequence gate is 50/50 GREEN
with `UNATTRIBUTED=0` and the marker present and PASS in 50/50 preserved
serials.

### What this costs, stated plainly

The x86 side of #568 is now **unobserved, not fixed**. Defect 1 and defect 2 are
fixed on x86 and stay fixed -- the §5 A/B evidence is computed from the strand
census, not from the oracle's verdict, so it does not depend on the oracle being
wired. What is no longer watched on x86 is the residual: a lost wake there would
now go unnoticed by any x86 gate. #697 carries the repair (deterministic fork
count, census pin derived from the workload, peer exit status and stamps in the
failure string) and its acceptance is a 30-boot `run-x86-boot-tests.sh` soak
green at the repaired bytes, with the KVM A/B re-run at those same bytes.

that "#568 is closed by the same change that wires this gate". That is false --

byte-identical to the bytes the 50/50 green run was measured at; it should be
