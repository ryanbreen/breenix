## 2. The instrument

`userspace/programs/src/poll_tcp_oracle.rs` runs on every boot of both
architectures — from `init` on aarch64, from `RING3_SMOKE` on x86. It exists
because nothing else in any profile blocks in `poll()` on an
`FdKind::TcpConnection`: `libbreenix`'s receive deadline was rewritten to avoid
that path (citing #568 by number) and `poll_test` only polls a *listener* with
`timeout=0`. Three stages:

| stage | what it drives | what it must show |
|---|---|---|
| `idle` | block on a connected fd with nothing to read, 120 ms timeout | returns 0 having consumed the whole timeout |
| `armed` | data already pending at the call | POLLIN from the entry scan |
| `late` | a forked peer publishes readiness *while the poller is parked* | POLLIN, delivered by the write and not by the clock |

Verdict marker `[POLL_TCP_ORACLE:PASS|FAIL:...]`, emitted twice because console
output interleaves at byte granularity.

## 3. Stage 3's bound, and the two ways it was wrong

Stage 3 is the only stage a stale snapshot cannot pass by luck, so its
anti-vacuity bound is the whole instrument. It took three revisions.

**Revision 1 (round 1) — measured the wrong two clocks.** It started the
parent's stopwatch at the parent's `poll()` entry and compared the elapsed time
against `LATE_WRITE_DELAY_MS`, which is the *child's* sleep. The child forks
first, so its 80 ms starts before the parent reaches `poll()`; the parent's
elapsed is `80 - (fork-return-to-poll latency)` and can only approach the bound
from below. The bound sat on top of its own distribution. In round 1's own
50-boot aarch64 gate the mode of `late_ms` was exactly 80 and four boots landed
under it (66, 71, 78, 79) — about 8% of healthy boots reddened by construction,
with the same string appearing on unmutated x86 boots.

**Revision 2 — right idea, wrong contents.** A shared absolute `write_deadline`
computed before the fork, with the child sleeping *until* it. Correct in
principle and unusable in practice: process creation was inside the window the
parent had to beat, and on beast's KVM x86 boot with 24 live userspace processes
the parent could not reach `poll()` inside 80, 160, 240 or 320 ms. Every trial
reported `late_parent_never_parked ... last_slack_ms=0`
(`serials/x86-forkwindow-precondition-miss-*-20260829.txt`).

**Revision 3 (shipped) — the peer measures, and proves it waited.** The parent
forks, hands the child a one-byte readiness token over the *reverse* direction
of the same connection (so it cannot make the polled fd readable), and only then
stamps `entry` and polls. Process creation is spent before either clock starts.
The child stamps the moment it receives the token, waits to `token_ms +
delay_ms` on its own clock, stamps again, and ships both stamps as the payload.
The parent proves:

```
entry    <= token_ms                  the parent had already committed to this
                                      poll before the peer's clock started
write_ms >= token_ms + delay_ms       the peer really waited
return   >= write_ms                  the poll did not return before the write
```

Together those put the whole of the peer's delay strictly inside the poll, so
the reported `park_ms = write_ms - entry` is at least `delay_ms`. `entry >
token_ms` is a **precondition, not a verdict**: the payload has already been
consumed, so the trial is retried with the delay doubled (80, 160, 320, 640,
1280 ms, all far inside the 5 s poll timeout) and only an exhausted budget
fails. That is the fix for revision 1's defect — parent-side scheduling latency
is not a kernel fault and must not be reported as one.

Two smaller repairs rode along:

* `IDLE_MIN_ELAPSED_MS` was a hand-picked 80 against a 120 ms timeout. It is now
  derived from the timeout itself (a poll that returns 0 consumed its whole
  timeout), with one millisecond of give for the truncation of the two stamps.
  Strictly stronger than what it replaced.
* `monotonic_ms()` folded a clock error onto `0`, a legal reading — a kernel
  fault could arrive disguised as a test-timing artifact. It now fails with
  `clock_error` naming the site that asked.

### The mutations

Each applied singly to otherwise-clean branch bytes, built, and run through a
real gate.

| mutation | what it breaks | observed |
|---|---|---|
| **A** — reintroduce the pre-#568 hand-inlined halt at both `sys_poll` blocking waits (the bare `hlt` with `IF=0`) | defect 1's fix | **hard wedge, 2/2** on beast KVM x86. The guest stops dead with the last kernel line `TCP: Accepted connection on fd 3, new fd 5` — the instruction before the oracle's first blocking `poll()`, and #568's recorded signature exactly. No oracle marker, gate FAIL (`serials/x86-mutation-A-bare-hlt-wedge-kernel-20260829.txt`) |
| **C** — the peer never sends | readiness is never published | `FAIL:late_lost_wake:ready=0 revents=0x0000 elapsed_ms=5002 delay_ms=80`; gate **FAILED** (`serials/aarch64-mutation-C-peer-never-writes-20260829.txt`) |
| **D** — the peer publishes immediately, ignoring the token and the delay | stage 3 degenerates into a second copy of stage 2 | `FAIL:late_peer_short_wait:token_ms=10084 write_ms=10084 waited_ms=0 delay_ms=80`; gate **FAILED** (`serials/aarch64-mutation-D-peer-writes-immediately-20260829.txt`) |

A is defect 1's proof: the kept fix is load-bearing, and the oracle is the
caller that reaches it. C and D are the instrument's own proof: stage 3 detects
a lost wake, and refuses a trial in which readiness preceded the poll.

Mutation D is why revision 3 has a third bound. Against the two-bound version it
**PASSED**, reporting `park_ms=0`: `entry <= write_ms` and `returned >=
write_ms` were both satisfied because the two stamps landed in the same
truncated millisecond. A bound a degenerate run satisfies is not a bound, and
only mutating the oracle found it.

Mutation D also found a defect in the build harness. `userspace/programs/build.sh`
pipes both cargo invocations into `while read line`, so the pipeline's status is
the loop's — always 0 — and the script printed "build successful" while leaving
the PREVIOUS ELFs installed. An uncompilable mutation silently reused the last
good binary and "passed". Both pipelines now run under `set -o pipefail` and
abort with the failing stage named; proven by appending `fn broken( {` to a
source file, which now exits 1 with `ERROR: userspace build FAILED` where it
previously exited 0.

## 4. The oracle's verdict is now gate-failing on both architectures

On x86 a FAIL was already gate-failing through the empty exit-code allowlist —
that is how review caught it. On aarch64 nothing asserted either the marker or
the exit status, so the round-1 run cited as "50/50 GREEN, UNATTRIBUTED=0"
contained four boots that printed `[POLL_TCP_ORACLE:FAIL` and logged
`poll_tcp_oracle exited pid=95 code=1`, invisibly.

`POLL_TCP_ORACLE` is now pinned everywhere its #575 peer `BLOCK_EINTR_ORACLE` is
pinned — all eight aarch64 scripts:

| script | how |
|---|---|
| `run-aarch64-full-test.sh` | new Phase 1a1, marker + no-FAIL |
| `run-aarch64-service-sequence-gate.sh` | classifier arm (FAIL and marker-absent), plus an early-break so a failing boot is not left to the wall clock |
| `run-aarch64-boot-test-strict.sh` | marker + no-FAIL |
| `run-aarch64-boot-test-native.sh` | marker + no-FAIL |
| `run-aarch64-prod-profile-boot-test.sh` | marker count >= 1, failure count == 0 |
| `run-aarch64-percpu-stack-custody-gate.sh` | wait-loop term + marker + no-FAIL |
| `run-aarch64-refusal-drain-gate.sh` | wait-loop term + marker + no-FAIL |
| `run-aarch64-arma609-arm.sh` | `ORACLE_FAIL` classifier arm + early break |

Every site pins the **pair** — presence AND absence-of-FAIL — because a marker
check alone passes a boot whose verdict was FAIL, and a FAIL grep alone passes a
boot where the program never started.

In the service-sequence gate a failure is scored `UNATTRIBUTED` rather than given
a bucket of its own: #568 is closed by the same change that wires the gate, so
there is no open defect for a failure here to be attributed *to*. `UNATTRIBUTED`
is gate-failing under R52, and the reason string carries the verdict line
verbatim. Both mutations above confirm the arm fires.

On x86 the FAIL was gate-failing but a boot in which the oracle never ran was
not — the exit floor is a `>=` bound, so one missing program hides under it.
`run-boot-parallel.sh` now pins the marker's presence before scoring the verdict.

Every one of these adds a failure condition. None removes one, none raises a
bound, none weakens an existing assertion.

## 5. Defect 2: the scheduler reorder is reverted, and the A/B says why

Review's re-run of round 1's Mutation B did not reproduce: the kernel *without*
the reorder passed the oracle 2/2 on beast's KVM host, and the red the mutation
was credited with (`late_vacuous`) is the same string an unmutated branch-head
boot produced on that host — revision 1's own false red. A mutation whose red
appears without it and whose green appears with it separates nothing.

With the reorder reverted, an A/B battery on beast (`breenix-x86`, KVM, host
CPU, `testing,external_test_bins`, 8 boots per arm, branch @ `59446903`, arms
differing only by that one hunk) settles what the reorder does and does not do:

A third arm, **M**, is pristine `main` @ `6d0d2ac5` on the same host with the
same driver, so both branch arms are read against a baseline rather than against
each other alone.

| | arm A — reorder OUT | arm B — reorder IN | arm M — pristine main |
|---|---|---|---|
| gate PASS | 2/8 | 6/8 | 5/8 |
| `loopback_wake_test_child:15, loopback_wake_test:1` | **1/8** | **2/8** | **0/8** |
| `USERSPACE TEST COMPLETE absent` (boot did not finish) | 5/8 | 0/8 | **3/8** |
| `[POLL_TCP_ORACLE:FAIL` | **0/8** | **0/8** | n/a (no oracle on main) |
| kernel panic / page fault | **0/8** | **0/8** | **0/8** |

**The reorder does not cause the loopback red.** It occurs on both sides, and
the two preserved serials carry a byte-identical tally line —
`TEST_TALLY: exited=21 nonzero=2 failed=[loopback_wake_test_child:15,loopback_wake_test:1]`
(`serials/x86-loopback-red-armA-reorder-out-kernel-20260829.txt`,
`serials/x86-loopback-red-armB-reorder-in-kernel-20260829.txt`).

**No page-fault panic was observed at all** — not in arm A, not in arm B, not in
arm M, in twenty-four boots. There is no panic for the reorder to cause. Every
non-oracle red in the battery is a *stall*, not a fault: the boot-did-not-finish
serials end with the idle thread alone and an empty ready queue, with no
exception record (`serials/x86-boot-did-not-finish-armA-kernel-20260829.txt`,
`serials/x86-boot-did-not-finish-MAIN-kernel-20260829.txt`).

**The boot-did-not-finish stall is main's.** It is 3/8 on pristine main, 5/8 on
arm A and 0/8 on arm B — a spread that runs the *opposite* way from any claim
that the reorder is harmful, on a shape that main produces on its own. Review's
independent 4-boot main baseline on the same host saw it too.

## 9. Honest statement about defect 2

The reorder is out and the repaired oracle is clean without it: 20/20 aarch64
boots at the shipped bytes and zero oracle failures in sixteen beast x86 boots
across both A/B arms. On that evidence **defect 2's existence is unproven**, and
no issue is filed on it — an unproven mechanism does not get an issue number. The
round-1 observation that motivated it — "blocked once and never ran again" —
cannot be distinguished from revision 1's own mis-derived bound firing, and the
mutation offered as proof does not separate. No issue is filed on an unproven
mechanism; the observation is recorded here and on #568 so that if the shape
returns, this is where the next investigator starts.

What the reorder would have changed is real and is written down for whoever
revisits it: `wake_expired_timers()`'s `is_current_on_any_cpu` arm publishes
`Ready`, consumes the timer-heap entry, and deliberately does not enqueue, on
the assumption that the running thread notices after its halt or that
`DEFERRED_REQUEUE` catches it — and `DEFERRED_REQUEUE` together with every
`requeue_thread_after_save()` caller is aarch64-only. That asymmetry is filed
(§8). It is a latent structural gap, not a demonstrated live defect, and it is
not what this branch fixes.
