# R113 red attribution — L1 boot_01 and boot_03

Branch `exp/772-r113-oracle`, `main @ bfbb7575` (PR #777 merge) plus the R113
instrumentation (`a715d0f8` .. `bd91d2a2`; `bd91d2a2` adds only docs/serials --
`git diff --stat a715d0f8 bd91d2a2` touches no `kernel/`, `userspace/`,
`scripts/`, or `docker/` path). Task: attribute the two L1 (`testing,
external_test_bins`) reds from the R113 measure slot -- boot_01
(`loopback_wake_test_child`) and boot_03 (`clock_gettime_test`) -- against
filed issues, and determine whether the branch's own instrumentation is a
contributing cause, using a 5-boot-per-tree beast comparison against main.

## Method

1. Read the committed serials for both red boots
   (`docs/planning/green-program/sockets/serials/772-r113/L1/boot_0{1,3}/`),
   extracted each failing process's exact exit line and, for boot_03, the
   userspace test's own per-assertion diagnostic (the source already prints
   which of its 5 sub-tests failed).
2. Traced each `exit(N)` back to the userspace source (`grep`) to know exactly
   which assertion each exit code encodes, rather than guessing from the
   number alone.
3. Searched `gh issue list`/`gh issue view` for exact signature matches (the
   `TEST_TALLY: ... failed=[...]` string, the process:code pair, the assertion
   text) rather than trusting the task brief's candidate issue numbers at face
   value -- one of the two named candidates (#764) turned out not to apply, on
   its own text.
4. Ran a beast A/B (branch vs. `main @ bfbb7575`, both `testing,
   external_test_bins`, 5 boots each) to check whether the branch's
   instrumentation elevates the x86 red rate.

## Boot_01 -- `loopback_wake_test_child`

`docs/planning/green-program/sockets/serials/772-r113/L1/boot_01/`:

```
verdict.txt:       x86 userspace gate: FAIL - failing process is not allowlisted: loopback_wake_test_child
serial_kernel.txt:2936  Process 17 'loopback_wake_test_child_17' (thread 27) exited with code 15
serial_kernel.txt:5114  TEST_TALLY: exited=22 nonzero=2 failed=[loopback_wake_test_child:15,loopback_wake_test:1]
serial_user.txt:774    LOOPBACK_WAKE_TEST: reader_stamps ... lat=1118
serial_user.txt:857    LOOPBACK_WAKE_TEST: reader_eof_stamps ready=27530 eof=31555 eof_wait=4025
```

`exit(15)` is `userspace/programs/src/loopback_wake_test.rs:225-226`:

```rust
if eof_wait_ms > EOF_WAKE_BOUND_MS {
    std_process::exit(15);
}
```

with `EOF_WAKE_BOUND_MS: u64 = 4000` (`:55`). The reader's own stamp line
gives `eof_wait=4025` -- 25 ms over a 4000 ms bound. This is the *EOF-wait*
wake-latency bound, not the *data-path* one (`exit(13)`, `DATA_WAKE_BOUND_MS`,
a different check at `:192`).

### Attribution: #692

<!-- claim-lint:ok: verbatim quote from `gh issue view 692 --comments`, issue #692 -->
**ATTRIBUTED to #692** by exact `TEST_TALLY` signature match. #692's own body
and comments cite `failed=[loopback_wake_test_child:15,loopback_wake_test:1]`
verbatim (its most recent comment: *"the failing tally is stable in shape
across all nine occurrences -- `loopback_wake_test_child:15` ... plus
`loopback_wake_test:1`, one child of several while its siblings exit 0"*) --
byte-identical to our boot_01 tally string, modulo `exited=22` vs. the issue's
`exited=21`/`exited=25` (more test binaries have been added to the roster
since). #692's own listed per-process exits from its original repro also read
`exited with code 15` (positive, not `-15`), matching our boot_01's `exited
with code 15`, so the two are the same assertion, not two different bugs that
happen to share a number.

**Not #764**, despite the task brief naming it as "the loopback_wake RCA."
#764's own opening paragraph draws the distinction explicitly: it documents
`exit(13)` (the *data-path* bound) and says in its own words this is *"a
distinct signature from #692 (exit 15)."* Our boot_01 is the exit-15 case, so
#764 does not apply here -- #692 does, and #764 says as much about itself.

**Caveat carried from #692, disclosed, not resolved here.** #692's own theory
for *why* the wake-path weakness surfaces was a specific added workload
(`poll_tcp_oracle`'s second concurrent loopback-TCP connection, wired only on
a since-reverted branch). That trigger is confirmed absent from this tree --
`kernel/src/main.rs:1503-1508` still reads *"poll_tcp_oracle ... is
deliberately NOT launched here [on x86]"* -- so boot_01's specific trigger is
not #692's originally-theorized one. #692 is still the correct attribution for
the *symptom* (same process, same exit code, same paired tally, an unexplained
signal/exit-15 teardown of one `loopback_wake_test_child` among several, an
issue #692 itself says stays "unexplained" and is left deliberately
un-allowlisted). What differs is that this occurrence's proximate trigger is
not established, which is consistent with #692's own status: open, "the
underlying weakness in the loopback wake path is untouched."

## Boot_03 -- `clock_gettime_test`

`docs/planning/green-program/sockets/serials/772-r113/L1/boot_03/`:

```
verdict.txt:       x86 userspace gate: FAIL - failing process is not allowlisted: clock_gettime_test
serial_kernel.txt:2518  Process 4 'clock_gettime_test' (thread 14) exited with code 1
serial_kernel.txt:4978  TEST_TALLY: exited=22 nonzero=1 failed=[clock_gettime_test:1]
serial_kernel.txt:442-445  Calibrating TSC frequency using PIT... TSC calibration complete: 2406 MHz
serial_user.txt:744-748   Test 3: Sub-millisecond precision
                           Elapsed: 2766335497 ns
                           FAIL: Elapsed time >= 1ms (possible PIT fallback)
serial_user.txt:806-808   === Test Summary === Passed: 4/5 Failed: 1/5
                           USERSPACE CLOCK_GETTIME: FAIL
```

The test source (`userspace/programs/src/clock_gettime_test.rs:34-63`)
already prints, per-assertion, which of its 5 tests failed -- this was NOT
added by this round, it is pre-existing in the tree. Test 3 issues two
back-to-back `clock_gettime(CLOCK_MONOTONIC)` calls with no work between them
and asserts the elapsed gap is under 1 ms ("TSC active"); a gap of 2.766
*seconds* fails it.

### Attribution: #631 (signature) + #766 (mechanism); #767 explicitly ruled out

**ATTRIBUTED to #631** by exact gate-failure signature: #631's own reproduction
reads `x86 userspace gate: FAIL - failing process is not allowlisted:
clock_gettime_test` / `TEST_TALLY: exited=19 nonzero=1
failed=[clock_gettime_test:1]` -- the same single-process, exit-1 tally shape
as boot_03's (`exited=22` vs. `19`, again just roster growth since). #631 was
filed with an evidence gap by its own admission -- *"the boot log alone does
not say which [assertion failed], which is the first thing to fix"* -- because
no serial was preserved for its own occurrence. Boot_03's serial closes that
gap: it is Test 3, the sub-millisecond-precision check, failing on an
elapsed-time gap between two immediately-sequential syscalls.

**#767 is explicitly ruled out for this occurrence.** The task brief named
#767 (x86 `get_monotonic_time()` returns 200 Hz PIT ticks scaled as if they
were ms, a 5x error) as a candidate. #767's own text says the bug lives
specifically in the PIT-*fallback* branch of `get_monotonic_time_ns()`, taken
only when TSC calibration fails, and states outright: *"No current gate red
has been attributed to this. It is derived from the code and its constants,
not from an observed failure."* Boot_03's own serial shows `TSC calibration
complete: 2406 MHz` at lines 442-445 -- TSC calibration succeeded on this
boot, so `get_monotonic_time_ns()` took the TSC branch, not the PIT-fallback
branch #767's defect lives in. A 5x scale error on a TSC-timed gap this small
would read as a few microseconds, not 2.77 seconds, so the magnitude also
does not fit #767's mechanism. **#767 does not apply to boot_03.**

**Mechanism: #766.** A 2.77 s gap between two syscalls with no work between
them (Test 3 issues the two `clock_gettime` calls back to back,
`clock_gettime_test.rs:35-39`), on a boot that otherwise ran to `USERSPACE
TEST COMPLETE` with 21 other
processes exiting cleanly, is not a clock defect -- it is the calling thread
getting preempted between the two `clock_gettime` calls and not being
redispatched for a while. #766 (open, filed from the #693 RCA) measures
exactly this quantity on this same x86 profile: one ready queue
(`MAX_CPUS=1` on x86), a 50 ms slice, wake re-enqueued at the tail with no
lateness ordering, so "wake at T" means "run at T plus a full round-robin
over everything runnable" -- measured p90 2592 ms, max 10318 ms over 324
trials. Boot_03's 2766 ms sits inside that measured distribution, between the
p90 and the max. clock_gettime_test's Test 3 is not exercising a novel
failure mode; it is a second, more sensitive oracle for the same
already-filed round-robin latency #766 documents (a bare two-syscall gap has
no slack at all, where #766's own sleep-based oracle needs the overrun to
exceed whatever grace the sleeper's own deadline check allows).

## Beast A/B: does the R113 instrumentation produce these reds?

`ssh beast` / `sudo -n incus exec breenix-x86`, container `/root/breenix-r113`
(fetched to branch tip `bd91d2a2`) vs. a fresh scratch clone
`/root/breenix-r113-main` at `main @ bfbb7575` (detached), both built
`--release --features testing,external_test_bins`, both `rust-fork` symlinked
to `/root/breenix/rust-fork-real`. Driver: `scripts/772-dispatch-boot.sh`
(unmodified), 5 boots per tree. **Run sequentially, not concurrently**: the
script's QEMU opens its gdbstub on the fixed default port (`-s` ==
`tcp::1234`), so two instances of it collide on that port if run at once --
peak concurrency observed was 1 QEMU, under the <=2 cap.

| tree | boots | PASS | FAIL |
|---|---|---|---|
| branch (`exp/772-r113-oracle`) | 5 | 4 | 1 (boot_05) |
| main (`bfbb7575`) | 5 | 3 | 2 (boot_02, boot_04) |

None of the 10 boots reproduced either of the two attributed signatures
(`loopback_wake_test_child:15` or `clock_gettime_test:1`) -- unsurprising
given #692's and #631's own measured base rates (double-digit percent only
under a specific added workload for #692; 1/70 for #631). All three A/B reds
share a **third, distinct, already-filed** signature instead:

```
TEST_TALLY: exited=22 nonzero=1 failed=[/usr/local/test/bin/clon:1]
Process 15 '/usr/local/test/bin/clonevm_exec_test' (thread 25) exited with code 1
```

(`clonevm_exec_test` renames itself to its full exec path, truncated by the
kernel's fixed-width process-name field to `/usr/local/test/bin/clon`.) This
is the well-documented `clonevm_exec_test` exit-1 flake family --
already filed and open as #695/#700/#738 (and previously as the now-closed
#608) -- not a new defect and not either red under investigation. It is noted
here only because the A/B surfaced it, not chased further; out of this
round's scope.

**Reading:** main -- zero R113 code, zero instrumentation -- reds at 2/5
(40%), the *same or a higher* rate than the branch's 1/5 (20%), on this same
x86/KVM profile, and the shared failure mode on both arms is a pre-existing,
independently-filed flake unrelated to either target red. This is evidence
against the branch's instrumentation elevating the x86 red rate: if the one
relaxed atomic add per park (`Thread::wait_loop_iters`, bumped inside
`arch_halt_with_interrupts()`) or the extra GS-relative store/load at the
dispatch mark write were perturbing timing enough to produce spurious reds,
the uninstrumented baseline should show *fewer* reds than the branch, not
more. It does not. Combined with the fact that neither target red's mechanism
(a userspace millisecond-scale timing bound; a scheduler round-robin
wake-dispatch delay) has any dependency on a counter or mark-word field no
control-flow anywhere reads (per the branch's own R113 instrument notes),
there is no basis to implicate the instrumentation.

Failing serials preserved in full at
`docs/planning/green-program/sockets/serials/772-r113/ab-verify/branch/boot_05/serial_kernel.txt`
(and its sibling `serial_user.txt` in the same directory),
`.../main/boot_02/serial_kernel.txt`, `.../main/boot_04/serial_kernel.txt`;
driver logs for 10 of 10 boots are at
`docs/planning/green-program/sockets/serials/772-r113/ab-verify/branch_boot_01.driver.txt`
through `.../main_boot_05.driver.txt` for the full pass/fail record.

## Verdict

| red | signature | attribution |
|---|---|---|
| L1 boot_01, `loopback_wake_test_child` | `exit(15)`, `eof_wait_ms=4025 > EOF_WAKE_BOUND_MS=4000` | **ATTRIBUTED to #692** (not #764, which documents itself as the distinct exit-13 signature) |
| L1 boot_03, `clock_gettime_test` | `exit(1)`, Test 3 sub-ms precision, `elapsed_ns=2766335497`, TSC calibrated | **ATTRIBUTED to #631** (signature; assertion identity newly established) and **#766** (mechanism; TSC-calibrated rules out #767) |

Both reds are pre-existing, independently-filed, open x86 flakes. Neither is
explained by, nor was reproduced alongside evidence implicating, the R113
instrumentation; the beast A/B shows main -- at `bfbb7575`, the commit before
any R113 change -- producing the same class of red at an equal-or-higher rate
(2/5 vs. the branch's 1/5).
