## Method

x86-only, on beast, scratch clone `/root/breenix-772diag` on the
`breenix-x86` Incus VM, fetched and checked out at
`origin/fix/772-no-progress-dispatch @ 020c3c40`. Userspace ELFs and both
test disk images (`test_binaries.img`, `ext2.img`) were built once, shared
across the 4 feature arms below (no arm's feature set touches `userspace/`).

Four feature arms, 10 boots each, `--release --features testing,external_test_bins[,...]`:

| arm | extra features | refusal | dispatch logs |
|---|---|---|---|
| A0 | `no_progress_refusal_disabled` | OFF | ON |
| A1 | (no extra feature beyond the base two) | ON | ON |
| B0 | `no_progress_refusal_disabled,quiet_dispatch_log` | OFF | OFF |
| B1 | `quiet_dispatch_log` | ON | OFF |

Each boot ran through `scripts/772-dispatch-boot.sh`: the guest is launched
with the QEMU gdbstub open (`-s`), the driver polls the boot's own serial
output for `USERSPACE TEST COMPLETE` + `TEST_TALLY:`, connects GDB **while
the guest is still running** and reads each `DISPATCH_*` counter symbol
present in that boot's own ELF (via `nm`, `772-dispatch-boot.sh:43-44`) out
of the kernel ELF's per-CPU slot 0 (the counter list is not hard-coded — it
is read from `nm` on the just-built binary, so the six `DISPATCH_NOPROGRESS_SAVE_*`
counters this round's per-reason census defines are picked up with no driver
change), only then kills the guest, and scores the boot with the same
`scripts/x86-gate-verdict.sh EXPECTED_EXITS=10` that `run-x86-gate.sh full`
uses. This is a disclosed deviation from running `run-x86-gate.sh` itself:
that script hard-codes `FEATURES=testing,external_test_bins` for full mode
with no per-arm override, does not background the guest, and does not open
the gdbstub, so it cannot produce an out-of-band counter read at all
(`qemu-uefi` does not self-exit via `isa-debug-exit` in this profile — no
line in `kernel/src/main.rs`'s `kernel_main_continue` path writes port
`0xf4`; the
guest runs until `run-x86-gate.sh`'s own `timeout` kills it). The verdict
scoring is identical either way.

**Bug found and fixed in this slot's own harness, disclosed.** The first A0
run backgrounds `timeout 150 qemu-uefi ...` and captures `$!` as `QPID`, then
cleans up with `kill -9 "$QPID"`. `$!` is the PID of `timeout`, not of the
`qemu-system-x86_64` grandchild it execs `qemu-uefi` into launching; `timeout`
does not put its child in a new process group in this non-interactive shell,
and `kill -9` gives `timeout` no chance to forward the signal even when it
would. Boot 1 of the first A0 attempt passed (`verdict_rc=0`), then 9 of the
remaining 9 boots (2-10) failed
immediately with QEMU's own `Failed to get "write" lock` on the shared
`breenix-uefi.img`, because boot 1's `qemu-uefi` and `qemu-system-x86_64`
were both still running, reparented to init. `ps -eo pid,ppid,cmd` run on the
VM at that point (this slot's own terminal output, not re-derived from a
saved file) showed both PIDs, `cmd` lines naming boot 1's own `-serial`
paths, still running after the driver had "finished". Fixed by walking the
process tree from the PID this script started — `pgrep -P` recursively, kill
leaves first — rather than by matching a process name (R84). The two
orphaned PIDs from the first attempt were killed individually by PID
(confirmed via their `cmd` lines naming this scratch clone's own boot-1
output paths) before
re-running the full A0 arm; each of the 4 arms after the fix ran its 10
boots with 0 lock contention.

Counters are read from the GDB dump captured before each guest is killed in
40 of 40 boots this battery ran — 0 boots read a counter from inside the
guest under test, per the task's requirement (`772-dispatch-boot.sh:69-93`
is the only counter-read site any arm's driver invokes).
`no_progress_proxy_pct` (the serial log's "Restored ... / Saved ..."
byte-identical RIP+RSP scan, `scripts/772-dispatch-census.py`, unchanged
from the prior round) is additionally available on the two logs-ON arms and
is used below only as a cross-check on the counter-derived reading, on the
one arm (A0) where both are present.

## Result: Q2 — silencing the logs does NOT collapse the proxy; if anything it rises

| arm | boots (gdb_ok) | proxyCounter % mean (range) | reds (verdict) | unattributed |
|---|---|---|---|---|
| A0 (refusal OFF, logs ON) | 10/10 | 63.7 (60.0-68.7) | 0 | 0 |
| B0 (refusal OFF, logs OFF) | 10/10 | 73.4 (63.9-77.4) | 0 | 0 |
| A1 (refusal ON, logs ON) | 9/10 | 60.8 (55.8-66.1) | 2 | 0 |
| B1 (refusal ON, logs OFF) | 10/10 | 74.2 (68.8-79.4) | 1 | 0 |

Holding the refusal constant and only removing the three log records raises
the counter-derived proxy by **9.7 points** (A0 63.7% → B0 73.4%) and by
**13.4 points** (A1 60.8% → B1 74.2%). Both logs-OFF arms sit *above* both
logs-ON arms; neither logs-OFF arm sits anywhere near collapse. **Answer to
Q2: no.** The masked ~20-30ms logging window that #775 and the spec's §1.5
theorized as the interrupt-storm driver behind the identical-RIP/RSP
dispatch is not what is producing most of this proxy — removing it made the
fraction of kernel-blocked restores that retire no instruction *larger*, not
smaller, while the absolute restore volume fell by more than half (A0 sum
4847 → B0 sum 2099 across the 10-boot arm; the same test suite completes far
more `DISPATCH_KERNEL_RESTORE_TOTAL`-generating episodes per boot when each
one is not paying ~20-30ms of masked serial I/O, which is a real and
separate effect from the proxy rate).

`no_progress_proxy_pct` (the serial scan) reads `null` and
`no_progress_proxy`/`restores_total`/`saved_records` read `0` in 20 of 20
B0/B1 boots, as `quiet_dispatch_log`'s own doc comment
(`kernel/Cargo.toml:161-172`) predicts — the "Saved kernel context for
blocked thread"/"Restored kernel context for thread" lines the scan and the
strand census both key on are compiled out. The counter path is unaffected:
`DISPATCH_SAVE_REASON_KERNEL_BLOCKED_{PREEMPT,MANDATORY}` and the six
`DISPATCH_NOPROGRESS_SAVE_*` counters are wired at the switch-save site
itself, not behind the log macros, so they read in 40 of 40 boots this
battery ran regardless of `quiet_dispatch_log`.

## Result: Q1 — which path produces the pair, and what the refusal actually touches

The per-reason census (Q1's own instrumentation, landed on this branch
before this slot) splits each kernel-blocked no-progress save into the two
arms `check_need_resched_and_switch` can take: `_PREEMPT` (via
`need_resched`, current thread not blocked/terminated — the arm the #772
refusal is conjoined into) and `_MANDATORY` (current thread blocked or
terminated — the arm the refusal is conjoined **out** of, per the spec's own
candidate-A design). Per-arm no-progress **rate** within each sub-population
(`DISPATCH_NOPROGRESS_SAVE_KERNEL_BLOCKED_X / DISPATCH_SAVE_REASON_KERNEL_BLOCKED_X`,
summed over the arm's 10 boots):

| arm | PREEMPT-arm no-progress rate | MANDATORY-arm no-progress rate | MANDATORY share of kernel-blocked no-progress saves |
|---|---|---|---|
| A0 (refusal OFF, logs ON) | 475/659 = 72.1% | 2634/4188 = 62.9% | 2634/3109 = 84.7% |
| A1 (refusal ON, logs ON) | 61/224 = **27.2%** | 2518/4007 = 62.8% | 2518/2579 = 97.6% |
| B0 (refusal OFF, logs OFF) | 130/170 = 76.5% | 1410/1929 = 73.1% | 1410/1540 = 91.6% |
| B1 (refusal ON, logs OFF) | 92/125 = 73.6% | 1586/2135 = 74.3% | 1586/1678 = 94.5% |

Three findings, read directly off this table:

1. **The MANDATORY-arm rate is untouched by the refusal, in both log
   conditions** (A0 62.9% → A1 62.8%; B0 73.1% → B1 74.3%, within noise).
   This is exactly what the design predicts — the refusal's
   `!current_thread_blocked_or_terminated` conjunct excludes this arm by
   construction — and the counters now confirm it holds at the per-boot
   level, not just as a code-reading argument. **The MANDATORY arm is the
   dominant producer of the identical-RIP/RSP pair in each of the 4 arms**
   (85-98% of kernel-blocked no-progress saves), which is why 0 of the 4
   arms' aggregate proxy moves much even when the PREEMPT-arm rate swings
   hard (next point).

2. **With logs ON, the refusal cuts the PREEMPT-arm rate by 45 points**
   (A0 72.1% → A1 27.2%) — the mechanism the spec designed clearly fires
   when it gets a turn. **With logs OFF, it barely moves it** (B0 76.5%
   → B1 73.6%, a 2.9-point move, an order of magnitude smaller). The
   refusal is one-shot per dispatch
   (`DISPATCH_MARK_REFUSAL_SPENT`, per `fix-a-notes.md`'s STEP 1): it
   re-arms `need_resched` and returns once, and if the *same* RIP/RSP is
   observed again on the very next preemption check, that second
   observation is not eligible for a second refusal and gets saved and
   counted as another no-progress PREEMPT-arm save. The measure slot offered the
   masked ~20-30ms logging window as the explanation (that removing it also
   removed the wall-clock room a refused dispatch needed to retire an
   instruction). **That explanation is superseded** by the REPORT sections
   below, which symbolise the two RIP values the entire proxy sits on: an
   identical-frame pair is a wait-loop halt-point revisit, so the
   PREEMPT-arm rate stays high with logs off for the same structural reason
   the MANDATORY-arm rate does. What stands from this bullet is the
   measurement itself — 72.1% → 27.2% with logs on, 76.5% → 73.6% with
   logs off.

3. **The PREEMPT arm is a small minority of the total in each of the 4
   arms** (13-16% of kernel-blocked no-progress saves; USER_PREEMPT
   no-progress saves are larger in raw count than KERNEL_BLOCKED_PREEMPT
   ones in each of the 4 arms — e.g. A0: 3366 vs. 475 — but USER_PREEMPT
   saves are not part of the serial-log proxy population at all, since the
   "Restored/Saved kernel
   context" lines are written only on the blocked-in-syscall path). Because
   the refusal's entire effect lands on this minority arm, and because that
   effect itself is contingent on the now-partially-explained logging
   condition, no combination tested here drives the aggregate kernel-blocked
   proxy anywhere near the spec's `DISPATCH_NO_PROGRESS == 0` bar or even
   meaningfully below the pre-fix baseline. This matches R111/R112's own
   reading (candidate A did not move the proxy) and locates precisely why:
   the refusal is conjoined out of the arm that produces 85-98% of the
   phenomenon it was built to remove, and on the arm it does reach, its
   effect appears to depend on exactly the log-timing behaviour #775
   separately flags as a hot-path violation.

Full per-reason counter sums (6 of 6 `DISPATCH_NOPROGRESS_SAVE_*` /
`DISPATCH_SAVE_REASON_*` pairs, arm totals) are in each arm's `census.json`
files under `docs/planning/green-program/sockets/serials/772-diag/<arm>/boot_NN/`
(this document's own committed copies); the derived rates above are
reproducible from those files alone (`grep`, no interpretation needed beyond

## Report: what the two dominant RIP values are

The whole proxy sits on two code addresses. In A0's specimen boot, 582 of
769 `Restored kernel context for thread` records carry `RIP=0x80001823a2`
and 141 carry `RIP=0x8000184d79` — 723 of 769 (94.0%) at two addresses, out
of 29 distinct RIP values across all 1538 restore/save records in that
boot. Same shape on A1's three committed serials: 500/533 (93.8%),
381/415 (91.8%), 384/419 (91.6%).

Those two addresses were symbolised against the binaries the battery built,
in the beast scratch clone `/root/breenix-772diag` (five kernel ELFs, one
per build; identified by whether `strings` finds `Restored kernel context
for thread`, which is exactly what `quiet_dispatch_log` removes). Exactly one
of the five ELFs — `kernel-07e97bc39ff5d543`, logs ON, built at 01:51,
the A0 re-run — places an instruction at `…1823a2`:

```
00000000001823a0 <_ZN6x86_6412instructions10interrupts14enable_and_hlt…>:
  1823a0:  fb      sti
  1823a1:  f4      hlt
  1823a2:  c3      ret          <-- the RIP 582 of 769 A0 restores carry
...
  184d74:  e8 …    call 186990 <…interrupts6enable…>
  184d79:  eb f0   jmp  184d6b  <-- inside …interrupts18without_interrupts…
```

<!-- claim-lint:ok: 6 of 6 hlt sites printed by this slot's own objdump run on both logs-ON ELFs -->
Six, of which four are the `x86_64` crate's `hlt`/`enable_and_hlt`
monomorphisations and two are spins in `kernel/src/syscall/entry.asm` that a
parked thread does not reach. The A1 binary `kernel-10a65b692264a663` has six
as well (`bf4f1`, `bf6b0`, `100ee0`, `2b6e31`, `379ad3`, `379b80`), and the A0
binary's `.text` runs `0xaa710`-`0x379d10` (`objdump -h`: vma `0xaa710`, size
`0x2cf600`), so all six sit inside `.text` and a `-j .text` reading does not
give four either. The likely origin of the error is counting only the
`x86_64`-crate sites and missing the two syscall-entry spins.

The premise this section needs is **not** a count of `hlt` sites. It is that
the restores land on two addresses and that both were symbolised directly out
of the disassembly above: `…1823a2` is the `ret` after `sti; hlt` inside
`enable_and_hlt`, and `…184d79` is the `jmp` after
`call …interrupts::enable` inside `without_interrupts`. The four symbolised
addresses — two per binary, and `…184d79`/`…2b7ee9` are not halts at all —
are correct as printed and were re-confirmed by the round-2 review's own
objdump and again by this correction slot's. Correcting the count strengthens
that reading rather than weakening it.

Runtime base is `0x8000000000` (`0x8000000000 + 0x1823a2` and
`0x8000000000 + 0x184d79` both land, which is a two-address consistency
check on the offset, not an assumption).

The A1 binary `kernel-10a65b692264a663` (logs ON, built 02:04) reproduces
the same two structural sites at its own addresses: `2b6e32` is the `ret`
after `sti; hlt` in `enable_and_hlt`, and `2b7ee9` is the instruction after
`call …interrupts::enable` inside `without_interrupts` — which are exactly
A1's own two dominant restore RIPs (`0x80002b6e32`, 366 of 533;
`0x80002b7ee9`, 134 of 533). Two independently built binaries, the same two
sites, the same rank order.

`enable_and_hlt` is where a blocked-in-syscall thread parks:
`arch_halt_with_interrupts()` (`kernel/src/lib.rs:394-404`,
`#[inline(always)]`) → `X86Cpu::halt_with_interrupts()` →
`x86_64::instructions::interrupts::enable_and_hlt`, which `handlers.rs`
calls from 11 sites. The two symbolised addresses account for 723 of 769
A0 restores and 500 of 533 A1 restores.

## Report: mechanism

A thread blocked in a syscall parks by calling `arch_halt_with_interrupts()`
(`kernel/src/lib.rs:394-404`, `#[inline(always)]`, reaching
`x86_64::instructions::interrupts::enable_and_hlt`), so its saved kernel RIP
is the `ret` immediately after that function's `sti; hlt` — one of the six
`hlt` instructions in the image, four of them `x86_64`-crate
monomorphisations (F1 above) — so that `ret` is at `0x1823a2` in the A0
binary and `0x2b6e32` in the A1 binary, which is where 582 of 769 and 366 of
533 kernel-context restores respectively land — and its RSP is that halt's
frame, fixed for a given wait site. When the scheduler dispatches such a
thread it resumes at that `ret`, re-evaluates its wait condition (e.g.
`sys_waitpid`'s loop, `kernel/src/syscall/handlers.rs:3459-3498`: check
signals, `yield_current()`, halt, re-read the child's state, loop), and if
the condition is still unmet it executes `sti; hlt` again and is saved at a
byte-identical RIP **and** RSP with its state still blocked — so the switch
away is the mandatory arm (`kernel/src/interrupts/context_switch.rs:500`,
recorded at `:699`), which is exactly the arm the refusal's
`!current_thread_blocked_or_terminated` conjunct (`:300`) excludes. The
identical-RIP/RSP predicate therefore cannot separate "this dispatch
retired no instruction" from "this thread went once around its wait loop
and re-parked on the same halt instruction", and the second reading is what
the data shows: <!-- claim-lint:ok: 186 of 226 frame-changed pairs re-derived in this slot from A0/boot_01/serial_kernel.txt -->
**186 of 226** frame-changed pairs in A0's specimen boot
(82.3%) re-park on one of the two symbolised wait sites — `…1823a2` 111
times, `…184d79` 75; the first is the `ret` after the wait loop's `sti; hlt`,
the second the `jmp` after `call …interrupts::enable` inside
`without_interrupts`, so "wait site" here names the park point, not a halt
instruction — rather than on a scattered PC; the other 40 land on 27
further RIPs, none of them symbolised, and 29 distinct RIPs cover all 1538
restore/save records. (An earlier version of this sentence said "226 of 226
… land on another halt point". False under its strict reading: 40 of the 226
land on 27 addresses this report never symbolised, and with six `hlt`
instructions in the whole image (F1) those 27 cannot all be halt points —
nor is `…184d79`, one of the two sites the sentence does rest on, a halt
instruction at all. Vacuous under the only other reading, "one of the RIPs
this census observed", which every save RIP is by construction. Re-derived in this slot by pairing
each `Restored kernel context` record with the next `Saved kernel context`
record for the same tid over the committed serial: 532 identical-frame, 226
frame-changed, 11 restores unpaired at EOF, summing to the boot's 769
restores.) The revisit reading rests on those 186 and on the alternation
below, not on the retracted 226. Thread 28 is observed alternating between the two sites
(`0x80001823a2` at RSP `…e9a448` and `0x8000184d79` at RSP `…e9a410`, one
stack frame apart), which it can only do by executing. That is why 84.7% of
the proxy population is the mandatory arm; why the refusal moves the arm it
can see (`KernelBlockedPreempt` 72.1% → 27.2%) without moving the aggregate
(63.7% → 60.8%, p = 0.09); and why removing the three log records raises the
rate (63.7% → 73.4%, p = 0.001) while halving the absolute per-boot cost
(484.7 → 209.9 restores, 1397 → 1061 ms median latency).

## Report: confidence

**High** on the two readings the decision rests on, because both are direct:
the symbolisation is `objdump` output from the battery's own binaries,
cross-checked on a second independently built binary; the arm split is a
counter read in 40 of 40 boots with `kernel_blocked_saves_match_records`
true in 19 of 19 boots that carry both counters and records.

**Medium-high** on the last step — that the mandatory-arm identical pairs
are loop revisits rather than zero-instruction dispatches. The alternation
and the 186 of 226 frame-changed pairs that re-park on one of the two
symbolised wait sites (F2 — the retracted claim was "226 of 226") make the
revisit reading the parsimonious one, and no wait loop body in `handlers.rs` re-enters the
blocked state from inside itself, but this battery has no counter that
increments per completed wait-loop iteration, so a dispatch that truly
retired nothing and one that completed an iteration are still recorded
identically. One boot with a per-iteration counter settles it; that is the
next instrument, not a new theory.

## Report: recommended fix

1. **Retire the identical-RIP/RSP proxy as #772's oracle before any fix
   lands.** It is measuring halt-point revisits, so a change scored against
   it is scored against something it cannot see. Replacement, cheap and
   falsifiable: a per-thread counter bumped once per iteration of each
   `arch_halt_with_interrupts()` wait loop in `kernel/src/syscall/handlers.rs`
   (11 sites; not a Tier-1 file — Tier-1 is `syscall/handler.rs`), and a
   dispatch scored as wasted only when that counter did not advance between
   the dispatch mark and the save. The existing mark
   (`per_cpu.rs`, `classify_dispatch_progress`) already carries the tid and
   the frame; it needs one more word.
2. **#775 is not the #772 fix, and should still land.** B0 does not collapse
   the proxy — it raises it (p = 0.001). But removing the three records
   halves the per-boot blocked-in-syscall dispatch volume (484.7 → 209.9
   restores) and is the battery's only directional latency result
   (1397 → 1061 ms, p = 0.034), on top of being the CLAUDE.md
   interrupt-path violation it was filed as. Precondition, already visible
   in this battery: migrate `scripts/x86-strand-census.sh` off the two log
   strings it keys on (`:49-50`, `:53-54`) — on a B-arm boot it reads
   `threads_saved_blocked=0 stranded=0` and is silently blind. The episode
   turn census (`scripts/772-dispatch-census.py`) has the same dependency
   and needs the same migration.
3. **If the re-instrumented oracle still shows real waste, the path to fix
   is the one Q1 names**: `KernelBlockedMandatory`, and the cost sits
   upstream of the switch, in the pick. A mandatory switch away from a
   blocked thread cannot be refused — but dispatching a thread whose state
   is already `is_blocked()` buys a full save/restore plus a CR3 write and
   can only end in that mandatory switch. `Scheduler::schedule()`'s
   selection loop (`kernel/src/task/scheduler.rs:1878` onward) skips only
   `ThreadState::Terminated`, not `state.is_blocked()`, and the requeue
   block just above it (`:1820-1868`) already documents the duplicate-entry
   case that can leave a blocked thread sitting in `per_cpu_queues`. A fix
   there touches that selection loop and the enqueue paths, and needs a
   counter at the pick before anything is changed. Disclosed risk: the
   post-halt re-check inside each wait loop is a poll that has historically
   masked lost wakes — the #568 comment at `scheduler.rs:1790-1817` is
   about exactly that class — so this is a soak-gated change, not a
   single-green-run change.
4. **Candidate A should not land as the #772 fix.** Its effect is real and
   measured — it removes 87% of `KernelBlockedPreempt` no-progress saves and
   61% of `UserPreempt` ones — but that lands outside the proxy population
   for the user arm and on 15.3% of it for the kernel arm, it does not move
   the aggregate proxy at n=10 (p = 0.09), it does not improve latency
   (p = 0.78), and both of the battery's `clonevm_exec_test` verdict
   failures are on refusal-ON arms. Whatever it is doing deserves its own
   issue and its own oracle; it is not a fix for #772 as #772 is currently
   stated.
