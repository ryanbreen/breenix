## Verdict

**Undecided — underpowered, not decided.** The 60-boot battery produced
0 of 60 specimens of the phenomenon #772 asks about (a reader dispatched two
or more times before consuming its wake). The two boots that did block each
consumed their wake on the first dispatch, which is a **1-turn** call — a
case where readings (a) and (b) make an identical prediction (`TRUE=0,
FALSE=1`) and therefore cannot be told apart. Section 1 shows the counters
measure what they claim, but this battery supplies no evidence for or
against reading (a) vs (b) on the actual multi-turn phenomenon, and Section 2
shows why: this battery's own instrumentation cut the multi-turn opportunity
from #764's 7 of 46 blocking boots down to 0 of 2.

## 2. Is the 2/60 block rate an observer effect?

**Yes — the counter-readback bracket itself is the cause, and the serials
show the mechanism directly, not just the correlation.**

`#764`'s battery (`serials/764-rca/battery.tsv`, 76 boots, same host
(beast `breenix-x86`, KVM), same driver (`docker/qemu/run-x86-gate.sh 4
full`), same profile) blocked on the data recv in **46/76 (61%)** boots, and
of those, **7/46 (15%) had `turns>=2`** (`resumes>=2` in that battery's own
`census.py`/`battery.tsv` schema, which counts the identical thing —
`Restored kernel context for thread <tid>` lines between `unblock()` and
`woken`). This experiment's battery blocked on **2/60 (3.3%)** and produced
**0 `turns>=2` specimens**. That is not a small gap; it is a ~20x drop in
the block rate and a complete absence of the multi-turn case the previous
battery found routinely.

The two batteries' reader code differs in exactly one relevant way. Both
stamp `w0` (peer's pre-write time), `acc` (this reader's `accept()`
return), `pre` (immediately before the blocking `read()`) and `data`
(immediately after). In `764`'s reader (`repro-boot-057`,
`serials/764-rca/README.md` Evidence 2), `acc` and `pre` are **the same
value** in every specimen quoted (`acc=23454 pre=23454`) — nothing runs
between `accept()` returning and the blocking read starting. In this
branch's reader (`c4e1e88a`, `userspace/programs/src/loopback_wake_test.rs:
193-215`), three new syscalls — `open("/proc/trace/counters")`, `read`,
`close` — run in `read_recv_wait_counters()` between `t_accept` and
`t_pre_read`, specifically so the counter delta brackets only the data
read. That bracket is exactly the new work sitting between `acc` and `pre`.

Measured directly from all 60 `reader_stamps` lines in this battery
(`grep -h "reader_stamps" boot_*/serial_user.txt`), `pre - acc` (the
counter-bracket's own wall-clock cost, including any scheduling delay
crossing it) is **never zero**: min 100 ms, median 1290 ms, max 6515 ms,
n=60. In `764`'s 76-row battery, `w0_to_pre` (which is 0 exactly when
`acc == pre`, since that battery's `pre` immediately follows `acc`) is
**zero in 55/76 (72%) of boots** — the reader was already sitting in its
blocking `read()` before the peer wrote, in nearly three out of four boots.
In this battery, `w0_to_pre` is zero in only **2/60 (3.3%)** — matching the
block rate almost exactly, because entering the blocking read before the
peer's write is precisely the precondition for blocking at all.

The causal chain is direct, not inferred from correlation alone: the
counter bracket inserts a median 1.3-second gap (and up to 6.5 s) between
`accept()` returning and the actual data `read()` starting; the peer's
write typically completes well inside that gap (the loopback peer's own
round trip is a few hundred ms per the `764`-rca evidence); by the time
this battery's reader reaches the real blocking read, the data is already
in the socket's receive buffer 58 of 60 times, so the wait loop this
experiment instruments never runs. This is a profile/host match (identical
VM, identical driver, identical branch lineage off the same main) with one
code difference — the in-band counter read — and that one difference
predicts, and the serials confirm, exactly the shift observed. Not a
profile or host difference: `772-exp/README.md` documents the same beast
VM and same `run-x86-gate.sh 4 full` driver as `764-rca/README.md`.

**The phenomenon is present in this battery's own serials, just outside the
counter bracket's scope.** `reader_child`'s *second* blocking call — the
EOF-wait `read()` at `loopback_wake_test.rs:275`, reached after the data
read returns, and not bracketed by any `read_recv_wait_counters()` call —
goes through the identical wait-loop code
(`kernel/src/syscall/handlers.rs:1403`) on the same socket fd. Widening the
same restore-count search (`Restored kernel context for thread <tid>`
between the loop's own `entering blocking path` line and its `woken` line)
across the whole battery, not just the data-read window, finds 59
resolvable blocking calls across the 60 boots (`grep -c "TCP recv:
entering blocking path"` — 55 boots with 1, 2 boots with 2, 3 boots with
0) and **6/59 have `restores>=2`**, one of them `boot_45`'s own
EOF read (`serial_kernel.txt:2648-2897`): `restore → CR3 switch → save`
five consecutive times at the identical `RIP=0x8000326f72
RSP=0xffffc90000e19958`, zero intervening kernel-log lines each time — the
exact shape #772 names — before `TCP_BLOCK: Thread 27 woken from recv
blocking` on the sixth dispatch. No `read_recv_wait_counters()` call
brackets this window, so **this specimen has no counter delta and cannot
be used to decide (a) vs (b)** — it corroborates that the phenomenon
recurs on this host/profile at a rate (6/59 ≈ 10%) in the same order as
`764`'s data-read rate (7/46 ≈ 15%), it does not supply the counter
evidence this experiment exists to produce. It also means the corrected
measure step in Section 3 does not need to depend on the data read
blocking at all — the EOF read supplies multi-turn specimens on its own,
unperturbed, in the same boots.

## 3. The corrected measure step

**Move the counter read out-of-band.** The bracket that isolates one call's
contribution is sound in principle — the problem is only that it currently
sits in-band, between `accept()` and the blocking read it means to observe.
Two ways to fix that, either sufficient:

- **GDB, post-test**: drop both of the 2 `read_recv_wait_counters()` calls
  currently in `reader_child`; after the boot completes (or after the
  watchdog/exit-code fires), attach GDB and run `call
  trace_dump_counters()` to read `RECV_WAIT_STILL_BLOCKED_TRUE` /
  `_FALSE` for the whole boot. This mixes the data read's contribution
  with the EOF read's — `grep -h "TCP recv: entering blocking path"
  boot_*/serial_kernel.txt` across all 60 boots of this battery returns 59
  lines, and each names a thread id (27/28/29/30) matching this boot's
  `loopback_wake_test` reader tid from `772-exp-results-final.jsonl`, so
  both calls, not just the data read, are `loopback_wake_test`'s own — but
  since both go through the identical wait-loop code (Section 2), a
  whole-boot total still answers reading (a) vs (b) for that code, and adds
  no syscalls to either blocking call's own path.
- **`/proc/trace/counters`, read once at process exit** (after
  `data_latency_ms` and the pass/fail verdict are already decided,
  matching the pattern this file already uses at
  `loopback_wake_test.rs:~260` for the `DATA_WAKE_BOUND_MS` probe) — same
  effect, no GDB dependency, but still costs the reader no additional
  syscalls before the read it means to observe.

Either way, the pass criterion for the next battery should be **loop until
at least 3 boots produce `turns>=2`, not a fixed boot count** — this
battery's 60-boot cap was sized to #772's stated budget, not to the
population's actual multi-turn rate. Two independent estimates of that
per-boot rate, both from unperturbed reader paths, agree to within a factor
of 2: `764`'s battery, 7/76 boots (~9%); this battery's own EOF-read
population (Section 2), 6/59 blocking calls across its 60 boots (~10%). At
either rate a few dozen boots under the corrected (out-of-band)
measurement should reach 3 specimens; if it does not, raise the boot count,
not the counter-bracket's cost.

## 4. Reading: undecided

The counters are validated on the one case this battery produced: both of
the 2/2 1-turn specimens show `still_blocked_true=0, still_blocked_false=1`, exactly
matching `TRUE + FALSE == turns` with `FALSE` firing on the turn that
proceeds — the instrument fires where the source
(`kernel/src/syscall/handlers.rs:1403-1430`) says it fires, and reports what
it says it reports. That is confirmation the tool works, not evidence for
either RCA reading: a 1-turn call is exactly the case where reading (a)
(`TRUE` increments once per wasted turn before `FALSE` fires) and reading
(b) (the loop is dispatched but does not run to completion on wasted turns,
so neither branch increments) predict the identical counter values
(`TRUE=0, FALSE=1`), because there are zero wasted turns to distinguish. On
`turns>=2` — the actual #772 phenomenon — this battery has no data at all.
**Reading: `undecided`.** The next experiment (Section 3, out-of-band
readback + loop-to-N stop condition) is what would decide it: if a
`turns=6` specimen shows `still_blocked_true=5, still_blocked_false=1`,
that is reading (a); if it shows `still_blocked_true=0, still_blocked_false=1`
(or any total well under 6), that is reading (b).
