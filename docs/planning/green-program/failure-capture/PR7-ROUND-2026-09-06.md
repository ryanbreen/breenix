## Deviations, with reasons

* **The commit split is kernel / guard+tests+gates+evidence / fixtures**, not
  the brief's kernel / guard+tests / gates+docs. The gate wiring and the
  preserved evidence moved into the second commit because that commit's own
  tests read both: `the_aarch64_gates_run_the_guard_on_their_own_kernel` asserts
  the gates call the guard, and
  `the_preserved_binary_evidence_is_a_red_and_a_green_on_real_kernels` reads the
  guard's saved output. Splitting them would have left a knowingly-red
  intermediate commit. The round doc landed in a fourth commit with this note.
* **The guard fixtures are committed, not assembled at test time.** The first
  draft built seven fixture ELFs with `clang`. The beast x86 container has no
  `clang` and no aarch64 cross toolchain, and
  `docker/qemu/lib/gate-structure-preflight.sh` runs every `tests/*_structure.rs`
  on that host, so that shape would have reddened the gates that call the
  preflight there. The `.s` sources and their linked `.aarch64-elf` files are now
  under `tests/fixtures/lockup-guard/`, and
  `the_committed_fixtures_match_their_sources` rebuilds 7 of 7 and requires the
  same verdict wherever an assembler exists. Recorded as a deviation because the
  plan said "build fixtures", and on one of the two hosts this suite runs on,
  nothing can.
* **`print_hex_u64` was left in place.** It is dead after this change, and it
  was dead before it too — 0 call sites in the tree at base. The plan pins
  its raw-output census row at 1 and says to keep it, so it was kept, and this
  is the disclosure that it is a pre-existing dead helper rather than something
  this round made dead.
* **`scripts/run-lockup-capture-oracle.sh` takes the host-wide QEMU lock**,
  which the plan did not name. `tests/qemu_host_lock_structure.rs` failed on the
  first draft without it.
* **The guard reports one path per sink**, so on the unfixed kernel the
  scheduler helper's allocating path is reachable but not separately printed;
  the process helper's path is the one the search reached first. Stated rather
  than worked around.

## What is NOT claimed

* No x86 guest gate was run, by design. The x86 evidence in this round is two
  clean builds; it is not a statement about x86 runtime behaviour.
* The two aarch64 gate samples are small on purpose: strict 3 boots, service
  sequence 1 boot per profile, production 1 boot. That is a bounded regression
  sample, not the service gate's own soak claim.
* The oracle establishes a peer-held scheduler stall with a live reporting CPU.
  It does not model a CPU0 hard wedge with interrupts masked, and it does not
  make `[BXCAP:NOTE sched_lock_held]` identify an owner.
* The binary guard reads one root. `task::scheduler::try_dump_state` still
  allocates for its remaining exception caller; that is issue #893, not
  something this round measured as absent.
* The per-thread and process diagnostics the old report printed are gone and are
  not replaced. Issue #892 carries them.
* Neither the guard's own analysis nor the source extractor was checked against
  a compiler other than the one on this host.
