## 1. What changed

`kernel/src/tracing/providers/irq.rs`'s `trace_timer_tick` used to record a
`TIMER_TICK` ring EVENT on each call. It now records one once per
`TICK_SAMPLE` ticks (`TICK_SAMPLE = 20`); `TIMER_TICK_TOTAL` — read by the
soft-lockup detector, per-CPU idle-tick accounting, and `/proc/stat` — still
increments on each call, unconditionally, before the sampling guard is
evaluated. The tick number already carried in the payload is what a reader
needs, so sampling costs density between recorded points, not information.

The Tier-1 caller (`kernel/src/interrupts/timer.rs:51`, x86) and the
critical-path caller (`kernel/src/arch_impl/aarch64/timer_interrupt.rs:730`)
are both untouched — same call, same signature, a 0-line diff on either
file. The change lives inside the provider function they call, and only there.

A `#[cfg(feature = "boot_tests")]` self-check (`ring_span_self_check`, same
file) runs inside `trace_timer_tick` itself — not a spawned kthread, because
on x86 the scheduler is not yet initialized at the point
`tracing::providers::init()` runs (`kernel/src/main.rs`: `tracing::providers::init()`
precedes `task::scheduler::init_with_current()`), so a kthread spawn there
would be unsafe; ticks only start flowing once the whole boot sequence is far
enough along for `kthread_run` to be safe regardless, so gating on tick count
is both simpler and more portable than a spawned watcher. It fires exactly
once, off a single relaxed-load latch, using only the lock-free `raw_serial_*`
writers `tracing::output`'s own panic-safe dump functions already use — no
lock, no allocation, no `format!` — because this code runs inside the same
ISR both timer handlers call directly, even though the feature gate keeps it
out of any shipped build.

## 2. The oracle, and what it actually measures

Marker: `[RING_SPAN:cpu=0:span_ms=<N>:writes=<W>:dropped=<D>]`, emitted once
at `tick_count * MS_PER_TICK >= 1000` (1s of guest wall-clock time,
arch-neutral). `span_ms` is the delta between the oldest and newest
**`TIMER_TICK`-typed** entries currently live in CPU 0's ring; `writes` and
`dropped` are ring-wide (`TraceCpuBuffer::write_index()` /
`dropped_count()`), kept for context.

### 2.1 The measurement that mattered: filtering by event type

The plan's own arithmetic (§2.2) computes the ring's `TIMER_TICK` cap as if
timer ticks were the ring's only writer — a fair assumption for the
near-idle/wedged failure edge PR-2 targets, and explicitly flagged in the
plan as arithmetic, not a boot measurement. The first real boot in this round
showed why that matters: an *unfiltered* oldest-to-newest span at the 1s
checkpoint read `span_ms=0` on **both** `TICK_SAMPLE=1` and `TICK_SAMPLE=20`
kernels, because once userspace bring-up starts, other providers (scheduler
context-switches, syscalls) write into the same per-CPU ring at a rate far
above either sampled or unsampled `TIMER_TICK`'s own rate — one boot at that
stage measured `writes=1,063,564` in the first ~5 real seconds, of which only
~150 were sampled `TIMER_TICK` entries. A shared FIFO ring's retention window
is set by its *total* write rate; sampling one contributor down cannot widen
it, and can only ever narrow that contributor's own share of it further.

Filtering `span_ms` to `TIMER_TICK`-typed entries specifically does not
escape that same-ring limit either — an entry of any type older than "now
minus 1024 total writes" is evicted regardless of its type. What filtering
buys is a `span_ms` that means what the marker's name says: how far back
`TIMER_TICK`'s *own* recorded history reaches, which is the number a
debugger reading a fatal dump's ring tail actually needs, rather than a
number dominated by whatever else happened to be writing at that instant.

### 2.2 Calibrating the checkpoint against the actual environment

`CHECK_AT_MS = 1000` was chosen empirically, per the plan's own Q1 ("pick it
so the measured span in PR-2's own oracle output clears the floor with
margin, not from this document's arithmetic"), by scanning checkpoints on
this branch:

| `CHECK_AT_MS` | `TICK_SAMPLE=1` (unsampled) span_ms | `TICK_SAMPLE=20` (fixed) span_ms | reading |
|---|---|---|---|
| 500  | 772 (unwrapped, `dropped=0`)  | 735 (unwrapped, `dropped=0`)   | ring not yet full either way — no signal |
| 800  | 1129 (`dropped=103`, just wrapped) | 1191 (`dropped=0`)        | crossover point, thin margin |
| **1000** | **851-896** (3 boots, `dropped>0` each time) | **1493-1509** (3 boots, `dropped=0` each time) | clean, reproducible gap |
| 1400-2000 | 0-5 (`dropped` in the hundreds of thousands) | 0 (`dropped` in the tens of thousands) | userspace bring-up traffic has started dominating the shared ring; neither configuration's `TIMER_TICK` history survives it |
| 9000 | (not reached within the boot's poll window under host contention, in 1 of 1 attempts) | (same) | too late to be a safe checkpoint |

At 1s, the unsampled baseline has already recorded ≥1024 `TIMER_TICK` entries
purely from its own volume (1024 ticks / 1000 Hz ≈ 1.02s, matching §2.2's
arithmetic almost exactly — measured 851-896ms, plan's estimate ~1.02s) and
is capped; the sampled build has recorded ~1024/20 ≈ 51 entries and is far
from its own cap, so its span keeps growing with real elapsed time instead —
measured 1493-1509ms. `RING_SPAN_FLOOR_MS = 1100` sits with margin on both
sides of that measured pair (≥204ms below each of the 3 green readings, ≥204ms above
each of the 3 red readings).

**What this does not claim**: that `TICK_SAMPLE=20` widens the ring's usable
history once userspace bring-up traffic has started (§2.1 measured it does
not, in this environment). What it does claim, measured, is the plan's
literal target case — the pre-bring-up and (by construction, since the only
running workload is the boot sequence itself) near-idle/wedged window — where
`TIMER_TICK` really is the ring's dominant or sole writer.

## 7. Hot-path cost (source-level, not measured)

`trace_timer_tick`'s steady-state cost is unchanged in shape: the sampling
guard adds one `%` and one `==` to an `if` condition that already short-circuits
on two atomic loads (`IRQ_PROVIDER.is_enabled()`, `crate::tracing::is_enabled()`),
and `TIMER_TICK_TOTAL.increment()` is bit-for-bit what it was before. The
`#[cfg(feature = "boot_tests")] ring_span_self_check::observe(tick_count)`
call compiles out of a features-off build (confirmed by the
prod-profile absence checks in §5); in a `boot_tests` build it is a single
relaxed atomic load and a comparison per tick until the one-shot latch fires,
after which it is the same single relaxed load forever. **Not claimed**: a
cycle count was measured on either path; the claim is about instruction
shape, matching the discipline the plan's own §9 states for PR-2.

## 8. What is NOT claimed

1. **Not claimed**: that sampling `TIMER_TICK` widens the ring's observable
   history once other providers dominate its write rate (§2.1, §2.2) — measured
   false in this environment past ~1-1.5s of boot. What is claimed, and
   measured, is the plan's literal near-idle target case.
2. **Not claimed**: any currently-open kernel issue is closed by this PR. It
   is the ring-depth precondition PR-4's fault/panic capture edges will read
   from; no capture edge reads that depth yet.
3. **Not claimed**: `scripts/check-critical-path-violations.sh` passes
   because of, or despite, this PR — it fails identically on the base commit
   (§6).
4. **Not claimed**: a cycle-accurate hot-path cost was measured (§7) —
   argued from instruction shape only.
5. **Not claimed**: `RING_SPAN_FLOOR_MS = 1100` is portable to a different
   host, a different QEMU acceleration mode, or a different `-smp` count
   without re-measuring; it is calibrated against this Mac's native
   HVF-accelerated `-smp 4` aarch64 boots and this beast container's x86
   `-smp 1` TCG boots, both recorded in §3-§5.
6. **No retry, probabilistic confidence target, soak, or "eventually passed"
   result is introduced.** Each gate result cited above is from a single
   real boot (or an explicitly-labelled small set of them, reported
   individually, not averaged).

(unsampled) nor `TICK_SAMPLE = 20` had come close to the ring's 1024-entry
capacity (200 of 1024, both configurations, per the same measurement below).

arithmetic (200 nominal ticks against a 1024-entry ring), not a separate claim. Reproduced independently on beast at this checkpoint: unsampled
`span_ms=2677:dropped=0`, sampled `span_ms=3642`-`3831:dropped=0` -- both
just elapsed wall time, no ring-wrap signal, so a build with the sampling
guard deleted passed the x86 gate anyway.

Scanning further checkpoints on beast (unsampled vs. `TICK_SAMPLE=16`, one
boot each, `[RING_SPAN_CAL:checkpoint_ms=N]` markers preceding each reading
in a temporary multi-checkpoint instrumented build, not shipped):

| checkpoint_ms | unsampled span_ms / dropped | `TICK_SAMPLE=16` span_ms / dropped |

| 1000 | 5447 / 0 | 4108 / 0 |

| 6000 | 18890 / 276 | 20203 / 0 |
| 9000 | 14146 / 925 | 27742 / 0 |
| 13000 | 14191 / 1784 | 37412 / 0 |

  batch): 0, 955, 946, 881, 924, 922, 937, 1120, 941, 967, 0, 1055, and one
  `marker missing` (9.3) -- 12 numeric readings, range 0-1120ms. One of the
  12 (1120ms) EXCEEDED the original 1100 floor: a real false pass at
  roughly 1-in-12 in this combined sample.
- Sampled (`TICK_SAMPLE=16`, the fix -- 16, not the original 20; see 9.3),
  `span_ms` across 9 boots (a solo boot plus two 4-boot batches): 1285,
  1280, 1284, 1285, 1318, 1313, 1330, 1328, and one 1903ms outlier -- 9 of 9
  comfortably above 1100, but the tight ~1280-1330ms cluster sits only
  ~200ms above the mutation's observed 1120ms peak, confirming the two
  distributions can come close enough for host jitter to flip a boot's
  verdict.

Root cause: `span_ms` measures how far back the ring's live `TIMER_TICK`
history reaches at a wall-clock checkpoint, which depends on both when the
checkpoint fires (itself a tick-count threshold, not truly wall-clock-fixed)
and on real per-tick timing under host scheduling jitter. Pushing the
checkpoint later to widen the gap trades directly against §2.2's own
finding that userspace bring-up traffic swamps the ring past roughly
1400-2000ms -- there is limited room to move in either direction on this
specific metric.

Fix: `span_ms` is no longer the pass/fail signal on either gate. See 9.4.

### 9.3 New defect found while investigating 9.2: the marker is missing on some boots

Widening the aarch64 sample (9.2) also surfaced a failure mode absent from
the original round's small sample: `grep`-ing for the `[RING_SPAN:...]`
marker sometimes finds nothing at all, distinct from "span_ms below floor".
Confirmed on the UNMODIFIED base commit (`TICK_SAMPLE=20`, before any
fix-round edit) at 2 of 6 boots, and reproduced again at 2 of 3 and 3 of 8
on other sample boots this round -- pre-existing, not caused by this PR.

Root cause, confirmed by reading the raw serial bytes: byte-level
interleaving between `ring_span_self_check::report()`'s own lock-free
`raw_serial_*` writes and ANOTHER unlocked serial writer active on a
different CPU at the same instant (an early-boot `[TEST:...:START]` self-test
marker in the cases caught), e.g.:

```
[TEST:filesystem:vi[rtio_RINGblk_writ_SPAN:cpu=0:spae_rn_ms=ead_verify:START]
```

This is a real, pre-existing gap in this PR's own claim ("the reporting path
... uses only the lock-free `raw_serial_*` writers", §1) -- lock-free
avoids a deadlock, but does not make the write atomic against another
CPU's own unlocked write to the same UART. Filed as
https://github.com/ryanbreen/breenix/issues/847 rather than fixed here: a
real fix needs mutual exclusion spanning whichever other unlocked or locked
serial writer is active during the self-check's window, which is a change to the
shared serial-write path well outside a same-day tick-sampling PR's scope.
This failure mode is safe-direction (it rejects a good boot, it does not
accept a bad one) and is unrelated to, and does not change, the finding or
fix in 9.2.

### 9.4 Fix for 9.1 and 9.2: a wall-clock-jitter-immune sampling-ratio oracle

`ring_span_self_check::report()` (`kernel/src/tracing/providers/irq.rs`) now
also reads `TIMER_TICK_TOTAL.aggregate()` (`ticks_total`, incremented
unconditionally on each tick, no sampling) and counts how many `TIMER_TICK`-typed entries CPU
0's ring currently holds (`tick_events`, counted in the same ring traversal
`span_ms`'s oldest/newest already used, not a second pass). Both gates now
require `ticks_total >= tick_events * RING_SPAN_RATIO_FLOOR` (`= 10` on both
gates) as the pass/fail signal; `span_ms` is kept in the marker and printed,
but is no longer gated on a floor (only checked `> 0`, a basic liveness
sanity check).

This ratio is a pure count relationship, not a timing one: a working
sampling guard holds `tick_events` near `ticks_total / TICK_SAMPLE` (times a
CPU-count factor on `-smp N`, since `ticks_total` sums each CPU's own tick count
while `tick_events` is CPU 0's own ring only) regardless of when in
the boot this fires or whether the ring has wrapped; a deleted guard (each tick recorded, the sampling step removed) collapses
the ratio toward 1 x that same CPU-count factor.

claim-lint:ok: the CPU-count-factor relationship is verified directly by the
table immediately below (aarch64 `-smp 4` ratios cluster near 4x the x86
`-smp 1` ratios, both at the same `TICK_SAMPLE`), not asserted separately.
Measured this round, real boots, `CHECK_AT_MS=1000` on both architectures:

### 9.5 Fix for the third review finding: sampling-guard hot-path cost (major)

`TICK_SAMPLE` changed from 20 to 16 (a power of two -- 16 is the nearest
power of two to the original 20, not an independently re-derived target;
the plan's own Q1 on this constant's exact value stays open) and the guard
changed from `tick_count % TICK_SAMPLE == 0` to
`tick_count & (TICK_SAMPLE - 1) == 0`, enforced as invariant by a `const`
assertion. A non-power-of-two divisor compiles to the compiler's
magic-number division-by-constant sequence (observed for the original `= 20`
in a release aarch64 `boot_tests` disassembly of `timer_interrupt_handler`:
a materialized 64-bit reciprocal constant via `mov`+`movk`, `mul`, `ror`,
`cmp`, `ccmp` -- roughly 6 ALU instructions); the bitwise-AND form is one
instruction plus the existing compare. This does not change the guard's
semantics (still the same Nth-tick cadence) or its call sites (both timer
handlers, untouched).
