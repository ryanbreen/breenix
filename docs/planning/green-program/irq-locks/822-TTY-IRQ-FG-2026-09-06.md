# #822 — the TTY interrupt path stops touching the console's `foreground_pgrp`

Branch `fix/822-tty-irq-no-fg-block`, off `origin/main` at `783a6a53`
(the #821 merge). R157 small-PR mode: one defect, one repair, one oracle, one
ratchet file.

## The lock, and who holds it unmasked

The console `TtyDevice`'s `foreground_pgrp: Mutex<Option<u64>>`
(`kernel/src/tty/driver.rs`) is a plain `spin::Mutex`. It performs no mask
operation of its own, so each of the 5 acquisitions of it in `driver.rs` runs
with interrupts unmasked, on both architectures. The thread-side reachers:

| reached from | through |
|---|---|
| `tcsetpgrp` / TIOCSPGRP (`tty/ioctl.rs`) | `set_foreground_pgrp` |
| TIOCGPGRP (`tty/ioctl.rs`) | `get_foreground_pgrp` |
| process creation (`process/creation.rs`, 2 sites) | `set_foreground_pgrp` |
| `sys_read`'s stdin arm (#821's consumer) | `adopt_deferred_foreground_pgrp` |
| the blocking input entry `input_char` | `send_signal_to_foreground` |

## The defect

At `origin/main`, 2 interrupt-side paths reached that mutex:

| site | shape | what a busy lock did |
|---|---|---|
| `input_char_nonblock` | `foreground_pgrp.try_lock().map(..).unwrap_or(false)` | answered "a foreground pgrp is set" whether or not one was, so the adoption #821 defers was skipped |
| `send_signal_to_foreground_nonblock` | `foreground_pgrp.try_lock()` with a returning arm on a busy lock | DROPPED the SIGINT/SIGQUIT/SIGTSTP it had just resolved, and announced the drop through `serial_println!` on x86 — itself a lock, taken from interrupt context |

Neither waited, so neither could wedge a CPU. That is why this is the narrowest
of the census's five findings and why the census called it "the same defect
shape one line below F3". What these two did instead was lose the keystroke's
meaning exactly when a `tcsetpgrp` was in flight — the moment a shell hands the
terminal to a new foreground job is precisely when its user is most likely to
be typing.

**One thing the census recorded is no longer true at this head, and is stated
rather than claimed.** #822's issue text names `driver.rs:304`
(`set_foreground_pgrp`, a blocking acquisition) reached from
`input_char_nonblock:191`. PR #878 (#821) removed that call from the interrupt
entry, so at `783a6a53` no BLOCKING acquisition of this mutex is reachable from
a TTY interrupt entry; #821's own document disclosed that and left #822 open on
its own terms. What this round repairs is what was left: the 2 `try_lock` sites
above.

## The repair

Both interrupt-side readers now read `foreground_pgrp_snapshot`, an `AtomicU64`
on the same device.

**Ordering.** Both writes of the field go through one private writer,
`store_foreground_pgrp`, which:

1. takes the mutex,
2. writes the field,
3. stores the snapshot `Release`,
4. releases the mutex.

Writers are therefore serialised by the mutex, so the cell's value sequence is
the field's own value sequence. It lags the field by at most the remainder of
one critical section and does not lead it. An interrupt reader loads it
`Acquire` and gets a value the field held at some instant — during a
`tcsetpgrp` window, the outgoing pgrp. That is a strictly better answer than
the `try_lock` gave: a busy lock gave it no value at all.

**The sentinel.** `u64::MAX` encodes "unset". 0 of the 3 production writers can
produce it: TIOCSPGRP returns `EINVAL` for a negative pgrp (so `pgrp as u64` is
in `[0, i32::MAX]`), and `process/creation.rs`'s 2 sites publish
`pid.as_u64()`. Rule 5 of the ratchet pins the TIOCSPGRP refusal for that
reason — it is load-bearing for the encoding, not decoration.

**Behaviour, uncontended.** The snapshot answers with the value the mutex would
have given. Both readers do the same thing with it they did before.

**Behaviour, contended.** The input entry defers the adoption when the field is
unset (rather than skipping it), and the signal path delivers to the last
published pgrp (rather than dropping the signal). The x86 `serial_println!` on
that degrade arm is gone with the arm.

### Why the snapshot rather than try-and-defer

The brief allowed either. The snapshot was taken because it removes the mutex
from the interrupt path outright rather than leaving a non-waiting touch on it,
and because the signal path has no sensible thing to defer: a Ctrl+C deferred
to the next `sys_read` is a Ctrl+C the reader will not see as a signal. The
brief's `TTY_IRQ_FG_DEFERRED` counter belongs to the try-and-defer design and
has no subject here; #821's `TTY_IRQ_PM_DEFERRED` already counts the one
deferral this entry makes, and this round leaves it counting the same thing.
What replaced it is named below.

## The detector, in production

`crate::process::in_no_blocking_process_manager_scope()` reports whether #821's
per-CPU `NoBlockingProcessManagerScope` is open on this CPU. That scope is
entered at exactly one place — `input_char_nonblock` — so a reading of true
means this CPU is inside a TTY interrupt entry. This round extends it to a
second lock rather than adding a second scope, which is what the brief
preferred.

`note_foreground_pgrp_acquisition(blocking)` runs immediately before each of the
5 acquisitions in `driver.rs` and, when the scope is open, bumps
`TTY_IRQ_FG_LOCK_TOUCHES` — plus `TTY_IRQ_FG_BLOCKING_ACQUIRES` for the blocking
subset. The note is taken BEFORE the acquisition, so a call that waits on a lock
its own CPU owns is counted rather than lost.

`try_lock` IS counted here, unlike `try_manager()` in #821. The reason is the
defect: a `try_lock` on this mutex cannot wedge, and it is still wrong, because
its degrade arm loses a signal. The two counters are kept separate so the x86
arm can key its refusal on the blocking one alone.

The other 4 counters: `TTY_IRQ_FG_SNAPSHOT_READS` (interrupt-side reads
answered from the snapshot) and `TTY_IRQ_FG_SIGNAL_CALLS` /
`TTY_IRQ_FG_SIGNAL_LAST_PID` / `TTY_IRQ_FG_SIGNAL_LAST_SIG`, recorded by
`send_signal_to_process_nonblock` at the delivery hop. The signal three are 3
relaxed cells and not one transaction: a reader sampling them while 2 CPUs
dispatch can pair a count with the other CPU's pid. The oracle reads them after
a single injection with preemption disabled, where that cannot happen.

## The oracle

`tty_irq_fg_oracle`, in `kernel/src/test_framework/registry.rs`, boot_tests
only. Registered in the aarch64 registry at `TestStage::ProcessContext` beside
#796's, #812's and #821's windows — tests within one subsystem run sequentially
on that subsystem's kthread, so its console borrow cannot overlap #821's — and
called from `main.rs`'s driver-test window on x86, where the boot thread runs
with IF=1 and a thread-context holder of this lock with interrupts live is the
exposed shape.

It borrows the console: saves the termios and foreground pgrp, clears ECHO so
its injected bytes (the INTR byte's `^C` included) cannot land in a serial log a
gate is scoring, installs pgrp 822, and puts both fields back afterwards
(`restored=1`, which checks the snapshot as well as the field).

Three legs.

1. **The detector, with the mutex free.** One ordinary byte (`s`) through
   `tty::push_char_nonblock`, with preemption disabled so the per-CPU scope is
   released on the slot it was taken on.
2. **The held-lock injection.** A thread holds `foreground_pgrp` for 20 ms,
   UNMASKED — aarch64 on a peer CPU through a kthread, x86 on this CPU with
   IF=1 — and the INTR byte (0x03) goes through the same entry under it.
   Unmasked is the point: `tcsetpgrp` holds this lock with interrupts live, so
   that is the shape an input interrupt has to survive.
3. **The thread side.** The field is cleared and set through the ordinary
   accessors, and the snapshot is read back both times (`snapshot_agrees`).

Verdict lines:

```
[TTY_IRQ_FG_ORACLE:aarch64:fg_known=822:target_absent=1:fg_lock_touches=0:fg_blocking_acquires=0:snapshot_reads=3:processed=2:buffered=1:irqs_enabled_before=1:holder_cpu=1:fg_busy_probe=1:hold_us=20002:entry_us=116:joined=1:sig_calls=1:sig_pid=822:sig_num=2:snapshot_agrees=1:restored=1:PASS:peer_hold]
```

`fg_lock_touches=0` and `fg_blocking_acquires=0` are the property.
`sig_calls=1:sig_pid=822:sig_num=2` is the injected Ctrl+C still reaching the
signal path with the right pgrp under the hold. `fg_busy_probe=1` is the
independent reading that the mutex really was owned at the instant of the
injection; `hold_us` is the holder's own measurement of its window. `entry_us`
is what the aarch64 arm measures: an entry that acquired the mutex waits the
peer's whole window out.

### Deviations from the brief, and why

* **The brief's red-on-main reading is `entry_us ~20000`; the unmutated
  `783a6a53` entry does not block.** Both interrupt-side sites there are
  `try_lock`, so the red the tree really has is `sig_calls=0` — the dropped
  Ctrl+C — not a 20 ms wait. Both reds are driven: leg M3 below is `main`'s
  exact text and reddens on `sig_calls=0`; leg M2 restores a blocking
  acquisition and reddens at `entry_us=20048`, which is the census's own F4
  shape measured rather than argued.
* **The byte is driven through `tty::push_char_nonblock`, not a hardware input
  event.** Neither a PS/2 scancode nor a virtio-input event can be injected from
  inside the guest. This is the real entry, one frame below the handler — the
  same deviation #821 records.
* **The aarch64 holder runs on a kthread, not in interrupt context.** What it
  measures is how long the entry takes while another CPU owns the lock, which is
  the same wait an interrupt would take; it does not claim the measurement was
  taken from an exception frame.
* **The x86 leg 2 is gated on leg 1**, and reports `arm=handler_would_block`
  when the entry still reaches a blocking acquisition. That machine boots
  `-smp 1`; the injection would take the boot with it.
* **`entry_us` is pinned tightly on aarch64 and loosely on x86**, for the reason
  #821 gives: the x86 profile's monotonic clock is TSC-backed only when the TSC
  is calibrated. The x86 boot recorded `entry_us=1125` against the aarch64
  gate's 116..154; that arm carries the completed-under-hold reading, not a
  timed one, and its gate pattern accepts any `[0-9]+`.
* **No live process's signal mask is touched.** See "What is NOT claimed".

## What is NOT claimed

* **No live process's signal mask is touched, and "reached the right process"
  is measured one hop short of that.** The oracle installs pgrp 822 after
  checking the process manager holds no row for it (`target_absent=1`), and its
  reading is `sig_calls`/`sig_pid`/`sig_num` — the pid the interrupt side
  resolved and handed to `send_signal_to_process_nonblock`, recorded at that
  hop. Setting SIGINT pending on a live process inside a boot gate would be a
  boot hazard: the target could take the signal and die between the injection
  and any attempt to clear it. So the oracle reads the signal as DISPATCHED to
  the right pid under a held lock, where the 2 red mutations above read
  `sig_calls=0`; it does not read a process row's pending mask at all.
* **No timing claim.** No cycle count was taken for the snapshot read, the
  counters or the scope on the input path. `entry_us` measures the oracle's own
  injection, not a benchmark.
* **The oracle does not run in interrupt context.** See the deviations above.
* **The x86 arm does not measure a wait**, and on an entry that still reaches a
  blocking acquisition it reports that fact rather than driving the wedge.
* **The snapshot is not a substitute for the mutex.** The thread side still owns
  the field and still takes the lock; what changed is that the interrupt side
  stopped asking for it. A reader that needs the CURRENT value under mutual
  exclusion — the ioctl paths, `store_foreground_pgrp`'s own check-then-set —
  still takes the mutex.
* **A `tcsetpgrp` in flight can still be raced, and now loses differently.**
  Before, a signal arriving mid-`tcsetpgrp` was dropped. Now it is delivered to
  the outgoing foreground pgrp. That is the POSIX-shaped outcome and it is
  better than a drop, but it is a behaviour change; this round adds 0
  synchronisation between an input interrupt and a `tcsetpgrp` in flight.
* **The PTY's own `foreground_pgid` was read, not surveyed.** It is a different
  lock on a different device, with no interrupt-side caller in this tree.
* **0 of #812, F2 and F5** of the IRQ-context lock census are addressed here.
  Those are the `PROCESS_MANAGER` and UDP-socket findings, and this branch
  changes 0 lines on their paths.
