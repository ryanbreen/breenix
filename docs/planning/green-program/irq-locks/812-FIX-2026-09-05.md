# #812 — the non-blocking process-manager acquisition masks local interrupts

Branch `fix/812-try-manager-masked`, off `origin/main` at `be412ee9`
(the #819 / #796 merge). R157 small-PR mode: one defect, one repair, one
oracle, one ratchet.

## The defect

`crate::process::try_manager()` (`kernel/src/process/mod.rs`) acquired
`PROCESS_MANAGER` — a non-reentrant `spin::Mutex` — without touching interrupt
state, while the two other accessors of the same lock mask around the hold:

| accessor | interrupt handling before this branch |
|---|---|
| `manager()`, aarch64 arm | `mrs daif` then `msr daifset, #0xf` before `PROCESS_MANAGER.lock()`; DAIF restored in `Drop`, after the release |
| `manager()`, non-aarch64 arm | no mask operation |
| `with_process_manager()`, x86_64 | `x86_64::instructions::interrupts::without_interrupts` |
| `with_process_manager()`, aarch64 | `crate::arch_impl::aarch64::cpu::without_interrupts` (`msr daifset, #3`) |
| `try_manager()` | 6 lines, one `try_lock()`, 0 interrupt-state operations |

Verified unchanged on this branch: the aarch64 `manager()` arm and both
`with_process_manager()` bodies still mask, and the diff touches 0 of those 3
bodies.

## The chain

1. `kernel/src/arch_impl/aarch64/syscall_entry.S` clears DAIF.I/F before
   `bl rust_syscall_handler_aarch64`, and the handler only raises
   `preempt_count`. An aarch64 syscall body therefore runs IRQ-unmasked.
2. A syscall body takes `try_manager()` and holds it. Interrupts are live.
3. An IRQ lands. `handle_irq` (`arch_impl/aarch64/exception.rs`) calls
   `per_cpu_aarch64::irq_exit()` and then `crate::task::softirqd::do_softirq()`
   unconditionally.
4. `do_softirq()` refuses on `in_interrupt() || in_softirq()`; the aarch64
   `in_interrupt()` reads HARDIRQ, NMI and SOFTIRQ_OFFSET and does not read the
   PREEMPT field, so a preempt-disabled interrupted context does not refuse it.
5. The NetRx handler runs: `net/mod.rs`'s `net_rx_softirq_handler` ->
   `drain_loopback_rounds` -> `ipv4::handle_ipv4` -> `udp::handle_udp` ->
   `udp::deliver_to_socket`.
6. `deliver_to_socket` acquires the same `PROCESS_MANAGER` through the
   **blocking** `with_process_manager`. The holder is on this CPU, so the mask
   inside that accessor does not help: the CPU waits for a lock it owns.

x86_64 does not have this chain, by accident of a different gate:
`per_cpu::irq_exit()` runs `do_softirq()` only at `preempt_count() == 0`, and
`rust_syscall_handler` brackets the whole syscall in
`preempt_disable`/`preempt_enable`.

## The repair (R178)

`try_manager()` becomes a masked acquisition on both arches. It saves the
interrupt-enable state, masks, and then `try_lock`s; a failed `try_lock`
restores at once; `TryProcessManagerGuard` carries the saved state and restores
it on drop **after** the `ManuallyDrop` release, the same release-then-restore
ordering `ProcessManagerGuard::drop` already documents. aarch64 uses the same
`daifset #0xf` mask `manager()` uses, so the two acquisition modes now differ
only in whether they block; x86_64 saves and restores RFLAGS.IF through
`crate::arch_interrupts_enabled()` / `arch_disable_interrupts()` /
`arch_enable_interrupts()`.

Two shapes were considered and not chosen, per the ruling: gating aarch64's
`do_softirq()` on the whole `preempt_count` (a chain repair — it does not reach
a holder that is not preempt-disabled), and converting `deliver_to_socket` to a
non-blocking acquisition (a chain repair — it reaches one of the lock's IRQ-side
consumers).

### What this does NOT reach

* **F4 / the TTY input path.** `tty/driver.rs`'s `input_char_nonblock` reaches
  the blocking `crate::process::current_pid()` -> `manager()` from a keystroke
  IRQ, and blocks on the console TTY's `foreground_pgrp` at
  `set_foreground_pgrp`. On aarch64 this branch removes the unmasked
  `try_manager()` holders from that window's exposed set; the x86 leg — where
  `manager()` itself is unmasked — is untouched, and the `foreground_pgrp`
  blocking acquisition is untouched on both arches.
* **F5 / the UDP socket lock.** `net/udp.rs`'s `deliver_to_socket` blocks on the
  per-socket `Mutex<UdpSocket>` while `ipc/poll.rs`'s `poll_fd` holds the same
  lock outside any mask on the `sys_poll` path. This branch does not touch that
  lock.
* **The x86_64 `manager()` arm** is still an unmasked blocking acquisition.
* Both remain open findings; neither is claimed closed here.

### The cost

Each acquisition gains one read of the interrupt-enable state and one mask, and
each guard drop gains one restore. On aarch64 that is `mrs Xn, daif` plus
`msr daifset, #0xf` at the acquire and `msr daif, Xn` at the drop; on x86_64 a
read of RFLAGS.IF plus `cli`, and a conditional `sti` at the drop. The 10
IRQ-side callers above pay it on a path that previously changed no interrupt
state; in IRQ context the saved state is already masked, so the restore puts
back what was there. **No timing measurement is claimed**: no cycle count was
taken, and the boot evidence below is a pass/fail reading, not a performance
one.

A second, real consequence: a `try_manager()` holder that logs now logs with
interrupts masked. `syscall/signal.rs`'s `sys_pause_with_frame_aarch64` does
exactly that inside its hold. `manager()` holders already had this property.

## The oracle

`irq_hold_oracle`, `kernel/src/test_framework/registry.rs`, boot_tests-only
(`test_framework` is compiled only under `boot_tests`/`btrt`), registered in
`SYSCALL_TESTS` at `TestStage::ProcessContext`.

Setup: bind a UDP socket on port 54540 to the first live process row and install
it in that row's fd table, so `deliver_to_socket` has a socket to resolve and
the oracle keeps an `Arc` to read the receive queue from. Torn down after the
verdict is printed.

Holder, on a peer CPU via `kthread_run_on_cpu_for_test`: `preempt_disable`, a
`try_manager()` hold, then loopback UDP datagrams to that socket — which raises
NetRx softirq-pending on that same CPU — and a 12 ms spin before the release.
The aarch64 tick target is 1 kHz, so the window spans more than two ticks. The
holder body contains 0 unmask operations: whether the window is interruptible is
decided by `try_manager()`.

Verdict line, 13 fields:

```
[IRQ_HOLD_ORACLE:aarch64:attempts=A:armed=1:holder_cpu=C:irqs_enabled_before=1:masked_in_hold=1:sends=N:hold_us=H:netrx_pending_at_release=1:received=R:stalled=0:hold_done=1:joined=1:PASS]
```

* `irqs_enabled_before=1` — the precondition: the holder entered with interrupts
  live, the way an aarch64 syscall body does. A window already masked by its
  caller cannot score.
* `masked_in_hold=1` — the repair's own signature, read from DAIF inside the
  hold.
* `netrx_pending_at_release=1` — the deadlock's trigger was pending on this CPU
  at the moment of release, so the window really did carry it.
* `hold_us` — the measured window, from CNTVCT_EL0, which advances while a CPU
  is masked.
* `stalled=0` — the holder came back. `stalled=1` is the defect's own signature
  and is the one reading that needs no publication from the holder: the wedge
  can land on the instruction after the acquire.
* `received` — the datagram reached the socket after the hold. Which context
  delivered it (the softirq, kloopbackd, or an idle drain) is deliberately not
  asserted.

### Deviation from the brief, and why

The brief said one datagram. The holder sends one at the top of the window and
re-queues about once per millisecond across it, reporting `sends=N`. A single
datagram does not make the red deterministic: an idle peer CPU drains the shared
loopback queue from its own idle loop, and a stealer that takes the batch then
blocks on the held lock leaves the holder's own softirq an empty queue. Observed
on the first red attempt, where the holder wedged before publishing and the
verdict read `armed=0`, which understates what happened. Re-queueing across the
window means the holder's next IRQ exit finds work whether or not the first
datagram was stolen.

## The ratchet

`tests/teardown_structure.rs`:
`try_manager_is_a_masked_acquisition_on_every_arch` derives the architecture
arms from the `*breenix*.json` target specifications at the repository root —
an arm added later is swept in, an arm deleted reddens — and requires each one
to save and mask before its `try_lock`, restore on the failed acquire, carry a
saved-state field on `TryProcessManagerGuard`, and restore on drop after the
`ManuallyDrop` release rather than before it.

`try_manager_mask_ratchet_is_not_vacuous` carries a green control and 6 red
legs over in-memory copies: aarch64 mask deleted, x86_64 mask deleted, aarch64
failed-acquire restore deleted, x86_64 restore deleted from the guard drop, the
release call renamed out of the drop, and the release moved below both restores
while staying present. Each leg asserts `assert_ne!` on the mutated text first.

The sixth leg is the one that reads the ordering half of
`restored_after_release`; the fifth removes the release and so reddens on
release presence whatever the ordering is. Its anti-vacuity run is
`serials/812/15`: with the detector weakened to
`drop_body.find(restore).is_some()`, the suite fails on the sixth leg and on 0
of the other 5, and that leg's census reads `failures were []` — before this
leg, 0 of the ratchet's legs reddened when the release moved below both
restores. The leg asserts
its own reorder landed (release still present, both restores ahead of it)
before it runs, so a mis-anchored mutation cannot pass by reddening on the
missing-release message instead.

Stated limits, in the file: the recogniser trusts the spellings `daifset` /
`msr daif` and `arch_disable_interrupts` / `arch_enable_interrupts` and does not
resolve them; it reads comment-stripped raw text rather than the code mask the
scheduler ratchet uses, because the aarch64 spellings are `asm!` operands inside
string literals; synchronous exceptions are outside the model, since
`msr daifset` masks I and F and not a data abort.

**Standing landing step.** A branch whose fix adds a new required line to
either aarch64 gate scorer's `score_serial` inherits every fixture that, at
merge time, `tests/*_structure.rs` replays through that scorer in
scoring-only mode — including fixtures a concurrently-landed branch added
after this one forked, which this branch never wrote and cannot have
anticipated. Concretely, at this landing that set was 2 fixture paths:
`grep -rn "BREENIX_STRICT_SCORE_ONLY\|BREENIX_PROD_SCORE_ONLY" tests/*.rs`
over the merged tree finds exactly `loopback_pump_structure.rs` and
`ttbr0_shadow_reconciliation_structure.rs`, and both thread the same 2 paths
into those variables:
`docs/planning/green-program/aarch64-testing/serials/slice3d/01-strict-boot1-serial.txt`
and
`docs/planning/green-program/aarch64-testing/serials/slice3d/02-prod-boot1-serial.txt`.
Neither is a fixture this branch's own round produced.
Re-recording those shared
fixtures at the merged head, from a boot of the merge commit's own
`--features boot_tests` kernel, is part of the R16 merge step for any branch
in this position — not a follow-up, and not scoped to only the fixtures the
branch's own round originally touched. `#796` did this for the asid-ratchet
fixture; `#812`'s own review round did it again for the same file; this
landing does it a third time, for a file `#812` never touched, because the
scorer it added a requirement to is shared.
