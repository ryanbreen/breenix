# #821 — the TTY input IRQ entry stops blocking on `PROCESS_MANAGER`

Branch `fix/821-tty-irq-no-pm-block`, off `origin/main` at `9538ebb7`
(the #873 merge). R157 small-PR mode: one defect, one repair, one oracle, one
ratchet file.

## The defect

`TtyDevice::input_char_nonblock` (`kernel/src/tty/driver.rs`) is the body both
architectures' input interrupts reach. Its own doc comment said "This version
uses try_lock and is safe for interrupt context" while its first statement
called `crate::process::current_pid()`, and `current_pid` blocks in
`crate::process::manager()`.

## The chain

| arch | from | through | to |
|---|---|---|---|
| x86_64 | `interrupts.rs` `keyboard_interrupt_handler` | `tty::push_char_nonblock` | `driver.rs` `input_char_nonblock` -> `crate::process::current_pid()` -> blocking `manager()` |
| aarch64 | `drivers/virtio/input_mmio.rs` `handle_interrupt` | `tty::push_char_nonblock` | the same two hops |

Two further interrupt-side callers of the same entry exist
(`drivers/virtio/input_pci.rs`, `drivers/usb/hid.rs`), and the ratchet counts
the 4 of them rather than listing them.

The blocking call sat inside `if self.foreground_pgrp.try_lock().map(|g|
g.is_none()).unwrap_or(false)`, so it ran while the console TTY had no
foreground process group set.

**What the two architectures pay is different, and this round measures each on
its own terms.**

* **x86_64.** `manager()`'s non-aarch64 arm performs 0 mask operations, so a
  thread-context holder runs with IF=1 — `main.rs`'s driver-test window is one.
  An input interrupt taken on top of such a holder, on a machine that boots
  `-smp 1`, waits for a lock its own CPU owns and does not return.
* **aarch64.** Each of the 3 PROCESS_MANAGER accessors masks (PR #833 gave
  `try_manager()` the mask #812 asked for), so the same-CPU wedge is not
  available. What is left is a remote hold: CPU A owns the lock with interrupts
  masked while CPU B takes the input interrupt, and B's entry waits out A's
  whole window in interrupt context. Measured here at 20022 us against a 20 ms
  hold.

## Why the pid was needed, and where it went

The pid fed exactly one statement — `self.set_foreground_pgrp(current_pid.as_u64())`
— whose comment reads "Auto-set foreground process group if not set. This
allows signals to work even if shell doesn't call tcsetpgrp." So the pid names a
foreground process group for `send_signal_to_foreground_nonblock` to deliver
SIGINT/SIGQUIT/SIGTSTP to.

An interrupt is a poor place to resolve that. `manager.current_pid()` returns
the process manager's notion of the *currently running* process, which in an
interrupt is whichever thread the keystroke preempted — not the terminal's
reader. The red leg below shows the sharper version of the same point: in the
oracle's context that call resolved no pid at all, so on the unrepaired kernel
the entry paid 2 blocking acquisitions and set 0 foreground pgrps
(`pgrp_set_by_entry=0` with `pm_blocking_acquires=2`).

The consumer can be resolved later, in thread context, and it is already in
hand there. `sys_read`'s stdin arm looks the reading process up through
`manager.find_process_by_thread(thread_id)`, which returns `(ProcessId,
&Process)`; the pid half was being discarded into `_pid`. The repair keeps it as
`reader_pid` and hands it to the TTY after `drop(manager_guard)`.

So:

* **IRQ side** — `input_char_nonblock` keeps the `foreground_pgrp.try_lock()`
  read (a `try_lock` with a degrade arm, unchanged), and where the pid lookup
  was it now sets a lock-free `adopt_pending` flag on the device and bumps
  `TTY_IRQ_PM_DEFERRED`. It takes 0 PROCESS_MANAGER acquisitions.
* **Thread side** — `TtyDevice::adopt_deferred_foreground_pgrp(pid)` swaps that
  flag down and, if the field is still unset, sets it and bumps
  `TTY_IRQ_PM_ADOPTED`. `tty::driver::adopt_foreground_pgrp_from_reader(pid)` is
  the module entry `sys_read` calls.

The check-then-set shape is the one the IRQ path already had, composed out of
the two existing accessors (`get_foreground_pgrp` + `set_foreground_pgrp`), so
this adds 0 new acquisition sites on the `foreground_pgrp` mutex. A second
setter racing this one wins exactly as it did before.

**Behaviour change, stated plainly.** The pgrp is now adopted when the first
byte is *consumed* rather than when it *arrives*. Before any read there is no
reader for a signal to reach, and `process/creation.rs` sets the field at
process creation on both of its paths, so the auto-set remains what it was: a
fallback for a console whose shell has not called `tcsetpgrp`.

## The detector, in production

`crate::process::NoBlockingProcessManagerScope` is an RAII marker with a per-CPU
depth. `input_char_nonblock` enters one; `manager()` and both
`with_process_manager()` bodies call `note_blocking_process_manager_acquisition()`
before acquiring, which bumps a global counter when a scope is open on this CPU.
`try_manager()` deliberately does not count: it does not wait, and since PR #833
it masks around its hold, so the interrupt side is allowed to use it —
`send_signal_to_process_nonblock` does.

The scope releases the slot index it captured at entry, so a region entered on
one CPU and left on another cannot leave a permanent depth behind.

The note is taken BEFORE the acquisition, so a call that wedges on a lock its
own CPU already owns is still counted — which is what lets the x86 arm read the
defect without driving the wedge.

## The oracle

`tty_irq_pm_oracle`, in `kernel/src/test_framework/registry.rs`, boot_tests
only. Registered in the aarch64 registry at `TestStage::ProcessContext`
alongside #796's and #812's PM-holding windows, for the same three reasons those
give; on x86 it is called from `main.rs`'s driver-test window, because that
window is where the boot thread runs with IF=1 and an x86 `manager()` holder
with interrupts live is exactly the exposed shape the census names.

It borrows the console TTY: saves the termios and the foreground pgrp, clears
ECHO so its injected bytes cannot land in a serial log a gate is scoring, clears
the foreground pgrp so the deferring branch is live, and puts both fields back
afterwards (`restored=1`).

Three legs.

1. **The detector**, with the lock free. One byte through
   `tty::push_char_nonblock`, with preemption disabled so the per-CPU scope is
   released on the slot it was taken on. Reads `pm_blocking_acquires`,
   `deferred` and whether the entry set the pgrp itself.
2. **The held-lock injection.** aarch64 parks a peer CPU on `manager()` for
   20 ms and measures `entry_us` across a second injection; x86 takes the lock
   on this CPU and injects under it. The x86 arm refuses to drive this leg when
   leg 1 says the entry still reaches a blocking acquisition, and reports
   `handler_would_block` instead — a uniprocessor injection under a held lock
   would take the whole boot with it.
3. **The consumer.** `adopt_foreground_pgrp_from_reader(ProcessId::new(821))`,
   then the pgrp is read back.

Verdict lines:

```
[TTY_IRQ_PM_ORACLE:aarch64:fg_unset_before=1:pm_blocking_acquires=0:deferred=2:pgrp_set_by_entry=0:processed=2:buffered=2:irqs_enabled_before=1:holder_cpu=1:pm_busy_probe=1:hold_us=20000:entry_us=2:joined=1:adopted=1:adopted_pgrp=821:restored=1:PASS:peer_hold]
[TTY_IRQ_PM_ORACLE:x86:fg_unset_before=1:pm_blocking_acquires=0:deferred=2:pgrp_set_by_entry=0:processed=2:buffered=2:irqs_enabled_before=1:pm_held_during_entry=1:entry_us=23:adopted=1:adopted_pgrp=821:restored=1:PASS:local_hold]
```

`fg_unset_before=1` is the precondition; `pm_busy_probe=1` (aarch64) and
`pm_held_during_entry=1` (x86) are the independent readings that the lock really
was held at the instant of the injection; `hold_us` is the peer's own
measurement of its window. `pm_blocking_acquires=0` is the property.

### Deviations from the brief, and why

* **The byte is driven through `tty::push_char_nonblock`, not through a
  hardware input event.** Neither a PS/2 scancode nor a virtio-input event can
  be injected from inside the guest, so the oracle drives the function both
  interrupt handlers call. It is the real entry, one frame below the handler.
* **The aarch64 arm's injection runs on a kthread, not in interrupt context.**
  What it measures is how long the entry takes while a remote CPU owns the
  lock, which is the same wait an interrupt would take; it does not claim the
  measurement was taken from an exception frame.
* **The x86 leg 2 is gated on leg 1.** Stated above and stamped into the
  verdict as `arm=handler_would_block`. On the unrepaired kernel the x86 arm
  therefore reports a FAIL derived from leg 1 rather than from a measured wait.
* **`entry_us` is pinned tightly on aarch64 and loosely on x86.** The x86
  profile's monotonic clock is TSC-backed only when the TSC is calibrated;
  a tight pin there would be a flake rather than a reading. The aarch64 gate
  carries the timed reading; the x86 gate carries the completed-under-hold one.

## What is NOT claimed

  readers (`get_foreground_pgrp`, `send_signal_to_foreground`, the two ioctl
  paths). This round adds 0 acquisition sites on that mutex.
  One thing did change on that lock's map and is disclosed rather than claimed:
  `input_char_nonblock` no longer calls `set_foreground_pgrp`, so the chain
  #822 records through `driver.rs:191` no longer exists. Whether any other
  interrupt-side caller reaches that blocking acquisition was not surveyed
  here, and #822 stays open on its own terms.
* **No timing claim.** No cycle count was taken for the counters or the scope
  added to the input path. `entry_us` is a measurement of the oracle's own

* **The x86 arm does not measure a wait.** On the unrepaired kernel it reports
  that the entry would block; it deliberately does not drive the wedge that
