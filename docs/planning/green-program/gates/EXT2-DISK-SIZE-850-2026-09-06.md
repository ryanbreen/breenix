# ext2 disk payload-vs-size guard (#850, R157 small-PR mode)

## The bug, re-derived

`scripts/create_ext2_disk.sh --arch aarch64 --size 8` failed partway
through the Docker copy step:

```
Creating ext2 disk image...
  Arch: aarch64
  Output: .../target/ext2-aarch64.img
  Size: 8MB
  Using Docker to create ext2 filesystem...
  WARNING: busybox.elf not found, skipping coreutils
Installing other binaries...
cp: write error: No space left on device
```

Measured directly against the real payload the script installs for
aarch64 (`du`/`stat` against `userspace/programs/aarch64/*.elf` and
`fonts/*.ttf` in a checkout with the aarch64 userspace binaries built):

```
find userspace/programs/aarch64 -name '*.elf' | wc -l   -> 149 files, 47424 KB total
find fonts -name '*.ttf' -exec du -k {} + | awk sum      -> 16120 KB total
```

Not claimed: that the exact file count and byte total above are a fixed,
reproducible property of this branch's commit. `userspace/programs/
aarch64/*.elf` files are gitignored build artifacts (`git ls-files |
grep '\.elf$'` returns 0 of them, and `git check-ignore` confirms
`.gitignore:9:*.elf` is why), not tracked content, so the precise
count/bytes are a property of whichever build produced the checkout's
binaries at the time of measurement, not of the branch itself -- the same
caveat this doc's "What is NOT claimed" section already applies to the
x86_64 46MB figure. What is reproducible, and was re-verified live in this
round's own review pass by re-running the script (`./scripts/
create_ext2_disk.sh --arch aarch64 --size 8`), is the rounded headline the
guard itself prints -- `Payload: 62MB` / `Minimum image size for this
payload: 94MB` -- which matches this doc's diagnosis section exactly and
is what the guard's pass/fail decision actually runs on, not these
byte-level figures.

That is roughly 62MB of real payload -- files the script's docker heredoc
copies into `/mnt/ext2` regardless of `--size` (busybox + hardlinked
coreutils, the other `.elf` binaries routed to `/bin`, `/sbin`,
`/usr/local/cbin`, `/usr/local/test/bin`, and the TrueType fonts to
`/usr/share/fonts`) -- against an 8MB image. `--size 8` fell far short of
enough; it is not a regression that recently stopped fitting, it is a
hardcoded number that predates today's binary/font set by a wide margin.

The one caller in the tree that passed this `--size 8`,
`docker/qemu/run-aarch64-userspace.sh`, used it both to size the initial
`dd`/`mke2fs` call and, on each subsequent run, to decide whether an
existing `target/ext2-aarch64.img` needed to be recreated (`stat`'s byte
size compared against a hardcoded `EXT2_SIZE_BYTES=$((8 * 1024 * 1024))`).
The other 12 of 13 real call sites in the tree -- `run.sh` (4 sites) and
nine further `docker/qemu/*.sh` gates -- call `create_ext2_disk.sh` with no
`--size` at all and get the script's own 256MB default, which was not at
risk (46MB payload on x86_64, 62MB on aarch64, both well under 256MB).

## Diagnosis: which resource is exhausted

This is payload space, not inode exhaustion. Reproduced directly against a
probe container building 8/64/72/80/88/96MB images and copying the real
aarch64 payload into each:

| Requested size | Result | `df` inside the mounted image |
|---|---|---|
| 8MB | `cp: write error: No space left on device` (as reported) | -- |
| 64MB | `cp: write error: No space left on device` (5 files) | 58.7M / 58.7M used, 0 available, 100% |
| 72MB | succeeds | 66.2M size, 61.8M used, 810.0K available (99%) |
| 80MB | succeeds | 73.5M size, 61.8M used, 7.6M available (89%) |
| 88MB | succeeds | 81.0M size, 61.8M used, 14.7M available (81%) |
| 96MB | succeeds | 88.5M size, 61.8M used, 21.8M available (74%) |

`mke2fs`'s own metadata (inode tables, block group descriptors, reserved
GDT blocks reserved for a future `resize2fs`) is not a fixed number of
bytes at these sizes -- the free space measured above scales with the
requested size, not with a constant overhead. 72MB (810KB free) is too
tight a margin to ship as a floor; 88-96MB left a comfortable 14.7-21.8MB
of genuine headroom over the same ~62MB of real content.

## The fix: `scripts/create_ext2_disk.sh` derives its own floor from the payload

The script now sums the real `*.elf` files directly under `$USERSPACE_DIR`
and the `*.ttf` files under `$PROJECT_ROOT/fonts` (portable `stat -f%z` /
`stat -c%s`, the same two globs its own copy loops use), derives a required
minimum with headroom, and refuses to proceed -- before `mkdir`, `dd`, or
`docker run` -- when the requested (or default) `SIZE_MB` cannot fit it:

```bash
required_bytes=$(( payload_bytes * 29 / 20 + 4 * 1024 * 1024 ))
required_mb=$(( (required_bytes + 1024 * 1024 - 1) / (1024 * 1024) ))
```

The `29/20` (1.45x) multiplier and the flat `+4MB` are the table above,
translated: 1.45x reproduces the 88-96MB range's comfortable margin from a
~62MB payload; the flat 4MB covers `/etc`, `/tmp`, `/home`, `/var/log` and
the built-in test text files, which don't scale with the binary/font
payload. On a shortfall the script prints the payload size, the computed
minimum, and the exact shortfall, then `exit 1`s -- it never truncates an
image or lets the Docker copy step discover the problem on its own.

`docker/qemu/run-aarch64-userspace.sh`'s own hardcoded `--size 8` and its
size-mismatch recreate logic are deleted; it now calls
`create_ext2_disk.sh --arch aarch64` with no `--size`, matching every other
caller (12 of 13 real call sites already did; this was the 13th), and
falls back to the script's own existence check the same way the rest of
the tree does.

## The ratchet: `tests/ext2_disk_size_structure.rs`

Two properties, both checked against the real files (`scripts/
run-structure-tests.sh ext2_disk_size_structure`, no crate dependency,
std-only):

1. `payload_guard_structure_is_present_and_load_bearing` -- three
   sub-predicates against the script's real text (payload computed from
   the real globs; a required minimum derived arithmetically from that
   payload, not a flat number; a failing branch that names the shortfall
   and actually exits with a failing status), each proven load-bearing by
   a targeted mutation of the real source: removing the glob-accumulation
   loop reddens only the first predicate, removing only the trailing
   `exit 1` (leaving each echo, including the shortfall message, intact)
   reddens only the third, and removing the whole guard block reddens the
   second and third together. This third mutation is the sharpest one:
   it is exactly the "print a warning but continue anyway" shape #850's
   own fix rules out.
2. `no_caller_passes_a_size_flag` -- a census over `docker/` (recursive),
   `scripts/` (recursive, excluding the script's own file), and `run.sh`:
   each real invocation of `create_ext2_disk.sh` (13 in total, matching
   the diagnosis section's own count) passes no `--size` flag. Anti-vacuity
   floor at 13, and a mutation reinstating
   `run-aarch64-userspace.sh`'s original `--size 8` reddens this test by
   name, reproducing #850's own bug shape rather than a synthetic string.

A review pass on this branch's initial round found `--whole-file` reporting

is clean.

## What is NOT claimed

- Not claimed: that the 18/20 first strict-gate attempt's two failures are
  a known, pre-adjudicated flake signature. They were observed once, under
  measured host contention from two concurrent `cargo build` processes,
  and the re-run without that contention scored 20/20; that is the extent
  of the investigation this round did. If this signature recurs on an
  otherwise idle host, it is a new finding, not a confirmation of this
  round's own guess.
- Not claimed: that `29/20` and `+4MB` are a permanently correct headroom
  formula. They are derived from one measured aarch64 payload (~62MB) at
  one point in time; as the binary/font set grows, the guard's own printed
  `Payload:`/`Minimum image size:` lines make a future shortfall visible
  and loud rather than silent, which is the property this round is
  actually fixing -- not a claim that the specific multiplier never needs
  retuning.
- Not claimed: x86_64 payload behavior was re-derived at HEAD by a real
  build in this round (it was not -- the worktree's x86_64 userspace
  binaries were not built here). The 46MB x86_64 figure this doc's "The
  bug, re-derived" section cites is carried over from the diagnosis phase
  against a separately available prior build of the same tree, not from a
  fresh build inside this branch's own worktree.
