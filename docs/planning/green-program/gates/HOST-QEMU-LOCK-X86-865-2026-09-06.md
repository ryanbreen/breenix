# Extending the host-wide QEMU lock to x86 (#865)

## Why

`docker/qemu/lib/qemu-host-lock.sh` (#826/#835/R181) serialized
`qemu-system-aarch64` boots on this Mac; the beast x86 host had no
equivalent. #865's own report: several `qemu-system-x86_64` TCG lanes
running concurrently on beast starve each other and hit the gates' own
timing ceilings on an otherwise healthy guest (Run Inspector run
`20260906T014135Z-x86_64-gate-864a`: `boot=900s total=1081s`, failed on
`clock_gettime_test`, the #631/#766 timing signature).

## What changed

**The lock helper is now arch-aware** (`docker/qemu/lib/qemu-host-lock.sh`):
`qemu_host_lock_dir`, `qemu_host_lock_count`, and `qemu_host_lock_acquire`
take the QEMU binary name as an argument, defaulting to
`qemu-system-aarch64` so the ~30 pre-existing aarch64 call sites keep
working byte-for-byte with no edit. One lock domain per binary
(`a64-qemu.lock` / `x86-qemu.lock` under the same cache root, or the
shared `BREENIX_QEMU_LOCK` override for either) -- an aarch64 boot and an
x86 boot on the same host do not contend with each other.
`gate-boot-facts.sh`'s `gbf_resolve_qemu_pid` takes the same second
argument so it walks past a `timeout(1)` wrapper to the right child on
either arch.

**17 x86 launch sites wired**, the full census
`grep -rln qemu-system-x86_64 docker/ scripts/ run.sh` found (reproduced
mechanically, not a hand list -- see the ratchet section below):
`docker/qemu/run-blocking-recv-test.sh`, `run-boot-parallel.sh`,
`run-dns-test.sh`, `run-ext2-lock-race-gate.sh`, `run-fs-fault-gate.sh`,
`run-interactive.sh`, `run-keyboard-test.sh`, `run-kthread-parallel.sh`,
`run-kthread-test.sh`, `run-nonblock-eagain-test.sh`,
`run-x86-boot-tests.sh`, `run-x86-prod-profile-boot-test.sh`,
`run-x86-tty-oracle-gate.sh`; `run.sh`; `scripts/run-interactive-native.sh`,
`scripts/test-workqueue.sh`, `scripts/test_tracing_via_gdb.sh`.
`run-fs-fault-gate.sh` and `run-ext2-lock-race-gate.sh` already had an
`ARCH`-branched aarch64 leg; the x86 leg now acquires its own domain the
same way, and the shared `qemu_host_lock_release` call after each gate's
poll loop was already ARCH-unconditional (a no-op on a leg whose own
acquire was skipped), so it needed no change.

`run-boot-parallel.sh` and `run-kthread-parallel.sh` launch their own
`COUNT` boots concurrently by design (a host-throughput optimization for
local stress-testing, not a kernel-concurrency test): each acquires the
lock once before its own launch loop and releases once after its own wait
loop, treating the whole `COUNT`-boot batch as one occupant of the x86
lock domain rather than serializing the batch's own internal launches.
Each other site acquires/tracks/releases around its single boot.

**Confirmed NOT wired, and why** (mirroring the #834 precedent's own
disclosed-exclusions style): `scripts/f21-bisect-verdict.sh`,
`scripts/772-dispatch-boot.sh`, and `scripts/ci/ring3_check.sh` mention
`qemu-system-x86_64` only inside comments about processes they explicitly
document not launching (confirmed by reading each); `docker/qemu/Dockerfile`'s
`CMD` is a version-check default no caller in this repository invokes
without overriding args, and it is not a `.sh` file the ratchet's
`shell_scripts_below` walk would reach anyway; `scripts/breenix_runner.py`'s
only reference is a `pkill`, not a launch, and it is Python (no `source`
mechanism), the same category #834 already excluded three `.py` launchers
from for the aarch64 lock.

## Real defects found and fixed along the way

Wiring the x86 gates was the first time a `qemu-system-x86_64` gate ran
this shared library on Linux with `set -o pipefail` (the two x86 gates
this round names set it; the two pre-existing aarch64 callers do not).
Three latent `set -e`/`pipefail` hazards in `gate-boot-facts.sh` surfaced
immediately, each the identical shape: a bare `v="$(pipeline)"` assignment
where the pipeline's FIRST stage can fail while a LATER stage (`awk`,
`tr`, `tail`/`cut`) still succeeds and exits 0 -- under `pipefail` the
pipeline's own reported status is still the earlier failure, and under
`set -e` that fails the whole script at the assignment, before the
function's own designed fallback ever runs.

1. `gbf_load_1m`'s `sysctl -n vm.loadavg` (a valid key on macOS, not on
   Linux) aborted `run-x86-boot-tests.sh` on beast before ever reaching
   its own `/proc/loadavg` fallback:
   ```
   QEMU HOST LOCK: host qemu-system-x86_64 count before acquire: 0
   x86 frame-custody gate run 1: FAIL (set -e abort at ./docker/qemu/run-x86-boot-tests.sh:507, exit 1)
     failing command: LOAD_AT_START="$(gbf_load_1m)"
   ```
   Full serial: `docs/planning/green-program/gates/865-x86-host-qemu-lock/beast-load1m-abort-2026-09-06.txt`.
2. `gbf_resolve_qemu_pid` and `gbf_qemu_cpu_seconds`'s own
   `ps -o ... -p "$pid" | tr -d ' '` assignments fail the identical way
   whenever `$pid` has already exited on its own -- exactly the "process
   died before the poll loop's own bound" path the new x86 `ended_by`
   buckets (`qemu_exited_early`) exist to name, and exactly the case each
   function's own doc comment already said it should report as `NA`
   rather than abort on.
3. `gbf_last_heartbeat_uptime_ms`'s two-stage grep fails the same way
   whenever the serial carries 0 `[heartbeat]` markers -- observed on
   each x86 boot this branch ran, since the x86 profile's init service
   does not print that literal.

Each of the 3 got the same `|| true` fix `gbf_load_1m` needed, with each
function's own doc comment corrected to describe the fix (and, for
`gbf_load_1m`'s own comment, corrected from an unverified "not a failure"
claim to name precisely which of the file's 4 callers the hazard is live
for: the 2 running under `pipefail`, not the 2 aarch64 ones -- `set -e`
alone, without `pipefail`, does not surface an earlier pipeline stage's
failure when the last stage succeeds).

A first version of the two named gates' `GATE_BOOT_FACTS` wiring derived
`ended_by` by re-grepping the same `BOOT_TESTS:FAIL|KERNEL PANIC|panic!`,
`TEST:network:*:FAIL`, and `TEST:userspace:*:FAIL` literal patterns a
second time after the poll loop (and, in the prod-profile gate, by
re-testing `$reached` a second time). `loopback_pump_structure.rs` and
`teardown_structure.rs` both pin the exact occurrence count of that
literal text in these two files (`== 2` for the FAIL/PANIC pattern and
each `TEST:*:FAIL` pattern, `$passed` reads `== 1`, `$reached`
occurrences `== 1`) and both went red on this branch as a direct result,
confirmed by running each locally. Both gates are revised to set a
`POLL_BREAK_REASON` variable inline at each poll loop's own existing
break sites (including the success branch, alongside
`passed=true`/`reached=true`) instead, so `ended_by` is read off that
variable with no new occurrence of any literal pattern either ratchet
counts.

## The ratchet: `tests/qemu_host_lock_structure.rs`, widened

Adds the x86 twin of each aarch64 predicate: `is_qemu_x86_launch_line`
(same shape -- a non-comment line that, once a trailing continuation is
stripped, ends with the bare `qemu-system-x86_64` token) and
`launches_qemu_x86`, plus a second whole-suite test,
`every_x86_qemu_launch_script_sources_and_acquires_the_host_lock`,
mirroring the aarch64 one. `calls_qemu_host_lock_acquire` is loosened from
an exact match on the bare identifier to also accept
`qemu_host_lock_acquire <argument>` -- still requiring a literal space
after the identifier, so the helper's own `qemu_host_lock_acquire() {`
definition line (no space before the `(`) is not mistaken for a call.

Anti-vacuity floor measured at 17 (the census above); not a closed list --
a future x86 launcher only needs to raise the count, not edit it down.
Two new mutation legs (`docker/qemu/run-x86-boot-tests.sh` under
`docker/qemu/`, `scripts/test-workqueue.sh` under `scripts/`) prove the
x86 whole-suite rule reddens by name the same way the two existing
aarch64 legs do.

## Beast demonstration: two concurrent invocations

Two private clones on beast (`/root/breenix-x86lock`,
`/root/breenix-x86lock-b`, each its own `rust-fork` copy so neither's
build touches the other's), both at `gates/x86-host-qemu-lock` HEAD
(`6cffead6b`).

**Trial 1** (before the launch-detachment fix below): clone A launched
`run-x86-boot-tests.sh 1` alone at `2026-09-06T06:09:00Z`, reached its
own boot and printed `QEMU HOST LOCK: host qemu-system-x86_64 count
before acquire: 0` by `06:11:26Z`, while holding the lock. Clone B was
launched at `06:11:35Z` and its own log shows:

```
QEMU HOST LOCK: host qemu-system-x86_64 count before acquire: 0
QEMU HOST LOCK: waiting for /root/.cache/breenix/x86-qemu.lock (30s elapsed, host qemu-system-x86_64 count=0)...
QEMU HOST LOCK: waiting for /root/.cache/breenix/x86-qemu.lock (60s elapsed, host qemu-system-x86_64 count=0)...
QEMU HOST LOCK: waiting for /root/.cache/breenix/x86-qemu.lock (90s elapsed, host qemu-system-x86_64 count=0)...
```
(read back at `06:18:56Z`, while A's own boot was still running its
userspace test cohort) -- the second invocation waiting on the lock,
exactly as required.

**Trial 2** (after the fix below, cleanest evidence): both clones
launched within the same second, `2026-09-06T06:28:54Z`. Both reached
`QEMU HOST LOCK: host qemu-system-x86_64 count before acquire: 0` within
seconds of each other; clone B's own log then shows 14 consecutive
30-second-interval wait messages while clone A held the lock:

```
QEMU HOST LOCK: waiting for /root/.cache/breenix/x86-qemu.lock (30s elapsed, host qemu-system-x86_64 count=0)...
QEMU HOST LOCK: waiting for /root/.cache/breenix/x86-qemu.lock (60s elapsed, ...)...
... (90s, 120s, 150s, 180s, 210s, 240s, 270s, 300s, 330s, 360s, 390s)
QEMU HOST LOCK: waiting for /root/.cache/breenix/x86-qemu.lock (420s elapsed, host qemu-system-x86_64 count=0)...
```
`ps` at `06:34:29Z` showed both the clone-A and clone-B script processes
alive (`05:34` elapsed each). At `06:40:32Z`, the lock directory's own
`pid` file read `1283243` -- clone B's own PID -- and `kill -0 1283243`
returned 0 (alive): clone A had released the lock (no "reclaiming stale
lock" message appears anywhere in clone B's log, so this was A's own
clean `qemu_host_lock_release`, not B's stale-holder reclaim path) and
clone B had acquired it and launched its own `qemu-system-x86_64` (`ps`
confirmed a clone-B-pathed QEMU process running since `06:36`). Clone B
then booted for approximately 10 more minutes.

This is the required demonstration: a second concurrent invocation of
`run-x86-boot-tests.sh 1` genuinely blocks on the lock (quoted
timestamps, sustained past 7 minutes in trial 2) while a first
invocation holds it, and correctly acquires and boots once the first
cleanly releases.

## What was NOT achieved on beast, and why: an unrelated, ongoing host disk failure

Neither trial produced two completed `PASS` verdicts, and the standalone
`run-x86-prod-profile-boot-test.sh` demonstration (the "prod gate PASS
with its facts line quoted" requirement) was not obtained either. Across
4 independent attempts (trial 1's two clones, trial 2's two clones, and one
standalone prod-profile run), each gate script's own process tree --
the bash script AND its `qemu-system-x86_64` child together -- vanished
from `ps` with **no** ERR-trap `FAIL` line, no `GATE_BOOT_FACTS` line, no
partial verdict: the signature of an uncatchable `SIGKILL` delivered to
the whole process group, not a script-internal `set -e` abort (which
this branch's own ERR traps are designed to print something for). The cutoff
point varied across attempts -- `[init] Breenix init starting (PID 1)`
in the fastest case (~90s after launch), `[RECLAIM_DRAIN:...]` deep in
the userspace test cohort in the other three (5-10 minutes after
launch) -- ruling out any single code path or elapsed-time threshold as
the trigger.

`sudo journalctl -k` **on the beast host** (not the container) shows an
active, ongoing hardware fault on physical disk `sdh` at the same wall-clock
moments as each of the 4 deaths, e.g. at the exact time of the
fastest (prod-profile) death:

```
Sep 06 06:48:51 beast kernel: device offline error, dev sdh, sector 0 op 0x0:(READ) flags 0x0 phys_seg 1 prio class 2
Sep 06 06:48:51 beast kernel: Buffer I/O error on dev sdh, logical block 0, async page read
Sep 06 06:48:51 beast kernel: ldm_validate_partition_table(): Disk read failed.
...
Sep 06 06:49:18 beast kernel: sd 4:0:3790:0: Power-on or device reset occurred
```
and, ~10 minutes earlier, at trial 2's own timeframe:
```
Sep 06 06:38:56 beast kernel: sd 4:0:3785:0: attempting task abort!scmd(0x00000000ac59a87e), outstanding for 30317 ms & timeout 30000 ms
```
A 5-minute journalctl window at the time carried 88 lines mentioning
`sdh`. This is scoped to the host's storage hardware, filed as
[#871](https://github.com/ryanbreen/breenix/issues/871) -- not a
Breenix code defect, not one of the pre-adjudicated x86 timing
signatures (#631/#766, which fail a *specific test* with a *specific
marker*, not silently vanish the whole process tree with no output at all),
and not something a gate script or this PR's own diff can fix or work
around. The lock mechanism itself is not implicated: trial 2's clean
release-then-reacquire hand-off (above) happened inside this same
failing window, and worked correctly.

Both beast clones were removed at the end of this session
(`/root/breenix-x86lock`, `/root/breenix-x86lock-b`, and their tmp
output/rust-fork-copy directories).

## What is NOT claimed

- **No clean two-PASS or prod-gate-PASS beast run was obtained**, for
  the disk-hardware reason above -- disclosed, not hidden. The
  lock-contention evidence (waiting timestamps, correct release/reacquire
  hand-off) stands independently of it.
- **This branch does not restructure `run-boot-parallel.sh` or
  `run-kthread-parallel.sh`'s own internal N-way concurrent launches
  into serialized ones**, unlike the #826/R181 precedent's own rewrite
  of `run-aarch64-kthread-parallel.sh`. Both scripts' internal
  parallelism is their own design (a host-throughput stress test, not a
  kernel-concurrency test); the lock added here covers cross-script/
  cross-lane contention, the shape #865 itself reports, not this
  internal one.
- **`gate_boot_facts_structure.rs` is not extended to police the two new
  x86 gates' own `ended_by` vocabulary** the way it polices the two
  aarch64 gates' 5-value one -- the two x86 gates use a different,
  smaller vocabulary (`scored_pass`/`failure_marker` or `crash_marker`/
  `qemu_exited_early`/`poll_exhausted`) suited to their own control flow,
  and extending that specific ratchet is a separate change with its own
  review, not named by #865's own ask (which named
  `tests/qemu_host_lock_structure.rs` specifically).
- **The 4 `.py`/comment-only/non-`.sh` files named in the census section
  above remain unwired**, for the reasons given there.
