# Kill-by-name-of-qemu fix and ratchet (#829, R157 small-PR mode)

## The hazard

`docker/qemu/run-aarch64-test.sh` and `docker/qemu/run-aarch64-userspace.sh`
each ended their cleanup with

```
docker kill $(docker ps -q --filter ancestor=breenix-qemu-aarch64) 2>/dev/null || true
```

`docker ps --filter ancestor=` matches any container currently running
from that image, not only the one this invocation started, so the first of
two concurrent invocations to finish kills the second invocation's
still-running container out from under it. #829's own comment thread found
the identical shape a second time, pre-`qemu_host_lock_acquire`, in
`docker/qemu/run-aarch64-interactive.sh`'s "kill any existing containers"
preflight. Auditing this round's own reachable set (each script that
sources `docker/qemu/lib/qemu-host-lock.sh`, the same set
`tests/qemu_host_lock_structure.rs` already walks) found a fourth,
differently-shaped instance: `scripts/run-arm64-boot-test.sh`'s
`pkill -9 -f "qemu-system-aarch64.*kernel-aarch64"` pre-launch cleanup --
#834's own F2 round had already moved this to run *after*
`qemu_host_lock_acquire` (closing the lock-cooperator-vs-lock-cooperator
case) but had not eliminated it as a mechanism: it could still reach a
process outside the lock's cooperation altogether, e.g. a human's own manual
`qemu-system-aarch64` boot for GDB debugging.

## Scope: the aarch64 host-lock reachable set (4 files)

This round fixes the four instances above -- the scripts that cooperate
with `docker/qemu/lib/qemu-host-lock.sh`, this project's own shared
mutual-exclusion lock for `qemu-system-aarch64` boots. Ten more scripts
carry the identical shape but launch `qemu-system-x86_64` (a lock domain
that helper does not cover, so they sit outside this round's reachable set
and its ratchet's census); filed as #849 rather than folded into this
round, per R157 small-PR mode. A separate, unrelated pre-existing bug in
`scripts/create_ext2_disk.sh`'s 8MB aarch64 sizing (found incidentally while
gathering this round's own live evidence) is filed as #850, also not fixed
here.

## The fix

Each of the four files gets the same shape #829's own "Shape of a fix"
section proposes and #834's F2 round already applied once to a sibling file
(`docker/qemu-aarch64/run-arm64-boot.sh`): capture this invocation's own
identifier and act on that, not on a name/pattern that could also match a
peer's.

### `docker/qemu/run-aarch64-test.sh`, `docker/qemu/run-aarch64-userspace.sh`

`CONTAINER_NAME="breenix-aarch64-test-$$"` (resp. `-userspace-`), passed to
`docker run --name`. Cleanup is a `trap`-installed function --
`docker stop -t 5 "$CONTAINER_NAME"` -- registered *before*
`qemu_host_lock_acquire` runs, so `qemu_host_lock_acquire`'s own
`_qhl_chain_exit_trap` (`docker/qemu/lib/qemu-host-lock.sh`) chains it onto
the lock's EXIT trap: it now fires on each exit path this script can take
(normal completion, an early `exit 1` from a missing kernel, or a signal),
not only the bottom-of-script line the pre-#829 version relied on.
`docker stop`'s own contract is exactly "TERM then KILL after a bounded
wait": SIGTERM to the container's PID 1, SIGKILL only if it has not exited
within the 5s timeout. A `docker rm -f "$CONTAINER_NAME"` preflight (a
no-op unless a same-PID-numbered container somehow survived an earlier
crash) precedes it, matching `run-arm64-boot.sh`'s own precedent.

No new fixed `/tmp` path is introduced -- `CONTAINER_NAME` is a Docker
identifier, not a filesystem path, and each script's `OUTPUT_DIR` was
already `BREENIX_GATE_TMP`-based from #825.

### `docker/qemu/run-aarch64-interactive.sh`

The pre-acquire "kill any existing containers" block (`EXISTING=$(docker ps
-q --filter ancestor="$IMAGE_NAME")`; `docker kill $EXISTING`) is replaced
outright, not merely re-scoped: now that each aarch64 launcher in this tree
cooperates with `qemu_host_lock_acquire`, a second invocation simply waits
for the lock instead of needing a peer's container force-killed out from
under it. The only container the replacement's own `docker rm -f
"$CONTAINER_NAME"` preflight can ever remove is a same-PID-numbered leftover
from an earlier crashed run of this exact script. Same `--name` +
trap-installed `docker stop -t 5` cleanup as the two scripts above.

### `scripts/run-arm64-boot-test.sh`

Different shape (no Docker container here -- this script launches
`qemu-system-aarch64` natively), so a different fix: `QEMU_PID_FILE` records
this script's own last-launched QEMU PID (written immediately after
`QEMU_PID=$!`, removed after the script's own later `kill $QEMU_PID; wait
$QEMU_PID` step). Before a new launch, a stale entry is read and acted on
*only* after a `kill -0` liveness check succeeds -- the identical
stale-PID-reclaim protocol `docker/qemu/lib/qemu-host-lock.sh`'s own
`qemu_host_lock_acquire` already uses for its lock directory. TERM is sent
first, then up to 5 one-second polls, then KILL if still alive. This is
strictly narrower than the pkill it replaces: `pkill -9 -f
"qemu-system-aarch64.*kernel-aarch64"` could reach *any* matching process on
the host, including one a human is running by hand; the pidfile can only
ever name a PID *this script itself* wrote there.

## The ratchet: `tests/qemu_kill_by_name_structure.rs`

One property: no `.sh` script that sources
`docker/qemu/lib/qemu-host-lock.sh` (29 scripts as of this round, the same
reachable set `tests/qemu_host_lock_structure.rs` already walks) kills a
qemu-ish process or container by name/pattern rather than by an identifier
this invocation captured. Three shapes:

1. `pkill`/`killall` naming a qemu-ish pattern (`pkill -P <pid>`, parent-PID
   targeting rather than a name pattern, is excluded).
2. `kill` fed from a `pgrep` search naming a qemu-ish pattern.
3. `docker kill`/`docker stop` fed from a `docker ps` ancestor/image query,
   inline or via a variable this same file assigns from exactly that query
   on an earlier line (the real `run-aarch64-interactive.sh` shape:
   `EXISTING=$(docker ps ... --filter ancestor=...)` on one line, `docker
   kill $EXISTING` on a later one -- checked as a same-file dataflow, not a
   same-line one).

Census-shaped: `kill_by_name_of_qemu_violations` re-derives each violation
from a script's own text each time it runs, so a new lock-cooperating
script that reintroduces any of the three shapes is caught automatically,
not only the four this round fixed.

### Anti-vacuity

`kill_by_name_predicates_are_not_vacuous` checks, in order:

- Each of the three shapes fires on a literal string built from the exact
  real pre-fix syntax.
- The safe shapes this round's own fix introduces (`docker kill
  "$CONTAINER_NAME"`, `docker stop -t 5 "$CONTAINER_NAME"`) do **not** fire,
  nor does `run-vmware-gate.sh`'s real `pkill -P "$pid"`, nor the lock
  helper's own real `pgrep -x qemu-system-aarch64` COUNT line (no `kill`
  verb on that line at all), nor a doc comment describing the hazard in
  prose.
- Each of the four fixed files, read from disk post-fix, is clean (no
  violations) -- sanity before the reddening mutation below.
- **Reddening, real pre-fix text**: the literal, verbatim pre-#829 line/block
  from each of the four files is spliced back into that file's real
  (post-fix) text read from disk, and `kill_by_name_of_qemu_violations` is
  asserted non-empty against the result -- for
  `run-aarch64-interactive.sh` this is the real two-line dataflow shape
  (the `EXISTING=$(docker ps ...)` assignment and the `docker kill
  $EXISTING` call on a later line), not a single-line synthetic stand-in.
- **Reach check**: the four fixed files are confirmed present in the
  ratchet's own `lock_cooperator_scripts()` census, confirming their clean
  text reflects real detection rather than files the census walk skipped.

## Disclosed, not fixed

- **#849**: the identical kill-by-name-of-qemu shape in ten more scripts
  that launch `qemu-system-x86_64` rather than `qemu-system-aarch64` --
  outside `docker/qemu/lib/qemu-host-lock.sh`'s own reachable set and this
  round's ratchet. Two of the ten
  (`docker/qemu/run-boot-parallel.sh`, `docker/qemu/run-kthread-parallel.sh`)
  are CLAUDE.md-documented canonical test scripts, not legacy/superseded
  ones -- higher production traffic than the four fixed here.
- **#850**: `scripts/create_ext2_disk.sh --arch aarch64 --size 8` fails with
  `cp: write error: No space left on device` (the 8MB image's own filesystem
  fills up, not the host disk) -- found incidentally while gathering this
  round's own live evidence, unrelated to the kill-by-name hazard, not fixed
  here.

## What is NOT claimed

- **The x86-side kill-by-name instances (#849) are not fixed or ratcheted
  by this round.** A concurrent `docker/qemu/run-boot-parallel.sh` /
  `docker/qemu/run-kthread-parallel.sh` invocation (or any of the other
  eight #849 lists) can still kill a peer's own running container/process.
- **This round is not a soak.** Each live check above is one invocation per
  script; the strict-gate run is 1 boot. Neither is a many-iteration
  statistical claim about contention frequency.
- **`docker/qemu-aarch64/run-arm64-boot.sh` is untouched by this round** --
  it was already fixed by #834's own F2 round and its predicates in
  `tests/qemu_kill_by_name_structure.rs`'s anti-vacuity suite confirm it
  stays clean; this round adds no new fix to that file.
- **The ratchet's reachable set is exactly "sources
  `docker/qemu/lib/qemu-host-lock.sh`", not "each script under `docker/`,
  `scripts/`, or `run.sh`".** A future script that launches
  `qemu-system-aarch64` without sourcing that helper (were one to exist)
  would not be walked by this ratchet; it would first need to be caught by
  `tests/qemu_host_lock_structure.rs`'s own wiring requirement.
