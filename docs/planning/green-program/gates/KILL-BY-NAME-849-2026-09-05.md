# Kill-by-name-of-qemu fix and ratchet widening (#849, R157 small-PR mode)

x86 twin of #829/PR #851. #829's own round fixed the four aarch64 scripts
that cooperate with `docker/qemu/lib/qemu-host-lock.sh`; that lock is
aarch64-only, so ten x86-side scripts launching `qemu-system-x86_64` carried
the identical hazard shape outside its reachable set, disclosed and filed
as this issue rather than folded into that round.

## The hazard, re-derived

Widening the census used to build #829's own ratchet
(`grep -rln "pkill\|killall\|pgrep" docker/ scripts/ run.sh`, plus a direct
walk for `docker kill`/`docker stop ... --filter ancestor=` shapes the
first grep alone does not surface) over the full x86-side tree found
exactly the ten scripts #849's own issue body lists, no more and no fewer:

| File | Shape |
|------|-------|
| `docker/qemu/run-boot-parallel.sh` | `docker kill $(docker ps -q --filter ancestor=breenix-qemu)` in its docker-fallback cleanup branch |
| `docker/qemu/run-kthread-parallel.sh` | same, unconditional (no native branch) |
| `docker/qemu/run-kthread-test.sh` | same, at two exit points (success and timeout) |
| `docker/qemu/run-dns-test.sh` | same, at two exit points |
| `docker/qemu/run-blocking-recv-test.sh` | same, at two exit points |
| `docker/qemu/run-nonblock-eagain-test.sh` | same, at three exit points |
| `docker/qemu/run-interactive.sh` | `EXISTING=$(docker ps -q --filter ancestor="$IMAGE_NAME")` / `docker kill $EXISTING` pre-launch preflight |
| `scripts/test-workqueue.sh` | `pkill -9 qemu-system-x86_64` + `docker kill $(docker ps ...)`, at a preflight and three further points including the EXIT trap |
| `scripts/f21-bisect-verdict.sh` | `pkill -9 qemu-system-x86` + `killall -9 qemu-system-x86_64`, in the EXIT trap and a pre-run preflight -- this script drives a Parallels VM and does not launch `qemu-system-x86_64` itself |
| `scripts/ci/ring3_check.sh` | `pkill -f qemu-system-x86_64` preflight |

Each carries the identical failure mode #829's own report names: the first
of two concurrent invocations sharing an image, ancestor filter, or bare
pattern to finish (or, for `test-workqueue.sh`/`ring3_check.sh`, to merely
*start*) can kill a different, concurrent invocation's own still-running
process out from under it. `f21-bisect-verdict.sh` is the sharpest instance
of the class: it does not launch `qemu-system-x86_64` at all (Parallels is a
hypervisor, not QEMU), so its two `pkill`/`killall` lines had no legitimate
target of their own to reach -- any host process they matched belonged to
someone else's concurrent gate.

## The fix

### The seven `docker run`-based scripts

Each names its own container from its own invocation identity
(`--name breenix-<script>-$$`, or `breenix-<script>-$$-<i>` for the two
scripts that launch several containers per invocation:
`run-boot-parallel.sh`'s docker-fallback branch and
`run-kthread-parallel.sh`), and stops that name specifically instead of an
ancestor-image match:

- `run-boot-parallel.sh`, `run-kthread-parallel.sh`: an array of
  per-iteration container names, stopped with `docker stop -t 5` in a loop
  at the bottom of the script (both already reap their *native*-runner PIDs
  the same way; only their docker-fallback path had the ancestor-filter
  bug, since native QEMU is what this project's own x86 gate host provides
  and docker is a fallback for a host without it).
- `run-kthread-test.sh`, `run-dns-test.sh`, `run-blocking-recv-test.sh`,
  `run-nonblock-eagain-test.sh`: a single `CONTAINER_NAME="breenix-<script>-$$"`,
  `--name`-scoped, stopped by a `trap`-installed cleanup function
  (`docker stop -t 5 "$CONTAINER_NAME"`) that fires on any exit path
  (each script's own success/timeout `exit 0`/`exit 1`, or an early
  `set -e` exit) instead of the per-exit-point ancestor-filtered kill lines
  it replaces.
- `run-interactive.sh`: the pre-launch "kill any existing container"
  preflight (`EXISTING=$(docker ps ...)` / `docker kill $EXISTING`) is
  dropped outright, matching #829's own precedent for
  `run-aarch64-interactive.sh` -- its own container is now `--name`-scoped
  and stopped by a `trap`-installed `docker stop -t 5` the same way; a
  same-PID-numbered leftover from an earlier crashed run of this exact
  script is the only thing the preflight's removal gives up reclaiming.

### `scripts/test-workqueue.sh`

Same `CONTAINER_NAME`/trap shape as the four single-container scripts
above, plus the bare `pkill -9 qemu-system-x86_64` preflight is dropped
(same rationale as `run-interactive.sh`'s dropped preflight): this
project's cleanup, once scoped to the invocation's own container name,
does not need a scorched-earth kill of any `qemu-system-x86_64` on the
host to reclaim its own leftovers.

### `scripts/f21-bisect-verdict.sh`

Both `pkill -9 qemu-system-x86` / `killall -9 qemu-system-x86_64` lines
(the `cleanup()` EXIT trap's copy and the pre-run preflight's copy) are
dropped, not replaced -- this script owns no process of its own for them to
reach. Its own two resources (`$VM_NAME`, the named Parallels VM; `$RUN_PID`,
its own `./run.sh` child) were already reclaimed by name/PID one line above
each removed pair.

### `scripts/ci/ring3_check.sh`

The top-level `pkill -f qemu-system-x86_64` preflight -- a duplicate of one
`scripts/breenix_runner.py`'s own `start()` also carries -- is dropped.
**Still open one layer down**: `breenix_runner.py`'s own internal copy of the
identical line could not be fixed in this round (its `.py` extension routed
through this session's own source-edit gate, which this round's dispatch
could not clear); filed as #854 and disclosed in-line in
`ring3_check.sh`'s own comment at the removal site, per this project's
"any failure you find is your problem" policy rather than silently folded
in as though the chain were closed end to end. `ring3_check.sh` invoking
`breenix_runner.py` still means a concurrent bystander QEMU can be killed
by this path today -- #854 is the open tracking item for that, not this
file.

## Live evidence: a private throwaway QEMU survives a scripted termination of the gate's own

Run on beast (`/root/breenix-t849`, this branch's own HEAD,
`159008b88...`), the designated x86 build/test host -- Docker is not
installed in this Incus container, so the seven `docker run`-based fixes
are proven at the source level (structural ratchet + mutation reddening
below) rather than with a live `docker ps` before/after, and the
PID-scoped idiom common to each of the fixed non-docker files (`kill "$PID"` /
`self.process.terminate()` / the native branches' `kill
"${RUNNER_PIDS[$i]}"`) is proven live instead, against real concurrent
QEMU processes on a genuinely shared host.

**The hazard is not hypothetical on this host.** While this round's own
`run-x86-boot-tests.sh 1` gate (PID 862148, below) was running, a
separate, unrelated x86 SMP investigation's own gate was *also* running
concurrently on the same beast container:

```
pgrep -a -f qemu-system-x86_64
862148 qemu-system-x86_64 ... /root/breenix-t849-tmp/breenix_x86_boot_tests_1/... (this round's own gate)
880237 qemu-system-x86_64 ... /root/breenix-smp1-tmp/... (an unrelated, concurrent x86 SMP gate)

pgrep -f qemu-system-x86_64 | wc -l
3   (the two above, plus the pgrep invocation's own argv self-match)
```

A bare `pkill -f qemu-system-x86_64` or `killall qemu-system-x86_64` --
either of the two exact shapes removed from `test-workqueue.sh`,
`f21-bisect-verdict.sh`, and `ring3_check.sh` above -- run at that moment
would have killed PID 880237, a process this session does not own and had
no way to know about in advance. Per this project's standing rule (kill
QEMU by own PID only, not by name) and to avoid disturbing a real concurrent
investigation on a shared host, that command was not executed live, even
as a demonstration; this `pgrep` snapshot is offered as the live evidence
of the hazard's shape instead of a destructive re-enactment of it.

**The fixed idiom, run against real processes (host quiescent, PID
880237 already finished on its own by this point):**

```
qemu-system-x86_64 -m 32 -display none -no-reboot -monitor none -serial none &
THROWAWAY_PID=887816
qemu-system-x86_64 -m 32 -display none -no-reboot -monitor none -serial none &
GATE_PID=887817

ps -p 887816,887817 -o pid,stat,cmd
    PID STAT CMD
 887816 Sl   qemu-system-x86_64 ...
 887817 Sl   qemu-system-x86_64 ...

--- scripted termination of the gate's own QEMU, by its captured PID ---
kill 887817

AFTER_TERMINATION:
THROWAWAY (887816) alive: YES
GATE (887817) alive: NO
```

`kill "$PID"` against a captured identifier is exactly the mechanism this
round's non-docker fixes rely on (`f21-bisect-verdict.sh`'s `kill
"$RUN_PID"`, `breenix_runner.py`'s `self.process.terminate()`/`.kill()`,
`run-boot-parallel.sh`'s and `run-kthread-parallel.sh`'s native-branch `kill
"${RUNNER_PIDS[$i]}"`) and the direct analog of the `docker stop -t 5
"$CONTAINER_NAME"` idiom the seven docker-based fixes use in place of an
ancestor-image filter: an invocation-captured identifier reaches only the
process/container that identifier names, not a bystander sharing the
same image or binary name. Both throwaway processes were torn down by this
report immediately after; `pgrep -a -f qemu-system-x86_64` afterward showed
0 running.

## The ratchet: `tests/qemu_kill_by_name_structure.rs`, widened

The file's one property is unchanged (no `.sh` script kills a qemu-ish
process or container by name/pattern rather than an invocation-captured
identifier), but its reachable set is widened from "each script that
sources `docker/qemu/lib/qemu-host-lock.sh`" (29 scripts, the aarch64-only
lock's own cooperators) to `all_shell_scripts()` directly: each `.sh` file
under `docker/` (recursive) and `scripts/` (recursive), plus `run.sh`
itself -- 95 scripts as of this round. `qemu-system-x86_64` has no
host-wide lock analogous to `qemu-host-lock.sh`, so the old scope had no way
to reach any of the ten files this round fixes; a script needs
no shared lock to owe this property, only the ability to run concurrently
with another script on the same host, which any script in this tree can.

The `sources_qemu_host_lock` / `lock_cooperator_scripts()` helpers are
retained (not deleted) for one narrower purpose: the anti-vacuity test's
own reach-check still confirms the four aarch64 files #829 fixed are
genuinely lock cooperators, as a sanity check on that round's own claim,
now that they are no longer what gates the ratchet's main assertion.

### Anti-vacuity, extended

`kill_by_name_predicates_are_not_vacuous` keeps each #829-era assertion
(the three shapes fire on literal pre-fix strings; the safe post-fix shapes
and the lock helper's own COUNT line do not; the four aarch64 files are
clean post-fix and reddenable with their own real pre-#829 text; the four
files are present in the census) and adds, one entry per file, for the ten
x86-side fixes:

- **Real-file-clean**: each of the ten now reads clean via
  `kill_by_name_of_qemu_violations`.
- **Reddening, real pre-#849 text**: each file's own real removed line(s)
  (verbatim -- `docker kill $(docker ps -q --filter
  ancestor=breenix-qemu)`/`ancestor="$IMAGE_NAME"` for the seven
  docker-based scripts, the two-line `EXISTING=.../docker kill $EXISTING`
  dataflow for `run-interactive.sh`, and the exact `pkill`/`killall` lines
  for `test-workqueue.sh`, `f21-bisect-verdict.sh`, and `ring3_check.sh`)
  are spliced back onto that file's real post-fix text read from disk, and
  the ratchet is asserted to redden against each one of them.
- **Reach check**: the fourteen fixed files (four aarch64 + ten x86, plus
  `run-interactive.sh`'s own two-line block checked alongside the other
  nine single-line entries) are confirmed present in the widened
  `all_shell_scripts()` census.
