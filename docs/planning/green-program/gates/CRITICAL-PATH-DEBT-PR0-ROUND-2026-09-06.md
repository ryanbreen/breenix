`CRITICAL_PATH_LOG_ANCHORS` (48 rows, summing to 135) is not hand-transcribed
from the plan doc's table. It was generated by writing the same `code_mask`/
`item_spans`/`item_path_at` pipeline as a standalone binary, running it
against this branch's checked-out tree, and pasting its output into the
`const`. The generator and its output are not part of this commit (scratch
tooling only); the const in the committed suite is what that pipeline
produces against `783a6a53` today, which this round's own `cargo test`/
`rustc --test` runs (below) re-confirm independently.

The wider census is not a second hand-maintained table -- `wider_anchors()`
appends exactly one row (`kernel/src/arch_impl/aarch64/
exception.rs :: fn sys_write`, count 1) to `CRITICAL_PATH_LOG_ANCHORS` at
test time, so "wider = narrow + the one escaped site" is visible in code
rather than asserted in two tables that could drift.

## What this round deliberately did not do

The plan doc's own PR-0 section says the suite should be "named in
`docker/qemu/run-x86-boot-tests.sh` and `docker/qemu/run-aarch64-boot-test-
strict.sh` beside the existing structure-suite calls." Checked the tree at
this commit for that wiring before adding to it: neither script invokes
`scripts/run-structure-tests.sh` or `cargo test --test <structure-suite>`
today, and a repo-wide search finds no gate script anywhere under
`docker/qemu/` that calls `run-structure-tests.sh`. `scripts/run-structure-
tests.sh`'s own header already says as much ("It does not run in any gate
... Wiring it into a gate is a separate change with its own review"). So the
plan's "beside the existing calls" premise does not hold against this tree,
and this round's actual DELIVER/PROOF list (from the dispatching brief) asks
only for `scripts/run-structure-tests.sh critical_path_logging_census_
structure` green plus the full suite battery -- not for gate wiring.

Separately, `docker/qemu/run-aarch64-boot-test-strict.sh` carries its own
documented hazard for exactly this kind of addition: its
`require_boot_tests_kernel` comment states that "ANY `cargo test` in the
same session" silently rebuilds and hardlinks a kernel binary without the
`boot_tests` feature over the one that gate expects, and that an earlier
acceptance battery that ran the structural suites and then this gate scored
0/6 against a production kernel that was never asked to emit the gate's
markers. A same-session `cargo test --test critical_path_logging_census_
structure` call added naively into that script would risk exactly that
failure mode. `scripts/run-structure-tests.sh` sidesteps it (it compiles via
`rustc --test` directly, not `cargo test`), so wiring this suite into that
gate -- if wanted -- should go through that script, sequenced before any
`boot_tests` kernel build in the same session, as its own deliberate change
with its own review, per that script's header. Left undone here rather than
done unreviewed.
