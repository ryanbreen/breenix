# x86_64 tracing leg — #533, the staged boot-test registry

Date: 2026-08-28. Branch `feat/green-tracing`, off `main` @ `54aa16a1`.
All runs on the beast x86 VM (`breenix-x86`), QEMU TCG, one boot per run.

## The state #533 described, measured

`#533` says the x86 boot "reaches marker-only stage advancement without
dispatching the staged boot-test registry" and can emit `[TESTS_COMPLETE:0/0]`.
A full `boot_tests,testing,external_test_bins` boot on `main` @ `54aa16a1`
produced exactly three registry markers across both serial ports:

```
[STAGE:user:ADVANCE]
[TESTS_COMPLETE:0/0]
[BOOT_TESTS:PASS]
```

`[BOOT_TESTS:START]` never appeared; `grep -c BOOT_TESTS serial_kernel.txt` was
`0`. All three lines come from `advance_stage_marker_only`, called from the first
Ring 3 syscall. Nothing in the registry ran, and the boot still printed a
pass-shaped verdict.

## Why the call was unreachable

`test_framework::run_all_tests()` was called from `main.rs` immediately before
`per_cpu::preempt_enable()`, several hundred lines below two hard stops:

1. `kernel_main_continue()` takes the boot sequence's scheduling brake with
   `preempt_disable()` near its top, and the executor joins its subsystem
   kthreads — it needs preemption.
2. Below that, the boot thread enters `test_exec::test_direct_execution()` and
   strands in the disk-backed `get_test_binary()` busy-wait. On the `main`
   baseline the last line `kernel_main_continue` ever printed was
   `=== MULTIPLE CONCURRENT PROCESSES TEST ===`; everything after it in the
   serial comes from userspace and the syscall handlers.

So the dispatch sat past the point the boot thread reaches, behind a brake that
would have deadlocked it anyway.

## What the fix does

* Dispatch from the top of `kernel_main_continue()`, the last x86 point that is
  both preemptible and still on the boot thread.
* Enable interrupts across the dispatch and restore the previous flag. Every
  `kthread_tests::*` case run immediately before ends with
  `arch_disable_interrupts()`, so control arrives with IF clear, and
  `kthread_join`'s `hlt` never wakes.
* Join each subsystem thread before spawning the next. With the cohort spawned in
  parallel the boot deadlocked between `kernel_stack::allocate` on the boot
  thread and `heap_large_alloc` in the Memory kthread. aarch64 keeps the parallel
  cohort.
* Dispatch `ProcessContext` from the same point; `Userspace` stays marker-only on
  both architectures, per #533's own constraint about syscall context.
* `[TESTS_COMPLETE:0/0]` is no longer a pass — it is `[BOOT_TESTS:FAIL:VACUOUS]`.
* A partial tally is no longer a verdict. The first Ring 3 syscall races the
  dispatch on x86; it now reports `[STAGE:user:COMPLETE:c/t]` and leaves the
  verdict to the dispatch. The same race used to push `CURRENT_STAGE` past
  `ProcessContext` and make `advance_to_stage` drop that cohort silently.
* The four tests #567 blocks announce `[TEST:...:DEFERRED:#567]` instead of
  vanishing.
