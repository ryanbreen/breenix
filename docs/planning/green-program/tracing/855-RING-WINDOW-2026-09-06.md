# #855: the trace ring's unfiltered window on a dispatching CPU

## 1. The reading and the decision

PR-3's `[BXCAP:RING]` section reported the unfiltered window of a capturing
CPU's ring at 15-30 ms, three orders of magnitude short of the seconds the
failure-capture plan's arithmetic assumed. Section 6.4 of
`docs/planning/green-program/failure-capture/PR-3-2026-09-05.md` traced this
to the `CTX_DIAG_*` and `DEFER_REQUEUE_*` diagnostic families
(`kernel/src/arch_impl/aarch64/context_switch.rs`) flooding the shared
1024-entry-per-CPU ring on a steadily dispatching CPU, and filed three
options: raise `TRACE_BUFFER_SIZE`, sample the diagnostic families the way
PR-2 sampled `TIMER_TICK`, or give `EV` a type filter.

**Decision: a combination, arrived at empirically rather than assumed up
front.** Sampling was applied first, because it adds only the sampling
counters' own few hundred bytes rather than a `TRACE_BUFFER_SIZE` increase
(claim-lint:ok: verified against the diff in section 6 -- the sampling
commits touch no `TRACE_BUFFER_SIZE` line), and the two families the plan
named looked like the whole problem. Real measurement on this branch found
a THIRD diagnostic family
(`SCHED_DIAG_*`, `kernel/src/task/scheduler.rs`) the original reading had
not named, and after sampling all three as far as could be justified,
retention plateaued at ~900 ms against **legitimate, non-diagnostic**
scheduler traffic (`CTX_SWITCH_ENTRY`, `SCHED_QUEUE_STATE`,
`SCHED_RESCHED_IPI_SEND`/`_RECV`) that criterion (b) below forbids sampling.
The remaining gap was closed with a stated, measured 2x `TRACE_BUFFER_SIZE`
increase -- the issue's own Option 1, taken as a 2x step rather than the 4x
the issue's arithmetic illustrated, because 2x already cleared the target
with real margin.

Final state, each part independently justified by a real boot measurement
on this branch, not by arithmetic alone:

| Constant | File | Value | Why |
|---|---|---|---|
| `TRACE_DIAG_SAMPLE` | `context_switch.rs` | `1024` | Samples `CTX_DIAG_*`/`DEFER_REQUEUE_*` ring writes; call-level, not sub-event-level |
| `TRACE_SCHED_DIAG_SAMPLE` | `scheduler.rs` | `8192` | Samples `SCHED_DIAG_*` ring writes; separate constant, different call-rate regime |
| `TRACE_BUFFER_SIZE` | `tracing/buffer.rs` | `2048` (was `1024`) | Arch-neutral; closes the gap sampling alone could not close without violating (b) |

### Criteria from the dispatch brief, and how each was met

- **(a) unfiltered window >= 1000 ms at 3 s uptime, `-smp 4` cortex-a72,
  `capture_selftest`**: met with real margin -- 1801/1638/1793 ms across
  three strict-gate boots (section 3).
- **(b) no information loss for non-diagnostic events**: `CTX_SWITCH_ENTRY`,
  `SCHED_QUEUE_STATE`, and `SCHED_RESCHED_IPI_SEND`/`_RECV` are outside
  every sampling guard added by this work (claim-lint:ok: verified by
  reading the three diffed functions in section 2.1/2.2 -- their sampling
  gates test only `CTX_DIAG_*`/`DEFER_REQUEUE_*`/`SCHED_DIAG_*` calls, and
  no other `record_event` call site in the two files was touched) --
  section 2.3 is the GDB evidence that they are what remained after all
  three diagnostic families were suppressed to single digits.
  Each sampled diagnostic family keeps a relaxed, registered drop counter
  (`CTX_DIAG_SAMPLE_DROPPED`, `DEFER_REQUEUE_SAMPLE_DROPPED`,
  `SCHED_DIAG_SAMPLE_DROPPED`) so the loss is visible through the existing
  `[BXCAP:CNT]` section and GDB, with no new wiring (claim-lint:ok: the
  `register_counter` calls added in `counters.rs`, section 6, are the only
  change needed for `[BXCAP:CNT]` to pick them up -- that section already
  iterates every registered counter). The `DEFER_REQUEUE_*` family's
  separate non-ring snapshot (`LAST_DEFER_REQUEUE_INFO`/`SP`/`ELR`/`X30`,
  used by `log_last_defer_requeue_snapshot`) stays outside the `if sampled`
  guard in the diffed function (claim-lint:ok: section 2.1 quotes the exact
  diff placement).
- **(c) the sampling guards add one relaxed atomic and one branch, and
  nothing else, on the dispatch paths they sit on** (claim-lint:ok: #855 --
  read directly from the 3-function diff in section 6: each of the three
  sampling gates is one `fetch_add` (relaxed) and one bitwise AND before an
  early return; no lock, no allocation, no `format!` call appears in any of
  the three diffed functions). `context_switch.rs` is Tier 2 -- the defect (unconditional
  ring writes on the diagnostic path) lives in the two functions edited,
  so the edit is a repair, not added instrumentation, and does not owe a
  GDB-insufficiency justification.
- **(d) `.bss` growth stated in bytes**: `(2048 - 1024) * 16 bytes/entry *
  16 (`MAX_CPUS`) CPUs = 262,144 bytes (256 KiB)`, on each architecture
  (`kernel/src/tracing/buffer.rs` is shared, not aarch64-only). Independently
  confirmed via `llvm-nm -S` on the built kernel binary in this session:
  `TRACE_BUFFERS` is `0000000000080400` bytes = 525,312 decimal at
  `TRACE_BUFFER_SIZE=2048`; the pre-change size (computed from the same
  formula, not separately built) is `0000000000040400` = 263,168 bytes;
  the delta is exactly 262,144 bytes, matching the arithmetic.
- **(e) x86 behaviour identical or stated** (claim-lint:ok: #855 --
  `kernel/src/task/scheduler.rs`, section 6): `trace_sched_diag`'s x86 arm
  is a no-op stub (`kernel/src/task/scheduler.rs`, unchanged by this work);
  `CTX_DIAG_*`/`DEFER_REQUEUE_*` live only in the aarch64-only
  `context_switch.rs`. `TRACE_BUFFER_SIZE` is the one arch-neutral change --
  x86's own per-CPU rings are 2x deeper as a side effect, stated here
  rather than claimed as "no change." The x86 gate (`run-x86-boot-tests.sh`,
  `-smp 1`) is therefore a no-regression check on this work, not a
  measurement of anything #855 is about: `-smp 1` has no "busiest non-zero
  CPU" for the oracle to examine, which is why the oracle itself is gated
  `target_arch = "aarch64"` (section 2.4).

## 2. What changed and why

### 2.1 Sampling `CTX_DIAG_*` / `DEFER_REQUEUE_*` (`context_switch.rs`)

`trace_ctx_diag` (8 `record_event` calls per invocation) and
`trace_defer_requeue` (4 ring-write calls, plus the unconditional
non-ring snapshot) each gained a per-CPU relaxed call counter
(`CTX_DIAG_CALL_COUNT`, `DEFER_REQUEUE_CALL_COUNT`, sized by
`crate::arch_impl::aarch64::constants::MAX_CPUS`) and an early-return guard:
one call in `TRACE_DIAG_SAMPLE` records its ring events; the rest increment
a registered drop counter and, for `trace_ctx_diag`, return immediately
before any `record_event` call. `trace_defer_requeue`'s non-ring
`LAST_DEFER_REQUEUE_*` snapshot writes stay outside the `if sampled` guard
-- they are a different consumer (`log_last_defer_requeue_snapshot`), not
part of the ring this issue is about, and sampling does not gate them
(claim-lint:ok: #855 -- `kernel/src/arch_impl/aarch64/context_switch.rs`,
diff quoted in section 6).

### 2.2 A third family the original reading missed: `SCHED_DIAG_*`

The issue's own hex range, `0xff39`-`0xff48`, already included
`SCHED_DIAG_STAGE`/`_TID_PAIR`/`_FLAGS` (`0xff46`-`0xff48`,
`kernel/src/task/scheduler.rs`, emitted from `trace_sched_diag` at 5 call
sites -- `ENTER`, `CURRENT_READY`, `PICK`, `RETURN`, `RETURN_NONE`, plus the
wake-timer attribution sites), but the first implementation pass grepped
only `context_switch.rs` and missed it. The oversight surfaced immediately
on the first real boot: at `TRACE_DIAG_SAMPLE=1024`, GDB found 960-1022 of
1024 ring slots on CPUs 1-3 still occupied by `SCHED_DIAG_*`, and the
strict gate's own three boots measured span_ms of 0, 22, and 0 -- worse
than the original 15-30 ms reading, because `SCHED_DIAG_*` fires more often
per second than the two families already sampled. `trace_sched_diag`'s
x86 arm was already a no-op stub, so this family was aarch64-only from the
start; the fix follows the identical pattern as 2.1, with its own constant
(`TRACE_SCHED_DIAG_SAMPLE`, because the call-rate regime differs) and its
own per-CPU counter and drop counter (`SCHED_DIAG_SAMPLE_DROPPED`).

### 2.3 Where sampling alone plateaus, and why that's the right place to stop

Doubling `TRACE_SCHED_DIAG_SAMPLE` from 8192 to 16384 bought nothing
measurable: 8192 measured 921/895/901 ms across three strict boots; 16384
measured 896/938/936 ms -- statistically flat. A live GDB probe at
`kernel::capture::emit` (aarch64 hardware debugging, not a log statement,
per this repo's interrupt/syscall-path rules) explained why: at 16384, a
peer ring held only 6-9 `SCHED_DIAG_*` events out of 1024 slots.
`CTX_SWITCH_ENTRY`/`SCHED_QUEUE_STATE` occupied 722-784 slots, and
`SCHED_RESCHED_IPI_SEND`/`_RECV` occupied 192-248. Those are ordinary
scheduler/context-switch trace events -- not diagnostic instrumentation
from the #607/#635 campaigns, outside the issue's `0xff39`-`0xff48` range --
and sampling them would be exactly the information loss criterion (b)
forbids. `TRACE_SCHED_DIAG_SAMPLE` was settled at 8192, not 16384: 16384
bought no measured improvement, so it would have been an unjustified
larger constant.

### 2.4 The oracle: `unfiltered_ring_span_self_check` (`irq.rs`)

(claim-lint:ok: #855 -- `kernel/src/tracing/providers/irq.rs`, diff quoted
in section 6.) A new self-check module, `#[cfg(all(feature = "capture_selftest",
target_arch = "aarch64"))]`, follows the existing "tick publishes, thread
prints" split ruling R188 (#847) established for `ring_span_self_check` in
the same file: it fires once, inside `trace_timer_tick`, at the same
3000 ms checkpoint `kernel/src/capture/selftest.rs`'s `CAPTURE_AT_MS` uses
(so it reads the same in-flight ring state the issue's own `[BXCAP:RING]`
evidence was measured from), scans `TRACE_BUFFERS` for the busiest CPU
excluding CPU 0 (the one with the highest `write_index()`), and computes
the **unfiltered** span -- oldest to newest of every live entry, any event
type, unlike `ring_span_self_check`'s `TIMER_TICK`-only filter. It writes
no serial output from the tick; a boot test in
`kernel/src/test_framework/registry.rs` (`ring_span_unfiltered_report`,
`Arch::Aarch64`) claims the published numbers from thread context and
prints `[RING_SPAN_UNFILTERED:cpu=<N>:span_ms=<N>:writes=<N>:dropped=<N>]`
through `serial_println!`.

One correction during implementation: the oracle originally ran
independently of `capture::selftest::observe` (both cfg-gated on
`capture_selftest`, both firing near the same checkpoint on possibly
different CPUs). A real boot then failed with "Unfiltered ring-span
self-check marker missing" -- not a measurement failure, a publication
race. The fix makes the oracle itself drive the synchronous BXCAP
self-test capture (`unfiltered_ring_span_self_check::observe` now calls
`capture::selftest::observe(tick_count)` after taking its own ring
snapshot and before releasing `READY`), and the plain
`#[cfg(feature = "capture_selftest")] crate::capture::selftest::observe(...)`
call site in `trace_timer_tick` is narrowed to
`#[cfg(not(target_arch = "aarch64"))]` so the two do not double-invoke it
on aarch64. `tests/ring_span_unfiltered_report_site_structure.rs`'s
`unfiltered_report_is_released_after_the_synchronous_capture` pins that
ordering.

### 2.5 The gate: `run-aarch64-boot-test-strict.sh`

(claim-lint:ok: #855 -- `docker/qemu/run-aarch64-boot-test-strict.sh`,
diff quoted in section 6.) The strict gate's normal kernel build does not include `capture_selftest`
(only `boot_tests`), so the new assertion must be conditional -- an
ordinary run must not fail on a marker its build was never asked to emit.
Detection follows the exact technique `require_boot_tests_kernel` already
uses for `boot_tests` itself: `[RING_SPAN_UNFILTERED:cpu=` is a string
literal that only compiles into the kernel binary's `.rodata` when
`capture_selftest` is enabled (the print site is
`#[cfg(all(feature = "capture_selftest", target_arch = "aarch64"))]`), so
`grep -aqF '[RING_SPAN_UNFILTERED:cpu=' "$KERNEL"` on the raw kernel FILE
(computed once, beside `require_boot_tests_kernel`, not per iteration)
tells the gate whether the handed-in kernel built that feature in. When it
did, `score_serial()` requires the marker and asserts `span_ms >= 1000`.

this session, section 5) pins: the sampling guard's shape in
`trace_ctx_diag`/`trace_defer_requeue`/`trace_sched_diag` (counter

constants and `TRACE_BUFFER_SIZE=2048` as literal text; anti-vacuity legs

`tests/ring_span_unfiltered_report_site_structure.rs` (10/10 tests passing,

the oracle-drives-the-capture ordering (2.4); the strict gate's
