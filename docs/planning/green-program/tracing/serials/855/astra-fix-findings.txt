**T-1 (major)** — `kernel/src/tracing/providers/irq.rs`, the `unfiltered_ring_span_self_check` module. Its `publish()` reads a *different, still-live, still-writing* CPU's trace ring via `iter_events()` with no synchronization, directly violating that function's own documented contract ("Disable tracing before calling this to avoid races" in `kernel/src/tracing/buffer.rs`). The codebase's only other cross-CPU-adjacent ring reader, `capture::sections::own_buffer`, is explicitly same-CPU-only ("a concurrent write to this CPU's buffer would require this CPU to be somewhere else, which it is not") — the opposite of what this module does.

**T-3 (minor)** — `kernel/src/arch_impl/aarch64/context_switch.rs:1872-1877` (`CTX_DIAG_CALL_COUNT`, `DEFER_REQUEUE_CALL_COUNT`) and `kernel/src/task/scheduler.rs:280-281` (`SCHED_DIAG_CALL_COUNT`). These are `[AtomicU64; 8]` per-CPU call-sampling counters on the context-switch/scheduler hot path. `MAX_CPUS` is 8 and `AtomicU64` is 8 bytes, so all 8 CPUs' counters pack into exactly one 64-byte cache line — `CacheLineAligned<[AtomicU64; 8]>` only aligns the *array's start*, not each element, so every CPU's own-index `fetch_add` still invalidates every other CPU's line (false sharing).
