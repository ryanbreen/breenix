The mask fixture uses the suite's forbidden `serial_println!` spelling
(previously at 5813). Direct adjacency is checked for plain and hash-delimited
raw strings. Because the mask defaults to true, skipping an ordinary identifier
does not itself hide that token. An additional adjacent raw opener containing

function span (this helper includes the signature), its closing brace, and the
separate CANARY function, for both delimiter forms.

### Review round: hash-count coverage widened to 2 and 3 (closes S-1)

The task brief asked for each raw-string hash-count shape (0 through 3),
and the first pass covered only 0 and 1. `code_mask_raw_string_close_preserves_next_byte`
now also feeds the scanner an isolated 2-hash literal
(`r##"x"##serial_println!`) and an isolated 3-hash literal
(`r###"x"###serial_println!`), and its compound/mixed leg gained a second
case at a 1-then-2 hash boundary (`r#"x"#r##"a"b"##serial_println!`) beside
the existing 0-then-1 case. `function_body_raw_string_close_preserves_next_byte`
gained matching 2-hash and 3-hash literals in its own fixture loop.

Verification used a standalone driver: the verbatim `raw_code_mask` and
`function_body` bodies from this file, compiled with `rustc` outside the
worktree (`/private/tmp/claude-501/-Users-wrb-fun-code-breenix/d69ffb9d-4539-4cf3-8a3d-a872ff7c830b/scratchpad/t522/verify/`),
run once against the fixed closing branch and once against the pre-fix
double-advance restored. Results:

| Fixture (hash count) | Fixed scanner | Pre-fix scanner |
|---|---|---|
| `r##"x"##serial_println!` (isolated, 2-hash) | offset matches | offset matches (isolated single literals don't move the byte the old bug drops onto anything lexically significant, at any hash count — same as the shipped 0- and 1-hash isolated legs) |
| `r###"x"###serial_println!` (isolated, 3-hash) | offset matches | offset matches, same reason |
| `r#"x"#r##"a"b"##serial_println!` (compound, 1-then-2) | offset matches | empty (`serial_println!` hidden) — reddens on the pre-fix scanner |
| `function_body`, 2-hash literal before the closing brace | returns the correct span, no CANARY | panics (`unterminated`) on the pre-fix scanner |
| `function_body`, 3-hash literal before the closing brace | returns the correct span, no CANARY | panics (`unterminated`) on the pre-fix scanner |

The isolated 2-hash and 3-hash `code_mask` legs confirm the fixed scanner's
correctness at those hash counts without themselves distinguishing old from
new behavior, matching the isolated 0- and 1-hash legs already shipped; the
compound leg and both `function_body` legs redden distinctly on the
pre-fix scanner, so hash counts past 1 are covered by cases that fail loudly
under the bug being fixed, not only by cases that happen to pass either way.

### Review round: pre-fix blast radius is wider than the token offset (closes S-2, informational)

The shipped fix is correct; this note is supporting rationale about how far
the pre-fix bug reached, not a defect in what shipped. Two additional
fixtures were run against the standalone driver above, each an ordinary
string with an escaped quote sitting immediately after a raw-string close:
`r"x""a\"b"CODE` (0-hash close) and `r##"x"##"a\"b"CODE` (2-hash close).

In both, the final `CODE` token offset comes out identical on the fixed and
pre-fix scanner (10 and 14 respectively) — a test that checked only that
offset would not have caught anything. Comparing the full boolean masks
does: on the 0-hash fixture, the fixed scanner correctly masks the ordinary
string's opening quote at byte 4 and its content at bytes 5–6 as non-code,
while the pre-fix scanner leaves those three bytes marked as code; the same
pattern recurs at bytes 8–10 on the 2-hash fixture. So the pre-fix bug's
effect on a fixture like this is not confined to a single skipped byte —
it flips the scanner's string/code classification for the following
ordinary-string span, and only a mask-level (not token-level) comparison
surfaces it. Neither of these two fixtures is added as a shipped test: the
shipped `code_mask_raw_string_close_preserves_next_byte` compound legs
already redden on the pre-fix scanner using a token-offset check (Table
above), which is sufficient to catch a regression; these two are recorded
here as the independently reproduced rationale for why the fix's `else`
placement is the right one, not as additional coverage the suite needs.
