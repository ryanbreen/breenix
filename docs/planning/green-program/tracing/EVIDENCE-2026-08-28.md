# Tracing subsystem — green-program evidence record

Date: 2026-08-28. Branch `feat/green-tracing`, off `main` @ `54aa16a1`.

This directory holds the raw artifacts, not just a verdict. Every claim below
names the file it is read out of.

## 1. The harness

`scripts/test_tracing_via_gdb.sh` boots a kernel under QEMU with the gdbstub
enabled, lets it free-run for a settle window so real events accumulate, attaches
GDB (the attach is what halts the guest), dumps the whole `TRACE_BUFFERS` region
and `TRACE_ENABLED`, and hands the dump to
`scripts/trace_memory_dump.py --validate`. The parser's verdict is the script's
exit status.

Two things the harness deliberately no longer contains, because both were silent
correctness holes before this arc:

* **No hardcoded breakpoint.** It used to break at `*(KERNEL_BASE + 0x18b090)`, a
  literal text address that stopped meaning anything the moment the kernel was
  rebuilt.
* **No hardcoded CPU count.** It used to dump `BUFFER_SIZE * 8` bytes while the
  kernel's `MAX_CPUS` is 16 — half the array. `MAX_CPUS` and
  `TRACE_BUFFER_SIZE` are now read out of `kernel/src/tracing/{core,buffer}.rs`
  at run time, and a short dump is a hard failure.

The script was also x86_64-only by construction (#677): x64 OVMF, a UEFI image,
`qemu-system-x86_64`, and a `! -name "*aarch64*"` filter on the kernel search. It
now takes `--arch aarch64|x86_64` and carries a per-arch QEMU command line and
load base (x86_64 PIE at 1 TiB; aarch64 linked at its runtime VA).

## 2. aarch64 — PASS

Command (from the repo root, kernel built with `--features boot_tests`):

```
BREENIX_GDB_BIN=/opt/homebrew/bin/gdb \
  ./scripts/test_tracing_via_gdb.sh --arch aarch64 --settle 20 --port 1244
```

Full transcript: `serials/aarch64-tracing-gdb-harness-20260828.txt`.
Parser output: `serials/aarch64-trace-validation-20260828.txt`.
GDB register/symbol read-out: `serials/aarch64-trace-gdb-output-20260828.txt`.

What it measured:

| fact | value |
| --- | --- |
| `TRACE_ENABLED` | set |
| CPU buffers parsed | 16 (`MAX_CPUS`, derived) |
| resident events | 4096 (four live CPUs, each a full 1024-entry ring) |
| CPU0 `write_idx` | 2116224, wrapped, `dropped` 2115200 |
| overflow accounting | exact on all four live CPUs: `write_idx - dropped == 1024` |
| distinct event types observed | 20, all decoding against the kernel's own table |
| `TIMER_TICK` | present |
| verdict | `TRACE_VALIDATION:PASS` / `TRACING_EVIDENCE:aarch64:PASS` |

The `write_idx - dropped == TRACE_BUFFER_SIZE` identity is the load-bearing
check. `TraceCpuBuffer::record` increments `dropped` exactly when it reserves a
slot that already held an event, so on a wrapped ring the two counters must
agree to the entry. That is a statement about the ring's own bookkeeping, not
about whether some bytes are nonzero.

The same boot exercises the tracing row's registry test. From
`serials/aarch64-bootgate-markers-20260828.txt`:

```

[BOOT_TESTS:TOTAL:109]
[TEST:process:deferred_fault_ring_overflow_injection:START]
[TEST:process:deferred_fault_ring_overflow_injection:PASS]
[TESTS_COMPLETE:109/109]
[BOOT_TESTS:PASS]
```

### Anti-vacuity

`serials/aarch64-validator-mutations-20260828.txt` applies five mutations, each
singly, to a copy of the passing dump. All five turn the run red, each with its
own message:

| mutation | result |
| --- | --- |
| whole region zeroed | no events / empty CPU0 / no TIMER_TICK |
| one `event_type` set to `0xDEAD` | undecodable event type |
| CPU1 `dropped` falsified | overflow accounting disagrees with `write_idx` |
| dump truncated to the old 8 CPUs | dump does not cover `TRACE_BUFFERS` |
| every `TIMER_TICK` rewritten to `IRQ_ENTRY` | timer provider never fired |

### One reported non-failure

The validator prints a `CENSUS:` line for per-CPU timestamp inversions and does
**not** fail on them. The count varies run to run: the recorded run shows
zero, an earlier one showed a single 6 µs step backwards between
`SCHED_RESCHED_IPI_RECV` and the `TIMER_TICK` in the next slot on the same CPU. `record_event` samples the timestamp before `TraceCpuBuffer::record`
reserves a slot, and `record` cannot mask interrupts — it runs in the timer and
IRQ paths under a sub-microsecond budget — so a nested record can take the
earlier slot with the later timestamp. Sampling the timestamp after the
reservation would not close it either: the same interrupt can land between the
reservation and the timestamp read. Slot order therefore does not imply
timestamp order on this ring. Asserting that it does would be a false invariant,
so it is reported and explained rather than gated.

## 3. x86_64 — the harness runs and validates; the row is still not green

Same harness, `--arch x86_64`, on the beast x86 VM:

```
./scripts/test_tracing_via_gdb.sh --arch x86_64 --settle 240 --port 1245
```

Transcript: `serials/x86-tracing-gdb-harness-20260828.txt`.
Parser output: `serials/x86-trace-validation-20260828.txt`.

| fact | value |
| --- | --- |
| `TRACE_ENABLED` | set (`0x1`) |
| CPU buffers parsed | 16 |
| resident events | 1024 (single-CPU boot: `-smp 1`) |
| CPU0 `write_idx` | 28348, wrapped, `dropped` 27324 |
| overflow accounting | exact: 28348 − 27324 = 1024 |
| distinct event types observed | 3, all decoding: `TEARDOWN_DEFER_EVENT`, `TIMER_TICK`, `WAITPID_WAKE` |
| verdict | `TRACE_VALIDATION:PASS` / `TRACING_EVIDENCE:x86_64:PASS` |

Two defects in the harness's x86 arm had to be fixed to get here, and both were
caught by the validator refusing to pass rather than by inspection:

* the kernel-binary search took the first `find` hit out of `target`, which
  holds one artifact directory per build hash. A stale binary put every derived
  address about 0x3a000 off, and the run read `TRACE_ENABLED` as
  `0x89485024448b48d0` — instruction bytes. Now the most recently built binary
  is used, which is the one the UEFI image embeds.
* the event-type table was read only from `impl TraceEventType`, but each
  provider composes its own ids as `((PROVIDER_ID as u16) << 8) | n`. The run
  failed with `1 event type(s) did not decode: 0x0a00 x2` —
  `TEARDOWN_DEFER_EVENT`. The provider files are read too now: 100 constants
  became 105, and the same aarch64 dump that resolved 20 types resolves 28.

This is functional evidence that the tracing framework records and accounts
correctly on x86. It is **not** enough to make the x86 tracing row green: #533,
#680 and #681 are open against it, and the registry test that exercises a
tracing provider (`deferred_fault_ring_overflow_injection`) still cannot run in
a shippable x86 configuration. See `X86-533-2026-08-28.md`.
