# #522 C4: per-worker exit-kick wait windows

## The reading and the decision

Issue #522 frames C4 as “multi-target waits use a summed union with a shared 8s floor, not strict per-target windows”. Its standing ruling says:

> Standing ruling (3) requires, for multi-target waits, "per-TARGET windows … each target its own 8 s first-schedule grace + 3 s no-progress window, FAIL names the target", with windows keyed to counters that advance **iff the awaited kthread itself executed**.

Source: `serials/522-c4/issue-522-body.txt:3-15`, captured with `gh issue view 522 --json body`.

Commit `1648b840` repairs two deviations in `kernel/src/tracing/providers/teardown.rs::exit_kick_protocol_gate_test`:

- `workers_ready` previously fed the sum of three workers' counters to one shared last-advance clock. Each worker bumps its own progress counter exactly once, then spins until the union reaches 3; two siblings' one-time bumps — not sustained progress — could each renew that shared clock while a third stayed frozen before its own bump, since the clock advanced on the sum of the three counters rather than on the specific incomplete target's own progress. `spin_with_resched_workers` now tracks `last_advance[3]`, updates an index from that target's own counter, and checks the incomplete target against `max(8s first-schedule floor, last own advance + 3s)`. Readiness retires the corresponding window.
- `storm_publisher_a_join` previously added `observer_progress` to `publisher_a_progress`. Its closure now reads publisher A's own work counter; the join helper also observes that awaited worker's exit stages. Observer activity cannot renew publisher A's window through this closure.

The existing aggregate gate/Phase-1 ceilings, absolute wait ceiling, and counter-failure classifications remain separate from target attribution. C4 does not adjust those budgets. The strict script's default QEMU timeout increases from 20s to 90s and polling budget to 60 iterations to accommodate the isolation fixture's deliberate waits.

## Fix pass — review findings closed (2026-09-07)

This #522 C4 review fix pass addresses two findings from the round's
Astra review (`REVIEW.md` in the round's working notes):

1. **W-1 (major/code)** — `kernel/src/tracing/providers/teardown.rs`, the
   `workers_ready` wait inside `exit_kick_protocol_gate_test`. `target_complete`
   was `|_, progress| progress != 0`, treating a worker's own progress
   counter going nonzero as evidence of readiness. The writer order in
   each of the three worker closures is: bump the worker's own progress
   counter (`Ordering::Release`), THEN bump the shared `workers_ready`
   counter (`Ordering::Release`), with no intervening yield or branch. A CPU freezing in
   that instruction gap left its own counter nonzero forever while
   `workers_ready` stayed below 3 on its account — `target_complete` would report
   it "complete" and the wait could then only time out via one of the
   three aggregate ceilings (PhaseOneCeiling/GateCeiling/AbsoluteCeiling),
   each of which leaves `target` unset, so the actually-frozen worker/CPU
   went unnamed. This defeated the gate's stated purpose.

   Fix: replace the `workers_ready: AtomicU64` summed counter with
   `workers_ready_bits: AtomicU64`, a per-worker readiness bitmask —
   the exact pattern the already-correct `exit_kick_worker_window_isolation_test`
   fixture already uses for its own `completed` field. Each worker now
   publishes readiness with a single `fetch_or` of its own bit
   (`WORKER_BIT_A`/`WORKER_BIT_B`/`WORKER_BIT_OBSERVER`); the wait's
   aggregate condition reads `workers_ready_bits.load(Acquire).count_ones()
   as u64`, and `target_complete` reads
   `workers_ready_bits.load(Acquire) & (1 << target) != 0` — the identical
   write drives both the aggregate condition and per-worker completeness,
   so a worker cannot be marked complete before it has actually
   contributed to the aggregate. A worker freezing anywhere before that
   single `fetch_or` now correctly stays eligible for NoProgress
   attribution; a worker freezing after it has already contributed cannot
   cause a false NoProgress verdict, because the aggregate condition
   itself would already be satisfied and the wait returns `Ok(())` before
   ever evaluating per-target completeness. Only
   `exit_kick_protocol_gate_test`'s own copy of `spin_with_resched_workers`
   and its call site were touched; the isolation fixture's separate nested
   copy (already correct) was not.

2. **W-7 (minor/code, test-strength gap)** — `tests/teardown_structure.rs`,
   the loop asserting each `storm_{a,b,observer}_progress` closure reads
   only its own counter. `call` was sliced starting at the `let
   {progress_source} =` anchor itself, so it included the LHS binding
   identifier regardless of the closure's body (e.g. `storm_publisher_a_progress`), which already
   contains the substring `publisher_a_progress`. The "positive" assertion
   `call.contains(counter)` therefore passed on the variable name alone,
   satisfiable even by a closure body of `|| 0`. The negative
   (sibling-exclusion) checks in the same loop stayed meaningful.

   Fix: slice `call` starting right after the `=` (`body_start = declaration
   + "let {progress_source} =".len()`), so it holds only the closure
   expression, excluding the LHS name. The positive assertion, and the
   `unrelated_counter == counter` case inside the paired `assert_eq!` loop
   (which was equally vacuous for the same reason), now both test real
   closure content.
