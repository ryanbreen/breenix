# #522 C4: per-worker exit-kick wait windows

## The reading and the decision

Issue #522 frames C4 as “multi-target waits use a summed union with a shared 8s floor, not strict per-target windows”. Its standing ruling says:

> Standing ruling (3) requires, for multi-target waits, "per-TARGET windows … each target its own 8 s first-schedule grace + 3 s no-progress window, FAIL names the target", with windows keyed to counters that advance **iff the awaited kthread itself executed**.

Source: `serials/522-c4/issue-522-body.txt:3-15`, captured with `gh issue view 522 --json body`.

Commit `1648b840` repairs two deviations in `kernel/src/tracing/providers/teardown.rs::exit_kick_protocol_gate_test`:

- `workers_ready` previously fed the sum of three workers' counters to one last-advance clock. Two active siblings could keep that union advancing while the third remained frozen. `spin_with_resched_workers` now tracks `last_advance[3]`, updates an index from that target's own counter, and checks the incomplete target against `max(8s first-schedule floor, last own advance + 3s)`. Readiness retires the corresponding window.
- `storm_publisher_a_join` previously added `observer_progress` to `publisher_a_progress`. Its closure now reads publisher A's own work counter; the join helper also observes that awaited worker's exit stages. Observer activity cannot renew publisher A's window through this closure.

The existing aggregate gate/Phase-1 ceilings, absolute wait ceiling, and counter-failure classifications remain separate from target attribution. C4 does not adjust those budgets. The strict script's default QEMU timeout increases from 20s to 90s and polling budget to 60 iterations to accommodate the isolation fixture's deliberate waits.

## Fixture coexistence repair

The first full strict run returned exit 1: 2/3 successes, boot 1 failed the scheduler strand injection requirement. Its C4 scenarios passed, but the serial contained:

```text
[STRAND_INJECT_ORACLE:aarch64:legA_exercised=1:legA_recovered=1:legB_exercised=0:legB_recovered=0:stranded=0]
```

Source: `serials/522-c4/strict-before-sleep-boot1-serial.txt:570`; command verdict in `serials/522-c4/strict-before-fixture-sleep.txt`. The new fixture's three pinned workers stayed runnable through about 39 seconds of deliberate waits. `kernel/src/arch_impl/aarch64/context_switch.rs::inline_schedule_trampoline` arms the normal strand injection only when the outgoing thread is idle; `kernel/src/task/strand_oracle.rs` gives it a 6s injection deadline. The continuously runnable fixture competes with that required idle handoff. Boot 1's leg B never fired, while boots 2 and 3 completed it: this was a timing-sensitive coexistence defect in the new fixture.

Changed the fixture's work loop to call the existing `strand_oracle::sleep_sample_period()` (50ms) between updates. This permits idle handoffs while retaining own-counter progress well within the 3s window. The frozen worker's counter stays at one, the siblings continue advancing after completion, and cleanup still joins three handles. The real and copied wait helpers, scenario deadlines, and gate scoring requirements were not changed by this repair. No context-switch or interrupt file was edited. The full three-iteration gate was restarted after rebuilding, rather than retrying just boot 1.
