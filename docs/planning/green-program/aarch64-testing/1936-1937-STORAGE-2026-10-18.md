# ARM64 testing storage: #1936 and #1937

## Cause and repair

The testing launchers omitted the separate read-only ext2 disk. They now copy the root image, add `/.breenix-readonly-fixture`, verify the marker, and attach the copy read-only as `/home`. The attachment order preserves the writable root as device zero in the driver's ascending MMIO scan.

The ARM64 MMIO block driver requested only RO, deliberately declined FLUSH, and implemented `flush()` as a no-op. On the flush-capable device, that selected writethrough operation: each sector write, including repeated allocation-bitmap updates during truncate, incurred stable-storage work. The unsafe interactive disk profile masked that cost. The defect was the kernel's missing cache-flush support; neither the truncate algorithm nor its deadline needed changing.

The driver now negotiates FLUSH and submits a header/status request at each existing filesystem barrier. Writes and flushes share their completion, status validation, request serialization and DMA-abandonment path. Devices without FLUSH retain writethrough operation. This follows [VirtIO 1.2 sections 5.2.5 and 5.2.6](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html). Testing mode uses the default disk cache, matching the strict gate's disk setting.
