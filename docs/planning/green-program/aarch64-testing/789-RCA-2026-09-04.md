# #789 — the production-profile wedge is a scheduler lock taken with interrupts enabled

`fix/562-761-aarch64-testing-profile` @ `2b3fb187` (PARKED). #789 recorded the
production profile at **3/8 against `main`'s 8/8** and said what the failures
look like — output stops, no crash marker, no `EXT2_LOCK_SPIN_STALL`, no
soft-lockup dump — but not what wedges. This round reproduced it three times
under GDB and read the answer off the halted machine.

**The wedge is a self-deadlock on the global `SCHEDULER` spin lock.** A thread
takes that lock from ordinary thread context with IRQs enabled, an interrupt
lands inside the critical section, and the IRQ path's unconditional
`lock_for_context_switch()` spins on the lock its own interrupted context is
holding. That CPU takes no further interrupt, so it does not resume to release
the lock; the other CPUs pile up on it in turn. In 3 of 3 specimens 4 of 4
vCPUs were spinning at EL1 with `PSTATE.I = 1` and the lock byte read 1.
claim-lint:ok: 3 of 3 specimens, `serials/r9-789/specimen-A/gdb-capture.txt`,
`specimen-B/gdb-stack-symbols.txt`, `specimen-C/gdb-stack-symbols.txt`.

The discriminating experiment #789 asked for — sample the QEMU process's CPU
while a boot is hung — answers itself: **392.6%** on the wedged specimen
(`serials/r9-789/specimen-C/qemu-cpu-sample.txt`), against 163–190% on the
passing boots in the same session's run logs. Spinning, not WFI with a lost
wake.

## 1. The mechanism, in causal order

| # | what happens | file:line |
|---|---|---|
| 1 | `Completion::wait_timeout_inner` — the wait the VirtIO block read path goes through — asks whether this context may sleep | `kernel/src/task/completion.rs:219` |
| 2 | `current_context_can_sleep()` computes `context_permits`, whose **first term is `crate::arch_interrupts_enabled()`** | `kernel/src/task/completion.rs:133-139` |
| 3 | if and only if that is true, it calls `idle_identity_must_not_sleep()` | `kernel/src/task/completion.rs:148` |
| 4 | which calls `scheduler::is_current_idle_thread()` | `kernel/src/task/idle_sleep.rs:158` |
| 5 | which does `try_lock_scheduler()` — acquiring the global `SCHEDULER` spin lock **without masking interrupts** | `kernel/src/task/scheduler.rs:5072` |
| 6 | an EL1 IRQ lands between the acquire and the release | measured, three specimens, §2 |
| 7 | the IRQ path calls `lock_for_context_switch()`, a **blocking** `SCHEDULER.lock()` | `kernel/src/arch_impl/aarch64/context_switch.rs:5247` and `:5367` → `kernel/src/task/scheduler.rs:587` → `:345` |
| 8 | that CPU spins with `PSTATE.I = 1`, so the interrupted context cannot resume to release the lock | measured |
| 9 | the other CPUs' next scheduler acquisitions join the spin — 4 of 4 vCPUs in 3 of 3 specimens | measured |

Step 3 is the hinge: the predicate reaches for the scheduler lock **precisely
in the window where an interrupt can preempt it**, because "interrupts are
enabled" is one of its preconditions for asking at all.

### The window is in the binary, not in an argument

`serials/r9-789/is_current_idle_thread-gate.disas` is the disassembly of
`is_current_idle_thread` out of the gate kernel this round booted:

```
+12   ldaxrb  w10, [x8]      <- try_lock: load-exclusive of the lock byte
+20   stxrb   w10, w9, [x8]  <- try_lock: store 1 == ACQUIRED
+56   clrex                  <- the "already held" exit ...
+60   ret                    <- ... returns None without holding anything
+200  stlrb   wzr, [x8]      <- release
+316  stlrb   wzr, [x8]      <- release
+348  stlrb   wzr, [x8]      <- release
+372  stlrb   wzr, [x8]      <- release
```

There is no `msr daifset` anywhere in the function. Everything from `+24` to
whichever release the path reaches runs with the lock held and interrupts
enabled.

The contrast is 350 lines away in the same file and is in the same committed
disassembly's sibling: `current_thread_id()` (`kernel/src/task/scheduler.rs:5423`)
wraps its acquisition in `without_interrupts`, and its machine code is
`mrs x9, daif` / `msr daifset, #0x3` **before** the `ldaxrb`, with
`msr daif, x9` **after** the release. `with_scheduler()` does the same and says
why in its doc comment: *"This function disables interrupts to prevent deadlock
with timer interrupt"* (`kernel/src/task/scheduler.rs:5083`). The rule is
already the file's rule. `is_current_idle_thread` is the one live acquisition
that does not follow it.
claim-lint:ok: the four `stlrb` releases, the single `ldaxrb`/`stxrb` acquire
and the absence of `daifset` are all in
`serials/r9-789/is_current_idle_thread-gate.disas`, produced by the
`disassemble` command recorded in §8.

## 3. Why the watchdog did not fire

`check_soft_lockup()` is called from exactly one place: inside the CPU-0 branch
of the aarch64 timer interrupt handler
(`kernel/src/arch_impl/aarch64/timer_interrupt.rs:741-744`). Its host is an
interrupt.

Once CPU 0 is spinning inside `check_need_resched_and_switch_arm64` with
`PSTATE.I = 1` — `cpsr 0x800023c5` on CPU 0 in 3 of 3 specimens — CPU 0 takes no
further timer interrupt, so `check_soft_lockup` is not invoked again. The
watchdog cannot report a lockup that has swallowed the interrupt it lives in.
This is not a tuning problem and no threshold change reaches it.
claim-lint:ok: 1 of 1 call site of `check_soft_lockup`,
`grep -rn check_soft_lockup kernel/src`; the three `cpsr` readings are in the
three specimen captures under `serials/r9-789/`.

It is also why the failure is *silent* rather than loud: the wedge takes all
four CPUs at once, so no thread is left running to print. In 3 of 3 specimen
serials the guest output stops mid-boot and adds no further line for the rest
of the window.
claim-lint:ok: 3 of 3, `serials/r9-789/specimen-A/serial.txt`,
`specimen-B/serial.txt`, `specimen-C/serial.txt`.

The one #789 shape that looks different — `head_5-serial.txt`, where heartbeats
ran for the whole 119 s window while the service chain stopped at
`clonevm_exec_test` — is **not** reproduced here and is not explained by this
mechanism. See §7.

## 4. The enabling change

`023e049d fix(761): one shared refusal keeps the idle identity out of every
blocking primitive` (its own subject line, quoted) — the commit that introduced
`kernel/src/task/idle_sleep.rs` and wired `idle_identity_must_not_sleep()` into
the `*_can_sleep` predicates.
claim-lint:ok: 9 of 9 call sites, enumerated below;
`git log --oneline -S idle_identity_must_not_sleep origin/main..2b3fb187` names
`023e049d` as the oldest.

Before it, no code path called `is_current_idle_thread()` at all. `git grep`
finds the function's definition and nothing else on `main`
(`kernel/src/task/scheduler.rs:4635`, carrying `#[allow(dead_code)]`), and
`main`'s equivalent predicate, `syscall_sleep_path_available()`
(`origin/main:kernel/src/task/completion.rs:131`), is lock-free: it reads
`preempt_count()` and `timer_interrupt::is_initialized()` and nothing else.
claim-lint:ok: 1 of 1 `git grep -n is_current_idle_thread origin/main -- kernel/src`
hit, which is the definition line.

On this branch the predicate has **9 call sites in 8 files**:

```
kernel/src/task/completion.rs:148          kernel/src/fs/ext2/mod.rs:1872
kernel/src/task/waitqueue.rs:72            kernel/src/drivers/virtio/block.rs:134
kernel/src/task/waitqueue.rs:116           kernel/src/drivers/virtio/gpu_pci.rs:87
kernel/src/drivers/ahci/mod.rs:756         kernel/src/drivers/virtio/sound.rs:120

```

claim-lint:ok: 9 of 9, `grep -rn idle_identity_must_not_sleep kernel/src`
excluding the definition file.

Every one of them is a sleep-eligibility question asked from thread context;
`waitqueue.rs:72` and `:116` ask it *before* anything else in
`prepare_to_wait` / `prepare_to_wait_checked`. The measured producer in 3 of 3
specimens is the `completion.rs` one, which is simply the busiest: every ext2
block read on the service-spawn path goes through it, which is why the serials
always stop a moment after a `[spawn]` line or a child exit.

The round-8 change to the unreadable-identity arm (`264294f5`) is **not** the
enabler and does not mitigate it: the deadlock happens when the `try_lock`
succeeds, and that arm only decides what to answer when it fails.
claim-lint:ok: 3 of 3 specimens were interrupted on the succeeding path, per
§2.

The r7 bisect table (`serials/r7/bisect/table.tsv`) does not speak to this: it
bisected the **strict** (`boot_tests`) gate against the `block_wedge_oracle`
and `census_widen_oracle` classes, and every row it records is one of those.
No prod-profile bisect exists, and none is needed — the caller does not exist
before `023e049d`, so no code path could reach the lock from that context.

## 5. Latent on main, in the same sense as the TTBR0 defect

* **The defective primitive is on `main`.** `origin/main`'s
  `is_current_idle_thread` is the same shape: `try_lock_scheduler()` with no
  interrupt masking, and a doc comment claiming it is "safe to call from IRQ
  context" — which it is, because in IRQ context interrupts are already masked.
* **The trigger is branch-only.** On `main` the function has no callers and is
  marked `#[allow(dead_code)]`.
  claim-lint:ok: 1 of 1 hit for
  `git grep -n is_current_idle_thread origin/main -- kernel/src`, which is the
  definition line.

So: present shape, no reachable trigger. Any future `main` change that calls
`is_current_idle_thread` (or the identically-shaped `try_schedule()`,
`kernel/src/task/scheduler.rs:5057`, whose own comment reads "Do not disable
interrupts; we only attempt a non-blocking lock here", also `#[allow(dead_code)]`)
from thread context re-arms it without touching this branch.

The census behind that claim: of the **8** `try_lock_scheduler()` call sites in
`kernel/src`, 6 are safe by their context — `try_liveness_snapshot` and
`try_dump_state` are the watchdog's, called from the timer IRQ;
`terminate_thread_best_effort` and `switch_to_idle_best_effort` are fatal-exception
handlers; `get_process_cpu_ticks` and `get_process_display_state` wrap
themselves in `without_interrupts`. The 2 that are not are
`is_current_idle_thread` (live on this branch) and `try_schedule` (dead on both).
claim-lint:ok: 8 of 8 call sites, `grep -rn "try_lock_scheduler()" kernel/src`,
each classified by reading its enclosing function.

## 7. What a fix touches, and what it must not

**Touches.**

1. `kernel/src/task/scheduler.rs::is_current_idle_thread` — the acquisition
   itself. Two shapes are both correct, and the second is better:
   * mask interrupts across the acquire/release (what `with_scheduler`,
     `current_thread_id`, `get_process_cpu_ticks` and
     `get_process_display_state` already do), or
   * **do not take the scheduler lock here.** The question is "is the running
     identity this CPU's idle task?", and `Scheduler::refuse_idle_block`
     (`kernel/src/task/scheduler.rs:1615`) already answers it from
     `self.cpu_state[cpu]` under a lock its callers hold. The lock-free
     equivalent of that read is what this advisory fast path wants; the
     scheduler lock buys this advisory read no information it cannot get
     lock-free, and costs it this deadlock. Removing the acquisition also
     removes the 3418 failed `try_lock` attempts specimen A recorded.
     claim-lint:ok: `IDLE_IDENTITY_UNREADABLE = 3418`,
     `serials/r9-789/specimen-A/gdb-capture.txt`.
2. `kernel/src/task/idle_sleep.rs::idle_identity_must_not_sleep` — only if the
   identity read moves; the 9 call sites do not need to change.
3. `kernel/src/task/scheduler.rs::try_schedule` — the same shape, currently
   dead. Delete it or mask it; leaving it is leaving the next instance of this
   bug lying in the road.
4. A ratchet. The durable rule is *"no `SCHEDULER` acquisition may happen with
   interrupts enabled"*, and it is checkable by shape, not by a list: census the
   functions in `kernel/src` whose bodies call `lock_scheduler`/`try_lock_scheduler`
   and require each to be inside `without_interrupts`/`arch_without_interrupts`,
   or to be an interrupt/exception-context entry point. Both known offenders
   fail such a census today, which is its anti-vacuity leg.

**Must not touch.** The Tier-1 prohibited list in `CLAUDE.md`:
`kernel/src/syscall/handler.rs`, `kernel/src/syscall/time.rs`,
`kernel/src/syscall/entry.asm`, `kernel/src/interrupts/timer.rs`,
`kernel/src/interrupts/timer_entry.asm` — 0 of those 5 appear in the §1 chain,
and a fix has no reason to reach them.
claim-lint:ok: 5 of 5 Tier-1 rows compared against the 5 files named in §1.

Also must not:

* **Do not "fix" this in the IRQ path.** Making
  `check_need_resched_and_switch_arm64` use `try_lock` instead of
  `lock_for_context_switch` would trade a hard deadlock for silently skipped
  context switches, and it is the wrong end: the producer is the unmasked
  acquisition.
* **Do not touch the watchdog.** It is silent for a structural reason (§3), not
  a threshold one. A watchdog change would hide the failure's silence without
  changing the failure.
* **Do not attribute this to the branch's kboot hand-off, the pinned-ksoftirqd
  work or the TTBR0 helper.** `kboot` is already retired in the specimen's
  thread table, `PINNED_HOME_CPU_UNAVAILABLE` is 0, and no fault record exists.

## 8. What does not fit, and how this was produced

**What does not fit.**

* **#789's `head_5` shape is unexplained by this mechanism.** In that serial
  heartbeats continued to 119319 ms while the service chain stopped — a live
  system with one stuck chain, not four spinning CPUs. It did not reproduce in
  the boots this round captured. It may be a second defect, or the same one
  reached from a context where only one thread wedged; this document does not
  claim to cover it.
* **Specimen A ran on a DWARF-enabled build**, produced by adding non-allocated
  `.debug_*` output sections to `kernel/src/arch_impl/aarch64/linker.ld` (a
  scratch edit, reverted; the tree's linker script is unchanged). That build's
  `.text` is not byte-identical to the gate kernel's — `--gc-sections` retains
  dead code that debug info references — so it is a same-source, different-layout
  binary. Specimens B and C are the gate binary itself, and the mechanism reads
  the same way in 3 of 3; `is_current_idle_thread`'s own offsets are identical
  in both builds at 8 of the 8 instructions that matter (`+12`, `+20`, `+56`,
  `+60`, `+200`, `+316`, `+348`, `+372`).
  claim-lint:ok: 8 of 8 offsets, the two disassemblies quoted in §1 and in
  `serials/r9-789/is_current_idle_thread-gate.disas`.
* **`trace_dump_latest(40)` could not be run.** The symbol is not in the linked
  production kernel: `nm` finds `trace_dump_counters` and no other `trace_dump*`
  entry, so `--gc-sections` collected the rest. The counters were read instead,
  and the per-CPU/per-thread state was read directly out of the scheduler.
* **The wedge does not need a specific interrupt.** Any EL1 IRQ that reaches
  `check_need_resched_and_switch_arm64` does it; the specimens' stacks show
  `handle_irq` frames without a distinguishing source.
* **This does not contradict #786's repairs.** In the specimens, `kboot` is
  retired, no fault record is present and `IDLE_SLEEP_REFUSED` is 0 — the three
  things #786 changed behave as that document says. The wedge is a different
  defect, which those repairs uncovered by letting boots run long enough to
  reach userspace service spawning.
  claim-lint:ok: specimen A's thread table (12 rows, no tid 11) and counter
  block, `serials/r9-789/specimen-A/gdb-capture.txt`.

**How to reproduce.** With the gate's kernel built
(`cargo build --release --target aarch64-breenix-kernel.json -Z build-std=core,alloc -Z build-std-features=compiler-builtins-mem -p kernel --bin kernel-aarch64`)
and `target/ext2-aarch64.img` present:

```
serials/r9-789/tools/run_until_wedge.sh <id> <gdbport> <kernel-elf> <max-attempts>
```

boots the gate's QEMU line with `-gdb tcp::<gdbport>`, declares a wedge when the
serial stops growing for 12 s (or `bsshd` is not reached in 75 s) and leaves the
QEMU alive. Then:

```
gdb -batch -x serials/r9-789/tools/full.gdb <kernel-elf>      # DWARF build
gdb -batch -x serials/r9-789/tools/capB3.gdb <gate-kernel>    # minsyms only
```

`full.gdb` prints the four backtraces, the lock byte, the interrupted contexts,
the per-CPU scheduler state, the ready queues, the thread table and the three

dump from `print ((void(*)(void))<trace_dump_counters>)()` on a halted CPU.
