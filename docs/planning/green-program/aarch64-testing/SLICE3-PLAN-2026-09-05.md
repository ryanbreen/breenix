### 3a — the census silence scan must reach the CPU the widening is about

* **Kind:** fix + oracle. Lands alone, and lands first.
* **Files:** `kernel/src/task/scheduler.rs` (the silence scan at `:741`),
  `tests/strand_handoff_structure.rs` (retarget the pin at `:2531`).
* **Approx lines:** 16 kernel + 40 test = 56. The test half is measured
  (`40  5  tests/strand_handoff_structure.rs`); the kernel half is the 16-line
  hunk in `96ef7fc3`.
* **Defect:** the scan runs `for cpu in 0..online_cpu_count`, but
  `queued_on_nondispatching_cpu` counts a thread queued on a CPU *at or past*
  that bound. The field named for CPU scheduler silence cannot sample the CPU
  the widening oracle arms.
* **Oracle:** `[CENSUS_WIDEN_ORACLE:...:cpu_silence_ms=...]` on the strict gate.
  `run-aarch64-boot-test-strict.sh:43` requires `cpu_silence_ms=[1-9][0-9]*`, so
  a 0 reading fails the gate. Before: the field reports the 4 busy CPUs and
  reads 0 whenever those 4 enter the scheduler inside 1 tick — the round-7 RCA
  enumerates 9 readings (0, 1, 2, 2, 2, 3, 4, 6, 7), 1 of which is the failing 0.
  After: `cpu_silence_ms` equals `queued_nondispatch_ms` and `worst_silence_cpu`
  names the armed CPU — 2 committed post-fix boots read 1142 and 1112.
  claim-lint:ok: the 9 readings and the 2 post-fix values are quoted in section
  4 of the round-7 RCA, posted as a comment on #786.
* **Anti-vacuity:** the old assertion string
  `"CPU-silence sampling must iterate exactly the derived online CPU count"` was
  itself the defect, so it is retargeted, not deleted; the new rules are that
  the census contains 0 `for cpu in 0..online_cpu_count`, exactly 1 silence
  scan, and a skip arm that requires both `cpu >= online_cpu_count` and
  `per_cpu_queues[cpu].is_empty()`.
* **Gates:** strict x3 (expected: the intermittent `cpu_silence_ms=0` class
  stops appearing), production x3 (expected unchanged), service-sequence
  (`run-aarch64-service-sequence-gate.sh:106` pins the same pattern; expected
  unchanged or improved).
* **Risk it re-opens:** 0 of the 3 branch regressions — #786's abort, #789's
  wedge, #562's panic. This hunk touches no address-space code, takes no lock it
  did not already hold, and the `testing` profile does not reach it. It is a
  `main`-side defect the branch happened to find.

## 3. #789's `head_5` shape, and which PR surfaces it

### The shape

`head_5-serial.txt` in the parked branch's round-8 production A/B is the 1 of
the 8 head-arm boots that does not stop dead. Read out of that file:

* the last service-chain line is `CLONEVM_EXEC_TEST: second stage`, at line 373.
  In a passing boot of the same round (`main_5-serial.txt`) that line is at 370
  and is followed at 372-374 by `post-exec rendezvous complete`,
  `post-exec futex keys derived` and `PASS`, then the `bsshd` spawn at 377 and
  `bsshd: listening on 0.0.0.0:2222` at 403.
* the file carries 122 lines matching `heartbeat`, the last of them
  `[heartbeat] tid=13 uptime_ms=119319 kbd_nonzero=0` — the whole 120 s window.
* the periodic samplers keep running to the end: `[net-rx-counters] sample=10`,
  and 6 further `[PT_ROOT_CUSTODY:...]` / `[TOMBSTONE_CENSUS:...]` pairs after
  the service chain stopped.
* `grep -c` for a crash marker, for `EXT2_LOCK_SPIN_STALL` and for
  `!!! SOFT LOCKUP DETECTED !!!` returns 0 on each of the 5 head-arm failures of
  that round, `head_5` included.

So: timer, scheduler, softirq, network RX and the reclamation censuses are
alive; 1 chain — init waiting on `clonevm_exec_test`'s post-exec rendezvous — is
stopped. That is a lost wake or an unsatisfied futex on a single thread, not the
4-CPU spin #789's RCA closed. The RCA says so in its own words: "It did not
reproduce in the boots this round captured. It may be a second defect."

### Which PR surfaces it, and how

Two candidates, and each PR's acceptance run must carry the discriminator:

* **3h**, the idle-refusal PR, is the primary. `head_5` was observed only on the
  branch arm that carried `idle_sleep.rs`; 3h is the first PR that puts that
  code onto a production-gated `main`. Its mechanism candidates are the
  waitqueue refusals — `prepare_to_wait` returning the empty result and
  `prepare_to_wait_checked` returning `PublishFailed` before a caller has
  published itself as a waiter — and `refuse_idle_block` returning early from
  `block_current_*` without publishing blocked state, leaving a caller that
  believes it is asleep.
* **3d**, the pinned-wake PR, is the secondary. `park_pinned_thread_without_home`
  turns an unblock into a park, sets `UnblockOutcome::NotFound`, and removes the
  thread from each per-CPU queue. If the thread it parks is `ksoftirqd/N`, the
  softirq that carries a futex wake can go undrained. The RCA's specimen A read
  `PINNED_HOME_CPU_UNAVAILABLE = 0`, so that mechanism was not the one in that
  boot — but the counter is exactly the discriminator, so print it.

**How to surface it deliberately.** 3 boots cannot see a 1-in-8 shape: at a
per-boot rate of 1 in 8, 3 boots miss it about 2 times in 3. So 3h's production
smoke is **10 boots minimum**, run with the A/B override
`BREENIX_PROD_PROFILE_OUTPUT_DIR` / `BREENIX_PROD_PROFILE_FAILURE_DIR` that
`6f099e38` adds, alongside a matched `main` arm. For each boot, pass or fail,
record: the last service-chain line, whether heartbeats ran to the end of the
window, `IDLE_SLEEP_REFUSED`, `IDLE_IDENTITY_UNREADABLE`,
`PINNED_HOME_CPU_UNAVAILABLE`, and a QEMU CPU sample. The CPU sample is the
cheap separator the RCA established: a 4-CPU spin samples at 392.6 to 398.6 %
and a healthy boot at 163.4 to 193.1 %, so a `head_5` boot — alive, 1 chain
stuck — should sample near the healthy band, not the spinning one.

A boot with that signature is filed as a new issue, not attributed to #789.
