## 1. The guard

`Scheduler::retain_cpu_affine_thread(&mut self, thread_id, taking_cpu) -> bool`,
`kernel/src/task/scheduler.rs:4581`. `true` means the guard has already disposed
of the thread — it is on the queue of the CPU its pin names, or its wake is held
for that CPU — and the caller must not place it again. `false` means the
caller's own placement stands.

Its arms, in order, and what each is for:

| # | test | disposition | why |
|---|---|---|---|
| 1 | the thread row is missing | `false` | 0 pins to read |
| 2 | `state == Terminated` | `false` | a pin constrains where a thread RUNS, and a `Terminated` thread has 0 CPUs it can run on: 4 of 4 pop-and-admit loops in `schedule` and `schedule_deferred_requeue` test for `Terminated` before breaking to a dispatch. This is what keeps `terminate_process_threads`' quarantine token on a queue with spare capacity, which it must, because a quarantine pass may not allocate under SCHEDULER |
| 3 | no pin | `false` | the unpinned path, byte for byte as before |
| 4 | `!pin.per_cpu_worker` | `false`, and `PINNED_HOLD_PEN_MIGRATED` counted when `pin.cpu != taking_cpu` | slice 3d's ruling M1: a hold pen is placement only, released by whoever set it, so a migration site may override it — but not in silence |
| 5 | `pin.cpu == taking_cpu` | `false` | the caller's destination IS home; 0 CPUs are crossed |
| 6 | `pin.cpu >= online_cpu_count()` | `false`, `PINNED_PUBLISH_DISCARDED` counted and the row's pin cleared | slice 3d's ruling (1) at a second face. 0 producers reach it: `spawn_on_cpu` asserts an online target, `add_thread_inner` discards an out-of-range pin at publication, and 0 of the 2 child-creation paths inherit one |
| 7 | the saved kernel SP stands in a per-CPU stack slot that is not `pin.cpu` (aarch64) | `false`, `PINNED_STACK_HOME_CONFLICT` counted | the stack slot is a hardware fact and outranks the pin: resuming the thread anywhere but the CPU that owns the stack under its saved SP puts 2 CPUs on 1 stack, the corruption family PR #645 repaired. Reachable only if the pin has already been violated. `percpu_stack_home_cpu` — the selection-side reroute rows 2, 3, 5 and 6 push from, which returns before this guard is reached — applies the same rule and counts into the same counter, so the disagreement has 2 reporting sites and 0 silent ones |
| 8 | otherwise, `cpu_accepts_wakeups(pin.cpu)` | `true`, queued on `pin.cpu`, `PINNED_MIGRATION_REFUSED` counted | a placement needs no delivery, so a hold here would only add a step |
| 9 | otherwise, `pinned_wake_is_waiting_here(thread_id, pin.cpu)` | `true`, slice 3d's `hold_pinned_wake_for_home` | the home CPU is not accepting wakeups; the hold writes 0 thread rows and 0 queues, and `deliver_pinned_wakes_for_this_cpu` completes the placement at the home CPU's next scheduler entry |
| 10 | otherwise | `true`, queued on `pin.cpu` anyway | the thread is not in the shape delivery recognises — some other reachability record still names it — and a hold then would leave a wake with 0 deliverers. It waits on its home CPU's queue instead, which is what a per-CPU worker must do, and the strand oracle is left free to report it if the home does not return |

Arm 10 is the one place this slice deviates from the brief's "use the 3d hold"
instruction, and it is deliberate: the hold is only recoverable for a thread in
the exact shape `pinned_wake_is_waiting_here` tests for, and at some of the 11
sites the thread can still be named by another CPU's `previous_thread` slot, a
`pending_next` handoff or a deferred requeue when the guard runs.

Site 9 was not one of those sites by nature — it was one by statement order.
Round 1 cleared `cpu_state[cpu].previous_thread` *after* the placement, so the
slot that site was itself in the middle of draining answered "yes" to
`pinned_wake_is_waiting_here` on 1 of 1 pass, and arm 9 was unreachable from
there. `9136c85e` moves the clear ahead of the placement. Section 10, F3.

**Hot-path cost, at source level.** For a thread with no pin — 1 of 1 thread in
the 3 profiles this round built — the guard reads
`CPU_PINS_STAMPED` (1 relaxed load), compares it to 0, and returns `false`. It
reads 0 thread rows on that path, so it walks `self.threads` 0 times and adds 0
work to the steal loops beyond the load and the compare. `CPU_PINS_STAMPED` is a
monotonic count of the `CpuPin` values both constructors have built, so a 0
reading is a statement that 0 threads carry a pin and the 9 arms below would
each answer `false` anyway.

Once a pin exists — the `boot_tests` oracle mints one, and slice 3f will mint
the first production one — the full path runs: 1 `self.get_thread(thread_id)`
linear search over `self.threads`, 3 field reads and 2 branches. That search is
the same one the caller's own arms already perform at 9 of the 11 sites, so on a
kernel that carries pins the added work is a second walk of the same vector
under a lock the caller already holds.

Neither path takes a lock, allocates beyond the `VecDeque` growth the caller's
own `push_back` would have caused, or logs. The guard is not on the interrupt or
syscall entry path: 11 of 11 call sites are inside `impl Scheduler` under the
scheduler lock.

Round 1 shipped the full path unconditionally and disclosed the doubled walk
rather than claiming O(1); the constant-cost arm is round 2's answer to that
disclosure. Section 10, F2.

**No row is exempted.** The brief allowed a "consultation-equivalent" for sites
that cannot consult a pin by construction; 0 of the 11 needed one. Rows 8, 10
and 11 call the guard and receive a constant answer for reasons stated in the
table, which is a consultation, not an exemption. Rows 2, 3, 5 and 6 sit inside
functions whose steal loop calls the guard on the pop, which is where the
migration actually happens — the push at those exact lines re-routes on the

Those 4 pushes are the one place where "the site consults the pin" was a

uses, so the 2 places where a stack slot and a pin can contradict each other
both report it. `percpu_stack_reroute_counts_a_pin_conflict` holds that, with a
mutation leg for the count and one for the pin read. Section 10, F1.

## 3. The oracle

`[PIN_GUARD_ORACLE:aarch64:...]`, emitted once per `boot_tests` boot from
`kernel_main` immediately before the pinned-placement census.

The probe builds 1 kernel thread through `kthread::build_pin_guard_probe_thread`,
stamps it with a `per_cpu_worker` pin naming a peer CPU, and drives 3 of the 11
sites against it under 1 scheduler-lock acquisition with interrupts masked:

* **leg 1, site 1** — the probe is staged on a queue index past the online range
  (an offline slot; `-smp 4` with `MAX_CPUS` 8 leaves 4 of them) so the reclaim
  pass has exactly 1 candidate there and moves 0 other threads off it, then
  `reclaim_unschedulable_cpu_queues()` runs;
* **leg 2, site 7** — `requeue_thread_after_save_onto(tid, here)`;
* **leg 3, site 9** — `resolve_exception_cleanup_previous_thread(here)` with the
  slot staged.

Between the legs the probe is cleared off 8 of 8 per-CPU queues, so each leg
reads the destination of its own site. Afterwards the probe is taken back out of
`self.threads` and dropped outside the lock; it takes 0 dispatches.

## 4. The census fields

`emit_pinned_placement_census` grows from 4 fields to 6:

```
[PINNED_HOME_CPU_UNAVAILABLE:count=0:publish_discarded=0:hold_pen_migrated=0:delivered=0:migration_refused=0:stack_home_conflict=0]
```

`migration_refused` counts a migration the guard refused. `stack_home_conflict`
counts arm 7. Both are gate-failing on 2 of 2 aarch64 gates, and both are gated
by the same whole-line comparison against the all-zero literal that slice 3d

claim-lint:ok: 6 of 6 census fields are inside that comparison and 3 of the 6
are varied by a leg of `both_aarch64_gates_fail_on_a_pinned_placement_refusal`

**Two new fields where the brief suggested one, disclosed.** They are different
conditions with opposite meanings — a refusal is the guard working, a stack-home
conflict is the guard declining because something upstream already violated the
pin — and folding them into 1 number would make a reading above 0
unattributable.

**The probe subtracts its own contribution.** `emit_pin_guard_oracle` snapshots
`PINNED_MIGRATION_REFUSED`, runs the probe, and subtracts exactly the delta it
measured, printing it as `refused=3` instead. The census reports boot health and
the probe's 3 migrations are manufactured, so leaving them in would make the
gate red on a healthy boot. 0 other writers can move the counter in the window:
1 of 1 mutating writer of `Thread::cpu_affinity` is `spawn_on_cpu`, whose 1 call
site has 0 callers, so the probe's own thread is the only pinned one in the
kernel, and the sequence runs under the scheduler lock with interrupts masked.
The probe also compares the other 5 census counters across its legs and reports
`census_clean=1` only if 0 of them moved; a `census_clean=0` reading fails the
oracle.

## 8. Deviations

1. **Arm 10 places rather than holds.** The brief said a site whose home CPU is
   not accepting wakeups "uses the 3d hold". It does, at arm 9, when the thread
   is in the shape `pinned_wake_is_waiting_here` recognises. When it is not —
   still named by another CPU's `previous_thread` slot, a `pending_next` handoff
   or a deferred requeue — a hold would leave a wake with 0 deliverers, so the
   thread goes onto its home CPU's queue instead. `pin.cpu >= online_cpu_count()`
   is excluded at arm 6, so that queue belongs to an online (if stalled) CPU and
   a later local dispatch or reclaim pass finds it; the strand oracle reports it
   if the home does not return. Section 1.

   Round 1 made arm 10 unconditional at site 9 by ordering rather than by
   nature — the clear of that CPU's own `previous_thread` slot ran after the
   placement, so the slot answered "yes" to the hold predicate on 1 of 1 pass.
   `9136c85e` moves the clear ahead of the placement, which makes arm 9
   reachable there. The deviation is narrowed, not removed: a thread named by
   another CPU's slot, by a `pending_next` handoff or by a deferred requeue
   still takes arm 10. Section 10, F3.
2. **Two census fields, not one.** Section 4.
3. **The oracle drives 3 sites, and a steal is not one of them.** The brief
   named "a reclaim of a stalled/offline queue, a steal, a requeue-after-save
   onto another CPU" and asked for at least 2. A steal is not callable from a
   probe: it happens inside `schedule`'s own loop on whichever CPU is
   scheduling, and driving it would mean entering the scheduler from inside the
   scheduler lock. The 3 sites driven are 1, 7 and 9; sites 2, 3, 5 and 6 — the
   steal loops — are covered by the source rules and by the guard being shared.
4. **The reclaim leg uses an offline queue index rather than a stalled CPU.**
   Forcing a live CPU stale would have made the reclaim pass drain that CPU's
   whole queue onto the probing CPU, which is a real scheduling perturbation. An
   offline slot's queue is empty, so the pass has exactly 1 candidate.
5. **The probe subtracts its own census contribution.** Section 4.
6. **The branch is cut from `e9b0a4f6`, and the red-on-main capture is at
