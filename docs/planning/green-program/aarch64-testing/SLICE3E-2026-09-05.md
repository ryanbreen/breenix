## 1. The guard

`Scheduler::retain_cpu_affine_thread(&mut self, thread_id, taking_cpu) -> bool`,
`kernel/src/task/scheduler.rs:4581`. `true` means the guard has already disposed
of the thread — it is on the queue of the CPU its pin names, or its wake is held
for that CPU — and the caller must not place it again. `false` means the
caller's own placement stands.

Its arms, in order, and what each is for:

| # | test | disposition | why |
|---|---|---|---|
| 1 | the thread row is missing | `false` | 0 pins to read |
| 2 | `state == Terminated` | `false` | a pin constrains where a thread RUNS, and a `Terminated` thread has 0 CPUs it can run on: 4 of 4 pop-and-admit loops in `schedule` and `schedule_deferred_requeue` test for `Terminated` before breaking to a dispatch. This is what keeps `terminate_process_threads`' quarantine token on a queue with spare capacity, which it must, because a quarantine pass may not allocate under SCHEDULER |
| 3 | no pin | `false` | the unpinned path, byte for byte as before |
| 4 | `!pin.per_cpu_worker` | `false`, and `PINNED_HOLD_PEN_MIGRATED` counted when `pin.cpu != taking_cpu` | slice 3d's ruling M1: a hold pen is placement only, released by whoever set it, so a migration site may override it — but not in silence |
| 5 | `pin.cpu == taking_cpu` | `false` | the caller's destination IS home; 0 CPUs are crossed |
| 6 | `pin.cpu >= online_cpu_count()` | `false`, `PINNED_PUBLISH_DISCARDED` counted and the row's pin cleared | slice 3d's ruling (1) at a second face. 0 producers reach it: `spawn_on_cpu` asserts an online target, `add_thread_inner` discards an out-of-range pin at publication, and 0 of the 2 child-creation paths inherit one |
| 7 | the saved kernel SP stands in a per-CPU stack slot that is not `pin.cpu` (aarch64) | `false`, `PINNED_STACK_HOME_CONFLICT` counted | the stack slot is a hardware fact and outranks the pin: resuming the thread anywhere but the CPU that owns the stack under its saved SP puts 2 CPUs on 1 stack, the corruption family PR #645 repaired. Reachable only if the pin has already been violated |
| 8 | otherwise, `cpu_accepts_wakeups(pin.cpu)` | `true`, queued on `pin.cpu`, `PINNED_MIGRATION_REFUSED` counted | a placement needs no delivery, so a hold here would only add a step |
| 9 | otherwise, `pinned_wake_is_waiting_here(thread_id, pin.cpu)` | `true`, slice 3d's `hold_pinned_wake_for_home` | the home CPU is not accepting wakeups; the hold writes 0 thread rows and 0 queues, and `deliver_pinned_wakes_for_this_cpu` completes the placement at the home CPU's next scheduler entry |
| 10 | otherwise | `true`, queued on `pin.cpu` anyway | the thread is not in the shape delivery recognises — some other reachability record still names it — and a hold then would leave a wake with 0 deliverers. It waits on its home CPU's queue instead, which is what a per-CPU worker must do, and the strand oracle is left free to report it if the home does not return |

Arm 10 is the one place this slice deviates from the brief's "use the 3d hold"
instruction, and it is deliberate: the hold is only recoverable for a thread in
the exact shape `pinned_wake_is_waiting_here` tests for, and at 4 of the 11
sites the thread can still be named by a `previous_thread` slot, a
`pending_next` handoff or a deferred requeue when the guard runs.

**Hot-path cost, at source level.** For a thread with no pin — every thread in
the 3 profiles this round built — the guard is 1 `self.get_thread(thread_id)`
linear search over `self.threads`, 3 field reads and 2 branches, then `false`.
That search is the same one the caller's own arms already perform at 9 of the 11
sites (each reads the thread's state or its idle status through `get_thread`
within a few statements), so the added work is a second walk of the same vector
under a lock the caller already holds. 0 locks are taken, 0 allocations are made
beyond the `VecDeque` growth the caller's own `push_back` would have caused, and
0 logging calls are added. The guard is not on the interrupt or syscall entry
path: 11 of 11 call sites are inside `impl Scheduler` under the scheduler lock.

## 3. The oracle

`[PIN_GUARD_ORACLE:aarch64:...]`, emitted once per `boot_tests` boot from
`kernel_main` immediately before the pinned-placement census.

The probe builds 1 kernel thread through `kthread::build_pin_guard_probe_thread`,
stamps it with a `per_cpu_worker` pin naming a peer CPU, and drives 3 of the 11
sites against it under 1 scheduler-lock acquisition with interrupts masked:

* **leg 1, site 1** — the probe is staged on a queue index past the online range
  (an offline slot; `-smp 4` with `MAX_CPUS` 8 leaves 4 of them) so the reclaim
  pass has exactly 1 candidate there and moves 0 other threads off it, then
  `reclaim_unschedulable_cpu_queues()` runs;
* **leg 2, site 7** — `requeue_thread_after_save_onto(tid, here)`;
* **leg 3, site 9** — `resolve_exception_cleanup_previous_thread(here)` with the
  slot staged.

Between the legs the probe is cleared off 8 of 8 per-CPU queues, so each leg
reads the destination of its own site. Afterwards the probe is taken back out of
`self.threads` and dropped outside the lock; it takes 0 dispatches.
