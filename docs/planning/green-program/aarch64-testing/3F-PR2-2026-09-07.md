## Kernel change

The helper is at the beginning of the existing `impl Scheduler`. The plan
requested proximity to the free boot-test helper, but the first placement in
a separate impl broke the existing coreproof scanner. The correction keeps
one impl and does not weaken that scanner.
`kernel/src/task/scheduler.rs:1910`
declines in the prescribed order: no minted pins, offline source, missing
thread, terminated thread, absent pin, non-worker or wrong home, then aarch64
stack-slot disagreement. It pushes back onto the source queue after those
checks. The stack-slot arm does not count: the existing reroute and migration
guard remain the two `PINNED_STACK_HOME_CONFLICT.fetch_add` writers.
The existing conflict ratchet now counts those writers as well as checking
the reroute body.

The rescue-call census at the implementation source is
`kernel/src/task/scheduler.rs:2090`, `:2531`, `:2605`, `:3047`, `:3119`.
These are the reclaim site and the two steal arms in each scheduling entry
point. Each restored candidate continues before the migration guard.
The reclaim comment and guard doc describe this predecessor now.

H4: an offline source declines. Where the worker's pin names that source,
`retain_cpu_affine_thread` counts `PINNED_PUBLISH_DISCARDED`, clears the row's
pin and lets reclaim place the thread on the current CPU. Retaining an offline
home would park work on a queue that contributes reachability without a
CPU dispatching it. Re-homing a per-CPU worker is not an ordinary legal
placement: `kernel/src/task/thread.rs:627` describes the CPU-local state it
services. The existing counted invalid-pin disposition stays visible.
`CPUS_ONLINE` in `kernel/src/arch_impl/aarch64/smp.rs` has one incrementing
writer; growth between the helper's and guard's reads can instead reach a
counted hold, as the plan describes.

H3: the guard's home-accepting enqueue, hold, and not-waiting-here enqueue
each call `send_resched_ipi_to_cpu(pin.cpu)` under aarch64 cfg. The helper's
restoration push sends no kick. The five wake-path holds and the hold method
are unchanged. An SGI requests rescheduling; it does not prove dispatch or
latency. The receiver sets `need_resched` at
`kernel/src/arch_impl/aarch64/exception.rs:2100`; the preempt-guard return at
`kernel/src/arch_impl/aarch64/context_switch.rs:5350` still limits delivery.
(claim-lint:ok: the 3 of 3 guard kick mutations are recorded in serials/3f-pr2/mutation-results.json; the dispatch limit names the receiver and preempt return above)

Cost: the unpinned helper path is one relaxed load and comparison. A pinned
candidate adds the acquire online-count read, a thread lookup, field checks,
and on aarch64 a stack-slot lookup. Retention restores capacity just freed by
a pop. The guard kick uses the existing bounds checks, trace event and SGI
write. PR 2 adds no lock acquisition or formatting. `rustfmt` also normalized
existing formatting and import ordering in the scheduler file.

Tier-2 touched: `[]`. The defect lives in `kernel/src/task/scheduler.rs`,
which is outside the supplied Tier-1/Tier-2 lists. No Tier-1 file was edited.
