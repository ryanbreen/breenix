# Slice 3d — a pinned wake goes through the liveness filter, or is held

Branch `sched/562-slice3d-pinned-wake-liveness`, cut from `origin/main`
`9b3dd4af` (PR #811, slice 3c). Ported per hunk from the parked branch
`origin/fix/562-761-aarch64-testing-profile` (`d277213d`); that branch is not
merged here, and no commit of it is cherry-picked. Section 3d of
`SLICE3-PLAN-2026-09-05.md` is the specification this round implements, and
section 10 of `SLICE3C-2026-09-05.md` is the list of dispositions it owes.

**Round R157 changed the disposition this branch ships.** The first pass
answered a refused pinned wake with a *park* — the thread published `Blocked`
and left every ready queue. Review found that park destroys the wake it was
given (findings B1, B2, B3), that it reports a wake that happened as one that
did not (M3), that the hold-pen half of the pin was overridden in silence (M1),
and that the source rule meant to compensate did not pin the publication (M2).
The park is gone. A refused wake is now **held** for the home CPU and delivered
by that CPU's next scheduler entry. Section 2 is the finding-by-finding record.

## 2. The R157 review, finding by finding

**B1 — the park consumed the wake, and 0 paths re-armed it.**
`wake_expired_timers` pops the timer-heap entry and clears `wake_time_ns`
before the placement decision, so a park there left the thread `Blocked`, off
each of the MAX_CPUS queues, with no deadline and 0 wakers left. Ruling: **the refusal does not
consume the wake.** `hold_pinned_wake_for_home` takes `&self`. It cannot write
a thread row and cannot write a queue, so the `Ready` its caller published
stands and the thread stays exactly where the wake path put it — reachable
through 0 of the 5 dimensions the strand oracle uses, but *runnable-pending*. `deliver_pinned_wakes_for_this_cpu` runs at
both scheduler entry points and completes the refused placement:

```rust
fn deliver_pinned_wakes_for_this_cpu(&mut self) {
    if PINNED_HOME_CPU_UNAVAILABLE.load(Ordering::Relaxed) == 0 {
        return;
    }
    let cpu = Self::current_cpu_id();
    let mut index = 0;
    while index < self.threads.len() {
        let tid = self.threads[index].id();
        index += 1;
        if !self.pinned_wake_is_waiting_here(tid, cpu) {
            continue;
        }
        self.per_cpu_queues[cpu].push_back(tid);
        PINNED_WAKES_DELIVERED.fetch_add(1, Ordering::Relaxed);
        ENQUEUE_SAME_LOCK_OK.fetch_add(1, Ordering::Relaxed);
    }
}
```

The held set is **derived, not recorded**: `pinned_wake_is_waiting_here` asks
whether the thread is `Ready`, carries a `per_cpu_worker` pin naming this CPU,
and is reachable through none of the 5 dimensions the strand oracle uses
(queued, current, previous, `pending_next`, deferred). That is exactly the
shape the hold leaves, so there is no side list to size, to overflow, or to
leave stale when another path wakes, requeues or terminates the thread first —
each of those changes the shape and the thread stops matching.
claim-lint:ok: 5 of 5 dimensions of `reachability_dimensions` in
`kernel/src/task/scheduler.rs` are tested by the predicate, counted by reading
both lists in this round

**B2 — the park collapsed the blocked kind to plain `Blocked`.**
Two of the five wake sites key on the kind they woke from, so a parked thread's
next signal or child-exit would have been a no-op. Ruling: **no state is
written at all**, so no kind is collapsed. This is enforced by the receiver
rather than by a substring: an `&self` method cannot reach `get_thread_mut`.

**B3 — the park reversed a publication it did not make.**
`wake_io_thread_locked`'s `_ =>` arm handles a thread another path already
published `Ready` while it is still `blocked_in_syscall`; a park there wrote it
back to `Blocked` with no waker left. Same ruling, same mechanism: the hold
writes no state and no queue, so that arm's job — a ready-queue insertion for a
thread already marked `Ready` — is deferred to the home CPU, not undone.

**M1 — a hold-pen pin was overridden in silence.**
Ruling: **a hold pen is never held, and the override is counted.** The two pin
kinds get opposite dispositions and this is the second one. A hold pen is
placement only, released by whoever set it, so holding its wake would strand
whatever the pen is holding; the wake falls through to the least-loaded arm and
the thread is placed where it can run. `PINNED_HOLD_PEN_MIGRATED` counts that
fall-through and 2 of 2 aarch64 gates fail on it, so the legal disposition is no
longer an invisible one.
claim-lint:ok: leg E of `both_aarch64_gates_fail_on_a_pinned_placement_refusal`
varies this field alone and reddens 2 of 2 gates

**M2 — the source rule did not pin the publication it advertised.**
The old validator's `if !compact.contains("ThreadState::Blocked")` was
satisfied by a comparison, and its three legs contained no publication-deletion
leg. Ruling: **the rule inverted, and legged in the direction that works.** The
repair is now the ABSENCE of a state write, which a deletion leg cannot see, so
`validate_pinned_hold_preserves_the_wake` carries **injection** legs — a state
write, a queue write and a pin write are each injected into the live hold and
each reddens it — plus a receiver leg, a delivery-enqueue deletion leg, and a
per-entry-point delivery-call deletion leg. 6 legs, listed in section 6.

**M3 — `unblock`'s documented contract was false and its census inflated.**
The park arm returned `UnblockOutcome::NotFound` for a thread that WAS in one
of the four states the doc says it transitions, after `set_ready()`,
`WAKE_SITE_UNBLOCK` and `record_ready_site` had already fired. Ruling: **the
outcome stays `Transitioned`, and the counters were right all along.** The
thread was transitioned; its wake is held, not refused. The `outcome =
UnblockOutcome::NotFound;` line is deleted and `unblock`'s doc now states the
held case explicitly. 1 of the 5 refusal sites reported anything to its caller
and it no longer does, so 5 of 5 now agree.

### One thing this ruling deliberately does not do

It adds **no reachability dimension to the strand oracle**. Between the hold
and the home CPU's next scheduler entry the thread is `Ready` and reachable
through none of the oracle's 5 dimensions, and the oracle is left free to
report it: a per-CPU worker whose home CPU has stopped dispatching IS stranded,
and the honest answer is to say so rather than to widen the definition of
reachable until it stops saying so. The census is the second reading of the
same fact, and it is gate-failing.

`reachability_dimensions` at `9b3dd4af` are the 5 there now, counted by grep
over `kernel/src/task/scheduler.rs` in this round

## 3. The dispositions slice 3c left representable

`SLICE3C-2026-09-05.md` section 10 names 4 states the pin makes expressible and
does not resolve, and binds 3d to rule on each. R157 added a fifth, M1. The
rulings, 5 of 5:

**(1) S3C-m4 — an out-of-range pin discarded in silence while the row keeps
naming the CPU. Ruling: count it and clear the row.**
`add_thread_inner` keeps the placement expression shape slice 3c's ratchet
pins, and gains, immediately after it:

```rust
if cpu_affinity.is_some_and(|pin| pin.cpu != target) {
    PINNED_PUBLISH_DISCARDED.fetch_add(1, Ordering::Relaxed);
    if let Some(thread) = self.get_thread_mut(thread_id) {
        thread.cpu_affinity = None;
    }
}
```

`pin.cpu != target` identifies exactly the rejected case: the bound only drops a
pin whose CPU is at or past `online_cpu_count()`, and `least_loaded_cpu()`
returns strictly below it, so the two cannot coincide. The counter is
gate-failing on both aarch64 boot gates. **Refusing the publish and parking were
the other two options and were not chosen**: a publish-time park changes the
semantics of each thread creation for a case that, after ruling (3) below, has
no producer left.

**(2) S3C-m5 — the pin arm's bound was weaker than the fall-through's. Ruling:
both halves, as the plan requires.** The liveness test is the conjunct in the
pin arm; the disposition when it fails is `hold_pinned_wake_for_home`. Adding
the conjunct alone would have converted a `per_cpu_worker` pin whose home CPU
stalled into the migration the pin forbids, which is why the two ship together.
What R157 changed is what the second half *is*: a hold, not a park.

**(3) S3C-m2 — the two child-creation paths disagreed about inheritance.
Ruling: a pin is not inherited, on either path.** `sys_clone`
(`clone.rs:244`) already wrote the empty state; the x86 `testing` CoW-fork
literal (`manager.rs:3111`) now writes `None` too instead of copying the
parent's. A `per_cpu_worker` pin is a claim about servicing one CPU's per-CPU
block, which a child does not inherit; a hold-pen pin says the parent is parked
in a staging pen the child was never put in. This inverts `ef97d86e` and removes
the disagreement rather than documenting it. Consequence worth stating: with
`spawn_on_cpu`'s `assert!(cpu < scheduler.online_cpu_count())` and no
inheritance, this kernel has no producer of an out-of-range pin at all, which is
why the counter in ruling (1) is expected to read 0 for a structural reason and
not only for want of a pin.
claim-lint:ok: 1 of 1 mutating writer of the field is `spawn_on_cpu`, and 14 of
15 `Thread` build sites carry `cpu_affinity: None` — both counted by grep over
`kernel/src` in this round.

**(4) S3C-m3 — two copies of the field, no single authority. Ruling: the
scheduler's publication copy is the authority for placement, and the refusal
writes no pin.** `find_target_cpu_for_wakeup` reads the pin through
`self.get_thread`, the hold and its delivery predicate read it through
`self.get_thread`, and `add_thread_inner`'s discard writes through
`self.get_thread_mut` **after** `self.threads.push(thread)` — so each read and
the one corrective write are on the scheduler's own copy. The hold writes no
pin at all, so it cannot leave one copy stale, and that is enforced:
`validate_pinned_hold_preserves_the_wake` rejects a hold whose body contains a
`cpu_affinity=` store, with an injection leg.

**(5) R157/M1 — a hold-pen pin whose home CPU cannot take the wake. Ruling:
migrate it, and count the migration.** Section 2. The pin kinds' doc comment in
`thread.rs` said a hold pen "is retained on its queue rather than parked"; the
wake path has no queue to retain it on when the home CPU is not accepting
wakeups, so the honest reading is that it must still be placed somewhere it can
run. `PINNED_HOLD_PEN_MIGRATED` is the record, and both gates fail on it.

## 4. The inertness argument

**No thread carries a pin at runtime, so the pin arm, the hold, the delivery
and the discard are unreachable in the 3 profiles this round built.**

```
$ grep -rn "spawn_on_cpu" kernel/src | grep -v for_test
kernel/src/task/scheduler.rs:4593:pub fn spawn_on_cpu(...)      # the definition
kernel/src/task/kthread.rs:79:        scheduler::spawn_on_cpu(thread, cpu)
$ grep -rn "kthread_run_on_cpu" kernel/src | grep -v for_test
kernel/src/task/kthread.rs:70:pub fn kthread_run_on_cpu<F>(     # the definition
```

`spawn_on_cpu` is the 1 mutating writer of `Thread::cpu_affinity`; it has 1 call
site, `kthread_run_on_cpu`, which has 0. After ruling (3), 14 of the 15 sites
that build a `Thread` write the empty state outright and the 15th is the `Clone`
impl, which carries whatever its source held — the empty state on each of them.
Therefore:

* `find_target_cpu_for_wakeup`'s `if let Some(pin) = …` is not entered, and the
  function's remaining arms are the ones `main` evaluates, wrapped in `Some(…)`.
* `hold_pinned_wake_for_home` has 5 call sites and 0 reachable ones.
* `deliver_pinned_wakes_for_this_cpu` returns at its first line on each of the
  2 scheduler entry points, because the counter it reads is 0.
* `add_thread_inner`'s discard arm has no producer.

That is why section 11's gates are expected **unchanged, not improved**, and it
is the claim those gates support. The first pinned thread appears in slice 3f,
where `ksoftirqd/N` is spawned through `kthread_run_on_cpu`.

**The delivery scan's cost on a healthy boot is 1 relaxed load and 1 branch per
scheduler entry.** Once a hold has happened the counter never returns to 0 and
the scan runs on each entry — which is a state the gate has already failed, and
the forced-hold boot in section 7 is a boot that ran the whole way to its
`BOOT_TESTS` completion with the scan armed.

## 5. The `head_5` discriminator

`SLICE3-PLAN-2026-09-05.md` section 3 names this slice as the **secondary**
candidate for surfacing #789's `head_5` shape — a boot that stays alive, with
heartbeats and samplers running to the end of the window, while one service
chain stops. The mechanism it names: if a refused wake strands `ksoftirqd/N`,
the softirq carrying a futex wake goes undrained, and a wake is lost without
anything crashing.

`PINNED_HOME_CPU_UNAVAILABLE` is that discriminator, and this round makes it
readable three ways rather than one:

* the **census line**
  `[PINNED_HOME_CPU_UNAVAILABLE:count=N:publish_discarded=M:hold_pen_migrated=K:delivered=D]`,
  emitted once from `kernel_main` in each profile and again on the boot-test
  sampling kthread's period, so a strict boot carries 3 or 4 of them and a
  production boot 1;
* the **one-shot marker**
  `[PINNED_HOME_CPU_UNAVAILABLE:first:tid=…:home=…:cpu=…:count=…]`,
  which fires whenever the first hold happens — including after the last census
  emission, which is the case the production profile would otherwise miss;
* both **gate-failing** on the strict and production gates.

`count` above `delivered` is the reading that says a wake is still waiting; the
two equal says a home CPU came back and the wake was placed. The RCA's specimen
A read `PINNED_HOME_CPU_UNAVAILABLE = 0`, so that mechanism was not the one in
that boot. **Until 3f and 3h land this is a prepared instrument and nothing
more**: no thread carries a pin, so the counter cannot move, and 3 boots of each
profile could not characterise a 1-in-8 shape even if it could.
claim-lint:ok: 1 of 1 mutating writer of the pin has 0 reachable callers,
counted by the greps in section 4.
