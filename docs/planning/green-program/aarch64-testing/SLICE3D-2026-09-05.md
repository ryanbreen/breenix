### Deviations from the parked branch, named

1. **The defect the parked commit fixes does not exist on `main`.**
   `5cefa78f`'s subject is "the affinity fast-return added in `4f6988cf`
   returned a pinned CPU after checking only that it was inside the online
   range". `4f6988cf`'s fast-return is not on `main`: slice 3c landed the pin in
   `add_thread_inner` alone, and `origin/main:kernel/src/task/scheduler.rs:3989`
   opens `fn find_target_cpu_for_wakeup(&self, tid: u64) -> usize` with 0
   references to `cpu_affinity` in its body. So this slice does not repair a
   drift; it adds the pin arm to the wake path **with the filter already in
   it**. What `main` does today with a pinned thread is worse than the parked
   defect — it ignores the pin entirely and routes by cache affinity and least
   load, which for a `per_cpu_worker` pin is the migration the pin exists to
   forbid — and that is what changes here.
   claim-lint:ok: 0 of 5 wake sites consulted a pin at `9b3dd4af`, counted by
   grep over `kernel/src/task/scheduler.rs`.
2. **The function is `park_pinned_worker_without_home`, not

## 2. What the parked head changed after `5cefa78f`, and is carried

Three things, 3 of 3 in the ported hunks:

* **The same-CPU exception.** `5cefa78f` reads
  `if pin.cpu < self.online_cpu_count() && self.cpu_accepts_wakeups(pin.cpu)`.
  `d277213d` reads
  `if pin.cpu < self.online_cpu_count() && (home_is_this_cpu || self.cpu_accepts_wakeups(pin.cpu))`,
  with the parked branch's own comment giving the reason: a per-CPU worker's
  wake arrives from its own CPU on the IRQ-exit path, where
  `arch_can_dispatch_here()` is false, so `cpu_accepts_wakeups` falls through to
  the staleness test — "has this CPU entered the scheduler in the last
  `CPU_STALL_TICKS`" — which is the wrong question to ask of a CPU that is
  demonstrably executing. Carried, in substance and with the reasoning.
* **The rename** (deviation 2 above).
* **The one-shot marker.** `5cefa78f`'s park increments the counter and emits
  no line; `d277213d` adds `PINNED_HOME_CPU_UNAVAILABLE_MARKED` and the
  `[PINNED_HOME_CPU_UNAVAILABLE:first:tid=…:home=…:cpu=…:count=…]` line, written
  with `crate::tracing::output::raw_serial_str` / `raw_serial_dec` because the
  park runs under the scheduler lock with interrupts masked. Carried.

## 3. The four dispositions slice 3c left representable

`SLICE3C-2026-09-05.md` section 10 names 4 states the pin makes expressible and
does not resolve, and binds 3d to rule on each. The rulings, 4 of 4:

**(1) S3C-m4 — an out-of-range pin discarded in silence while the row keeps
naming the CPU. Ruling: count it and clear the row.**
`add_thread_inner` keeps the placement expression shape slice 3c's ratchet
pins, and gains, immediately after it:

```rust
if cpu_affinity.is_some_and(|pin| pin.cpu != target) {
    PINNED_PUBLISH_DISCARDED.fetch_add(1, Ordering::Relaxed);
    if let Some(thread) = self.get_thread_mut(thread_id) {
        thread.cpu_affinity = None;
    }
}
```

`pin.cpu != target` identifies exactly the rejected case: the bound only drops a
pin whose CPU is at or past `online_cpu_count()`, and `least_loaded_cpu()`
returns strictly below it, so the two cannot coincide. The counter is
gate-failing on both aarch64 boot gates. **Refusing the publish and parking were
the other two options and were not chosen**: a publish-time park changes the
semantics of each thread creation for a case that, after ruling (3) below, has
no producer left.

**(2) S3C-m5 — the pin arm's bound was weaker than the fall-through's. Ruling:
both halves, as the plan requires.** The liveness test is the conjunct in the
pin arm; the park is `park_pinned_worker_without_home`. Adding the conjunct
alone would have converted a `per_cpu_worker` pin whose home CPU stalled into
the migration the pin forbids, which is why the two ship together.

**(3) S3C-m2 — the two child-creation paths disagreed about inheritance.
Ruling: a pin is not inherited, on either path.** `sys_clone`
(`clone.rs:244`) already wrote the empty state; the x86 `testing` CoW-fork
literal (`manager.rs:3111`) now writes `None` too instead of copying the
parent's. A `per_cpu_worker` pin is a claim about servicing one CPU's per-CPU
block, which a child does not inherit; a hold-pen pin says the parent is parked
in a staging pen the child was never put in. This inverts `ef97d86e` and removes
the disagreement rather than documenting it. Consequence worth stating: with
`spawn_on_cpu`'s `assert!(cpu < scheduler.online_cpu_count())` and no
inheritance, this kernel has no producer of an out-of-range pin at all, which is
why the counter in ruling (1) is expected to read 0 for a structural reason and
not only for want of a pin.
claim-lint:ok: 1 of 1 mutating writer of the field is `spawn_on_cpu`, and 14 of
15 `Thread` build sites carry `cpu_affinity: None` — both counted by grep over
`kernel/src` in this round.

**(4) S3C-m3 — two copies of the field, no single authority. Ruling: the
scheduler's publication copy is the authority for placement, and the park writes
no pin.** `find_target_cpu_for_wakeup` reads the pin through `self.get_thread`,
the park reads it through `self.get_thread`/`get_thread_mut`, and
`add_thread_inner`'s discard writes through `self.get_thread_mut` **after**
`self.threads.push(thread)` — so each read and the one corrective write are on
the scheduler's own copy. The park deliberately writes no pin at all, so it
cannot leave one copy stale, and that is enforced:
`validate_pinned_park_leaves_no_queue_holding_the_thread` rejects a park whose
body contains a `cpu_affinity=` store. The field's doc comment in `thread.rs`
now states the rule, in the shape the neighbouring `wait_loop_iters` comment
uses.

## 4. The inertness argument

**No thread carries a pin at runtime, so the pin arm, the park and the discard
are unreachable in the 3 profiles this round built.**

```
$ grep -rn "spawn_on_cpu" kernel/src | grep -v for_test
kernel/src/task/scheduler.rs:4593:pub fn spawn_on_cpu(...)      # the definition
kernel/src/task/kthread.rs:79:        scheduler::spawn_on_cpu(thread, cpu)
$ grep -rn "kthread_run_on_cpu" kernel/src | grep -v for_test
kernel/src/task/kthread.rs:70:pub fn kthread_run_on_cpu<F>(     # the definition
```

`spawn_on_cpu` is the 1 mutating writer of `Thread::cpu_affinity`; it has 1 call
site, `kthread_run_on_cpu`, which has 0. After ruling (3), 14 of the 15 sites
that build a `Thread` write the empty state outright and the 15th is the `Clone` impl,
which carries whatever its source held — the empty state on each of them.
Therefore:

* `find_target_cpu_for_wakeup`'s `if let Some(pin) = …` is not entered, and the
  function's remaining arms are the ones `main` evaluates, wrapped in `Some(…)`.
* `park_pinned_worker_without_home` has 5 call sites and 0 reachable ones.
* `add_thread_inner`'s discard arm has no producer.

That is why section 10's gates are expected **unchanged, not improved**, and it
is the claim those gates support. The first pinned thread appears in slice 3f,
where `ksoftirqd/N` is spawned through `kthread_run_on_cpu`.

## 5. The `head_5` discriminator

`SLICE3-PLAN-2026-09-05.md` section 3 names this slice as the **secondary**
candidate for surfacing #789's `head_5` shape — a boot that stays alive, with
heartbeats and samplers running to the end of the window, while one service
chain stops. The mechanism it names: if `park_pinned_worker_without_home` parks
`ksoftirqd/N`, the softirq carrying a futex wake goes undrained, and a wake is
lost without anything crashing.

`PINNED_HOME_CPU_UNAVAILABLE` is that discriminator, and this round makes it
readable three ways rather than one:

* the **census line** `[PINNED_HOME_CPU_UNAVAILABLE:count=N:publish_discarded=M]`,
  emitted once from `kernel_main` in each profile and again on the boot-test
  sampling kthread's period, so a strict boot carries 4 of them and a production
  boot 1;
* the **one-shot marker** `[PINNED_HOME_CPU_UNAVAILABLE:first:tid=…:home=…:cpu=…:count=…]`,
  which fires whenever the first park happens — including after the last census
  emission, which is the case the production profile would otherwise miss;
* both **gate-failing** on the strict and production gates.

The RCA's specimen A read `PINNED_HOME_CPU_UNAVAILABLE = 0`, so that mechanism
was not the one in that boot. What this slice adds is that the reading is now
taken on each gated boot rather than by hand, and that a `head_5` boot which
did carry a park would be a gate failure naming the tid and its home CPU, not a
silent pass. **Until 3f and 3h land this is a prepared instrument and nothing
more**: no thread carries a pin, so the counter cannot move, and 3 boots of each
profile could not characterise a 1-in-8 shape even if it could.
claim-lint:ok: 1 of 1 mutating writer of the pin has 0 reachable callers,
counted by the greps in section 4.
