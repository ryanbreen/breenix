## 1. The instruction abort — a stale `next_cr3` applied to a userspace ERET

### Mechanism

`FAR=0x40004530 ELR=0x40004530 ESR=0x8200000e IFSC=0xe TTBR0=0x40200000
from_el0=1`. `0x40004530` is `init::main+0x24` in the userspace ELF — the return
address of init's *first* `svc`. `ESR 0x8200000e` is a level-2 permission fault:
the page is mapped under the kernel root's identity map but is not
EL0-executable. So init returned from its first syscall onto the **kernel** page
table.

Two per-CPU words decide which root a return to EL0 runs on, and both are read by
the syscall return corridor in `kernel/src/arch_impl/aarch64/syscall_entry.S`:

| word | offset | corridor behaviour |
|---|---|---|
| `next_cr3` | 64 | read first (`:376`); a set value is installed and cleared |
| `saved_process_cr3` | 80 | the fallback (`:393`), restored when `next_cr3` is clear |

claim-lint:ok: 7 of 7 `#64`-relative reads in `boot.S` are frame-relative, per
the round-6 RCA recorded on #786.
Every idle dispatch on a CPU runs `setup_idle_return_locked`
(`context_switch.rs:4614`), which stores `next_cr3 = kernel_root`,
`saved_process_cr3 = 0`. Nothing on the idle return corridor consumes that store
— `boot.S` never reads per-CPU offset 64 — so it sits armed.

`launch_init_from_elf` (`main_aarch64.rs`) then installed init's root with a raw
`msr ttbr0_el1` and reconciled neither shadow. The ERET to EL0 worked, because
the *register* was right. Init's first `svc` entry stub saved the real TTBR0 into
offset 80, and the return stub read the still-armed offset 64, installed the
kernel root, and ERETed — instruction abort at init's own return address.

Intermittent -- 13 of the 26 committed baseline boots
(`serials/r7/aba/baseline-26/`, counted in `serials/r7/aba/CLASSIFICATION.tsv`)
-- because a timer preemption that
re-dispatched init through `dispatch_thread_locked` overwrote the stale value
first.

Init is the one thread that reaches EL0 without passing through
`dispatch_thread_locked`, which is why no other userspace thread hit it.

### Fix

`kernel/src/arch_impl/aarch64/ttbr0.rs` grows `adopt_process_ttbr0(ttbr0_value)`:
the barrier/`msr`/TLBI sequence, then `set_saved_process_cr3(ttbr0_value)` and
`set_next_cr3(0)`. Clearing `next_cr3` is part of the install, not a courtesy —
after the call the architectural register is the decision, so a pending "switch
to some other root on the way out" request is either the same root or a stale
one, and applying either on the return path is wrong.

claim-lint:ok: 7 of 7 censused install functions, enumerated under Ratchets below.
Every reachable process-root install now goes through it, not just init's:

| site | what it was |
|---|---|
| `main_aarch64.rs` `launch_init_from_elf` | the measured producer |
| `arch_impl/aarch64/syscall_entry.rs` exec | published `saved_process_cr3`, left `next_cr3` armed |
| `arch_impl/aarch64/syscall_entry.rs` signal delivery | reconciled neither |
| `arch_impl/aarch64/context_switch.rs` IRQ-path signal delivery | reconciled neither |
| `syscall/wait.rs`, `syscall/futex.rs`, `syscall/graphics.rs`, `syscall/handlers.rs` `ensure_current_address_space` | reconciled neither; the `graphics.rs` copy also had no TLB invalidation at all |

## 2. The block wedge — a contended `try_lock` turned into a permanent verdict

### Mechanism

claim-lint:ok: 12 of 25 round-6 boots, #786.
`block_wedge_oracle` reported `BLOCK_WEDGE_ORACLE_BAD_CONTEXT` ("second lock was
not sleep-permitted"). The path: `block_mmio_request_gate_can_sleep` →
`completion::current_context_can_sleep` → `idle_identity_must_not_sleep`
(`kernel/src/task/idle_sleep.rs`), whose `None` arm returned `true` — refuse.

`is_current_idle_thread` returns `None` **only** when `try_lock_scheduler`
fails. The probe builds measured it, and those serials are now committed under
`serials/r7/aba/`. Re-derived from them in round 8: 10 `[RCA786_WEDGE] refused`
lines survive, 8 of them legible through `idle_ans=0`, and all 8 read
`irq_on=1 in_irq=0 in_sirq=0 pc=1 timer=1 idle_ans=0`; the 5 printed by the
build that also carried the counters read
`unknown_identity_refusals=1 idle_refused=0`. The later build that classifies
the three ways `None` can arise left 4 `[RCA786_W2]` lines, and all 4 read
`trylock_fail=1 idle_refused=0` (`cur_id=39` three times, `cur_id=53` once). So
every other eligibility term held, the `Some(true)` arm never fired at all, and
the identity a few instructions later was a *kernel thread*, not idle. A
momentary SMP lock collision was being converted into a permanent "this context
may not sleep" for the caller.
claim-lint:ok: 10 refusal lines, 8 legible, 5 with the counter tail, 4 of 4
`RCA786_W2` lines -- the three greps in `serials/r7/aba/README.md`

### Fix

The `None` arm returns `false` and counts the outcome in a new
`IDLE_IDENTITY_UNREADABLE` (not gate-failing, and deliberately separate from
`IDLE_SLEEP_REFUSED`, which means "the idle task was observed reaching for a
blocking primitive" — an unreadable identity is not that observation).
claim-lint:ok: kernel/src/task/idle_sleep.rs, #786

Being permissive there does not let the idle identity block. The refusal that
enforces the rule is `Scheduler::refuse_idle_block`, which reads the identity
exactly, from inside the scheduler lock, and is called by all 6 blocking
primitives that publish the caller's blocked state — including
`block_current_for_io_publish`, the one behind the waitqueue path that
`idle_identity_must_not_sleep` also guards. The lock-free predicate is an
advisory fast path; the authoritative check cannot be bypassed by it.
claim-lint:ok: 6 of 6 `self.refuse_idle_block()` call sites, pinned by
`an_unreadable_identity_is_not_a_refusal`

### Ratchet

`an_unreadable_identity_is_not_a_refusal` asserts the `None` arm neither calls
`refuse_idle_identity` nor evaluates to `true`, that it counts into
`IDLE_IDENTITY_UNREADABLE`, and that the in-lock refusal still reads the identity
exactly and is still called at 6 or more sites.
claim-lint:ok: tests/aarch64_testing_profile_structure.rs, 16 of 16 passing

## 3. The boot-continuation strand — found by this round, not by #786

With the abort and the wedge gone, boots ran long enough to reach the scheduler
strand census, which stranded `kboot` in 3 of the first 3:

```
[SCHED_STRAND_FIRST:tid=11:shape=running:priv=kernel:state=1:dwell_ms=2027]
[SCHED_STRAND_ORACLE:aarch64:...:stranded=1:running_shape=1:...:worst_dwell_ms=13488:...]
```

claim-lint:ok: 3 of 3 boots, `serials/r7/strand/` (`dwell_ms` 2025, 2027, 2043;
`stranded=1` in all three). Round 7 wrote "2 of 3" from the gate's
first-reported failure class, and boot 1 was reported under
`census_widen_oracle` instead; that stdout was not preserved, so the number is
restated to what the three committed serials show.
tid 11 is `kboot`, the boot continuation kernel thread this branch introduced
(`ead21609`). `launch_init_from_elf` called `spawn_as_current(init_thread)`,
whose `add_thread_as_current` overwrites `cpu_state[cpu].current_thread` and
never touches the identity it displaces. `kboot` therefore stayed `Running`
forever, on no CPU, in no queue, in no handoff slot — which is exactly the strand
census's own definition of a strand — and, being a kernel thread that is never
`Terminated`, its kernel stack could never be reclaimed either.

The same stale identity is what made the abort report against the wrong thread:
both preserved abort serials print `[INSTRUCTION_ABORT] deferred_tid=11
queued=1`, a fault-SIGSEGV queued against a kernel thread.
claim-lint:ok: 3 of 3 boots, `serials/r7/strand/`

### Fix

`spawn_as_current_retiring_outgoing` installs the incoming thread and retires the
displaced one in a single scheduler critical section, skipping the idle identity
(on the boot paths where the displaced identity IS this CPU's idle task, that
task is still the CPU's fallback). `kthread::publish_current_kthread_exit`
performs the rest of the kthread ending — exit code, `exited` flag, registry
removal — which `kthread_exit` cannot do here because it halts waiting to be
scheduled away and this identity never comes back through the scheduler.
claim-lint:ok: kernel/src/task/scheduler.rs `spawn_as_current_retiring_outgoing`,
kernel/src/task/kthread.rs `publish_current_kthread_exit`

Retiring while still executing on the retired thread's stack is safe by the
existing fence, not by luck: `reclaim_terminated_threads` waits on
`retirement_grace_target`, which requires a second scheduler entry on every
online CPU *including this one* — and this CPU is inside the handoff with
interrupts masked until the ERET, so the fence cannot elapse before the stack is
dead.
claim-lint:ok: kernel/src/task/scheduler.rs `retirement_grace_target` /
`note_scheduling_epoch`

## 4. `census_widen_oracle` — a field that could not see the CPU it was about

`[CENSUS_WIDEN_ORACLE:...:queued_nondispatch_ms=1721:cpu_silence_ms=0:...:FAIL]`.
The oracle requires `cpu_silence_ms >= 1`. It arms `arm_target=4` — a CPU past
`online_cpu_count` (4 online: 0..3) — and the census's scheduler-silence scan
iterated `0..online_cpu_count`, so the silence of CPU 4 could never be sampled.
The field reported the four *busy* CPUs instead, which is 0 whenever all four
happen to enter the scheduler inside one tick. Observed range across this
session's serials: 0, 1, 2, 2, 2, 3, 4, 6, 7 ms — 1 of those 9 readings is the 0
that fails the oracle, a coin flip rather than a measurement.
claim-lint:ok: 1 of 3 boots failed this way, 9 readings enumerated here

The scan now covers every CPU slot and skips only a CPU that is both past the
online count and holding no queued work. The oracle's own reading went from a
0–7 ms race to `cpu_silence_ms` equal to `queued_nondispatch_ms` --
`1142` and `1112` in the two committed post-fix boots
(`serials/r7/strand/post-census-fix-silence-1142.txt` and
`-1112.txt`) -- and `worst_silence_cpu=4` now names the CPU the widening is
about. Round 7 wrote `1192` for this reading; that value appears in no preserved
serial from the round, so it is restated to the two that do. This code is on
`main` too, so the repair is not branch-local.
claim-lint:ok: 2 of 2 committed post-fix serials, `serials/r7/strand/README.md`
claim-lint:ok: serials/r7/testing-profile-boot1-serial.txt and
serials/r7/strict-3boots-run-log.txt, 3 of 3

`tests/strand_handoff_structure.rs` had pinned the old bound
(`"CPU-silence sampling must iterate exactly the derived online CPU count"`).
That pin *was* the defect, so it is retargeted, not removed: the census must
contain zero `for cpu in 0..online_cpu_count`, exactly one silence scan, and the
scan must skip only an offline CPU with an empty queue.
claim-lint:ok: tests/strand_handoff_structure.rs, 38 of 38 passing
