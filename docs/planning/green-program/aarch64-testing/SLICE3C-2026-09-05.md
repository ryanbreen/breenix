## 4. The ratchet and its mutation

`tests/loopback_pump_structure.rs` gains 2 validators and 6 tests. Both
validators are censuses; neither pins a line, and neither carries a list of
today's names as data.

**`validate_thread_placement_honours_the_cpu_pin`** derives its subject: a
scheduler function that resolves a ready-queue target through
`least_loaded_cpu()` is a placement function. That is 1 of 1 today
(`add_thread_inner`), located by walking `function_spans`, not by asking for
that name. Each placement function must

1. read `cpu_affinity` **before** the first `least_loaded_cpu` reference,
2. resolve the pin with `.map(|pin| pin.cpu)`,
3. bound it with `.filter(|cpu| *cpu < self.online_cpu_count())`, and
4. fall through with `.unwrap_or_else(|| self.least_loaded_cpu())`.

An empty census is itself an error, so deleting the placement path does not
silence the rule.

**`validate_cpu_pin_records_its_reason`** censuses the constructors inside
`impl CpuPin`: each must set `per_cpu_worker` explicitly, both kinds must be
constructible, and `Thread::cpu_affinity` must carry the pin rather than a bare
CPU index.

## 9. What is not claimed

* **No defect is fixed here.** 0 of the 5 issues this slice sits among -- #562,
  #761, #786, #789, #763 -- is moved by this branch, and it should not be cited
  as moving one.
* **The pin is not exercised.** 0 threads carry a pin at runtime in the 3
  profiles this round built, so the gates evidence only that the scaffolding is
  inert; whether pinned placement works is unmeasured here. The first evidence
  of that is slice 3f, where a `ksoftirqd/N` actually holds one.
* **The wake filter is not present.** A pinned thread woken through
  `find_target_cpu_for_wakeup` would still take the unfiltered path `main` has
  today; that arm does not exist yet, which is precisely why 3d is a separate
  slice. This branch should not be read as having closed that gap.
* **`CpuPin::hold_pen` has no caller and no test of its behaviour.** The ratchet
  requires it to exist and to name its kind. That is a structural claim about
  the type, not a claim that a hold pen has ever held anything.
* **Boot counts are 3 and 3 and 1 and 1.** They are sized to detect a
  regression this branch plausibly causes (it changes 1 placement expression),
  not to characterise an intermittent class. A 1-in-8 shape would be missed
  about 2 times in 3 by 3 boots, so the rare-class question is out of this
  round's scope and no reading of these 8 boots settles it.
* **The x86 legs are 1 boot each.** They exist because the two-field literal
  hazard is x86-testing-only; they are not a production-stability measurement.
