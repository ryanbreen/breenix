Slice 1 (`TTBR0-SHADOW-SLICE-2026-09-04.md`, PR #795) routed 9 of the 10
aarch64 process-root install decision sites through
`kernel/src/arch_impl/aarch64/ttbr0.rs::adopt_process_ttbr0`. It left the tenth
alone and said so: `kernel/src/syscall/time.rs::ensure_current_address_space`
lives in a file CLAUDE.md lists as Tier-1 prohibited, and slice 1 had no
approval to touch it. Three of its censuses were built around that gap — they

This slice closes the site and retires the exemption. Base: `origin/main`
`350d9fb5`. Branch: `fix/786-slice1b-time-rs-ttbr0`.

### 2b. The ASID that publication changed, and the repair (S1B-01)

Publishing the corridor word is what the routing was for, and it is also what
made the first cut of this slice a behaviour change nobody had disclosed. The
root this site computes is
`page_table.level_4_frame().start_address().as_u64()` --- a physical address
with an empty ASID field. Before the routing, that untagged value went into the
register with a raw `msr` and the shadows were left alone, so
`.Lrestore_saved_ttbr` reinstalled whatever the last dispatch had published,
and the dispatch path tags: `set_next_ttbr0_for_thread` in
`kernel/src/arch_impl/aarch64/context_switch.rs` computes
`ttbr0 | (1u64 << 48)` with the comment that ASID 0 is what the boot identity
map's TLB entries carry. After the routing, the untagged value became the
shadow, and `syscall_entry.S` installs that word verbatim --- so the return to
EL0 ran on ASID 0.
claim-lint:ok: the corridor arm is `.Lrestore_saved_ttbr` in
`kernel/src/arch_impl/aarch64/syscall_entry.S`, which loads offset 80 and writes
the register with no masking; the dispatch tag is
`kernel/src/arch_impl/aarch64/context_switch.rs`.

The repair is one rebinding inside `adopt_process_ttbr0`, not a fix at this call
site: `process_root_ttbr0` masks the ASID field off and sets the userspace ASID,
and the discipline installs and publishes that normalised value. Every routed
site inherits it.
claim-lint:ok: of the 10 routed process-root install decision sites, 8 hand over
a bare `level_4_frame().start_address().as_u64()`, 1
(`launch_init_from_elf` in `kernel/src/main_aarch64.rs`) already tags ASID 1,
and 1 (`switch_to_process_page_table` in `kernel/src/memory/process_memory.rs`)
passes back whatever ASID the register held; all 10 now install the same
normalised value.

Two things this does NOT say. It does not say `main` was correct: on `main` the
raw `msr` put an untagged root in the register for the rest of the kernel-side
window, and any user-memory access in that window --- the EINTR arm's write of
the remaining time, for instance --- used ASID 0 until the corridor healed the
register on the way out. And it does not say a fault was observed either way: no
boot in this round or the last carries a wrong-ASID observation, because no boot
was instrumented to take one.
claim-lint:ok: 0 of 2 boots at this head read TTBR0's ASID field at a return to
EL0; the two are
`docs/planning/green-program/aarch64-testing/serials/slice1b/r157/prove/strict-1.txt`
and
`docs/planning/green-program/aarch64-testing/serials/slice1b/r157/prove/prod-1.txt`.

The dispatch tag and the discipline's constant are now pinned against each
other by `the_discipline_publishes_the_dispatch_asid`, so changing the ASID on
one side of the kernel and not the other fails a check rather than silently
splitting the two return paths.

### 4b. The blocking-resume restore, and its guard (S1B-06)

`ensure_current_address_space` is one of five byte-identical copies of the same
helper --- `kernel/src/syscall/time.rs`, `wait.rs`, `futex.rs`, `graphics.rs`,
and `poll_ensure_address_space` in `handlers.rs` --- and none of them had a
root-equality guard. `adopt_process_ttbr0` installs unconditionally, so a
`nanosleep` whose root never moved still issued `tlbi vmalle1is`, an
inner-shareable broadcast, on the way out. The two sibling install sites in the
kernel both guard: `switch_ttbr0_if_needed` reads `ttbr0_el1` and installs only
`if current_ttbr0 != next_ttbr0`, and `switch_to_process_page_table` compares
frames before doing anything.
claim-lint:ok: 5 of 5 copies are the census printed by
`every_blocking_resume_restore_uses_the_guarded_helper -- --nocapture`, recorded
in
`docs/planning/green-program/aarch64-testing/serials/slice1b/r157/anti-vacuity/00-branch-green.txt`.

`ttbr0::restore_process_ttbr0` is the disposition those five sites now use. It
normalises the ASID, publishes BOTH corridor words unconditionally, and skips
only the register write and its invalidation, and only when TTBR0 already holds
exactly that root under that ASID. The asymmetry is the point: the register can
be right while `next_cr3` still holds a pending redirect the corridor would
apply first, which is #786 itself, so the words are written on both arms.

Why the skip is offered here and not to the adopt path, stated as the argument
it is rather than as a measurement: a root is reclaimed only once no CPU shadow
names it (`is_ttbr0_root_live_in_mask`), and every transition off a root runs a
broadcast `tlbi vmalle1is`, so for this CPU's register to still hold the
resuming thread's root this CPU installed it and installed nothing since --- its
shadow still names it, and the frame cannot have been reclaimed and re-issued
underneath. That covers root REUSE. It is NOT an argument that a concurrent
unmap under the same root is covered: TLB maintenance for a mapping change
belongs to the code that changes the mapping, and if the resume path's
incidental invalidation were what made `munmap` correct then every non-blocking
syscall return would already be broken. The corridor's own unconditional
invalidation on each syscall return is untouched by this guard, so what the
change removes is one of two broadcasts on the blocking path, not the only one.
claim-lint:ok: the corridor's unconditional invalidation is the `tlbi vmalle1is`
in both arms of the TTBR0 block in
`kernel/src/arch_impl/aarch64/syscall_entry.S`.

`sys_exec_aarch64` reaches two of the census's three conjuncts and is
deliberately not a member: the root it installs comes from its exec receipt, a
new address space it chose, so its install stays an unconditional adopt. The
census asserts its exclusion rather than relying on the reached list happening
to omit it.

The mechanism-primitive exemption is untouched and still documented where it
was: a function whose installed value traces back to its own parameter installs
what a caller decided, so the caller owns the shadows. Two functions hold it
(`paging.rs::write_root`, `memory/arch_stub.rs::Cr3::write`), and
`every_aarch64_caller_of_a_mechanism_primitive_settles_the_shadows` is what
holds their callers to the discipline.
