## 1. The defect

`collect_strand_census` (`kernel/src/task/scheduler.rs`) computes
`worst_cpu_scheduler_silence_ms` — the `cpu_silence_ms` field of
`[CENSUS_WIDEN_ORACLE:...]` — as a running maximum of scheduler silence over a
range of CPU slots. Before this change that range was `0..online_cpu_count`.

The armed CPU comes from `stale_peer_cpu_for_test`, and that function scans
`0..MAX_CPUS`:

```rust
pub fn stale_peer_cpu_for_test() -> Option<usize> {
    with_scheduler(|scheduler| {
        let current_cpu = Scheduler::current_cpu_id();
        (0..MAX_CPUS).find(|&cpu| cpu != current_cpu && scheduler.cpu_dispatch_stale(cpu))
    })
    .flatten()
}
```

`MAX_CPUS` is 8 on aarch64 (`kernel/src/task/scheduler.rs`), and
`online_cpu_count()` clamps `cpus_online()` into `1..=MAX_CPUS`. So the armed CPU
can be at or past `online_cpu_count`, and when it is, the old bound could not
sample it.

The sibling field is what makes the exclusion incoherent rather than merely
narrow. `queued_on_nondispatching_cpu` counts a thread queued on a CPU that is
`cpu >= online_cpu_count || cpu_dispatch_stale(cpu)` — so the census reports a
thread stuck on a CPU past the online count in one field while refusing by
construction to measure that CPU's silence in the next.
<!-- claim-lint:ok: both field computations are 1 function apart in
kernel/src/task/scheduler.rs, `fn collect_strand_census` -->

**What the field is, and what no gate checks (R6).** `cpu_silence_ms` is a
maximum over the slots the scan considered. It is not a reading taken from
`arm_target`, and the emitted line does not say which slot produced it: the
census does compute the owning index as `worst_silence_cpu`, and
`[SCHED_STRAND_ORACLE:...]` publishes it, but
`[CENSUS_WIDEN_ORACLE:...]` does not. The only runtime requirement any gate
places on the field is `cpu_silence_ms=[1-9][0-9]*`
(`docker/qemu/run-aarch64-boot-test-strict.sh:43`,
`docker/qemu/run-aarch64-service-sequence-gate.sh:106`), which a pre-fix kernel
satisfies too — measured, 5 of 5 boots, section 5. So this change is enforced
structurally, by the ratchet leg in section 6, and not by any boot gate. #804
carries the follow-up that would let a gate discriminate the two scans, and
records why that assertion has nothing to discriminate until slice 3g.

## 3. The port

Two hunks, ported per hunk. `git diff origin/main --numstat` for the code half is
`15 1` in `kernel/src/task/scheduler.rs` and `77 6` in
`tests/strand_handoff_structure.rs`. The kernel half matches `96ef7fc3`'s own
stat line; the test half is larger than `96ef7fc3` because round 2 added the
pins R1 and R2 asked for.

**Kernel.** The scan becomes `for cpu in 0..MAX_CPUS` with one skip:

```rust
for cpu in 0..MAX_CPUS {
    let holds_work = !scheduler.per_cpu_queues[cpu].is_empty();
    if cpu >= online_cpu_count && !holds_work {
        continue;
    }
    let silence_ms = now_ticks.wrapping_sub(scheduler.cpu_state[cpu].last_schedule_ticks);
```

A CPU past the online count with an empty queue is silence with no work behind
it, and is skipped. A CPU past the online count with threads queued on it is the
exact shape `queued_on_nondispatching_cpu` reports, and is now measured.

The constraints the round was held to, and what the hunk does about each: no new
lock (the scan runs inside the `with_scheduler` closure that already held the
scheduler lock; the added read is `scheduler.per_cpu_queues[cpu].is_empty()`, a
field read on the same borrow); no allocation (`is_empty()` on a `VecDeque`);
no logging (the hunk adds no macro call of any kind); lock order unchanged (no
second lock is taken). The loop bound moves from `online_cpu_count` (at most 8)
to `MAX_CPUS` (8), so the worst case is unchanged and the added per-iteration
work is one `is_empty()`.

**Test.** The old pin was
`"CPU-silence sampling must iterate exactly the derived online CPU count"` — the
pin asserted the defect. It is retargeted, not deleted. The rules now are:

* the census contains no `for cpu in 0..online_cpu_count`;
* the census keeps exactly 1 occurrence of
  `worst_cpu_scheduler_silence_ms = silence_ms`, i.e. 1 silence scan;
* the silence scan is the first all-CPU scan and completes before
  `for thread in scheduler.threads.iter()` reads its result;
* the considered CPU contributes `cpu_state[cpu].last_schedule_ticks`, once;
* the skip decision reads
  `let holds_work = !scheduler.per_cpu_queues[cpu].is_empty();`, once;
* the skip arm names both `per_cpu_queues[cpu].is_empty()` and
  `cpu >= online_cpu_count`, once each;
* the block guarded by `if cpu >= online_cpu_count && !holds_work` has
  `continue;` as its code content, and the scan carries exactly 1 `continue`.

Round 2 changed two things about how those rules are checked, both of them
findings R1 and R2:

* the slice bounds and the needles are matched with `code_occurrences`, not raw
  `str::contains`. `function_body` and `braced_body` return slices of the raw
  file with comments intact, so a raw `contains` let a comment naming the two
  needles stand in for the code that used to be there;
* the last two rules are new. Naming the conjuncts cannot pin what the guard
  DOES, so the guarded block is extracted with `braced_block_after` and its code
  content compared against `continue;`.
