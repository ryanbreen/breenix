## 1. The defect

`collect_strand_census` (`kernel/src/task/scheduler.rs`) computes
`worst_cpu_scheduler_silence_ms` — the `cpu_silence_ms` field of
`[CENSUS_WIDEN_ORACLE:...]` — by taking the maximum scheduler silence over a
range of CPUs. Before this change that range was `0..online_cpu_count`.

The field exists to report the CPU the widening oracle arms. That CPU comes from
`stale_peer_cpu_for_test`, and that function scans `0..MAX_CPUS`:

```rust
pub fn stale_peer_cpu_for_test() -> Option<usize> {
    with_scheduler(|scheduler| {
        let current_cpu = Scheduler::current_cpu_id();
        (0..MAX_CPUS).find(|&cpu| cpu != current_cpu && scheduler.cpu_dispatch_stale(cpu))
    })
    .flatten()
}
```

`MAX_CPUS` is 8 (`kernel/src/arch_impl/aarch64/constants.rs`), and
`online_cpu_count()` clamps `cpus_online()` into `1..=MAX_CPUS`. So the armed CPU
can be at or past `online_cpu_count`, and when it is, the old bound could not
sample it: the field then reported the busy online CPUs, whose silence is 0
whenever each of them enters the scheduler inside one tick.

The sibling field is what makes the exclusion incoherent rather than merely
narrow. `queued_on_nondispatching_cpu` counts a thread queued on a CPU that is
`cpu >= online_cpu_count || cpu_dispatch_stale(cpu)` — so the census reports a
thread stuck on a CPU past the online count in one field while refusing by
construction to measure that CPU's silence in the next.

kernel/src/task/scheduler.rs, `fn collect_strand_census` -->

`docker/qemu/run-aarch64-boot-test-strict.sh:43` requires
`cpu_silence_ms=[1-9][0-9]*`, so a 0 reading fails the kernel-merge gate.

## 2. What is NOT claimed

**This is a by-construction repair of a latent defect on `main`, not the repair
of an observed red on `main`.** The plan's section 3a describes the defect as
live; this round measured that premise and it does not hold on `main` today.

On `main`'s aarch64 kernel the strict-gate boot brings 4 CPUs online (PSCI
`CPU_ON` fails for CPU 4) and the boot context stays on CPU 0, so CPU 0 is the
dispatch-stale peer `stale_peer_cpu_for_test` returns. `arm_target=0` is inside
`0..online_cpu_count`, so the old bound did sample the armed CPU. The pre-fix
baseline in section 5 reads `cpu_silence_ms` = 1419, 1337, 1657, 1894, 1632 —
5 of 5 boots at or above 1, 5 of 5 equal to `queued_nondispatch_ms`.

The intermittent `cpu_silence_ms=0` class the plan quotes (readings 0, 1, 2, 2,
2, 3, 4, 6, 7) was recorded on the parked branch, whose boot-sequence relocation
into a `kboot` kernel thread moves the boot context off CPU 0 and makes the
oracle arm CPU 4 of 4 online. That relocation is slice 3g. So the ordering the
plan gives is right for a different reason than the plan gives: 3a lands first
because 3g is what makes this shape reachable, not because 3a stops a red that
is firing on `main` now.

Two further things this round does not claim:

* It does not claim the change alters any reading on today's `main`. The fixed
  and baseline arms in section 5 are indistinguishable at this sample size,
  which is the expected result: in 10 of 10 boots across both arms the serial
  reads `[smp] 4 CPUs online`, so slots 4 through 7 hold no queued work and the
  new skip arm removes them from the scan exactly as the old bound did.

* It does not claim the aarch64 `--features testing` profile was booted. Only

## 3. The port

Two hunks, ported per hunk. `git diff --stat origin/main..HEAD` for the code
half is `16 +1` in `kernel/src/task/scheduler.rs` and `40 +5` in
`tests/strand_handoff_structure.rs`, matching `96ef7fc3`'s own stat line.

**Kernel.** The scan becomes `for cpu in 0..MAX_CPUS` with one skip:

```rust
for cpu in 0..MAX_CPUS {
    let holds_work = !scheduler.per_cpu_queues[cpu].is_empty();
    if cpu >= online_cpu_count && !holds_work {
        continue;
    }
    let silence_ms = now_ticks.wrapping_sub(scheduler.cpu_state[cpu].last_schedule_ticks);
```

A CPU past the online count with an empty queue is silence with no work behind
it, and is skipped. A CPU past the online count with threads queued on it is the
exact shape `queued_on_nondispatching_cpu` reports, and is now measured.

The constraints the round was held to, and what the hunk does about each: no new
lock (the scan runs inside the `with_scheduler` closure that already held the
scheduler lock; the added read is `scheduler.per_cpu_queues[cpu].is_empty()`, a
field read on the same borrow); no allocation (`is_empty()` on a `VecDeque`);
no logging (the hunk adds no macro call of any kind); lock order unchanged (no
second lock is taken). The loop bound moves from `online_cpu_count` (at most 8)
to `MAX_CPUS` (8), so the worst case is unchanged and the added per-iteration
work is one `is_empty()`.

**Test.** The old pin was
`"CPU-silence sampling must iterate exactly the derived online CPU count"` — the
pin asserted the defect. It is retargeted, not deleted. The rules now are:

* the census contains no `for cpu in 0..online_cpu_count`;
* the census keeps exactly one occurrence of
  `worst_cpu_scheduler_silence_ms = silence_ms`, i.e. one silence scan;
* the silence scan is the first all-CPU scan and completes before
  `for thread in scheduler.threads.iter()` reads its result;
* each considered CPU contributes `cpu_state[cpu].last_schedule_ticks`;
* the skip arm names both `per_cpu_queues[cpu].is_empty()` and
  `cpu >= online_cpu_count`, so only a CPU that is both past the online count
  and holding no queued work may be skipped.

## 6. Anti-vacuity

### (a) The structural leg, and its two mutations

The leg is `strand_census_progress_axes_and_ordering_cannot_shrink` in
`tests/strand_handoff_structure.rs`. It reads
`kernel/src/task/scheduler.rs` from disk, so a mutation is applied to the real
source, the leg is run, and the source is restored. Each mutation was applied
singly; the unmutated source was confirmed green before and after each.

Run as
`scripts/run-structure-tests.sh strand_handoff_structure strand_census_progress_axes`.

| leg | mutation | exit | assertion that fired |
|---|---|---|---|
| unmutated | — | 0 | `test result: ok. 1 passed` |
| 1 | replace the scan header and skip arm with `for cpu in 0..online_cpu_count` (the pre-fix source) | 101 | `CPU-silence sampling must not stop at the online prefix` (`tests/strand_handoff_structure.rs:2536`) |
| unmutated | reverted | 0 | `test result: ok. 1 passed` |
| 2 | drop the `cpu >= online_cpu_count` conjunct, leaving `if !holds_work { continue; }` | 101 | `only a CPU that is both past the online count and holding no queued work may be skipped by the silence scan` (`tests/strand_handoff_structure.rs:2567`) |
| unmutated | reverted | 0 | `test result: ok. 1 passed` |

Mutation 1 is the one the brief names: re-introducing the old busy-CPU iteration
reddens the leg. Mutation 2 exists because mutation 1 alone would pass a scan
that skipped each CPU with an empty queue, online or not — which would restore a
different blindness. Together they pin the scan to "each slot, minus the
offline-and-empty ones".

### (b) The boots

Section 5. The strict arm reads `cpu_silence_ms` at or above 1 in 5 of 5 boots
and the gate passes 5 of 5. The baseline arm is the honest counterweight: it
also reads at or above 1 in 5 of 5, which is why section 2 states the defect is
latent rather than live on `main`.
