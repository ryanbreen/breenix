## Implementation

The reader's `eof_wait_ms > EOF_WAKE_BOUND_MS` arm now calls the existing
`dispatch_gap_probe(DISPATCH_PROBE_MS)` before exit 15. It prints one line:

```text
LOOPBACK_WAKE_TEST: reader_eof_dispatch_probe max_gap_ms={} samples={} window_ms={} verdict=eof_timeout
```

The field order follows the data arm: largest consecutive clock-sample gap,
sample count, and requested sampling window (2000 ms). The verdict records the
already-decided EOF timeout. The existing EOF bound and exit code remain intact.
Both timeout arms use the same probe; successful reads do not run it.

This gives an x86 EOF timeout its own subsequent dispatch-gap measurement.
A large gap records a pause between clock samples while the reader is runnable;
it does not retroactively measure scheduling during the preceding blocked read
or establish the cause of that earlier delay. A sample count of 0 retains the
existing probe's clock-failure meaning. No kernel, interrupt, or context-switch
source is changed.

## Structural ratchet

`validate_loopback_eof_timeout_measures_dispatch` locates the reader's EOF
bound arm and checks the probe assignment, measured output arguments, verdict
text, and ordering before exit 15. Its delete-mutation removes only the EOF
probe assignment, leaving the data arm's call intact.

The local suite passed 137/137 tests (`serials/586-pr4/structure-loopback.txt`).
Temporarily deleting the EOF call from the actual source made the focused test
exit 101; the source was restored and the suite rerun
(`serials/586-pr4/delete-mutation.txt`). This is a host structural mutation,
not a boot with a forced EOF timeout.
