## The measurement

Three quantities bracket the budget window, each a read of state that already
exists:

* the TICK clock, `crate::time::get_monotonic_time()`, which is
  `TICKS * MS_PER_TICK` and advances only when this guest takes a timer
  interrupt;
* the COUNTER clock, `monotonic_now_ns()`, which reaches `CNTVCT_EL0` on
  aarch64 and the TSC on x86_64 and advances with the host whether or not this
  guest is scheduled;
* `CTX_SWITCH_TOTAL.aggregate()`, the context switches the guest performed.

A window in which the counter ran far ahead of the ticks, or in which the
guest performed few switches, is the guest's own measurement of time it did
not get. That is the discriminator PLAN-586 Q3 asks for.

The marker grammar, one line per invocation:

```
[LOOPBACK_WAKE_BUDGET:arch=A:test=T:budget_ms=N:elapsed_tick_ms=N:elapsed_ctr_ms=N:ctx_delta=N:extensions=N:reader_state=S:queued_cpu=C:queued_idx=I:idle_cpus=0xB:woke_ms=N:verdict=V]
```

`verdict` names the BUDGET's outcome, not the test's: `ok` when the reader ran
inside the budget, `wake` when the reader never left Blocked, `starved` when
the reader left Blocked and the window bought the guest no measurable
execution, `dispatch` when the reader left Blocked, the guest was measurably
executing, and the reader still had not run.
claim-lint:ok: the 4 tokens are the 4 arms of the verdict selector at
`kernel/src/test_framework/registry.rs:3128-3137`, 4 of 4; see #586.

## The rule that sets the two constants

One rule sets both, so neither is a separate act of judgement:

**Each constant is placed a factor of two clear of the worst value the
measured population showed, rounded outward to a whole number.**

Applied:

* `LOOPBACK_WAKE_CTX_FLOOR`. The population's smallest `ctx_delta` is 60
  (boot 5, `under_load`). Half of 60 is 30, so the floor is **30**. Every one
  of the 20 green lines carries at least twice the floor.
  claim-lint:ok: 20 of 20 lines in the table above carry ctx_delta of 60 or
  more; see #586.
* `LOOPBACK_WAKE_DIVERGENCE_NUM` / `_DEN`. The population's largest
  counter/tick ratio is 1.85 (boot 5, `under_load`, 209 over 113). Twice 1.85
  is 3.70, rounded outward to **4**, so the ceiling is 4/1.
  claim-lint:ok: 20 of 20 ratios in the table above are 1.85 or less; see
  #586.

The guest is credited with having executed across the window when both hold:
`ctx_delta` is at least the floor, and `elapsed_ctr_ms * DEN` is at most
`elapsed_tick_ms * NUM`. A fully starved window -- one in which the tick clock
did not advance at all -- fails the second test whatever the counter read,
because the right-hand side is then zero.
claim-lint:ok: the 2 conjuncts are read off the `guest_executed` binding at
`kernel/src/test_framework/registry.rs:3121-3123`, 2 of 2; the zero case is
arithmetic on that expression, not an observation -- 0 of 20 lines in the
table exercised it. See #586.

**What the constants are, and are not.** The ratio they bound is a property of
this host under this gate's own load, not of the kernel. A different host, or
this host under different concurrent load, would want the population
re-measured before either number is read as a threshold. That caveat is in the
constants' own doc comments, not only here.

**Nothing in this round is gated on either constant.** Both feed only the
`starved` / `dispatch` split, which is reached only when `wake_ms` is 0. All
20 lines in the population read `verdict=ok` by the `wake_ms` test alone, so
no boot in the proof exercised either number. They are pre-registered for
PR 3, which is the round that spends them.
claim-lint:ok: 20 of 20 lines in the table above read verdict=ok; see #586.

## Two disclosures about how the evidence was produced

**1. The booted kernel and the committed kernel differ in two literals.** The
strict 10 was run before the constants were chosen, because choosing them from
a measured population is what the run is for. The kernel that produced the 20
lines carried placeholder values -- `LOOPBACK_WAKE_CTX_FLOOR` of 1 and a
divergence ceiling of 2/1 -- and the committed tree carries 30 and 4/1. The
difference between the booted source and the committed source is those two
literals, their doc comments, and the `claim-lint:ok` annotations added
afterwards. No printed field of the marker reads either constant, and the
verdict on all 20 lines was decided by the `wake_ms` test above them, so no
line in the table would read differently had the final values been booted. The
committed tree was rebuilt clean and re-validated against the whole structure
suite; it was not re-booted.

the fail-path mutation leg by hand, this round restored the mutated file with
`git checkout --`, which discarded the uncommitted PR-2 edits to
`kernel/src/test_framework/registry.rs` along with the mutation. The file was
reconstructed from the diff captured earlier in the same session, rebuilt with
zero warnings, and re-validated:
claim-lint:ok: the rebuild emitted 0 warnings and 0 errors from the kernel

## Deviations from PLAN-586 Q3

* **The `cpu_silence_ms` and `silence_cpu` fields are not in the marker.**
  Q3's grammar sources them from `collect_strand_census`, which wants two
  `STRAND_CENSUS_CAPACITY` arrays on the caller's stack; the caller here is a
  kthread. The two fields are deferred rather than sampled, and the marker is
  13 fields rather than 15. The stated reason is in the emitter's own comment.
* **The passing verdict token is `ok`, not `dispatched`.** The round brief
  fixes the four values as `wake` / `starved` / `dispatch` / `ok`, and `ok`
  also reads better against a line that is printed on failing paths for
  reasons other than the budget.
* **`idle_cpus` is a union of two point samples**, one before the sleep and
  one at the deadline -- not a continuous observation of the window. It says a
  CPU was idle at one of those two instants, never that one was idle
  throughout. Stated at the sampling site.
  claim-lint:ok: 2 of 2 reads of `idle_cpu_bitmap` in the test are point
  samples; see #586.
* **`idle_cpus` is informative on aarch64 and constantly 0 on x86_64**, because
  `is_cpu_idle_raw` returns a constant `false` on x86_64. PLAN-586 Q5 records
  the same limitation. The field's own doc says so.
