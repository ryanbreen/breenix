# Filesystem — fault-injection evidence, 2026-08-28

Green program, arc 2. Branch `feat/green-fs`, based on `main` @ 70c33b00.

This document is the durable record for the ext2/VFS fault-injection leg: what
it injects, what each shape is required to do, what was measured on each
architecture, and the mutations that prove the measurements are not vacuous.
Every serial referenced here is in `serials/` beside this file.

---

## 1. What was missing

The Filesystem row entered this arc with **zero open defects on aarch64** and one
instrument issue on x86 (#564). ext2 is load-bearing on every boot of both
architectures — it is where the userspace binaries come from — so the row's
functional coverage is exercised continuously. What no gate in the tree covered
was the other half: **what the filesystem does when the block device misbehaves.**
A boot-completion gate structurally cannot see that failure class, because a
device that answers correctly never produces it.

## 2. What was built

`kernel/src/fs/fault_inject.rs` (feature `fs_fault_inject`, test profile only),
called from both architecture mains immediately after `init_root_fs()`. It builds
its own `Ext2Fs` over its own block-device handle — it never touches the mounted
root filesystem — and drives the ext2 read path through three block-layer fault
shapes.

`docker/qemu/run-fs-fault-gate.sh` builds and boots it on either architecture and
scores it. It carries the #668 ERR-trap discipline: a red gate names the failing
assertion, the file and line, and dumps serial, instead of dying silently under
`set -e`. Crash checks are ordered before completion checks, so a panic is
reported as a panic rather than as "the leg never finished" — that ordering was
derived from a measured mutation run, see §5.

### The contract, arm by arm

| arm | what the device does | what the filesystem must do |
|---|---|---|
| `baseline_mount` | nothing | mount succeeds — the floor under every assertion below |
| `baseline_read` | nothing | the root directory reads, 1024 bytes |
| `short_read` | returns `Ok` for the superblock sector having delivered only its first 16 bytes, leaving the caller's tail untouched | REFUSE the mount. The ext2 magic lives at offset 56 and is never written, so a filesystem built from this block would be a phantom |
| `eio_data_block` | returns `Err(IoError)` for the root directory's own first data block, named by the inode rather than guessed | propagate the error to the caller |
| `eio_recovery` | stops failing | the identical read succeeds again, same byte count. This is what separates "the error propagated" from "the error wedged the filesystem" |
| `corrupt_inode` arm=size | returns `Ok` with the inode record rewritten to `i_size = 0xFFFFFFF0` | `Err`, and no panic |
| `corrupt_inode` arm=blocks | returns `Ok` with the inode record's 15 block pointers rewritten to `0xDEADBEEF` | `Err` |
| `liveness` | nothing | the shadow filesystem still reads AND the untouched mounted root filesystem still reads |

And, common to all of them: **no panic, no hang, kernel still live afterwards.**
The gate proves the last clause by requiring the boot to reach its normal
completion markers *after* the leg — on aarch64 the heartbeat/exec-smoke markers,
on x86 `USERSPACE TEST COMPLETE`. The leg's own final line is not accepted as
evidence that the kernel is still usable.

### Two design points that carry weight

* The injecting wrapper deliberately does **not** override `read_blocks`. The
  trait's default per-block loop therefore runs and every sector passes through
  the injection decision; a multi-sector fast path would let a fault window be
  stepped over silently.
* Target sectors are computed from the filesystem's own metadata — the root
  inode's `i_block[0]` for the data block, and the inode-table arithmetic
  mirrored from `Ext2Inode::read_from` for the inode record. Guessed offsets
  would make "EIO on a data block" a claim rather than a fact.

### Why not pre-corrupted fixture images

Fixtures cannot express two of the three shapes. `short_read` and
`eio_data_block` are **device behaviours**, not disk contents: no image can make
a read return `Ok` with fewer bytes than requested, or return `EIO`. Only
`corrupt_inode` has an image equivalent. Splitting one leg across two mechanisms
to serve one arm buys nothing, and the seam route is what makes the fault window
addressable from the filesystem's own metadata.

## 4. Anti-vacuity — each shape disarmed singly

Each shape has its own disarm feature that turns *that shape's* arming into a
no-op while leaving its assertion in place. The operation then succeeds, the arm
reports the missing fault, and the gate goes red. The gate's `--disarm` mode
additionally requires every OTHER arm to stay green, so each mutation is proven
singly rather than as a blanket kill switch.

| disarm | reddened | stayed green | verdict |
|---|---|---|---|
| `short_read` | `short_read` | the other 7 arms | ANTI-VACUITY PASSED |
| `eio` | `eio_data_block` | the other 7 arms, `eio_recovery` included | ANTI-VACUITY PASSED |
| `corrupt_inode` | `corrupt_inode:arm=size` and `arm=blocks` | the other 6 arms | ANTI-VACUITY PASSED |

The reddened arms report `detail=fault-not-observed...` and the gate requires
that specific reason: an arm going red for any other cause fails the
anti-vacuity leg rather than satisfying it.

Serials: `serials/aarch64-disarm-{short_read,eio,corrupt_inode}-serial-20260828.txt`
Gate verdicts: `serials/aarch64-disarm-*-gate-verdict-20260828.txt`

Note that "the fault was not injected" and "the fault was not detected" surface
as the same line here. That is deliberate: an injector that quietly stopped
working reddens the *armed* gate too, rather than passing forever.

## 5. By-catch: the leg panicked the kernel on its first run

`read_file_range()` read the on-disk `i_size` and immediately allocated a `Vec`
of that many bytes. A corrupt or hostile inode table therefore turned a read into
an arbitrary allocation request. With `i_size = 0xFFFFFFF0` on the 256 MiB test
filesystem:

```
KERNEL PANIC!
panicked at kernel/src/memory/heap.rs:179:5:
allocation error: Layout { size: 4294967280, align: 1 (1 << 0) }
```

The kernel died *before reaching a single block pointer*, so no amount of
downstream block validation could have caught it.

**Fixed** (commit `c402009e`): an `i_size` past `s_blocks_count * block_size` is
structurally impossible for a real file, so it is corruption and is refused with
`BlockError::IoError` before the allocation. Linux bounds the same field against
`ext2_max_size()` and validates blocks on the way out; it never allocates the
file into memory, which is why the bound has to be checked earlier here.

**Mutation proof of the fix.** Reverting the bound and re-running the gate:

```
fs fault gate (aarch64): FAIL - kernel panic during or after the fault leg
```

with the leg's first five arms green and the boot dead at `corrupt_inode:arm=size`.
Serial: `serials/aarch64-mutation-isize-bound-removed-PANIC-20260828.txt`.

This run is also what produced the gate's crash-check ordering: the first version
reported "the leg never reached its COMPLETE marker", which named the symptom
while the panic line scrolled past. Crash checks now run first.

## 6. Production cleanliness

The leg's whole module and both of its call sites are behind
`#[cfg(feature = "fs_fault_inject")]`. That is a claim about an ELF and about the
source that produces it, so both halves are measured, not asserted:

* `scripts/check-fs-fault-production-clean.sh` builds the production-profile
  AArch64 kernel with **no features at all** and requires zero symbols matching
  the leg and zero occurrences of its `[FSFAULT:` marker. `--prove` runs the same
  scan against an `fs_fault_inject` build and requires both legs to fire.
* `scripts/check-fs-fault-seams.sh` is the source half: every reference to the
  leg outside its own module must be cfg-guarded, and no Tier-1 or hot-path file
  may reference it at all (a prohibition census at file granularity, never an
  allow-list of blessed call sites). `--prove` plants an unguarded call in a
  throwaway copy and requires the scan to go red.

Both run in the host suite via `tests/fs_fault_production_clean.rs`: 4 passed,
0 failed.

**Stated narrowing, not a silent one:** there is no `.text` byte-identity leg
here, and the reason is structural rather than economy. The core-proof harness
needs one because its seams are macro invocations at *production* call sites,
where "expands to nothing" and "the optimiser removed it this time" are different
claims. This leg has no production call sites for such a comparison to be about.
The seam ratchet is what guards the property that makes that true.

## 7. #564 — the x86 gate wrapper

Premise re-verified live before fixing. Two halves:

* the repack half was **already fixed in-repo** (`docker/qemu/run-x86-boot-tests.sh`
  removes and repacks `target/test_binaries.img` every run), and
* the untracked-wrapper half was **still live**: no in-repo x86 gate wrapper
  existed, and the beast VM's `/root/run-x86-gate.sh` — read in full — builds the
  userspace ELFs and goes straight to `cargo build`, never packing the image the
  kernel actually boots from.

`docker/qemu/run-x86-gate.sh` now carries both properties that lived only on the
VM: the repack (test-binaries image and ext2 image, both gitignored build
outputs) and the `scripts/x86-gate-verdict.sh` scoring with the mandatory
`EXPECTED_EXITS` instead of a liveness-marker grep. VM-specific bits are env vars
with working defaults (`BREENIX_REPO_DIR`, `BREENIX_QEMU_ACCEL`/`CPU` with
`/dev/kvm` auto-detection, `BREENIX_RUST_FORK`, `BREENIX_GATE_TIMEOUT`).

Measured on beast:

```
[gate] Build clean (0 warnings) in 16s
  Test 1: PASS
GATE: PASS (1/1 boot tests passed; mode=kthread build=16s boot=12s total=36s)
```

**Disclosed narrowing:** the fetch/checkout of the branch under test cannot move
into the repository. Something outside the working tree has to place the code
before a script inside it can run, and a script that `git reset --hard`s the
checkout it is being read from is a self-modification hazard. The VM keeps a
~10-line bootstrap that fetches and execs the in-repo script; the boundary is
stated in the script header rather than left implicit.
