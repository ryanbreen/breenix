# TTY — production-profile evidence, 2026-08-30

Green program, arc 4 (TTY-aarch64). Branch `feat/green-tty`, based on `main` @ `a86ce876`.

This document is the durable record for the aarch64 TTY leg: what it drives, what each
arm is required to observe, what was measured on the shipped profile, and the mutations
that prove the measurements are not vacuous. Every serial and gate verdict referenced
here is in `serials/` beside this file.

---

## 1. What was missing

The atlas rates the TTY row (subsystem 10) `complete / MEDIUM` on aarch64 with **no open
issue chipping the TTY or PTY layer** — "TTY layer is clean; consumers #478, #430, #439
are chipped at their own rows." The zero-issue half of the green bar was therefore already
satisfied when the arc opened, and the arc's job was the other half: evidence.

The evidence that existed did not measure the shipping kernel. Every TTY proof in the tree
lived in the kernel's `boot_tests` registry — `pty_support_aarch64`, `tty_foreground_pgrp`,
`test_arm64_pty_ioctl_path`, and the `utest_tty` / `utest_session` / `utest_ctrl_c` /
`utest_job_control` / `utest_kill_process_group` set. All of it is compiled out of the
production profile, so all of it scored a kernel that is not the one
`scripts/parallels/build-efi.sh` deploys.

On the production profile the surface was driven **not at all**. PTY's two production
consumers, `bsshd` and `telnetd`, allocate a PTY only when a client connects, and no
client connects during a boot gate. A boot-completion gate structurally cannot see this
failure class, because a terminal nobody opens never produces it.

## 2. What was built

`userspace/programs/src/tty_oracle.rs` — a plain userspace program launched from init's
aarch64 sequence (`run_tty_oracle()`, between the #568 poll oracle and the exec smoke). It
drives PTY allocation, the line discipline, and termios through real syscalls.

**It adds zero kernel bytes.** There is no feature flag, no injection seam and no
`#[cfg]`-guarded kernel hook behind this leg, so unlike the ext2 fault leg (`fs_fault_inject`)
there is nothing that has to be proven absent from a production build — the production build
is simply what it runs on. The only kernel change on this branch is a defect fix (§3) that
ships.

`docker/qemu/run-aarch64-tty-oracle-gate.sh` builds and boots it and scores it. It builds
with **no `--features`**, the same command line as the production image script — adding one
would make the gate measure a different kernel than the one that ships. It keeps the #528
soft-float guard and carries the #668 ERR-trap discipline: a red gate names the failing
assertion, its file and line, and dumps the oracle's lines plus a serial tail instead of
dying silently under `set -e`. Crash checks are ordered before completion checks, so a panic
is reported as a panic rather than as "the leg never finished".

The standing production gate, `run-aarch64-prod-profile-boot-test.sh`, also gained the leg
as an assertion pair — presence of `[TTY_ORACLE:COMPLETE:` and absence of `[TTY_ORACLE:FAIL`
— in the same shape as the `BLOCK_EINTR` and `POLL_TCP` oracles already pinned there.

### The contract, arm by arm

Every arm is a **two-sided** claim: each contains its own contrast, so a path that silently
did nothing would fail the second half of its own arm.

| arm | stimulus | what the TTY layer must do |
|---|---|---|
| `openpt` | `posix_openpt` → `grantpt` → `ptsname` → `unlockpt` | the handshake succeeds AND the slave **refuses to open** while still locked |
| `nonblock_open` | open both ends `O_NONBLOCK` | the flag is present on both fds (`F_GETFL`) and both idle reads return `EAGAIN` |
| `isatty` | query master, slave, and `/etc/passwd` | yes, yes, **no** |
| `termios_roundtrip` | read defaults, write a modified set, restore | defaults are canonical+echo; the modified set reads back exactly (`lflag`, `iflag`, `VMIN`, `VTIME`, `VINTR`); the restore also takes |
| `canonical_line` | write `hello` with no newline, then `\n` | the unterminated line is **withheld** (`EAGAIN`), and the same bytes are delivered as `hello\n` once the newline lands |
| `icrnl` | write a bare `\r`, then clear `ICRNL` and repeat | CR terminates the line and arrives as `\n`; with `ICRNL` cleared the same CR terminates nothing |
| `raw_passthrough` | clear `ICANON`, write `xy` with no newline | the very bytes canonical mode withheld arrive immediately |
| `echo` | write a line with `ECHO` set, then cleared | input returns to the master side, and stops when `ECHO` is cleared |
| `onlcr` | slave writes `a\n`, then again with `OPOST` cleared | master reads `a\r\n`, then `b\n` untouched |
| `winsize` | `TIOCSWINSZ` on the master | `TIOCGWINSZ` on the **slave** returns it, and the probe differs from the default |
| `foreground_pgrp` | `TIOCSPGRP` on the master | `TIOCGPGRP` on the **slave** returns it |
| `hangup` | close the last slave fd | master read is `EAGAIN` while open, `EOF` after close |
| `ctty` | `setsid` → `TIOCSCTTY` on a `/dev/pts/N` slave → open `/dev/tty` → close it → drive the original slave | `/dev/tty` aliases the same PTY (proven by a marker written through it and read on the master); after closing the alias the master is **still `EAGAIN`, not `EOF`** (#704); after closing the remaining slave the master **now** sees `EOF` |

And, common to all of them: **no panic, no hang, kernel still live afterwards.** The gate
proves the last clause by requiring `bsshd: listening` *after* the leg. The oracle's own
final line is not accepted as evidence that the kernel is still usable.

### Two design points that carry weight

* The oracle opens both ends **non-blocking and asserts the flag is on the fd before it
  reads anything**. A PTY read with no data parks the calling thread; an oracle that
  discovered a regression by blocking would wedge the boot and be diagnosed only by a
  harness timeout. Checking `F_GETFL` first turns that failure into a named assertion.
* `winsize`, `foreground_pgrp` and `hangup` set state on one end and observe it from the
  **other**. State that is merely stored on the fd that wrote it would pass a same-end
  round trip and still be wrong.

## 3. The defect this leg found

Driving the surface immediately surfaced a live POSIX defect that the zero-issue count did
not cover: **both PTY open paths discarded the caller's flags**, so an fd opened
`O_NONBLOCK` reported blocking semantics.

* `sys_posix_openpt` passed a literal `0` as the master's status flags — the comment even
  said "No status flags for PTY master" — although POSIX lists `O_NONBLOCK` among the flags
  `posix_openpt()` accepts.
* `handle_devfs_open` took its flags as `_flags` and never passed them on, so
  `handle_devpts_open` allocated `/dev/pts/N` with `FileDescriptor::new()`, whose
  `status_flags` are zero.

Both read handlers in `handlers.rs` already branch on `status_flags & O_NONBLOCK` to choose
between `EAGAIN` and parking the thread. The effect was a **live branch that `open` could
not reach**: `fcntl(F_SETFL)` was the only way in, and a caller that asked for a
non-blocking terminal silently got a blocking one.

Fixed in `de569d9f`. The master site masks the caller's `O_NONBLOCK` into the fd's status
flags, guarded by a `const` assertion against `ipc::fd::status_flags` so the two definitions
cannot drift; the slave site plumbs the flags through and builds the entry with
`FileDescriptor::with_flags`, also honouring `O_CLOEXEC`. Other `/dev` device kinds keep
ignoring flags, so the blast radius is the pts path alone. No existing caller changes
behaviour: every `posix_openpt()` user in the tree goes through libbreenix's `openpty()`,
which passes `O_RDWR|O_NOCTTY` and no `O_NONBLOCK`.

## 3b. #704 — round two: the `/dev/tty` refcount defect, now fixed and measured

The first round found the same flags-dropped shape a third time, at the `/dev/tty` arm of
`handle_devfs_open` (the path that resolves a session's controlling terminal), and fixed it
by parity rather than measurement — reaching that arm needs a controlling terminal, and the
leg at the time opened every PTY `O_NOCTTY` and never established one. Fixing that arm by
parity surfaced a second, separate defect in the same few lines: unlike `handle_devpts_open`,
the `/dev/tty` arm handed out an `FdKind::PtySlave` fd **without calling `pair.slave_open()`**,
while nine of the ten paths that hand out or retire an `FdKind::PtySlave`/`FdKind::PtyMaster`
fd (`kernel/src/ipc/fd.rs`'s `close()`, `dup2`'s overwrite arm, `dup_at_least`'s handout and
EMFILE unwind, `FdTable::drop`; `kernel/src/task/process_task.rs`'s deferred reclaim; process
exit on both architectures) call `pair.slave_close()`/decrement `master_refcount`
symmetrically. (The tenth path, `close_cloexec()`, did **not** — see §3c; round one's audit
walked nine of the ten and did not catch it, so this sentence claimed a universal invariant
that the tree did not yet have. Corrected this round.) Two failure modes follow: closing a
`/dev/tty` fd while another slave fd is still open drops the shared refcount to zero and the
master sees a premature `EOF`; closing a `/dev/tty` fd as the only slave fd underflows the
count to `u32::MAX` and the master can never see a real hangup again. Filed as **#704**,
disclosed as production-reachable (`bsshd`/`bterm` establish a ctty via `TIOCSCTTY`, and a
shell opening `/dev/tty` is ordinary), and left unfixed at round-one landing because it could
not be exercised without a ctty-driving oracle.

Round two builds that oracle — arm 13, `ctty` — and fixes the defect it was filed to measure.
`handle_devfs_open`'s `/dev/tty` arm now calls `pair.slave_open()` in its success path,
mirroring `handle_devpts_open` exactly (`kernel/src/syscall/fs.rs`). The `ctty` arm makes the
fix observable end to end on the shipped profile: it opens its own PTY pair, opens the
`/dev/pts/N` slave, `setsid()`s (unconditional success on this kernel — see
`kernel/src/syscall/session.rs`), issues `TIOCSCTTY`, opens `/dev/tty` and proves it aliases
the same PTY by writing a marker through it that only that PTY's master could receive, closes
the `/dev/tty` fd, and then asserts the thing #704 breaks: an **idle** master read (nothing
written, nothing pending) must return `EAGAIN`, never `EOF` — the assertion has to be checked
idle because `master_read()` drains any buffered data ahead of its hangup check, so a
write-then-read alone would pass on the broken kernel too. A functional write/read round trip
then confirms the survivor is genuinely live, not merely unchecked, before the arm closes the
last slave fd and requires `EOF` **now**, not before.

Mutation-proven (**M704**): reverting only the `pair.slave_open()` call — the single hunk shown
in the fix above — reproduces #704 exactly:
`[TTY_ORACLE:FAIL:ctty:slave_hung_up_after_alias_close:post_alias_close_idle_read=unexpected_data:n=0:bytes=]`,
gate exit 1. Reapplying the hunk restores `[TTY_ORACLE:ctty:verdict=PASS:...]` and
`[TTY_ORACLE:COMPLETE:pass=13:fail=0]`. Serials:
`serials/aarch64-mutation-M704-devtty-slave-open-reverted-verdict-20260830.txt` (broken) against
`serials/aarch64-prod-armed-serial-boot1-20260830.txt` (fixed).

## 3c. Round three: `close_cloexec()` was the tenth path, and it was asymmetric too

Closing out §3b's fix meant re-walking every path that hands out or retires a
`FdKind::PtySlave`/`FdKind::PtyMaster` fd, since the `/dev/tty` defect was found by exactly
that audit missing one arm. It missed a second one: `close_cloexec()`
(`kernel/src/ipc/fd.rs`), the path `exec()` uses to retire `FD_CLOEXEC`-marked fds, decremented
pipe/FIFO/`UnixStream` reference counts on release but routed `FdKind::PtySlave` and
`FdKind::PtyMaster` through its catch-all `_ => {}` arm — no accounting at all. This is the
identical failure class to #704, one hunk away in the same file family, on the path this
same round's round-one `O_CLOEXEC`-on-open plumbing (`de569d9f`) newly made reachable for a
`/dev/pts/N` slave (before that commit, `open(..., O_CLOEXEC)` could not produce an
`FD_CLOEXEC`-marked `PtySlave` fd at all; `fcntl(F_SETFD)` was the pre-existing route). Two
failure modes follow, same shape as #704: a slave fd marked `FD_CLOEXEC` that survives past
an `exec()` leaks the shared refcount permanently (the entry is `take()`n out of the fd table
by `close_cloexec()` regardless of whether the accounting ran, so no later cleanup path ever
sees it again), and the corresponding master can never observe a real hangup for that pty
again.

Fixed alongside this round's other work: `close_cloexec()` now carries the two PTY arms,
mirroring `sys_close`'s disposition exactly — `pair.slave_close()` for `FdKind::PtySlave`,
and `pair.master_refcount.fetch_sub(1, ...)` with `crate::tty::pty::release()` on the last
reference for `FdKind::PtyMaster` (`kernel/src/ipc/fd.rs`).

Made observable by a new arm, **arm 14, `cloexec_exec`**: opens a fresh, self-contained PTY
pair, marks the slave `FD_CLOEXEC` via `fcntl(F_SETFD)`, `fork()`s, and has the child `exec()`
a fresh copy of `/bin/tty_oracle` with a marker argv (`--cloexec-child`) that does nothing but
exit(0) — so the only kernel-side event that can retire the child's fork-cloned slave fd is
`close_cloexec()` itself, not anything the child does. The parent reaps the child, closes its
own slave fd, and requires the master to see `EOF` on an idle read (same framing as arm 13,
for the same reason: `master_read()` drains any buffered data ahead of its hangup check, so a
write-then-read would not discriminate fixed from broken).

Mutation-proven (**M-CLOEXEC**): reverting only the two PTY arms added to `close_cloexec()` —
the single hunk shown above — reproduces the defect exactly:
`[TTY_ORACLE:FAIL:cloexec_exec:leaked_refcount_across_exec:post_parent_close_read=EAGAIN_not_EOF]`,
gate exit 1. Reapplying the hunk restores `[TTY_ORACLE:cloexec_exec:verdict=PASS:...]` and
`[TTY_ORACLE:COMPLETE:pass=14:fail=0]`. Serials:
`serials/aarch64-mutation-M-CLOEXEC-close-cloexec-pty-accounting-reverted-verdict-20260830.txt`
(broken) against `serials/aarch64-prod-armed-serial-r3-boot1-20260830.txt` (fixed).

`close_cloexec()`'s same catch-all arm also drops `FdKind::TcpConnection`/`FdKind::TcpListener`
with no `tcp_close`/`tcp_listener_ref_dec` — where `sys_close` and `close_all_fds` both do them
(`kernel/src/ipc/fd.rs`). That is arc 3's declared-green sockets row, not this one: filed as
**#707** against sockets rather than fixed here (cross-row by-catch), and not counted toward
this row's zero-issue bar.

a skip.

## 6. Ratchets

`tests/tty_oracle_structure.rs` (8 tests: 7 rule-asserting tests plus the mutation battery
that verifies all seven) keeps the two halves of the leg from drifting:

* **Census, not a list.** The arms are read out of the oracle's own `const ARM: &str = "…"`
  bindings and required to equal the gate's `EXPECTED_ARMS` array exactly. Adding a
  thirteenth arm needs no edit to the ratchet — arm 13 (`ctty`, §3b) proved this: it was
  picked up by the census with no change to this file, only to the oracle and the gate's
  `EXPECTED_ARMS`; adding one the gate does not score fails it. Round three's arm 14
  (`cloexec_exec`, §3c) proved it a second time the same way: only the oracle and the gate's
  `EXPECTED_ARMS` changed, and `cargo test --test tty_oracle_structure` went 8/8 with no edit
  to this file.
* `ARM_COUNT` must equal the census, so the `COMPLETE:pass=N` marker the gate matches on
  cannot go stale.
* The gate must build with no `--features` and must keep the #528 no-NEON guard.
* The gate must carry the #668 ERR trap, with `set -E` and a file:line message.
* Crash checks must textually precede completion checks.
* init must still launch `/bin/tty_oracle`, and `build.sh` must still install it.
* `run-aarch64-full-test.sh` Phase 2 must not accept a bare PTY unlock as evidence of a shell
  (the false-green rule added in round one, §8 below).

All seven rules are mutation-tested in `deliberately_broken_variants_fail_the_ratchets`,
including a guard against the census parser itself going blind — if the `const ARM` binding
were renamed, the census would report too few arms and the vacuity floor fires.

## 7. Scope and honest limits

* **aarch64 only.** The oracle is launched from init's `#[cfg(target_arch = "aarch64")]`
  sequence, and the gate is an aarch64 gate. `kernel/src/syscall/{fs,pty}.rs` are not
  arch-gated, so the round-one `O_NONBLOCK` fix, the round-two #704 fix, and round three's
  `close_cloexec()` fix (§3c) all ship on the x86 kernel too — the change is **arch-neutral**.
  x86 beast battery: **PROVEN, scored full mode.** Round two's Prove slot ran
  `docker/qemu/run-x86-gate.sh` on beast VM `breenix-x86` at this HEAD (`02fe4051`):
  `GATE: PASS (1/1 boot tests passed; mode=kthread build=17s boot=11s total=176s)`. Zero reds
  — none of the known pre-existing x86 signatures (#631, #700, #692, #702, the #636 family)
  fired, because nothing failed to attribute against. Getting there required a one-time beast
  host repair unrelated to this branch's code: `/root/breenix`'s gitignored `rust-fork`
  build dependency (a real clone of `ryanbreen/rust@breenix-target`, pinned at `d6e82857`,
  plus its `library/stdarch` and `library/backtrace` submodules) was entirely absent — the
  two sibling checkouts on that VM (`bx589main`, `bx-main-fresh`) held only dangling symlinks
  to the same missing target. This is exactly the "fresh-clone landmine" the beast-host memory
  already documents; it was re-established (clone + submodule init + symlink), which
  incidentally repairs the sibling checkouts' dangling symlinks too. No kernel or userspace
  source was touched to get this leg green. `#681` (an x86 registry test tripping the
  userspace runner's terminal verdict) remains open and out of scope here.

  **Round three's Prove slot ran the FULL scored mode** (`./docker/qemu/run-x86-gate.sh 1
  full`, not round two's kthread liveness default), on the same beast VM (`breenix-x86`) via
  `ssh beast` → `incus exec`, at this round's final HEAD (`a97912d4`, freshly fetched and
  hard-reset from `origin/feat/green-tty` before building — no drift from what merges).
  `full` mode builds with `testing,external_test_bins` (not `boot_tests`) and scores via
  `scripts/x86-gate-verdict.sh` with `EXPECTED_EXITS=10`, which requires all ten expected
  userspace test-process exits, a `USERSPACE TEST COMPLETE` marker, a `TEST_TALLY` line, and
  the strand census run first (so a silenced thread is named by cause, not by the terminal
  symptom it produces). Result: `GATE: PASS (1/1 boot tests passed; mode=full build=16s
  boot=150s total=175s)`, `STRAND_CENSUS: threads_saved_blocked=9 stranded=0 lines=5087`, `x86
  userspace gate: PASS - exited=19 expected>=10 nonzero=0 allowlist=0`. Zero reds: none of
  #631, #700, #692, #702, or the #636 family appear anywhere in the run's output (grepped for
  all five, no hits) — full mode's own 19 exits already clear the 10-exit floor cleanly.

  **What this does and does not prove.** `full` mode is a scored boot-test battery over the
  general syscall/exec/fd/process machinery (the 85+ kernel `testing`-feature subsystem
  checks plus `external_test_bins`, including `cloexec_test`), so it proves the arch-neutral
  changes in §3c compile clean and do not regress that battery on x86 hardware (KVM,
  `cpu=host`). It does **not** exercise the PTY-specific arms this round's fix touches: the
  TTY oracle that drives `close_cloexec()`'s `PtyMaster`/`PtySlave` match arms (§3c) is
  launched from init behind `#[cfg(target_arch = "aarch64")]` (`userspace/programs/src/

### A false green this leg created, and the repair

Worth stating first, because it is the most important thing this arc found about its own
blast radius. On the first full-test run against final bytes, `ARM64 FULL SYSTEM TEST:
PASSED` — Phase 2 reported `PASS (shell spawned)` on a boot whose serial contained **zero**
occurrences of `breenix>` and `bsh `.

Phase 2 accepted three alternatives as evidence of a shell, and the third was
`[pty] Unlocked PTY` — a proxy resting on the assumption that only a shell-spawning service
unlocks a PTY during boot. `/bin/tty_oracle` calls `unlockpt()` on every boot, which made
that assumption false and silently converted #593's permanent, honest red into a pass. The
serial shows the unlock arriving from the oracle itself:

```
[pty] sys_posix_openpt(flags=0x902)
[pty] Created master fd=3 (pty 2)
[pty] Unlocked PTY 2 (fd 3)
[TTY_ORACLE:openpt:verdict=PASS:slave=/dev/pts/2:locked_open_refused=1]
```

A gate that passes without testing what it claims is worse than one that fails, so the
proxy was removed rather than kept: Phase 2 now requires actual shell output and is red
again, correctly, until #593 is fixed. `tests/tty_oracle_structure.rs` carries a rule that
keeps the proxy from returning, since this leg makes it permanently false.

The false-green run is preserved at
`serials/aarch64-full-test-593-FALSE-GREEN-before-predicate-repair-20260830.txt` as the
record of what the unrepaired predicate reported.

### The one red, attributed by exact signature

**#593**, which states the failure is structural and "cannot pass as currently written, on any
branch": `run_boot_script()`'s aarch64 arm spawns `/bin/xhci_counters`, `/bin/bwm` and
`/sbin/telnetd` and returns without ever spawning `/bin/bsh`.

Attribution evidence, not assertion:

* Phase 1 passes **109/109** on this branch, and every phase through 1e plus Phase 5 passes.
  The same binary run as `--boot-tests-only` is fully green.
* This branch's only edit to `init.rs` is additive — the `run_tty_oracle()` launcher and its
  call. `run_boot_script()` is byte-identical to `main`.
* The failing serial contains **zero** occurrences of `breenix>` and `bsh ` — two of the
  three markers #593 cites as absent across its six evidence boots. The third,
  `[pty] Unlocked PTY`, is now present on every boot because this leg unlocks a PTY, which
