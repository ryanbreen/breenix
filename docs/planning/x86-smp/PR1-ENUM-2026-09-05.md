## 1. What existed before this round

x86 had no processor enumeration. `Scheduler::online_cpu_count()` answered with
the compile-time `MAX_CPUS` (`kernel/src/task/scheduler.rs`), which is 1 on this
arch, so the answer was right at `-smp 1` by construction and would be wrong the
moment a second processor existed. aarch64 has answered the same question from
`smp::cpus_online()` since `25afe0e1`.

The bootloader was already handing the kernel the RSDP —
`bootloader_api::BootInfo::rsdp_addr` — and the kernel was not reading it: a
repo-wide `grep -rn "rsdp" kernel/src` returned one hit, an unrelated field of
the aarch64 Parallels `HardwareConfig`.

### Where the reads are safe

`main.rs`'s `BOOTLOADER_CONFIG` sets `mappings.physical_memory =
Some(Mapping::Dynamic)`, and the pinned bootloader maps `[0, max_phys_addr)` at
the reported offset, with `max_phys_addr` raised to at least 4 GiB so that
firmware and MMIO regions below 4 GiB are reachable. `build_master_kernel_pml4`
copies the bootloader's PML4 entries into the table the kernel installs — its
lower-half loop names "physical memory offset" as one of the mappings it exists
to preserve — so the window survives the CR3 switch inside `memory::init`. On
the boots measured here that offset was `0x28000000000`, a lower-half address.

`acpi.rs` relies on one part of that window: physical addresses below 4 GiB. A
table address at or above that ceiling is refused with a named reason rather
than dereferenced, since establishing that a higher address is mapped would
mean reading the memory map, which this module does not do. Reads are one byte
at a time and composed into 32- and 64-bit fields, because ACPI table fields are
not necessarily naturally aligned and a wide unaligned `read_volatile` is
undefined behaviour.

## 3. The marker and what each field means

```
[X86_SMP_ENUM:madt_cpus=N:enabled=M:x2apic=K:bsp_apic_id=B:cpuid_logical=L:present=P:online=1:max_cpus=1:src=madt:reason=none]
```

| field | source | meaning |
|---|---|---|
| `madt_cpus` | MADT type-0 + type-9 entries | what the firmware reports. This is the field that tracks `-smp` |
| `enabled` | the same entries' flags bit 0 | of those, the ones flagged enabled |
| `x2apic` | type-9 entries | of those, the ones that arrived as x2APIC structures. QEMU's `pc` machine emits type-0 at these APIC ids, so this reads 0 on the measured legs |
| `bsp_apic_id` | CPUID leaf 0xB EDX when the leaf is implemented, else leaf 1 EBX[31:24] | the APIC id of the processor emitting the line |
| `cpuid_logical` | CPUID leaf 1 EBX[23:16] | a cross-check, not a count anything derives from — see below |
| `present` | `madt_cpus` clamped into `[1, MAX_CPUS]` | what this kernel's per-CPU state can address. 1, until `MAX_CPUS` moves |
| `online` | `cpus_online()` | processors that have entered the scheduler. 1: no AP is started |
| `max_cpus` | `crate::task::scheduler::MAX_CPUS` | the clamp itself, printed so the two numbers can be read together |
| `src` | `madt` or `cpuid_fallback` | which path answered |
| `reason` | the placeholder `none`, or a refusal token (claim-lint:ok: field quoted from `kernel/src/arch_impl/x86_64/smp.rs`) | why the MADT path did not answer |

`cpuid_logical` earns its place by disagreeing: the `-smp 1` leg measured
`cpuid_logical=0` while the `-smp 2` and `-smp 4` legs measured 2 and 4. QEMU's
`qemu64` model leaves CPUID leaf 1 EBX[23:16] at 0 for a single-vCPU guest, so a
kernel that derived its count from that field alone would read a count of 0
processors on the `-smp 1` profile the existing x86 gates run. The MADT is the source for that
reason, and CPUID is printed beside it.

The nine refusal tokens `reason=` can carry are
`no_rsdp_from_bootloader`, `above_read_ceiling`, `rsdp_signature`,
`rsdp_checksum`, `no_root_table`, `root_table_header`, `no_madt_in_root_table`,
`madt_header` and `madt_entry_length`. None of them was exercised by a boot in
this round: `src=madt:reason=none` on 3 of 3 legs.

### 5.4 aarch64 is untouched, and how that was checked

The two new modules live under `kernel/src/arch_impl/x86_64/`, and
`kernel/src/arch_impl/mod.rs` gates `pub mod x86_64;` behind
`#[cfg(target_arch = "x86_64")]`, so neither file is parsed in an aarch64
build. `kernel/src/main.rs` is the x86 binary. That leaves one shared file,
`kernel/src/task/scheduler.rs`, whose aarch64 arm this PR does not touch.

A byte comparison was attempted and found the aarch64 build is not
reproducible on its own: two builds of identical source differ in 5 bytes,
which are the `BREENIX_BUILD_ID` timestamp `kernel/build.rs` stamps into
`.rodata`. So the comparison was taken per section instead
(`serials/pr1/aarch64-section-comparison.txt`):

- `.text`, `.data` and `.init_array` are byte-identical between the branch and
  its base — including at the branch head, after the rewordings;
- `.rodata` differs in 107 bytes: 5 are that build id, and the rest sit on a
  24-byte stride, which is `sizeof(core::panic::Location)`. The differing field
  is the line number, each one +11 — the number of lines this PR adds above
  those call sites in `scheduler.rs`;
- `.strtab`, which is not loaded, is 365 bytes shorter: 746 of 4058 symbols
  differ in LLVM's `.llvm.<n>` internal-linkage suffix, whose value moves with
  the crate's contents, while each symbol's Rust hash `17h…E` is the same on
  both sides.

The same +11 shift is visible in a second, independent place:
`scripts/check-critical-path-violations.sh` reports the identical set of sites
on both sides, with the `scheduler.rs` line numbers moved from 5746/5882/5886/5890
to 5757/5893/5897/5901.

Review round 2 reported 2 findings, both against
`kernel/src/arch_impl/x86_64/acpi.rs`, and both the same shape: a length check
that ran after the read it was there to bound. Neither moves what section 5

### 10.1 The MADT's fixed body header, read before the length was checked

`census_of_madt()` read the Local Interrupt Controller Address at table offset
36, and set its cursor to 44 past the 4-byte flags word, before checking that
the table declares enough length to contain either field. `sdt_length()`
enforces `length >= SDT_HEADER_LENGTH` (36, the bytes an SDT header occupies)
and checksums exactly `length` bytes, so a MADT declaring a length in
`[36, 44)` passed that check and then had its body header read at offsets the
table's own checksum does not cover.

What it was not: a memory-safety break. `PhysReader::readable()` still refuses
an address at or above the 4 GiB ceiling, and on such a table the entry walk
after the read no-ops (`cursor` 44 > `end`), so `processor_entries` stays 0 and
the `madt_cpus`/`enabled`/`x2apic` fields the gate scores are unaffected on the
3 legs section 5 boots. `census.local_apic_address` is read by no kernel code
outside `acpi.rs` -- a grep across `kernel/src` finds 3 hits, its declaration,
its initialiser and this assignment; the assertions in the new test file are
its only readers, which is the same fact commit `c9551279`'s
message states as "no consumer in the tree today", counted before that file
existed. What makes it worth closing now rather than later:
`X86-SMP-CENSUS-PLAN-2026-09-05.md`'s PR-2 row proposes seeding LAPIC MMIO init
from that field, and that PR would inherit an unbounded read.

The repair is a named floor — `MADT_MIN_LENGTH`, `SDT_HEADER_LENGTH +
MADT_BODY_HEADER_LENGTH` = 44 — checked in `census_of_madt` before either field
is read. The refusal it takes is the existing `MadtHeader`, so the 9 tokens
`reason=` can carry (section 3) do not move; that variant's doc comment now
says the length case is one of them.

### 10.2 The revision-2 RSDP held to 33 bytes rather than 36

`root_table()`'s ACPI 2.0+ path accepted an RSDP `Length` as low as 33 before
walking the extended checksum and reading the XSDT address at offsets 24..32.
33 is exactly enough to reach the extended-checksum byte at offset 32 and no
further, while an ACPI 2.0 RSDP is 36 bytes: the 20-byte ACPI 1.0 prefix, the
4-byte `Length`, the 8-byte `XsdtAddress`, the extended checksum byte and 3
reserved bytes. The reads stayed inside the reader's ceiling and the checksum
walked only the declared bytes, so this was a bounds-precision gap and the
review rated it minor.

The floor is now the named `RSDP_V2_LENGTH` (36). Below it the reader takes the
ACPI 1.0 fallback and uses the RSDT address at offsets 16..20, which the
20-byte checksum it has already verified does cover — the same path a `Length`
above `MAX_TABLE_LENGTH` already took.

### 10.3 `tests/x86_madt_reader_bounds.rs`: the reader, run

Round 1's evidence for the reader was the gate (3 legs of well-formed QEMU
tables) and `tests/x86_smp_enum_structure.rs` (source text). Neither reaches
what the reader does with a malformed table, which is what both findings are
about. This file does: it compiles `acpi.rs` itself into a host test binary —
possible because the reader's only import is `core::ptr::read_volatile` — and
drives it over synthetic RSDP/RSDT/XSDT/MADT tables built byte by byte, each
sealed with a checksum over exactly the bytes it declares. The reader turns a
physical address into a pointer by adding the `physical_memory_offset` it is
handed, so the tests hand it `image_pointer - IMAGE_BASE` and its reads land in
the synthetic image.

| test | what it measures |
|---|---|
| `a_well_formed_madt_is_counted_entry_by_entry` | the anti-vacuity baseline: 2 type-0 entries and 1 type-9 give `processor_entries` 3, `enabled_entries` 2, `x2apic_entries` 1 and ids `[0, 1, 32]` |
| `a_madt_too_short_for_its_body_header_is_refused_at_every_such_length` | the 8 declared lengths in `[36, 44)`, each refused with the `madt_header` token, with a sentinel written at offset 36 first so a refusal is a decision and not an empty image |
| `a_madt_of_exactly_the_minimum_length_is_read` | 44 is a floor and not a blanket refusal: the census is produced and carries the body header |
| `an_entry_that_runs_past_the_declared_length_is_not_counted` | the length bound on the entry walk, beside the one on the body header |
| `a_full_length_revision_2_rsdp_is_followed_through_its_xsdt` | anti-vacuity for the pair: at `Length` 36 the XSDT is followed, and its MADT reports 4 processors |
| `a_revision_2_rsdp_shorter_than_its_own_structure_falls_back_to_the_rsdt` | at `Length` 33, 34 and 35 the RSDT is followed instead, and its MADT reports 1 |

The 2 MADTs behind the 2 root tables carry different processor counts on
purpose: which root table the reader followed is then readable off the census
it returns, rather than inferred.

What this file does not reach, stated rather than implied: that the kernel hands
the reader the RSDP the firmware really reported, and that the physical-memory
window it reads through is mapped at boot. Those are boot properties and the
gate is their evidence. `tests/x86_smp_enum_structure.rs` gains a source-level
pin for the new guard, and its header now says which file measures the
behaviour.
